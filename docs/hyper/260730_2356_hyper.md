## 1. Hyper란

### 개념

Hyper는 Rust에서 **HTTP 프로토콜을 구현**하는 저수준(low-level) 라이브러리입니다.

하는 일:

- HTTP/1.1, HTTP/2 메시지 파싱·직렬화
- 연결 위에서 요청/응답을 주고받기
- `http` 크레이트의 `Request` / `Response` 와 `Body` 스트림을 연결

하지 않는 일 (의도적으로):

- 라우팅 (`/users/{id}` 매칭) → Axum 등
- JSON 자동 변환 → serde + 상위 프레임워크
- 쿠키 jar, 리다이렉트 따라가기, 타임아웃 기본값 → reqwest 등
- TLS 핸드셰이크 자체 → rustls / native-tls + 커넥터
- 비동기 런타임 → Tokio (또는 다른 executor)

한 줄로:

> Hyper = “바이트 스트림 위에서 HTTP를 말하고 듣는 엔진”

### 체크포인트

- [ ] Hyper가 “웹 프레임워크”가 아니라 “HTTP 구현”임을 설명할 수 있는지
- [ ] 라우팅·JSON은 Hyper 밖 계층의 일임을 구분했는지

## 2. 생태계 위치

### 개념

이 저장소와 Rust 웹 스택을 층으로 보면:

```text
┌─────────────────────────────────────┐
│  앱 코드 (핸들러, 비즈니스 로직)      │
├─────────────────────────────────────┤
│  Axum / 직접 만든 Service            │  ← 라우팅, Extractor, 미들웨어
├─────────────────────────────────────┤
│  Tower (Service / Layer)             │  ← 미들웨어 합성
├─────────────────────────────────────┤
│  Hyper (+ hyper-util)                │  ← HTTP/1·2 프로토콜
├─────────────────────────────────────┤
│  Tokio (TcpStream, runtime)          │  ← 비동기 I/O · 실행기
├─────────────────────────────────────┤
│  OS 소켓                             │
└─────────────────────────────────────┘
```

클라이언트 쪽:

```text
앱 ──▶ reqwest ──▶ hyper (+ hyper-util) ──▶ Tokio ──▶ 네트워크
```

그래서 Axum 문서를 읽을 때 나오는 `axum::serve` / `Body` / `Request`는 결국 Hyper·`http`·`http-body` 타입과 이어집니다. Hyper를 알면 Axum이 “마법”이 아니라 **얇은 편의 계층**으로 보입니다.

### 체크포인트

- [ ] Axum / Hyper / Tokio / Tower 역할을 한 줄씩 쓰기
- [ ] “reqwest는 Hyper 클라이언트 위에 편의 API를 올린 것”이라고 말할 수 있는지

```toml

tower = "0.5"
http = "1"
tracing = "0.1"
tracing-subscriber = { version = "0.3", features = ["env-filter"] }
```

최소 서버만:

```toml
[dependencies]
hyper = { version = "1", features = ["server", "http1"] }
hyper-util = { version = "0.1", features = ["tokio"] }
http-body-util = "0.1"
bytes = "1"
tokio = { version = "1", features = ["macros", "rt-multi-thread", "net"] }
```

### Hyper feature

| feature | 역할 |
|---|---|
| `http1` | HTTP/1.1 |
| `http2` | HTTP/2 |
| `server` | 서버 conn API |
| `client` | 클라이언트 conn API |
| `full` | 위 전부 묶음 |
| `tracing` | 내부 로그 |

Hyper 1.x의 `default`는 **비어 있습니다**. feature를 안 켜면 거의 아무것도 없습니다. `features = ["full"]` 또는 필요한 조합을 명시하세요.

### hyper-util이 필요한 이유

Hyper 1.0은 “순수 프로토콜”에 가깝게 줄였습니다. 예전에 Hyper 안에 있던 편의 기능이 **hyper-util**로 빠졌습니다.

| hyper-util | 용도 |
|---|---|
| `rt::TokioIo` | `tokio::net::TcpStream` ↔ Hyper의 IO 어댑터 |
| `rt::TokioExecutor` | HTTP/2 등이 쓸 executor |
| `client::legacy::Client` | 연결 풀이 있는 고수준 클라이언트 (옛 hyper::Client) |
| `server::conn::auto` | HTTP/1 + HTTP/2 자동 선택 |
| `server::graceful` | graceful shutdown 도우미 |

### 체크포인트

- [ ] `cargo new hyper-lab` 후 의존성 추가, `cargo check` 통과
- [ ] Hyper `default`가 비어 있어서 feature가 필수인 이유 설명

## 4. http 크레이트 타입

### 개념

Hyper는 메시지 뼈대를 직접 정의하지 않고 **`http` 크레이트**를 씁니다. Axum·reqwest도 같은 타입을 씁니다.

| 타입 | 의미 |
|---|---|
| `Request<B>` | 요청 (메서드, URI, 버전, 헤더, body `B`) |
| `Response<B>` | 응답 (상태, 버전, 헤더, body `B`) |
| `Method` | GET, POST, … |
| `Uri` | 경로 + 쿼리 등 |
| `StatusCode` | 200, 404, … |
| `HeaderMap` | 헤더 맵 |
| `Version` | HTTP/1.1, HTTP/2, … |
| `Extensions` | 타입맵 (미들웨어가 값 꽂을 때) |

### 요청 만들기

```rust
use http::{HeaderValue, Method, Request};
use http_body_util::Full;
use bytes::Bytes;

fn build_get() -> Request<Full<Bytes>> {
    Request::builder()
        .method(Method::GET)
        .uri("http://example.com/hello?x=1")
        .header("user-agent", "hyper-lab")
        .body(Full::new(Bytes::new()))
        .unwrap()
}

fn build_post_json(json: &str) -> Request<Full<Bytes>> {
    Request::builder()
        .method(Method::POST)
        .uri("/api/items")
        .header("content-type", "application/json")
        .body(Full::new(Bytes::from(json.to_owned())))
        .unwrap()
}
```

### 응답 만들기

```rust
use http::{Response, StatusCode};
use http_body_util::Full;
use bytes::Bytes;

fn ok_text(body: &'static str) -> Response<Full<Bytes>> {
    Response::builder()
        .status(StatusCode::OK)
        .header("content-type", "text/plain; charset=utf-8")
        .body(Full::new(Bytes::from_static(body.as_bytes())))
        .unwrap()
}

fn not_found() -> Response<Full<Bytes>> {
    Response::builder()
        .status(StatusCode::NOT_FOUND)
        .body(Full::new(Bytes::from_static(b"not found")))
        .unwrap()
}
```

### 헤더

```rust
use http::header::{CONTENT_TYPE, HeaderName, HeaderValue};

let mut res = ok_text("hi");
res.headers_mut().insert(
    HeaderName::from_static("x-request-id"),
    HeaderValue::from_static("req-1"),
);
assert_eq!(
    res.headers().get(CONTENT_TYPE).unwrap(),
    "text/plain; charset=utf-8"
);
```

`HeaderValue`는 **유효한 헤더 바이트**만 받습니다. 임의 유니코드 문자열은 `from_str`이 실패할 수 있습니다.

### 체크포인트

- [ ] `Request::builder` / `Response::builder`로 메시지 하나씩 만들기
- [ ] body 타입 파라미터 `B`가 “바디 구현”을 담는 자리임을 이해

## 5. Body — 요청·응답의 핵심

### 개념

HTTP 메시지는 **헤더(유한) + 바디(스트림)** 입니다. Hyper 1.x에서 바디는 `http_body::Body` 트레이트를 구현한 타입입니다.

```text
Request / Response
  ├── method / status / headers / ...
  └── body: impl Body
            ├── poll_frame → Data / Trailers
            ├── size_hint
            └── is_end_stream
```

자주 쓰는 구현체는 **`http-body-util`** 에 있습니다.

| 타입 | 용도 |
|---|---|
| `Empty<Bytes>` | 빈 바디 (GET 등) |
| `Full<Bytes>` | 한 번에 올라간 완전한 바디 |
| `Collected<T>` | 수집 결과 |
| `StreamBody` | 비동기 Stream을 Body로 |
| `BodyExt` | `.collect()`, `.frame()` 등 확장 메서드 |

`bytes::Bytes`는 참조 카운트 바이트 버퍼로, 바디 청크에 거의 표준처럼 쓰입니다.

### Full / Empty

```rust
use bytes::Bytes;
use http_body_util::{Empty, Full};

let empty = Empty::<Bytes>::new();
let full = Full::new(Bytes::from("hello"));
```

### Body 전체를 메모리로 모으기

```rust
use http_body_util::BodyExt;
use bytes::Bytes;
use http_body_util::Full;

async fn collect_demo() {
    let body = Full::new(Bytes::from("abc"));
    let collected = body.collect().await.unwrap();
    let bytes = collected.to_bytes();
    assert_eq!(&bytes[..], b"abc");
}
```

큰 업로드를 무조건 `collect()` 하면 메모리 폭증합니다. 서버에서는 **크기 제한**을 두거나 스트리밍으로 처리하세요.

### 왜 Axum의 `Body`와 이름이 겹치나

Axum은 `axum::body::Body`라는 타입 소거(boxed) 바디를 제공합니다. 내부적으로는 같은 `http_body` 생태계입니다. Hyper 예제에서는 보통 `Full<Bytes>` / `Empty<Bytes>`처럼 **구체 타입**을 쓰고, 프레임워크에서는 타입 소거 Body를 자주 씁니다.

### 체크포인트

- [ ] `Empty` / `Full` / `collect()` 각각 언제 쓰는지 한 줄씩
- [ ] “Body는 문자열 하나가 아니라 프레임 스트림”이라고 설명할 수 있는지

## 6. Service 트레이트

### 개념

Hyper 서버는 “연결마다 요청을 받아 응답을 돌려주는 **Service**”를 기대합니다. Tower의 `Service`와 같은 모양입니다.

개념적으로:

```rust
trait Service<Request> {
    type Response;
    type Error;
    type Future: Future<Output = Result<Self::Response, Self::Error>>;

    fn call(&self, req: Request) -> Self::Future;
}
```

Hyper 서버에 넘길 때 흔한 형태:

- `Request<Incoming>` → `Response<impl Body>`
- 에러 타입은 보통 `Infallible` 또는 `Box<dyn Error + Send + Sync>`

`Incoming`은 **서버가 받은 요청 바디**를 나타내는 Hyper 타입입니다.

### 클로저로 Service 만들기

`service_fn`으로 async 함수/클로저를 Service로 감쌉니다.

```rust
use std::convert::Infallible;
use hyper::service::service_fn;
use hyper::{Request, Response};
use hyper::body::Incoming;
use http_body_util::Full;
use bytes::Bytes;

async fn handle(
    _req: Request<Incoming>,
) -> Result<Response<Full<Bytes>>, Infallible> {
    Ok(Response::new(Full::new(Bytes::from("ok"))))
}

// let svc = service_fn(handle);
```

### 왜 Service인가

1. 미들웨어(Tower Layer)와 합성하기 쉽다
2. 연결당 / 요청당 서비스 인스턴스 모델을 통일한다
3. Axum `Router`도 결국 `Service`로 Hyper에 연결된다

### 체크포인트

- [ ] `service_fn` + async 핸들러 한 개 작성
- [ ] Axum Router가 Service인 이유와 연결해 보기

## 7. 서버 Hello World (HTTP/1)

### 코드

```rust
use std::convert::Infallible;
use std::net::SocketAddr;

use bytes::Bytes;
use http_body_util::Full;
use hyper::body::Incoming;
use hyper::server::conn::http1;
use hyper::service::service_fn;
use hyper::{Request, Response};
use hyper_util::rt::TokioIo;
use tokio::net::TcpListener;

async fn hello(
    _req: Request<Incoming>,
) -> Result<Response<Full<Bytes>>, Infallible> {
    Ok(Response::new(Full::new(Bytes::from("Hello, Hyper!"))))
}

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error + Send + Sync>> {
    let addr = SocketAddr::from(([127, 0, 0, 1], 3000));
    let listener = TcpListener::bind(addr).await?;
    println!("listening on http://{addr}");

    loop {
        let (stream, remote) = listener.accept().await?;
        println!("accepted {remote}");

        // Tokio TcpStream → Hyper가 기대하는 IO
        let io = TokioIo::new(stream);

        tokio::task::spawn(async move {
            let service = service_fn(hello);

            if let Err(err) = http1::Builder::new()
                .serve_connection(io, service)
                .await
            {
                eprintln!("connection error: {err}");
            }
        });
    }
}
```

### 설명

1. `TcpListener::accept`로 TCP 연결을 받는다 (Tokio)
2. `TokioIo::new(stream)`으로 Hyper IO 어댑터를 만든다
3. `http1::Builder::serve_connection(io, service)`가 그 연결에서 HTTP/1을 말한다
4. 연결마다 `tokio::task::spawn`으로 동시에 처리한다

검증:

```bash
curl http://127.0.0.1:3000/
# Hello, Hyper!
```

### Axum과 비교

Axum:

```rust
axum::serve(listener, app).await
```

안에서는 비슷하게 accept 루프 + HTTP conn + Service(Router)를 돌립니다. Hyper를 직접 쓰면 그 루프를 **내가** 작성합니다.

### 체크포인트

- [ ] 위 서버를 띄우고 curl로 확인
- [ ] `TokioIo`가 하는 일을 한 문장으로

## 8. 요청 읽기 — 메서드·경로·헤더

### 코드

```rust
use std::convert::Infallible;

use bytes::Bytes;
use http_body_util::Full;
use hyper::body::Incoming;
use hyper::{Method, Request, Response, StatusCode};

async fn route(
    req: Request<Incoming>,
) -> Result<Response<Full<Bytes>>, Infallible> {
    let method = req.method();
    let path = req.uri().path();
    let ua = req
        .headers()
        .get("user-agent")
        .and_then(|v| v.to_str().ok())
        .unwrap_or("-");

    println!("{method} {path} ua={ua}");

    let (status, body) = match (method, path) {
        (&Method::GET, "/") => (StatusCode::OK, "home"),
        (&Method::GET, "/health") => (StatusCode::OK, "ok"),
        _ => (StatusCode::NOT_FOUND, "not found"),
    };

    let mut res = Response::new(Full::new(Bytes::from(body)));
    *res.status_mut() = status;
    Ok(res)
}
```

### 설명

- Hyper에는 Axum 같은 라우터가 **없습니다**. `match`로 직접 나눕니다.
- `req.uri()`는 요청 라인의 URI입니다. 프록시/절대형 URI면 `http://host/path` 형태일 수도 있습니다.
- 쿼리: `req.uri().query()` → `Option<&str>` (`"a=1&b=2"`)

```rust
if let Some(q) = req.uri().query() {
    println!("query = {q}");
}
```

### 체크포인트

- [ ] `/` 와 `/health` 와 그 외 404를 손으로 라우팅
- [ ] User-Agent를 로그로 남기기

## 9. 요청 Body 수집

### 코드

```rust
use bytes::Bytes;
use http_body_util::{BodyExt, Full};
use hyper::body::Incoming;
use hyper::{Method, Request, Response, StatusCode};

async fn echo(
    req: Request<Incoming>,
) -> Result<Response<Full<Bytes>>, hyper::Error> {
    if req.method() != Method::POST {
        let mut res = Response::new(Full::new(Bytes::from_static(b"POST only")));
        *res.status_mut() = StatusCode::METHOD_NOT_ALLOWED;
        return Ok(res);
    }

    // 크기 힌트 / 제한 (간단 버전)
    let content_length = req
        .headers()
        .get("content-length")
        .and_then(|v| v.to_str().ok())
        .and_then(|s| s.parse::<usize>().ok())
        .unwrap_or(0);

    if content_length > 1024 * 64 {
        let mut res = Response::new(Full::new(Bytes::from_static(b"too large")));
        *res.status_mut() = StatusCode::PAYLOAD_TOO_LARGE;
        return Ok(res);
    }

    let collected = req.into_body().collect().await?;
    let bytes = collected.to_bytes();

    Ok(Response::new(Full::new(bytes)))
}
```

### 설명

1. `req.into_body()`로 `Incoming`을 꺼낸다 (Request를 소비)
2. `BodyExt::collect`로 프레임을 모아 `Bytes`로 만든다
3. 에러 타입이 `hyper::Error`가 될 수 있으므로 `Infallible` 대신 `hyper::Error`를 쓴다

실무에서는 `content-length`만 믿지 말고, 실제로 읽은 바이트 수를 세며 제한하는 편이 안전합니다 (chunked 전송 등).

### JSON을 직접 파싱하려면

```rust
// serde_json = "1"
let collected = req.into_body().collect().await?;
let bytes = collected.to_bytes();
let value: serde_json::Value = serde_json::from_slice(&bytes).unwrap_or_default();
```

## 11. 스트리밍 응답

### 개념

큰 파일·로그·SSE처럼 **한 번에 모으지 않고** 청크로 보내는 경우 Stream → Body 변환을 씁니다.

```rust
use bytes::Bytes;
use futures_util::stream;
use http_body_util::{StreamBody, BodyExt};
use http::Response;
use std::convert::Infallible;
use std::time::Duration;
use tokio_stream::StreamExt as _;

async fn countdown() -> Response<StreamBody<impl futures_util::Stream<Item = Result<http_body::Frame<Bytes>, Infallible>>>> {
    let s = stream::iter(0..5).then(|i| async move {
        tokio::time::sleep(Duration::from_millis(200)).await;
        let chunk = Bytes::from(format!("tick {i}\n"));
        Ok(http_body::Frame::data(chunk))
    });

    Response::builder()
        .header("content-type", "text/plain; charset=utf-8")
        .body(StreamBody::new(s))
        .unwrap()
}
```

```toml
futures-util = "0.3"
tokio-stream = "0.1"

```

## 12. 클라이언트 — 저수준 handshake

### 개념

Hyper 1.x 순정 클라이언트는 “연결 풀 Client”가 없고, **TCP 연결 → HTTP handshake → send_request** 흐름을 직접 탑니다.

### 코드 (HTTP/1 GET)

```rust
use bytes::Bytes;
use http_body_util::{BodyExt, Empty};
use hyper::Request;
use hyper_util::rt::TokioIo;
use tokio::net::TcpStream;

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error + Send + Sync>> {
    let host = "httpbin.org";
    let port = 80;
    let address = format!("{host}:{port}");

    let stream = TcpStream::connect(address).await?;
    let io = TokioIo::new(stream);

    let (mut sender, conn) = hyper::client::conn::http1::handshake(io).await?;

    // Connection 을 백그라운드에서 poll 해야 요청이 진행된다
    tokio::task::spawn(async move {
        if let Err(err) = conn.await {
            eprintln!("connection failed: {err}");
        }
    });

    let req = Request::builder()
        .method("GET")
        .uri("/ip")
        .header("host", host)
        .body(Empty::<Bytes>::new())?;

    let mut res = sender.send_request(req).await?;
    println!("status = {}", res.status());

    while let Some(frame) = res.body_mut().frame().await {
        let frame = frame?;
        if let Some(data) = frame.data_ref() {
            println!("{}", String::from_utf8_lossy(data));
        }
    }

    Ok(())
}
```

### 설명

1. `TcpStream::connect` — 전송 계층
2. `http1::handshake` — HTTP/1 세션 (`SendRequest` + `Connection`)
3. **`conn`을 spawn해서 await** — 안 하면 송수신이 멈춘 것처럼 보일 수 있음
4. `SendRequest::send_request` — 요청 전송, 응답 수신
5. HTTP/1 absolute-form이 아니면 **`Host` 헤더 필수**

이 패턴은 프록시·커스텀 프로토콜·한 연결에 요청 여러 번(keep-alive)을 세밀히 제어할 때 유용합니다. 일반 API 호출은 reqwest / hyper-util Client가 편합니다.

### 체크포인트

- [ ] httpbin(또는 로컬 서버)에 GET 한 번 성공
- [ ] `conn`을 spawn하지 않으면 어떻게 되는지 한번 실험해 보기

## 14. HTTP/2 개요

### 개념

HTTP/2는 한 연결에서 **멀티플렉싱**, 바이너리 프레임, 헤더 압축(HPACK), 서버 푸시(지금은 거의 안 씀) 등을 제공합니다.

Hyper에서:

- 서버: `hyper::server::conn::http2`
- 클라이언트: `hyper::client::conn::http2`
- 둘 다 executor가 필요 → `TokioExecutor`
- cleartext h2c 또는 TLS+ALPN(`h2`)로 협상

### 서버 스케치

```rust
use hyper::server::conn::http2;
use hyper_util::rt::{TokioExecutor, TokioIo};

// accept 루프 안에서:
let io = TokioIo::new(stream);
http2::Builder::new(TokioExecutor::new())
    .serve_connection(io, service)
    .await?;
```

### HTTP/1·2 자동 (hyper-util)

```rust
use hyper_util::server::conn::auto::Builder;
use hyper_util::rt::TokioExecutor;

Builder::new(TokioExecutor::new())
    .serve_connection(io, service)
    .await?;
```

브라우저 HTTPS 트래픽은 보통 ALPN으로 `h2` / `http/1.1`을 고릅니다. TLS 종료를 직접 할 때만 이 계층을 만집니다. 많은 배포는 **Nginx/Caddy/ALB 뒤의 HTTP/1** 로 앱을 둡니다.

## 15. 연결 수명과 동시성

### accept 루프

```text
listener.accept()
   │
   ├─ spawn connection task  ──▶ serve_connection (여러 요청 keep-alive)
   ├─ spawn connection task
   └─ ...
```

- **연결 하나** 안에서 HTTP/1 keep-alive면 요청이 순차(또는 파이프라인)로 올 수 있음
- HTTP/2면 한 연결에 스트림이 여러 개
- 연결마다 task를 나누지 않으면 accept가 막혀 동시 접속이 불가능

### keep-alive / 타임아웃

Hyper builder에서 HTTP/1 옵션 예:

```rust
use std::time::Duration;
use hyper::server::conn::http1;

http1::Builder::new()
    .keep_alive(true)
    .timer(hyper_util::rt::TokioTimer::new())
    // 버전에 따라 header_read_timeout 등 옵션이 있다
    .serve_connection(io, service);
```

정확한 메서드명은 사용 중인 `hyper` / `hyper-util` 버전 docs를 보세요. “무한 대기 연결”을 줄이려면 **읽기 타임아웃·idle 타임아웃**을 꼭 검토합니다.

### backpressure

Body를 천천히 읽으면 상대 송신도 결국 멈춥니다(흐름 제어). 반대로 응답 Stream을 빨리 안 폴하면 메모리에 버퍼가 쌓일 수 있습니다. Hyper는 “빠르고 안전한 기본값”을 주지만, **느린 클라이언트·대용량 업로드**는 앱에서 제한해야 합니다.

### 체크포인트

- [ ] 연결당 spawn을 빼면 무슨 일이 생기는지 실험
- [ ] keep-alive와 “요청당 TCP 새로 열기” 차이 말하기

## 16. 에러 처리

### 계층별 에러

| 계층 | 예시 |
|---|---|
| Tokio I/O | `std::io::Error` (연결 리셋, bind 실패) |
| Hyper 프로토콜 | `hyper::Error` (잘못된 메시지, body 읽기 실패) |
| 앱 | 404/400 등 **정상적인 HTTP 응답** |

중요: 앱 논리적 실패(잘못된 JSON, 권한 없음)는 보통 `Err`로 연결을 끊지 말고 **`Ok(Response)` + 4xx/5xx** 로 돌려줍니다. `Service::Error`는 “응답을 만들 수 없는 치명적 실패”에 가깝습니다.

```rust
use std::convert::Infallible;
use bytes::Bytes;
use http_body_util::Full;
use hyper::{Request, Response, StatusCode};
use hyper::body::Incoming;

async fn handler(req: Request<Incoming>) -> Result<Response<Full<Bytes>>, Infallible> {
    if req.uri().path() != "/ok" {
        let mut res = Response::new(Full::new(Bytes::from("not found")));
        *res.status_mut() = StatusCode::NOT_FOUND;
        return Ok(res); // Err 가 아님!
    }
    Ok(Response::new(Full::new(Bytes::from("ok"))))
}
```

body `collect()` 실패는 `hyper::Error`이므로 핸들러에서 `Result<_, hyper::Error>`로 올리거나, 잡아서 400/500 응답으로 변환합니다.

### 체크포인트

- [ ] “404는 Err가 아니라 Ok(Response)”를 코드로 보여 주기
- [ ] body 읽기 실패를 500 JSON으로 바꿔 보기

## 17. Graceful Shutdown

### 개념

프로세스 종료 시:

1. 새 `accept` 중단
2. 진행 중 연결의 요청을 마무리
3. idle 연결 정리

### 스케치

```rust
use tokio::sync::watch;

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error + Send + Sync>> {
    let listener = tokio::net::TcpListener::bind("127.0.0.1:3000").await?;
    let (shutdown_tx, shutdown_rx) = watch::channel(false);

    tokio::spawn(async move {
        tokio::signal::ctrl_c().await.ok();
        let _ = shutdown_tx.send(true);
    });

    loop {
        let mut rx = shutdown_rx.clone();
        tokio::select! {
            _ = rx.wait_for(|v| *v) => {
                println!("shutdown: stop accepting");
                break;
            }
            accepted = listener.accept() => {
                let (stream, _) = accepted?;
                let io = hyper_util::rt::TokioIo::new(stream);
                let mut rx = shutdown_rx.clone();
                tokio::spawn(async move {
                    let conn = hyper::server::conn::http1::Builder::new()
                        .serve_connection(io, hyper::service::service_fn(hello));
                    // 간단판: shutdown 신호를 보면 연결 future를 drop
                    tokio::select! {
                        _ = rx.wait_for(|v| *v) => {},
                        r = conn => { if let Err(e) = r { eprintln!("{e}"); } }
                    }
                });
            }
        }
    }

    // 여기서 in-flight 연결 대기(타임아웃)를 더 두는 게 운영형
    Ok(())
}

async fn hello(
    _: hyper::Request<hyper::body::Incoming>,
) -> Result<hyper::Response<http_body_util::Full<bytes::Bytes>>, std::convert::Infallible> {
    Ok(hyper::Response::new(http_body_util::Full::new(bytes::Bytes::from("ok"))))
}
```

`hyper-util`의 `server::graceful` / `GracefulShutdown`을 쓰면 연결에 `http1::Builder::serve_connection(...).with_upgrades()` 등과 함께 더 정석적으로 처리할 수 있습니다. Axum `with_graceful_shutdown`이 이 계층을 감싼 것입니다.

### 체크포인트

- [ ] Ctrl+C 후 새 연결이 안 붙는지 확인
- [ ] Axum graceful shutdown과 같은 문제임을 연결해 보기

## 18. TLS / HTTPS 맛보기

### 개념

Hyper는 TLS를 직접 구현하지 않습니다. 흐름:

```text
TCP accept
  → rustls/native-tls 로 암호화 스트림
  → TokioIo 로 감싸기
  → http1/http2 serve_connection
```

클라이언트:

```text
TCP connect
  → TLS connector (SNI, 인증서 검증)
  → handshake
  → send_request
```

학습·실무에서는 보통:

- **로컬 개발**: HTTP plain
- **운영**: 앞단 리버스 프록시가 TLS 종료, 앱은 내부 HTTP
- **앱이 직접 HTTPS**: `axum-server` / `hyper-rustls` / `tokio-rustls`

직접 구현은 인증서 로딩·ALPN(`h2`, `http/1.1`)·클라이언트 인증(mTLS)까지 책임이 커집니다. 이 문서에서는 “Hyper 바깥 계층”임을 아는 것이 목표입니다.

### 체크포인트

- [ ] Hyper와 TLS의 경계를 그림으로 그려 보기
- [ ] 왜 많은 팀이 TLS를 프록시에 맡기는지 한 가지 이유

## 19. Hyper vs Axum vs reqwest

### 비교표

| | Hyper | Axum | reqwest |
|---|---|---|---|
| 역할 | HTTP 프로토콜 | 서버 웹 프레임워크 | HTTP 클라이언트 |
| 라우팅 | 손수 match | 풍부 | N/A |
| JSON | 손수 | Extractor | 내장 편의 |
| 미들웨어 | Tower 직접 | Tower + from_fn | 제한적/내장 |
| 언제 | 프록시, 커스텀 서버, 학습 | REST API 서버 | 앱에서 외부 호출 |

### 선택 가이드

- API 서버 만든다 → **Axum** (내부적으로 Hyper)
- 다른 HTTP API 호출한다 → **reqwest** (내부적으로 Hyper)
- L7 프록시·특수 프로토콜·극한 최적화·학습 → **Hyper 직접**

이 저장소 `api`는 Axum을 쓰므로, 평소 코드는 Axum으로 두고 Hyper는 “바닥이 어떻게 생겼는지” 볼 때 꺼내면 됩니다.

### 체크포인트

- [ ] 세 가지 중 지금 필요한 도구 고르기
- [ ] “Axum을 쓴다 = Hyper를 안 쓴다가 아니다” 설명

## 20. 0.14 → 1.x 변경점

옛 튜토리얼(0.14)을 볼 때 자주 깨지는 부분입니다.

| 0.14 | 1.x |
|---|---|
| `hyper::Server::bind(...).serve(make_svc)` | accept 루프 + `http1::Builder::serve_connection` |
| `hyper::Client` | `hyper_util::client::legacy::Client` 또는 저수준 conn |
| `Body::from("...")` 통합 Body | `Full` / `Empty` / `http-body-util` |
| IO가 Tokio에 밀착 | `TokioIo` 어댑터 필요 |
| feature default 풍부 | default 비어 있음 → feature 명시 |

업그레이드 가이드: https://hyper.rs/guides/1/upgrading/

## 21. 자주 하는 실수

1. **Hyper만 추가하고 feature 안 켬**  
   → `default = []` 이라 컴파일은 돼도 쓸 API가 없음. `full` 또는 `server`+`http1` 등.

2. **`TokioIo` 없이 `TcpStream`을 그대로 넘김**  
   → 타입 에러. `hyper_util::rt::TokioIo::new(stream)`.

3. **클라이언트에서 `conn`을 spawn/await 안 함**  
   → `send_request`가 영원히 안 끝나는 것처럼 보임.

4. **HTTP/1 요청에 `Host` 헤더 누락**  
   → 서버/중간 장비가 거부하거나 이상 동작.

5. **앱 에러를 `Service::Error`로만 처리**  
   → 연결 종료. 4xx/5xx는 `Ok(Response)`.

6. **무제한 `collect()`**  
   → OOM. 업로드 크기 제한 필수.

7. **accept 루프에서 spawn 없이 serve**  
   → 한 연결 끝날 때까지 다음 연결 불가.

8. **0.14 예제 복사**  
   → `Server::bind` / 옛 `Body` API는 1.x에서 없음.

9. **HTTPS를 Hyper만으로 해결하려 함**  
   → TLS 크레이트·커넥터 필요. 또는 reqwest/프록시.

10. **Axum 쓰면서 Hyper Body 타입을 섞어 헤맴**  
   → 경계에서 `BodyExt` / `Full` 변환을 명시적으로.

## 22. 실전: 작은 echo 서버

메서드·경로·바디 echo + health + 404를 한 파일에 모은 예제입니다.

```rust
use std::convert::Infallible;
use std::net::SocketAddr;

use bytes::Bytes;
use http_body_util::{BodyExt, Full};
use hyper::body::Incoming;
use hyper::server::conn::http1;
use hyper::service::service_fn;
use hyper::{Method, Request, Response, StatusCode};
use hyper_util::rt::TokioIo;
use tokio::net::TcpListener;

async fn handle(req: Request<Incoming>) -> Result<Response<Full<Bytes>>, Infallible> {
    match (req.method(), req.uri().path()) {
        (&Method::GET, "/health") => Ok(text(StatusCode::OK, "ok")),
        (&Method::GET, "/") => Ok(text(StatusCode::OK, "hyper echo server")),
        (&Method::POST, "/echo") => match read_body_capped(req, 64 * 1024).await {
            Ok(bytes) => Ok(Response::new(Full::new(bytes))),
            Err(status) => Ok(text(status, "body error")),
        },
        _ => Ok(text(StatusCode::NOT_FOUND, "not found")),
    }
}

fn text(status: StatusCode, body: &'static str) -> Response<Full<Bytes>> {
    let mut res = Response::new(Full::new(Bytes::from_static(body.as_bytes())));
    *res.status_mut() = status;
    res.headers_mut().insert(
        hyper::header::CONTENT_TYPE,
        "text/plain; charset=utf-8".parse().unwrap(),
    );
    res
}

async fn read_body_capped(
    req: Request<Incoming>,
    max: usize,
) -> Result<Bytes, StatusCode> {
    let len = req
        .headers()
        .get(hyper::header::CONTENT_LENGTH)
        .and_then(|v| v.to_str().ok())
        .and_then(|s| s.parse::<usize>().ok());

    if let Some(n) = len {
        if n > max {
            return Err(StatusCode::PAYLOAD_TOO_LARGE);
        }
    }

    let collected = req
        .into_body()
        .collect()
        .await
        .map_err(|_| StatusCode::BAD_REQUEST)?;
    let bytes = collected.to_bytes();
    if bytes.len() > max {
        return Err(StatusCode::PAYLOAD_TOO_LARGE);
    }
    Ok(bytes)
}

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error + Send + Sync>> {
    tracing_subscriber::fmt::init();

    let addr = SocketAddr::from(([127, 0, 0, 1], 3000));
    let listener = TcpListener::bind(addr).await?;
    println!("listening on http://{addr}");

    loop {
        let (stream, remote) = listener.accept().await?;
        println!("accept {remote}");
        let io = TokioIo::new(stream);

        tokio::task::spawn(async move {
            let svc = service_fn(handle);
            if let Err(err) = http1::Builder::new().serve_connection(io, svc).await {
                eprintln!("conn error: {err}");
            }
        });
    }
}
```

## 부록 A. 타입 지도 (한눈에)

| 이름 | 크레이트 | 역할 |
|---|---|---|
| `Request` / `Response` | `http` | 메시지 메타 + body 슬롯 |
| `Body` trait | `http-body` | 바디 프레임 스트림 |
| `Full` / `Empty` / `BodyExt` | `http-body-util` | 바디 구현·조합 |
| `Incoming` | `hyper` | 서버 수신 바디 |
| `http1::Builder` | `hyper` | HTTP/1 연결 서버/클라 |
| `TokioIo` | `hyper-util` | Tokio ↔ Hyper IO |
| `legacy::Client` | `hyper-util` | 풀링 클라이언트 |
| `service_fn` | `hyper` | 함수 → Service |

## 부록 B. 학습 순서 제안

1. 생태계 그림 + Cargo feature (1–3절)
2. `http` 타입 + Body Full/Empty (4–5절)
3. Hello 서버 + 수동 라우팅 (6–8절)
4. body collect + echo (9–10, 22절)
5. 저수준 클라이언트 handshake (12절)
6. legacy Client / reqwest와 비교 (13, 19절)
7. 스트리밍·HTTP/2·shutdown·TLS는 필요할 때 (11, 14, 17, 18절)

## 부록 C. 이 저장소와의 연결

- `api` / `backend`는 **Axum**을 사용 → 런타임에 Hyper가 아래 mid 계층으로 동작
- 평소 핸들러는 Axum으로 작성
- “왜 `axum::body::Body`가 있지?”, “왜 serve가 TcpListener를 받지?” 같은 질문이 생기면 이 문서로 내려가서 보면 됨
- 외부 HTTP 호출 학습은 [docs/reqwest](../reqwest/)

연습 과제:

1. 7절 Hello 서버를 포트를 `3002`로 바꿔 저장소 API와 나란히 띄우기
2. `/health` JSON(`{"status":"ok"}`) 응답을 Hyper만으로 만들기
3. POST `/echo` body 길이만 JSON으로 돌려주기
4. 같은 echo를 Axum으로 다시 짜 보고 코드량 비교
5. (선택) 12절 저수준 클라이언트로 자기 Hyper 서버에 GET
