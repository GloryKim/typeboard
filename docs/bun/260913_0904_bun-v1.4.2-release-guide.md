## 1. 개요 및 릴리즈 핵심 요약

Bun v1.4.2는 직전 v1.4.1 버전에서 발생했던 치명적인 회귀 버그(Regression)들을 긴급 진화하고, 프로덕션 워크로드에서 런타임 안정성과 웹 표준 호환성을 대폭 끌어올린 업데이트입니다.

### v1.4.1 vs v1.4.2 핵심 비교표

| 컴포넌트 | v1.4.1 (이전 버전의 문제점) | v1.4.2 (현재 버전의 개선점) | 심각도 |
| :--- | :--- | :--- | :---: |
| **`bun build`** | 블록 내 `var`를 같은 블록의 `let` 이름으로 맹글링하여 `SyntaxError: Cannot declare a var...` 발생 (Elysia 프레임워크 임포트 실패) | AST 스코프 트리 분석기 수정으로 변수 섀도잉 및 식별자 충돌 완벽 차단 | **Critical** |
| **`AsyncLocalStorage`** | `store.exit()`이나 중첩 `run()` 내부 타이머/Promise가 상위 컨텍스트(수십 MB의 요청 객체)를 GC하지 못해 메모리 누수 유발 | 비동기 수명 주기 분리(Decoupling)를 통해 타이머 존재 여부와 무관하게 즉각 GC 회수 | **Critical** |

| **`.json()` 파싱** | 손상된 JSON 본문 수신 시 무의미한 `Failed to parse JSON` 제네릭 에러 반환 | 구체적 토큰 위치와 문법 오류를 담은 `SyntaxError` 반환 (예: `Expected '}'`) | **DX** |

## 2. 핵심 업데이트 심층 분석 & 원인 규명

### 2.1 `bun build` 변수 스코핑 및 섀도잉 충돌 (Elysia 회귀 해결)

#### 1) 결함 발생 메커니즘
Bun v1.4.1의 번들러는 코드 최적화 및 식별자 축소(Mangling) 단계에서 스코프 트리(Scope Tree)를 순회할 때, 블록 스코프(`let`, `const`)와 함수/모듈 스코프(`var`)의 경계를 정확히 구분하지 못하는 버그가 있었습니다.

특히 CommonJS 호환 래퍼나 Elysia 프레임워크 코드에서 흔히 쓰이는 아래와 같은 코드 패턴에서 문제가 드러났습니다:

```javascript
// 원본 코드 (index.js)
function foo () {
  {
    let exports2 = {};
    var exports = exports2;
  }
  return exports;
}
module.exports = foo();
```

v1.4.1 번들러는 블록 내부의 `var exports` 변수를 상위 스코프로 끌어올리면서(Hoisting), 동일 블록 내에 이미 선언된 `let exports2`와 충돌을 일으켜 `exports`의 이름을 `exports2`로 리네이밍해 버렸습니다:

```javascript
// v1.4.1 번들러의 잘못된 출력 (out.js)
function foo() {
  {
    let exports2 = {};
    var exports2 = exports2; // 💥 SyntaxError 발생!
  }
  return exports2;
}
```

이로 인해 자바스크립트 엔진은 즉시 다음 구문 오류를 발생시키며 서버 기동 자체가 불가능했습니다:
```text
SyntaxError: Cannot declare a var variable that shadows a let/const/class variable
```

#### 2) 무음 런타임 오류(Silent Failure)의 위험성
이 버그는 문법 에러뿐만 아니라, `let` 변수가 함수의 매개변수(parameter)나 `catch (error)` 바인딩과 같은 이름을 부여받게 만들어, 구문 에러 없이 통과되지만 런타임에 엉뚱한 값을 계산하는 치명적인 논리적 결함까지 유발했습니다.

#### 3) v1.4.2의 해결책
Bun v1.4.2에서는 식별자 할당기가 재작성되어, 렉시컬 환경(Lexical Environment)에 등록된 변수와 바인딩된 매개변수/catch 절의 이름을 엄격히 격리함으로써 완벽한 번들링 정합성을 복구했습니다.

### 2.2 `AsyncLocalStorage` 메모리 누수(Memory Leak) 결함 수정

#### 1) 결함 발생 메커니즘
`node:async_hooks`의 `AsyncLocalStorage`는 Node.js 및 Bun 생태계에서 HTTP 요청별 컨텍스트(인증 유저 정보, 데이터베이스 세션, 트랜잭션 ID 등)를 전역적으로 추적하기 위한 핵심 표준입니다.

v1.4.1에서는 `store.exit()` 또는 중첩 `store.run()` 블록 내부에서 비동기 리소스(`setTimeout`, `setImmediate`, `Promise`)가 생성될 때, 런타임 내부의 `AsyncContext` 포인터가 외부 스토어 객체에 대한 강한 참조(Strong Reference)를 유지하는 회귀 버그가 있었습니다.

```typescript
const store = new AsyncLocalStorage();

store.run(hugePerRequestContext, () => {
  // 클라이언트 요청 처리 도중 백그라운드 작업 분리
  store.exit(() => {
    // 1시간(3,600,000ms) 뒤 실행되는 타이머
    setTimeout(() => {
      /* 백그라운드 텔레메트리 전송 */
    }, 3_600_000);
  });
  // ❌ v1.4.1 결함:
  // 클라이언트 HTTP 요청이 완전히 끝나도, 타이머가 살아있는 1시간 동안
  // hugePerRequestContext(수십 MB의 메모리)가 가비지 컬렉션(GC)되지 않고 잔류!
});
```

`getStore()` 메서드 자체는 `undefined`를 올바르게 반환하여 기능적으로는 정상인 것처럼 보였으나, **메모리 내부에서는 객체가 해제되지 않고 지속적으로 누적되어 결국 서버 OOM(Out of Memory) 크래시**를 유발했습니다.

#### 2) v1.4.2의 해결책
C++ 런타임 레벨에서 `store.exit()` 스코프가 생성하는 비동기 태스크의 컨텍스트 바인딩을 재설계하여, 상위 스토어 인스턴스와의 참조 고리를 즉시 끊도록 수정되었습니다.

### 2.3 `node:worker_threads` `'online'` 이벤트 순서 정상화 (@discordjs/ws 행 해결)

#### 1) 결함 발생 메커니즘
Node.js 공식 명세에 따르면, `new Worker(...)`를 통해 워커 스레드를 시작하면 자바스크립트 엔진이 부팅되고 스크립트 실행 준비가 완료되는 즉시 메인 스레드로 `'online'` 이벤트가 먼저 전달되어야 합니다.

그러나 Bun v1.4.1에서는 워커 스레드가 시작되자마자 최상위 레벨에서 `parentPort.postMessage()`를 호출할 경우, 메인 스레드의 이벤트 루프에서 `'message'` 이벤트가 `'online'` 이벤트보다 먼저 도착하거나 큐 순서가 역전되는 현상이 발생했습니다.

많은 프로덕션 라이브러리(대표적으로 `@discordjs/ws`)는 다음과 같은 정석 패턴으로 워커를 초기화합니다:

```typescript
import { Worker } from "node:worker_threads";
import { once } from "node:events";

const worker = new Worker("./gateway_shard.js");

// 1. 워커가 온라인 상태가 될 때까지 명시적으로 대기
await once(worker, "online");

// 2. 온라인 이벤트 수신 후 비로소 메시지 리스너 등록
worker.on("message", (msg) => {
  console.log("샤드로부터 메시지 수신:", msg);
});
```

- **v1.4.1에서의 참사:** 워커가 부팅 즉시 보낸 최초의 메시지(예: `SHARD_READY` 핸드셰이크)가 `once(worker, 'online')`가 완료되기 전에 이미 지나가 버렸습니다. 메인 스레드는 메시지 리스너를 등록하기도 전에 메시지를 놓치게 되고, 이후 워커로부터의 응답만을 하염없이 기다리며 프로세스가 무한 행(Hang)에 빠졌습니다.

#### 2) v1.4.2의 해결책
워커 스레드의 C++ 수명 주기 이벤트 디스패치 순서가 교정되어, **모든 사용자 메시지보다 `'online'` 이벤트가 반드시 앞서 메인 스레드로 방출**되도록 보장되었습니다.

### 2.4 `Bun.Image` 인쇄용 4채널 CMYK 및 YCCK JPEG 디코딩 지원

#### 1) 결함 발생 메커니즘
디지털 카메라나 스마트폰, 일반 웹 환경은 빛의 3원색인 **RGB (Red, Green, Blue / 3채널)** 색공간을 사용합니다.  
반면, 인쇄 출판 업계(Adobe Photoshop, Illustrator, InDesign 등)에서 브로슈어, 카탈로그, 포스터용으로 내보낸 JPEG 이미지는 잉크의 4원색인 **CMYK (Cyan, Magenta, Yellow, Key/Black / 4채널)** 또는 변형된 **YCCK** 색공간으로 저장됩니다.

Bun의 초고속 네이티브 이미지 프로세싱 모듈인 `Bun.Image`는 v1.4.1까지 4채널 JPEG 디코더를 갖추지 못해 다음과 같은 치명적 오류를 발생시켰습니다:
```text
error: Image: decode failed
 code: "ERR_IMAGE_DECODE_FAILED"
```

이로 인해 이커머스나 CMS, 인쇄 플랫폼 등에서 사용자가 인쇄용 이미지를 업로드하면 서버가 500 에러를 뿜으며 리사이징에 실패했습니다.

#### 2) v1.4.2의 해결책
- 4-component CMYK 및 YCCK JPEG 디코딩 엔진이 내장되었습니다.
- 디코딩과 동시에 표준 sRGB(3채널) 색공간으로 자동 역변환(Color Space Inversion & Mapping)이 이루어집니다.
- 따라서 사용자는 별도의 변환 라이브러리(sharp, ImageMagick) 없이도 Bun 내장 API 하나로 모든 리사이즈, WebP/AVIF 인코딩 작업을 고속으로 수행할 수 있습니다.

### 2.5 JavaScriptCore (WebKit) ~350개 업스트림 커밋 최신화

Bun은 Google의 V8 대신 Apple WebKit의 JavaScriptCore(JSC) 엔진을 기반으로 동작합니다. v1.4.2에는 약 350여 개의 업스트림 JSC 커밋이 반영되었습니다:

1. **BigInt 지원이 추가된 `Intl.PluralRules`:**
   ```typescript
   new Intl.PluralRules("en").select(1n); // Bun v1.4.2: "one" (v1.4.1: TypeError: Number required)
   ```
2. **TypedArray 변조 공격 방어:**
   `new Int32Array(array)` 등의 생성자가 배열 요소를 순회하여 변환할 때, 요소 내부의 `valueOf()` 메서드가 악의적으로 원본 배열의 길이나 내용을 변조하더라도 오래되거나(stale) 댕글링된 메모리를 읽지 않도록 메모리 안정성을 강화했습니다.
3. **`TypedArray.prototype.slice` 버퍼 오버랩 정합성:**
   `Symbol.species`를 통해 동일 버퍼를 공유하는 오버랩 뷰를 슬라이스할 때 ECMA 사양에 정의된 순서대로 복사를 진행합니다.
4. **`Intl.DurationFormat` (`style: "digital"`):**
   분(minutes)이 0이어서 표시가 생략되어야 하는 경우 불필요한 콜론(`:`)이 출력되던 버그를 수정했습니다.
5. **Proxy 핸들러 `setPrototypeOf(handler, null)` JIT 크래시 방지:**
   자주 호출되는 함수 내에서 생성된 프록시 핸들러의 프로토타입을 제거할 때 JIT 최적화 컴파일러가 크래시를 내던 문제를 해결했습니다.
6. **초경량 `Date` 객체 최적화:**
   `new Date()` 인스턴스의 메모리 풋프린트와 할당 비용이 대폭 절감되어 초당 수백만 회의 인스턴스 생성을 손쉽게 처리합니다.

### 2.6 `.json()` 정밀 구문 오류(SyntaxError) 메시지 제공

`Response.json()`, `Blob.json()`, `Bun.file().json()`, `proc.stdout.json()` 등 Bun의 비동기 JSON 파서가 v1.4.1까지는 유효하지 않은 JSON을 만나면 단순히 제네릭한 에러만을 반환했습니다:

### 2.7 플랫폼 안정성 및 기타 치명적 버그 수정 (Alpine/musl GC 등)

1. **Alpine Linux (musl libc) GC 크래시 해결:**
   - Docker 컨테이너의 표준인 Alpine Linux 환경에서 객체 배열에 대해 `Array.prototype.splice`, `shift`, 또는 `array.length`를 줄이는 동작을 수행할 때, 가비지 컬렉터의 마킹(Marking) 스레드가 동시에 실행되면 프로세스가 크래시되거나 영구 교착(Hang) 상태에 빠지던 버그를 해결했습니다.
2. **`bun install` / `bun add` 패닉 방지:**
   - `bun.lockb`나 로컬 레지스트리 캐시에서 패키지명 해시가 패키지명과 불일치할 때 발생하던 `panic: range end index out of range` 결함을 해결했습니다.
3. **Linux `Bun.file().writer()` FileSink 더블 클로즈 방지:**
   - Linux 환경에서 `fs.epoll.max_user_watches` 한도가 고갈되어 epoll 등록에 실패할 경우, 내부 파일 디스크립터(FD)가 두 번 닫혀(Double-Close) 해당 FD 번호를 재사용한 무관한 다른 소켓이나 파일이 강제 종료되던 보안/안정성 문제를 해결했습니다.
4. **JIT 프로토타입 인라인 캐시 GC 크래시 해결:**
   - 장시간 구동되는 서버 프로세스에서 JIT가 최적화한 프로토타입 속성이 GC된 후 드물게 발생하던 메모리 크래시를 방지했습니다.

### 예제 3. `worker_threads` 'online' 핸드셰이크 & Resilient Worker Pool

```typescript
/**
 * [예제 3] worker_threads 'online' 핸드셰이크 & Resilient Worker Pool
 * 실행: bun run src/03_worker_threads_pool.ts
 */
import { Worker, isMainThread, parentPort, workerData } from "node:worker_threads";
import { once, EventEmitter } from "node:events";

// ============================================================================
// [워커 스레드 실행 코드 (isMainThread === false)]
// ============================================================================
if (!isMainThread) {
  const shardId = workerData?.shardId ?? 0;
  
  // v1.4.1에서는 이 postMessage가 'online' 이벤트보다 먼저 도착하여
  // 메인 스레드가 미처 message 리스너를 등록하지 못해 메시지가 유실되었습니다.
  parentPort?.postMessage({
    type: "SHARD_READY",
    shardId,
    pid: process.pid,
    timestamp: Date.now(),
  });

  // 메인 스레드로부터의 작업 요청 수신
  parentPort?.on("message", (task: { taskId: string; payload: number }) => {
    // 무거운 CPU 연산 (피보나치 수열)
    const compute = (n: number): number => (n <= 1 ? n : compute(n - 1) + compute(n - 2));
    const result = compute(task.payload);

    parentPort?.postMessage({
      type: "TASK_COMPLETED",
      taskId: task.taskId,
      result,
    });
  });
}

// ============================================================================
// [메인 스레드 실행 코드 (isMainThread === true)]
// ============================================================================
if (isMainThread) {
  console.log("=== 3. worker_threads 'online' 이벤트 순서 및 고성능 워커 풀 아키텍처 ===\n");

  // 1단계: @discordjs/ws 패턴 검증
  console.log("-> 1단계: @discordjs/ws 패턴 (await once(worker, 'online')) 메시지 수신 테스트");

  async function testDiscordWsPattern() {
    const worker = new Worker(new URL(import.meta.url), {
      workerData: { shardId: 101 },
    });

    // 1. 'online' 이벤트를 대기
    await once(worker, "online");
    console.log("   [메인] 워커 'online' 이벤트 감지 완료!");

    // 2. online 이후에 message 리스너 등록 (v1.4.1에서는 여기서 무한 대기 발생)
    const initialMessage = await new Promise((resolve, reject) => {
      const timeout = setTimeout(() => {
        reject(new Error("타임아웃: 워커의 초기 메시지를 수신하지 못하고 행(Hang)에 걸렸습니다."));
      }, 1000);

      worker.on("message", (msg) => {
        clearTimeout(timeout);
        resolve(msg);
      });
    });

    console.log("   [메인] 워커의 초기 메시지 수신 성공:", initialMessage);
    await worker.terminate();
    console.log("   [메인] 1단계 검증 통과 (이벤트 순서 정상 동작)\n");
  }

  await testDiscordWsPattern();

  // 2단계: 엔터프라이즈급 Resilient Worker Pool 구현
  console.log("-> 2단계: 다중 코어 분산 처리를 위한 고급 Worker Pool 가동");

  interface PoolTask {
    taskId: string;
    payload: number;
    resolve: (val: unknown) => void;
    reject: (err: unknown) => void;
  }

  class ShardedWorkerPool extends EventEmitter {
    private workers: Worker[] = [];
    private freeWorkers: Worker[] = [];
    private taskQueue: PoolTask[] = [];
    private workerTaskMap = new Map<Worker, PoolTask>();

    constructor(private poolSize: number) {
      super();
    }

    async init() {
      console.log(`   [WorkerPool] ${this.poolSize}개의 전용 워커 스레드 초기화 중...`);
      const initPromises: Promise<void>[] = [];

      for (let i = 0; i < this.poolSize; i++) {
        const worker = new Worker(new URL(import.meta.url), {
          workerData: { shardId: i },
        });

        const initPromise = (async () => {
          // Bun v1.4.2의 안정적인 online 이벤트 대기
          await once(worker, "online");

          await new Promise<void>((resolve) => {
            const readyHandler = (msg: any) => {
              if (msg.type === "SHARD_READY") {
                worker.off("message", readyHandler);
                resolve();
              }
            };
            worker.on("message", readyHandler);
          });

          // 작업 결과 처리 리스너 등록
          worker.on("message", (msg: any) => {
            if (msg.type === "TASK_COMPLETED") {
              const task = this.workerTaskMap.get(worker);
              if (task) {
                this.workerTaskMap.delete(worker);
                task.resolve(msg.result);
              }
              // 워커 반환 및 큐의 다음 작업 스케줄링
              this.freeWorkers.push(worker);
              this.processQueue();
            }
          });

          this.workers.push(worker);
          this.freeWorkers.push(worker);
        })();

        initPromises.push(initPromise);
      }

      await Promise.all(initPromises);
      console.log(`   [WorkerPool] 모든 워커(${this.poolSize}개) 준비 완료!`);
    }

    execute(payload: number): Promise<unknown> {
      return new Promise((resolve, reject) => {
        const taskId = `task_${Math.random().toString(36).slice(2, 9)}`;
        this.taskQueue.push({ taskId, payload, resolve, reject });
        this.processQueue();
      });
    }

    private processQueue() {
      if (this.taskQueue.length === 0 || this.freeWorkers.length === 0) return;

      const worker = this.freeWorkers.pop()!;
      const task = this.taskQueue.shift()!;
      this.workerTaskMap.set(worker, task);

      worker.postMessage({ taskId: task.taskId, payload: task.payload });
    }

    async destroy() {
      await Promise.all(this.workers.map((w) => w.terminate()));
      console.log("   [WorkerPool] 모든 워커 종료 완료.");
    }
  }

  // 4개의 워커 풀 생성 및 고부하 피보나치 계산 병렬 처리
```

```typescript
// 1. 엔터프라이즈 이미지 프로세서 인터페이스 및 클래스
export interface ProcessOptions {
```

```typescript
      );
      enhancedError.name = "JsonDeserializationError";
      throw enhancedError;
    }
  }
```

## 4. ALL-IN-ONE 실무 종합 프로덕션 서버 구현체

이 코드는 Bun v1.4.2의 **핵심 4대 기능(`Bun.serve`, `AsyncLocalStorage 분산 트레이싱`, `Bun.Image 온더플라이 변환`, `worker_threads CPU 오프로딩`, `정밀 JSON 에러 처리`)**을 하나의 완전한 실무 마이크로서비스로 통합한 프로덕션 소스 코드입니다.

```typescript
/**
 * [종합 프로덕션 서버] ALL-IN-ONE 실무 마이크로서비스
 * 파일 경로: src/07_production_server.ts
 * 실행: bun run src/07_production_server.ts
 */
import { AsyncLocalStorage } from "node:async_hooks";
import { Worker } from "node:worker_threads";
import { once } from "node:events";

// 1. 요청 컨텍스트 스코프 정의
interface TraceScope {
  traceId: string;
  clientIp: string;
  startedAt: number;
}

const traceStorage = new AsyncLocalStorage<TraceScope>();

// 2. CPU 집약적 연산을 위한 전용 워커 스레드 인라인 생성
const workerCode = `
  import { parentPort } from "node:worker_threads";
  parentPort?.postMessage({ type: "ONLINE_READY" });
  parentPort?.on("message", (msg) => {
    let res = 1;
    for (let i = 1; i <= msg.n; i++) res = (res * i) % 1000000007;
    parentPort?.postMessage({ id: msg.id, result: res });
  });
`;

const worker = new Worker(workerCode, { eval: true });
// Bun v1.4.2: online 이벤트가 최초 메시지보다 먼저 방출됨을 보장
await once(worker, "online");

const pendingWork = new Map<number, (res: number) => void>();
worker.on("message", (msg: any) => {
  if (msg.type === "ONLINE_READY") return;
  const resolver = pendingWork.get(msg.id);
  if (resolver) {
    pendingWork.delete(msg.id);
    resolver(msg.result);
  }
});

let taskIdSeq = 0;
function dispatchHeavyCalculation(n: number): Promise<number> {
  return new Promise((resolve) => {
    const id = ++taskIdSeq;
    pendingWork.set(id, resolve);
    worker.postMessage({ id, n });
  });
}

// 3. 테스트용 1x1 투명 PNG 버퍼
const samplePngBase64 = "iVBORw0KGgoAAAANSUhEUgAAAAEAAAABCAYAAAAfFcSJAAAADUlEQVR42mNk+M9QDwADhgGAWjR9awAAAABJRU5ErkJggg==";
const sampleBuffer = Buffer.from(samplePngBase64, "base64");

// 4. 고성능 Bun.serve 인스턴스 기동
const server = Bun.serve({
  port: 0, // 임의의 가용 포트 바인딩
  async fetch(req) {
    const trace: TraceScope = {
      traceId: req.headers.get("x-trace-id") || `tr_${Math.random().toString(36).slice(2, 9)}`,
      clientIp: req.headers.get("x-forwarded-for") || "127.0.0.1",
      startedAt: performance.now(),
    };

    return await traceStorage.run(trace, async () => {
      const url = new URL(req.url);

      // 엔드포인트 1: 헬스체크 및 런타임 버전
      if (url.pathname === "/health") {
        return Response.json({ status: "healthy", bunVersion: Bun.version });
      }

      // 엔드포인트 2: Bun.Image 온더플라이 이미지 변환 (인쇄용 CMYK/RGB 자동 지원)
      if (url.pathname === "/api/transform-image") {
        const w = Number(url.searchParams.get("w")) || 100;
        const h = Number(url.searchParams.get("h")) || 100;

        const img = new Bun.Image(sampleBuffer);
        const webpBytes = await img.resize(w, h).webp().bytes();

        return new Response(webpBytes, {
          headers: {
            "Content-Type": "image/webp",
            "X-Trace-Id": trace.traceId,
          },
        });
      }

      // 엔드포인트 3: Worker Thread 연산 오프로딩 & 누수 없는 백그라운드 로깅
      if (url.pathname === "/api/heavy-calc") {
        const n = Number(url.searchParams.get("n")) || 5000;
        const calcResult = await dispatchHeavyCalculation(n);

        // v1.4.2 수정: store.exit() 내부에서 타이머를 실행해도 상위 요청 컨텍스트 메모리 누수 0!
        traceStorage.exit(() => {
          setTimeout(() => {
            // 외부 요청 객체를 메모리에 잡지 않고 깔끔하게 정리됨
          }, 50);
        });

        return Response.json({ n, calcResult, traceId: trace.traceId });
      }

      // 엔드포인트 4: v1.4.2 정밀 SyntaxError 메시지를 반환하는 JSON 파서
      if (url.pathname === "/api/parse-json" && req.method === "POST") {
        try {
          const body = await req.json();
          return Response.json({ ok: true, data: body });
        } catch (err: any) {
          // v1.4.2: "JSON Parse error: Expected '}'" 등의 구체적 메시지 반환
          return Response.json(
            {
              ok: false,
              error: err.message,
              errorType: err.name,
            },
            { status: 400 }
          );
        }
      }

      return new Response("Not Found", { status: 404 });
    });
  },
});

console.log(`[ProductionServer] Bun HTTP 서버 구동 완료: http://localhost:${server.port}`);

// 5. 자체 검증 테스트 호출
console.log("-> 1. 헬스체크 엔드포인트 호출...");
const healthRes = await fetch(`http://localhost:${server.port}/health`);
console.log("   응답:", await healthRes.json());

console.log("-> 2. Worker Thread 연산 엔드포인트 호출...");
const calcRes = await fetch(`http://localhost:${server.port}/api/heavy-calc?n=10000`);
console.log("   응답:", await calcRes.json());

console.log("-> 3. 잘못된 JSON 파싱 에러 엔드포인트 호출...");
const badJsonRes = await fetch(`http://localhost:${server.port}/api/parse-json`, {
  method: "POST",
  body: '{"invalid": json_value}',
});
console.log("   에러 응답(HTTP 400):", await badJsonRes.json());

console.log("-> 4. 이미지 변환 엔드포인트 호출...");
const imgRes = await fetch(`http://localhost:${server.port}/api/transform-image?w=64&h=64`);
console.log("   이미지 응답 Content-Type:", imgRes.headers.get("Content-Type"), "크기:", (await imgRes.arrayBuffer()).byteLength, "bytes");

// 정리
server.stop(true);
await worker.terminate();
console.log("\n종합 프로덕션 서버 테스트 성공 및 종료 완료!\n");
```

## 6. 설치, 업그레이드 및 마이그레이션 권고사항

### 1) 즉시 업그레이드 명령어
현재 Bun이 설치되어 있는 경우 터미널에서 다음 명령어를 실행하면 최신 v1.4.2로 즉시 업그레이드됩니다:
```bash
bun upgrade
```

신규 설치 시:
```bash
# macOS / Linux
curl -fsSL https://bun.sh/install | bash

# Windows (PowerShell)
powershell -c "irm bun.sh/install.ps1|iex"

# Homebrew
brew install oven-sh/bun/bun

# Docker
docker pull oven/bun:1.4.2
```

### 2) 프로덕션 마이그레이션 권고사항
- **Elysia 사용자:** v1.4.1에서 번들링 실패(`SyntaxError`)로 인해 빌드가 중단되었던 문제가 해결되었으므로, 빌드 스크립트의 워크어라운드를 제거하고 즉시 v1.4.2로 올리는 것을 권장합니다.
- **Discord 봇 개발자:** `@discordjs/ws` 무한 대기(Hang) 현상이 완전히 해결되었습니다. 워커 샤딩 모드를 안심하고 활성화할 수 있습니다.
- **대규모 트래픽 웹 서버:** `AsyncLocalStorage`의 타이머 관련 메모리 누수가 잡혔으므로, 장기 실행되는 마이크로서비스의 메모리 사용량이 극적으로 안정화됩니다.
- **이미지 업로드 서비스:** 인쇄용 CMYK/YCCK JPEG가 별도 라이브러리 없이 네이티브 `Bun.Image`로 처리 가능해져, 무거운 외부 C++ 바인딩 라이브러리 의존성을 제거할 수 있습니다.
