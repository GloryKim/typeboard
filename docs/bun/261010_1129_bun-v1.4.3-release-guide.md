## 1. 개요 및 릴리즈 핵심 요약

Bun v1.4.3은 **166개 이슈를 수정(👍 122개 해소)**한 대형 패치 릴리즈입니다. 버전 번호는 패치(x.y.Z)지만 내용은 기능 릴리즈에 가깝습니다. 가장 큰 변화는 TypeScript 7.0.2(typescript-go)를 포팅한 **내장 타입 체커 `bun check`**이며, `bun run` / `bun test` / `bun build`에 `--check` 게이트가 붙어 "타입 오류가 있으면 실행·테스트·번들 자체를 거부"하는 흐름이 런타임 하나로 완결됩니다.

그 밖에 GC 스케줄링 조정으로 **유휴 서버 CPU 67–89% 절감**, 요청 그룹별 연결 풀을 격리하는 **`Bun.FetchSession`**, 한 프로세스에서 앱 인스턴스를 여러 개 띄우는 **실험적 `Bun.ModuleGraph`**, 그동안 받아만 두고 무시하던 **`--disallow-code-generation-from-strings`의 실제 적용**, **`node:http` 대용량 응답 최대 2.7배**, **대량 거부 Promise의 2차 → 선형 시간 개선**, 그리고 수십 건의 TLS·HTTP 보안 강화가 포함됩니다.

## 2. 핵심 업데이트 심층 분석 & 원인 규명

### 2.1 bun check 내장 TypeScript 타입 체커

#### 1) 무엇이 바뀌었나
`bun check`는 Microsoft의 Go 기반 TypeScript 구현(typescript-go, TypeScript 7)을 Bun에 포팅한 **순수 타입 체커**입니다. `tsconfig.json`을 읽고, `tsc`와 같은 오류를 같은 위치·같은 코드로 보고하며, 모든 CPU 코어를 사용합니다. `typescript` 패키지를 설치할 필요가 없습니다.

```text
$ bun check
1 | import { greet } from "./user";
2 |
3 | const message = greet({ id: "1", name: "Ada" });
                            ^
error: TS2322: Type 'string' is not assignable to type 'number'.
    at src/index.ts:3:25

Found 1 error in 1 file, checked 2 files [14.00ms]
```

**하지 않는 것**도 분명합니다. JavaScript나 `.d.ts`를 출력(emit)하지 않고, 언어 서버(LSP)도 없습니다. 에디터는 계속 TypeScript를 쓰며, `bun check`는 CI·pre-commit·실행 직전 게이트 용도입니다.

주요 플래그(`bun check --help` 실측):

| 플래그 | 설명 |
| :--- | :--- |
| `-p, --project=<path>` | 다른 `tsconfig.json` 또는 그 디렉터리 지정 |
| `-b, --build` | `references`의 프로젝트까지 검사 (`tsc -b`처럼, 미리 빌드할 필요 없음) |
| `--no-pretty` | 오류당 한 줄 (`tsc --pretty false`와 동일, 파이프 시 기본값) |
| `--all` | 모든 오류 표시 (기본은 50개 초과 시 같은 오류를 묶음) |
| `--threads=<n>` | 스레드 수 (기본: CPU 코어당 1개) |
| `--timing` | 로드·검사 시간 출력 |
| `--strict`, `--target=...` 등 | `tsc`의 모든 컴파일러 옵션을 그대로 받아 `tsconfig.json`을 덮어씀 |

#### 2) `--check` 게이트: run / test / build
- **`bun run --check src/index.ts`**: 타입 검사 후 실행합니다. 타입 오류가 있으면 코드가 실행되지 않습니다. `package.json` 스크립트(`bun run --check dev`)와 `--watch`(재시작마다 재검사)에서도 동작합니다.
- **`bun test --check`**: 테스트 파일과 그 파일이 import하는 모든 것을 검사하고, 오류가 있으면 **테스트를 하나도 실행하지 않습니다**.
- **`bun build --check`** / **`Bun.build({ check: true })`**: 타입 오류를 일반 빌드 오류처럼 취급하고 **아무 파일도 쓰지 않습니다**.

#### 1) 결함 발생 메커니즘

### 2.3 Bun.FetchSession 과 프록시 환경 개선

#### 1) `Bun.FetchSession`
요청 그룹에 **전용 TLS·프록시·keep-alive 설정과 전용 연결 풀**을 줍니다. 세션끼리, 그리고 일반 `fetch()`와도 연결을 공유하지 않습니다.

```typescript
const session = new Bun.FetchSession({
  tls: { ca: await Bun.file("corp-ca.pem").text() },
  proxy: { url: "http://proxy.internal:8080" },
  keepAlive: { idleTimeout: 30, maxIdleSockets: 8 },
});

const client = new SomeClient({ fetch: session.fetch });
await fetch("https://example.com", { session }); // 같은 의미
```

- `session.fetch`는 **bind되어 있어** `fetch` 함수를 주입받는 SDK에 그대로 넘길 수 있습니다.
- 요청 단위 옵션이 세션 옵션보다 우선합니다.
- `session.close()` 또는 `using`으로 유휴 연결을 닫습니다.
- 세션의 `tls.checkServerIdentity`는 **연결당 한 번**만 실행되고, 연결을 재사용하는 요청은 건너뜁니다.

**실무 의미:** 사내 CA가 필요한 내부 API, 프록시를 거쳐야 하는 외부 API, keep-alive를 짧게 가져가야 하는 불안정한 업스트림을 **한 프로세스 안에서 서로 간섭 없이** 다룰 수 있습니다. 장애 업스트림이 연결 풀을 고갈시켜도 다른 세션은 영향을 받지 않습니다. 예제 2에서 세션 2개와 일반 `fetch`가 각자 다른 TCP 연결 하나씩만 재사용하는 것을 클라이언트 포트로 확인했습니다.

#### 2) `NO_PROXY` / `ALL_PROXY` / `proxy: false`

```bash
NO_PROXY="*.internal.example.com, 10.0.0.0/8, fd00::/8, localhost:3000"
```

- `NO_PROXY`가 **와일드카드, CIDR 블록, 대괄호 없는 IPv6, `host:port`**를 받습니다.
- `HTTP_PROXY` / `HTTPS_PROXY`가 비어 있으면 **`ALL_PROXY`**를 사용합니다.
- 요청 하나만 프록시 환경을 무시하려면 `fetch(url, { proxy: false })`.

#### 3) `ERR_PROXY_TUNNEL`
프록시가 `CONNECT`를 2xx가 아닌 상태로 거부하면, 이제 `fetch()`가 **`ERR_PROXY_TUNNEL`로 reject**하고 오류 객체에 프록시의 `status`와 `headers`를 담습니다. 이전에는 **프록시의 거부 응답을 원본 서버 응답인 것처럼 resolve**했습니다. 예제에서 1.4.0은 `407`을 정상 응답처럼 돌려주고, 1.4.3은 `ERR_PROXY_TUNNEL 407`로 거부하는 것을 확인했습니다. 프록시 URL의 사용자명·비밀번호가 오류 메시지에 노출되던 문제(`node:http`/`node:https`)도 함께 수정됐습니다.

> **실측 함정:** 셸·CI·사내망이 소문자 `http_proxy`, `no_proxy`를 주입해 두면 대문자 변수만 바꿔서는 결과가 바뀌지 않습니다. 예제 2는 시작 시 대소문자 8개 변수를 모두 지웁니다.

### 2.4 (실험적) Bun.ModuleGraph: 한 프로세스, 여러 앱 인스턴스

#### 1) 개념
하나의 앱을 **한 프로세스 안에서 여러 인스턴스로** 실행합니다. 그래프마다 **새 모듈 상태, 자기만의 `require.cache`, 타이머와 I/O**를 갖고, **파싱된 코드와 바이트코드는 그래프끼리 공유**합니다. 멀티 테넌트 SaaS, 테스트 격리, 플러그인 호스트, 핫 리로드 서버처럼 "같은 코드를 상태만 분리해 여러 벌 돌리는" 상황에 맞습니다.

```typescript
const graph = new Bun.ModuleGraph({
  globals: { process: tenantProcess },
  onError: (error, kind) => console.error(kind, error),
});

const app = await graph.import("./app.ts");
await graph.run(() => app.handle(request));

graph.dispose(); // 그래프의 서버, 소켓, 타이머, 자식 프로세스를 닫음
```

- `graph.run(fn, ...args)`: `fn`을 그래프 컨텍스트에서 호출하므로, 그 안에서 연 리소스는 그래프 소유가 됩니다.
- `graph.dispose()`(또는 `using`): `worker.terminate()`처럼 동작합니다.
- `Bun.ModuleGraph.current`: 호출자가 속한 그래프 (바깥에서는 `null`).

#### 2) 반드시 알아야 할 한계
**보안 샌드박스가 아닙니다.** 같은 프로세스·같은 힙이므로 신뢰할 수 없는 코드를 격리하는 용도로 쓰면 안 됩니다. 예제 3에서는 같은 파일을 두 그래프로 import했을 때 모듈 인스턴스가 다르고(`appA === appB`가 `false`), 두 번째 import가 0.17ms로 끝났으며(바이트코드 공유), 테넌트 타이머의 예외가 호스트를 죽이지 않고 `onError("uncaughtException")`로 전달되고, `dispose()` 후 그 그래프의 HTTP 서버와 타이머만 정확히 멈추는 것을 확인했습니다.

### 2.5 --disallow-code-generation-from-strings 실제 적용

#### 1) 결함 발생 메커니즘
Node.js의 `--disallow-code-generation-from-strings`는 `eval()`과 `new Function()`을 금지하는 보안 플래그입니다. **Bun은 이 플래그를 받기만 하고 무시**했습니다. 예제에서 Bun 1.4.0에 플래그를 주고 `eval("1+1")`을 실행하면 그대로 `2`가 나옵니다. 보안 설정을 했다고 믿는 상태에서 실제로는 아무 효과가 없었던 셈입니다.

#### 2) v1.4.3의 해결책

| 경로 | 플래그 없음 | 기본 (Node 호환) | `=strict` (Bun 전용) |
| :--- | :---: | :---: | :---: |
| `eval()` | 허용 | **차단** | **차단** |
| `new Function()` | 허용 | **차단** | **차단** |
| `node:vm` (`runInNewContext` 등) | 허용 | 허용 | **차단** |
| `import("data:...")` | 허용 | 허용 | **차단** |
| `new Worker(code, { eval: true })` | 허용 | 허용 | **차단** |
| `module._compile()`, 소스 텍스트를 돌려주는 플러그인, `napi_run_script()`, 인스펙터 | 허용 | 허용 | **차단** |

차단 시 `EvalError: Code generation from strings disallowed for this context`가 발생하며, 모든 `Worker`를 포함한 **프로세스 전체**에 적용됩니다.

#### 3) 단일 실행 파일에 내장
```bash
bun build --compile ./server.ts --outfile server \
  --compile-exec-argv="--disallow-code-generation-from-strings=strict"
```
실행 파일에 내장한 플래그는 **항상 적용**되고, `BUN_OPTIONS`로 **수준을 올릴 수는 있어도 낮출 수는 없습니다**. 예제 4에서 내장 `=strict` 바이너리에 `BUN_OPTIONS="--disallow-code-generation-from-strings"`(기본 수준)를 줘도 `vm`·`data:` import·Worker eval이 계속 차단되는 것을 확인했습니다.

> **실측 함정:** `import("data:text/javascript,...")`처럼 리터럴로 쓴 data URL은 `bun build --compile`이 **빌드 시점에 인라인**해 버려 런타임 차단 대상이 아니게 됩니다. 런타임에 문자열을 조립해야 차단 동작을 검증할 수 있습니다.

### 2.6 node:http 대용량 응답 최대 2.7배

#### 1) 결함 발생 메커니즘
16 KB를 넘는 응답을 **한 tick 안에서 최대 16번 나눠 write**하고 있었습니다. 시스템 콜과 이벤트 루프 왕복이 늘어나, 8개 대용량 응답 벤치마크 중 6개에서 Node.js보다 느렸습니다.

#### 2) v1.4.3의 해결책
16 KB 초과 응답을 **tick당 한 번의 write**로 내보냅니다. `node:http`와 `Bun.serve` 모두, HTTP와 HTTPS 모두 적용되며 작은 응답은 그대로입니다. `Bun.serve` direct 스트림의 4 × 16 KB 쓰기는 83% 빨라졌습니다.

| 응답 (공식, req/s) | v1.4.3 | v1.4.2 | Node.js 26.3 |
| :--- | ---: | ---: | ---: |
| 4 × `res.write(16 KB)` | **19,160** | 6,983 | 17,735 |
| 4 × `res.write(16 KB)`, HTTPS | **15,510** | 6,110 | 11,720 |
| 40 × `res.write(2 KB)` | **14,980** | 6,140 | 9,879 |
| `res.end(64 KB)` | **19,889** | 16,528 | 18,535 |

본 문서 실측(예제 6, 같은 프로세스 안에서 `fetch` 부하, 상대 비교용)에서는 4 × 16 KB가 **10,297 → 22,234 req/s(2.2배)**, 40 × 2 KB가 **8,923 → 18,839 req/s(2.1배)**, `res.end(64 KB)`가 **20,811 → 26,827 req/s(1.3배)**였습니다.

이와 함께 `Bun.serve`가 파이프라인된 HTTP/1.1 요청에 **배치 전체를 `send()` 한 번으로** 응답하도록 바뀌었습니다(응답당 시스템 콜 약 14회 → 배치당 1회, v1.2.6 회귀 수정).

### 2.7 JavaScriptCore 업그레이드

| 연산 (공식) | 변화 |
| :--- | :--- |
| npm 레지스트리 manifest `JSON.parse()` (331 KB–8 MB) | 1.2–1.5배 빠름 |
| 같은 키를 가진 객체 1,000개 `JSON.parse()` | 1.5배 빠름 |
| 라우터 벤치의 `/^\/users\/(\d+)$/.test(path)` | 약 5배 빠름 |
| 속성 9개 이상 `Object.values(obj)` | 2.3–3.2배 빠름 |
| `arr.copyWithin(0, 1)` | 약 2배, 구멍(hole) 있는 배열은 약 45배 |
| 긴 number 배열 `arr.includes(x)` | 2.4–3.3배 빠름 |
| `arr.splice(2, 1, x)` | 새 fast path |
| `for (const x of arr)` (문자열 포함), `const [a, b] = arr` | 이터레이터 객체를 할당하지 않음 (최상위 JIT 단계 전 코드에 효과) |

본 문서 실측(예제 5, 1.4.0 → 1.4.3): `JSON.parse` 같은 키 1,000개 173.81 → 116.43µs, npm manifest 형태 91 KB 190.62 → 125.59µs, 라우터 정규식 16 → 6ns, `Object.values` 100 → 57ns, `copyWithin` 408 → 215ns, `splice` 24 → 17ns. `arr.includes`는 마지막 원소 검색 기준 4~5ns로 차이가 없었는데, 이 벤치가 이미 JIT 최적화가 끝난 짧은 루프라 공식 측정 조건과 다르기 때문으로 보입니다.

사양·정확성 수정:
- WebAssembly **wide arithmetic**(`i64.add128`, `i64.mul_wide_u` 등) 기본 활성화. Windows에서 WebAssembly fast memory 재활성화.
- `RegExp.escape()`가 U+2002A 같은 보충 평면 코드 포인트를 더 이상 이스케이프하지 않음.
- `Atomics.isLockFree(4294967297)`이 `1`로 감기지 않고 `false` 반환.
- strict 모드 async generator의 `return someCall()`이 반환된 Promise를 await.
- 루프 안 `++arr.length`가 10만 원소를 넘어서도 2차 시간으로 느려지지 않음.
- `BigInt("-")`, `BigInt("+")`, `BigInt("0x")`가 `0n` 대신 `SyntaxError`.
- `(a?.b)(x)`에서 `a`가 `null`/`undefined`면 `TypeError` (이전에는 괄호가 없는 것처럼 `undefined` 반환).
- `` super.tag`x` ``가 현재 `this`로 `tag` 호출.
- `Error.stackTraceLimit`을 스택 캡처 시점에 `Error` 생성자에서 읽음(V8과 동일), `node:vm` 컨텍스트는 10부터 시작.
- 부동소수점 값이 많은 JIT 코드에서 `arr[i]`(때로는 `Float32Array`/`Float64Array`, 때로는 다른 객체) 읽은 뒤 값 하나가 `NaN`이 되던 문제 수정.
- `Intl.DurationFormat`이 -1과 0 사이 기간의 부호 유지(`{ milliseconds: -500 }` → `-0.5`), `Intl.Segmenter#containing()`이 서로게이트 쌍 앞쪽 인덱스에서 올바른 세그먼트 반환.
- `--bytecode` 출력 3–6% 축소.

### 2.8 대량 거부 Promise 처리: 2차 시간 → 선형 시간

같은 턴에 거부되는 Promise 다수에 핸들러를 다는 작업이 **2차 시간**이었습니다. 수천 개의 async 호출이 던지는 `Promise.allSettled`가 멈춘 것처럼 보였습니다.

```typescript
await Promise.allSettled(
  Array.from({ length: 100_000 }, async () => {
    throw new Error("nope");
  }),
);
```

| 측정 | 공식 | 본 문서 실측 (macOS arm64) |
| :--- | :--- | :--- |
| `allSettled` 10만 개 throw | 24 s → **148 ms** (Node.js 475 ms) | 1.4.0 1,163.1 ms → 1.4.3 **76.9 ms** (15배) |
| 이미 거부된 16만 개에 `.catch()` | 83 s → **24 ms** | 1.4.0 2,936.8 ms → 1.4.3 **105.9 ms** (28배) |

배치 작업, 크롤러, 대량 업스트림 팬아웃처럼 **실패가 몰려서 발생하는** 워크로드에서 체감 차이가 큽니다.

### 2.9 CompressionStream 압축 레벨과 Bun.serve If-Range

#### 1) `CompressionStream({ level })`
```typescript
const stream = new CompressionStream("brotli", { level: 4 });
```
- `gzip`, `deflate`, `deflate-raw`: 0–9 / `brotli`: 0–11 / `zstd`: 1–22
- 범위 밖 값은 `RangeError`, `level`을 생략하면 각 포맷의 기존 기본값 유지 (**brotli 기본값은 여전히 11**).

예제 6 실측(583 KB JSON)에서 brotli level 11은 12.0 KB를 836ms에 만들었고, **level 4는 15.5 KB를 2.1ms**에 만들었습니다. 동적 응답이라면 크기 3.5 KB를 더 쓰고 지연을 약 400분의 1로 줄이는 선택이 대개 합리적입니다. 같은 코드를 1.4.0에서 실행하면 **`level`이 조용히 무시되어 모든 레벨의 결과 크기가 같고**, 범위 밖 값(`gzip 10`, `brotli 12`, `zstd 0`)도 오류 없이 통과합니다. 1.4.3으로 올리는 순간 잘못된 레벨을 쓰던 코드는 `RangeError`를 던지므로 주의해야 합니다.

#### 2) `Bun.serve`의 `If-Range`
클라이언트가 다운로드를 안전하게 이어받을 수 있습니다. `Range` 요청에 `If-Range`가 있으면 파일이 바뀌지 않았을 때만 범위(206)를, 바뀌었으면 전체 본문(200)을 보냅니다. `Bun.file` 응답과 `{ dir }` 라우트에서 동작합니다.

```typescript
await fetch("http://localhost:3000/big.bin", {
  headers: { Range: "bytes=1000-", "If-Range": lastModified },
});
// 파일 미변경: 206 / 변경: 200 + 전체 본문
```

예제 6에서 1.4.0은 **파일이 바뀐 뒤에도 206 부분 응답**을 보냈습니다(If-Range 무시). 이어받기 클라이언트 입장에서는 옛 파일 앞부분과 새 파일 뒷부분이 섞인 손상 파일이 만들어질 수 있는 동작입니다.

> **실측 함정:** `routes: { "/x": Bun.file(p) }`처럼 **정적 라우트**로 주면 `Last-Modified`가 자동으로 붙지만, 핸들러에서 `new Response(Bun.file(p))`를 반환하면 `Last-Modified`가 **붙지 않습니다**. 동적 핸들러에서는 `file.lastModified`로 헤더를 직접 넣어야 `If-Range`가 의미를 가집니다.

### 2.10 bun install 과 bun build 개선

#### 1) `bun install`이 설치하지 않을 tarball을 받지 않음
lockfile 없이 `bun install` / `bun add`를 실행할 때, `node_modules`에 들어가지 않는 패키지(bundled dependencies, 다른 플랫폼 전용 패키지, `--production` / `--omit`으로 제외된 그룹)의 tarball을 더 이상 다운로드하지 않습니다.

| 설치 (콜드 캐시, lockfile 없음) | v1.4.3 | v1.4.2 |
| :--- | ---: | ---: |
| `npm@10.9.2` | **1** | 196 |
| `express` + dev deps, `--production` | **69** | 403 |

#### 2) 엔트리 포인트가 많은 빌드의 메모리
| 최대 RSS, 엔트리 800개 | v1.4.3 | v1.4.2 |
| :--- | ---: | ---: |
| 각자 20만 개 export 파일에서 하나씩 import, `--splitting` | **276 MB** | 2,121 MB |
| 모듈 13개씩, `--splitting` 유무 무관 | **200 MB** | 405 MB |

v1.4.1의 회귀(청크 ~800개 `--splitting`에서 7.7 GB, Windows에서 `memory allocation of N bytes failed` 중단)도 함께 해결됐습니다.

#### 3) 출력 이름의 `[hashN]`
큰 `--splitting` 빌드에서 내용이 다른 두 청크가 같은 8글자 `[hash]`를 받아 "Multiple files share the same output path"로 실패하던 문제가 해결됐습니다. 이제 충돌하면 서로 달라질 때까지 해시 글자를 늘립니다. `[hash9]`~`[hash13]`으로 최소 길이를 지정할 수 있고 **`[hash13]`은 64비트 전체 해시**입니다.

#### 4) metafile의 `entryPoint`
`--splitting`에서 `metafile.inputs`의 각 동적 `import()`에 그 import가 로드하는 입력 파일을 가리키는 **`entryPoint`** 필드가 붙습니다. 모듈 그래프를 만드는 도구가 `outputs`를 거쳐 조인할 필요가 없어졌고, metafile 바이트 수와 `--metafile-md` 출력도 정확해졌습니다.

```json
{
  "path": "./chunk-abc123.js",
  "kind": "dynamic-import",
  "original": "./lazy.js",
  "entryPoint": "lazy.js",
  "external": true
}
```

### 2.11 단일 실행 파일: --bytecode-order 와 시작 시간 단축

#### 1) 프로필 기반 바이트코드 배치 (`--bytecode-order`)
실제 실행에서 사용된 바이트코드를 **파일 앞쪽에 모아** 배치합니다. 공식 사례의 대형 CLI 앱은 **콜드 스타트 1.01s → 0.53s**, 프롬프트 시점 상주 바이트코드 메모리 **59.5 MB → 20.5 MB**였습니다.

```bash
bun build --compile --bytecode ./cli.ts --outfile myapp
# 사용자가 실제로 쓰는 방식대로 실행. 종료 시 프로필 기록
BUN_BYTECODE_ORDER_OUT=myapp.order ./myapp --help
bun build --compile --bytecode --bytecode-order=myapp.order ./cli.ts --outfile myapp
```
- 함수는 **구문 해시**로 매칭되므로 이전 빌드의 프로필도 적용됩니다.
- `--bytecode-order=a.order,b.order`로 여러 프로필(자주 쓰는 순)을 줄 수 있습니다.
- `Bun.build`에서는 `compile: { bytecodeOrder: "./myapp.order" }`.
- `bun:jsc`의 `bytecodeOrderStats()`가 로드된 함수 중 프로필이 커버한 수를 보고합니다.

#### 2) `--compile --bytecode` 시작 시간
ESM 실행 파일이 **사전 해석된 모듈 그래프와 최적화된 바이트코드를 내장**하고 번들된 모듈을 한 번에 로드합니다. ~2,300개 모듈 CLI에서 첫 프롬프트까지 698ms → 579ms(−17%).

#### 3) JIT 정책
`--compile-jit-policy <n>`(`Bun.build`의 `compile: { jitPolicy: n }`)은 JIT 단계 상승 임계값을 배율로 조정해, 한 번만 실행되는 시작 코드를 인터프리터에 더 오래 둡니다. 앱이 상호작용 가능해지면 `Bun.unsafe.setJITPolicy(1)`로 정상 정책으로 되돌립니다. `--no-optimize-bytecode` / `optimize: { bytecode: false }`는 빌드 시 바이트코드 최적화를 건너뜁니다.

> **실측 결과의 해석:** 예제 7의 300개 모듈짜리 작은 CLI에서는 `--bytecode-order` 적용 전후 시작 시간이 12.4ms / 12.2ms로 사실상 같았고, JIT 정책 1과 4의 차이도 측정 오차 수준이었습니다. 이 기능들은 **바이트코드가 수십 MB에 이르는 대형 CLI**에서 효과가 나는 최적화이며, 작은 앱이라면 굳이 파이프라인을 복잡하게 만들 필요가 없습니다.

### 2.14 Node.js 호환성 및 버그 수정 요약

공식 노트의 수정 항목은 수백 줄에 이릅니다. 실무 영향이 큰 것을 모듈별로 정리합니다.

**`node:http` / `node:https`**
- `req.pause()` 중 작은 본문이 `req.resume()` 전까지 도착하지 않던 문제, 본문 도착 전 `res.end()` 시 나머지 본문이 버려지던 문제, `'request'`/`'data'` 리스너 안의 동기 `res.destroy()`가 `'aborted'` 대신 `'end'`를 내던 문제 수정.
- 큰 응답 + 느린 클라이언트에서 `'finish'`와 `res.end()` 콜백이 마지막 바이트 전송 전에 발생하던 문제, `res.write()`가 `false`를 반환한 뒤 하트비트 타이머가 다시 write하면 `'drain'`이 영영 오지 않아 `stream.pipe(res)`가 멈추던 문제 수정.
- `server.close()`가 keep-alive 연결이 열린 채로 콜백되고 `closeAllConnections()`가 아무것도 하지 않던 문제, `closeAllConnections()`가 리스너와 터널·WebSocket까지 멈추던 문제 수정.
- 이미 요청을 처리한 keep-alive 연결의 `'upgrade'`/`'connect'` 소켓 write가 `socket.end()`까지 버퍼링되어 **npm `ws` 패키지가 멈추던** 문제 수정.
- 이미 listen 중인 서버에 `listen()`을 다시 호출하면 `ERR_SERVER_ALREADY_LISTEN` (Node와 동일). `headersTimeout`/`requestTimeout` 뒤 `'clientError'`가 반복 발생하던 문제 수정.
- 프록시 오류(`ERR_PROXY_TUNNEL`, `ERR_PROXY_INVALID_CONFIG`) 메시지에 **프록시 URL의 사용자명·비밀번호가 포함되던** 문제 수정.

**`node:http2` / `node:tls` / `node:net` / `node:dns`**
- Linux에서 닫힌 포트로 `http2.connect()` 시 `ECONNREFUSED` 대신 `ECONNRESET`, `'error'` 리스너가 없으면 조용히 삼켜지던 1.4.0 회귀 수정.
- `[http2.sensitiveHeaders]`가 헤더 이름 목록을 리터럴 헤더로 함께 보내던 문제 수정.
- 클라이언트 측 `new tls.TLSSocket(socket)`(STARTTLS)이 핸드셰이크를 시작하지 않아 **`mysql` 패키지의 `ssl` 연결이 실패하던** 문제 수정. `tls.Server#setSecureContext()`가 listen 중인 서버에 적용되지 않던 문제 수정.
- 부분 `writev()` 뒤 `node:net` 소켓이 바이트를 버리거나 재전송할 수 있던 문제, `net.Socket#write()`가 즉시 실패해도 `true`를 반환하던 문제 수정.
- 임시 DNS 실패(SERVFAIL, 모든 네임서버 타임아웃)를 `EAI_AGAIN` 대신 `ETIMEOUT`으로 보고해 **`EAI_AGAIN` 기반 재시도 로직이 동작하지 않던** 문제 수정.

**`node:child_process` / `node:fs` / `node:util` / `node:crypto` / `node:buffer`**
- `spawnSync()`가 실행할 수 없는 명령에 대해 `status: null`, `pid: 0`, `output: null`을 반환 (Node와 동일).
- `child.stdin.end(cb)`가 이전 write가 가득 찬 파이프에서 대기 중인데도 `cb`를 먼저 호출해, 부모가 `cb`에서 종료하면 자식 입력이 잘리던 문제 수정.
- Linux/macOS에서 `node:fs`가 `O_CLOEXEC` 없이 파일을 열어 **`node-pty` 등 네이티브 코드가 fork한 자식이 디스크립터를 상속**하던 문제 수정.
- `util.format('%s', value)`가 `Buffer`, `URL`, `URLSearchParams`에 대해 `toString()` 결과 출력. 1.4.1 회귀로 `util.promisify(setTimeout)`이 `setImmediate`의 promise 버전을 돌려줘 **`await sleep(300)`이 즉시 끝나던** 문제 수정.
- `crypto.hkdfSync()`의 `keylen` 0이 빈 버퍼 대신 오류. `buf.utf8Write(123)` 등이 문자열이 아닌 값에 `ERR_INVALID_ARG_TYPE`.

**Bun API / fetch / WebSocket / Streams**
- `Bun.serve`가 101 응답 전에 같은 TCP 읽기로 도착한 WebSocket 프레임을 버리던 문제, Linux에서 1 MB 이상 파일 응답이 거대 헤더 뒤에서 헤더 끝 전에 파일 바이트를 보낼 수 있던 문제 수정.
- `http2: true` / `http3: true` 서버에서 스트리밍 응답이 해제되지 않아 graceful `server.stop()`이 끝나지 않던 문제, HTTP/3에서 핸들러 안 `server.stop()`이 CPU 100%를 쓰던 문제 수정.
- `req.clone()` 후 어느 쪽도 읽지 않으면 요청당 약 7 KB가 누수되던 문제 수정.
- 1.4.1 회귀: 한 keep-alive 오리진에 64개를 넘는 동시 `fetch()`가 끝난 뒤 남는 유휴 연결을 RST로 닫아 서버에 `ECONNRESET`이 찍히던 문제 수정.
- `fetch()`가 `#` 뒤에 `?`가 있는 fragment(`/#/users?id=1`)를 요청 줄에 보내던 문제, `delete process.env.HTTPS_PROXY`가 이후 `fetch()`에 반영되지 않던 문제 수정.
- `br`/`zstd` 스트리밍 응답이 큰 청크의 앞 4096바이트만 전달하던 문제, 느린 리더에서 압축 본문을 읽는 속도가 아니라 도착 속도로 풀어 메모리가 수백 MB 늘던 문제 수정.
- `type: "direct"` 스트림의 `controller.write()`가 느린 리더를 기다리지 않던 문제 수정 (이제 `highWaterMark` 64 KiB에서 Promise 반환). `new Response(asyncIterable)`이 소비자가 멈춘 뒤에도 이터레이터를 계속 당기던 문제 수정 (이제 `return()` 호출로 `finally` 실행).
- macOS에서 `subprocess.signalCode`와 `kill()`이 Linux 시그널 번호를 써서 SIGBUS가 `"SIGUSR1"`로 보고되던 문제 수정.
- `Bun.file(path).exists()`가 한 번 `false`를 본 뒤 파일이 생겨도 계속 `false`를 반환하던 문제 수정.

**번들러 / 트랜스파일러 / 테스트 러너 / SQL**
- 1.4.1 회귀 다수 수정: 순환 import 중 `const { v } = require("./b.js")`가 나중 값을 보던 문제, `--splitting`에서 쿼리 문자열로 엔트리가 두 번 실행되던 문제, **opencode가 1.4.1/1.4.2로 빌드할 때 겪은** 공유 청크의 순환 출력 순서 문제, `--minify-syntax` 후 `ReferenceError: m is not defined`.
- `jsxImportSource: "solid-js"`가 `React.createElement`를 출력하던 문제, `Bun.build({ tsconfig })` 옵션이 무시되던 문제 수정.
- `--react-compiler`: 컴포넌트 크기에 따라 메모리가 2차(800항 `||` 체인이 3 GB OOM → 78 MB)·지수적으로 늘던 문제, 재할당 순서 오류 다수 수정.
- `bun test`: `mock.module()` 팩토리가 이미 import된 모듈에 대해 pending promise를 반환하면 CPU 100%로 멈추던 문제(vitest 부분 모킹 패턴), `--isolate`/`--parallel`에서 끝난 파일의 타이머·서버·`process.chdir()`이 다음 파일로 새던 문제 수정.
- `Bun.SQL`(Postgres): `bytea`에 `number[]`·객체·`Date`를 바인딩하면 빈 값이 저장되던 문제(이제 `TypeError`), 인코딩 실패한 파라미터 하나가 연결 전체와 트랜잭션을 닫던 문제, **콜백이 실패 쿼리 오류를 삼키면 서버가 롤백했는데도 `sql.begin()`이 resolve되던** 문제(이제 `ERR_POSTGRES_COMMIT_ROLLED_BACK`) 수정.
- `bun:sqlite`: 65,535개를 넘는 파라미터에서 잘못된 오류가 나 대량 insert가 깨지던 문제 수정. S3 멀티파트 업로드가 전체 페이로드를 메모리에 들고 있던 문제(500 MB 업로드 시 RSS +850 MB) 수정.

### 예제 1. bun check 타입 체커와 --check 게이트 통합 검증

타입 오류가 있는 최소 프로젝트를 만들고 `bun check`, `bun run --check`, `bun test --check`, `Bun.build({ check: true })`가 각각 어떻게 막는지 확인한 뒤, 오류를 고쳐 통과시키고, `tsconfig.json`을 건드리지 않고 더 엄격한 옵션을 시험합니다.

```typescript
/**
 * [예제 1] bun check 타입 체커 & --check 게이트(run/test/build) 통합 검증
 * 실행: bun run src/01_bun_check_pipeline.ts
 */
import { mkdirSync, rmSync } from "node:fs";
import { join } from "node:path";

console.log("=== 1. bun check 내장 타입 체커 & --check 파이프라인 게이트 ===\n");

const root = join(import.meta.dir, "temp_check_project");
rmSync(root, { recursive: true, force: true });
mkdirSync(join(root, "src"), { recursive: true });

// 1. 타입 오류가 하나 들어 있는 최소 프로젝트 생성 (typescript 패키지 설치 불필요)
await Bun.write(
  join(root, "tsconfig.json"),
  JSON.stringify(
    {
      compilerOptions: {
        target: "ESNext",
        module: "Preserve",
        moduleResolution: "bundler",
        strict: true,
        noEmit: true,
        skipLibCheck: true,
        types: [],
      },
      include: ["src"],
    },
    null,
    2,
  ),
);

await Bun.write(
  join(root, "src/user.ts"),
  `export interface User {
  id: number;
  name: string;
}

export function greet(user: User): string {
  return "hello " + user.name;
}
`,
);

const BROKEN = `import { greet } from "./user";

console.log(greet({ id: "1", name: "Ada" }));
`;
const FIXED = `import { greet } from "./user";

console.log(greet({ id: 1, name: "Ada" }));
`;
await Bun.write(join(root, "src/index.ts"), BROKEN);

await Bun.write(
  join(root, "src/user.test.ts"),
  `import { test, expect } from "bun:test";
import { greet } from "./user";

test("greet", () => {
  expect(greet({ id: "1", name: "Ada" })).toBe("hello Ada");
});
`,
);

// 2. 하위 명령 실행 헬퍼: 현재 실행 중인 bun 바이너리를 그대로 사용
async function sh(args: string[]) {
  const started = performance.now();
  const proc = Bun.spawn([process.execPath, ...args], {
    cwd: root,
    stdout: "pipe",
    stderr: "pipe",
    env: { ...process.env, NO_COLOR: "1" },
  });
  const [out, err, code] = await Promise.all([
    proc.stdout.text(),
    proc.stderr.text(),
    proc.exited,
  ]);
  return { code, out: (out + err).trim(), ms: performance.now() - started };
}

// 3. bun check: 타입만 검사 (JS / .d.ts 출력 없음)
console.log("-> [A] bun check --no-pretty (tsc --pretty false 와 같은 한 줄 형식)");
const a = await sh(["check", "--no-pretty"]);
console.log(`   종료 코드: ${a.code}`);
console.log("   " + a.out.split("\n").join("\n   "));

// 4. bun run --check: 타입 오류가 있으면 코드 자체가 실행되지 않음
console.log("\n-> [B] bun run --check src/index.ts");
const b = await sh(["run", "--check", "--no-pretty", "src/index.ts"]);
console.log(`   종료 코드: ${b.code}, 'hello Ada' 출력 여부: ${b.out.includes("hello Ada")}`);

// 5. bun test --check: 테스트 파일과 import 대상까지 검사, 오류 시 테스트 0개 실행
console.log("\n-> [C] bun test --check");
const c = await sh(["test", "--check"]);
console.log(`   종료 코드: ${c.code}, 테스트 실행 여부: ${/\d+ pass/.test(c.out)}`);

// 6. Bun.build({ check: true }): 타입 오류는 일반 빌드 오류처럼 실패하고 아무것도 쓰지 않음
console.log("\n-> [D] Bun.build({ check: true })");
const outdir = join(root, "out");
try {
  const result = await Bun.build({
    entrypoints: [join(root, "src/index.ts")],
    outdir,
    target: "bun",
    check: true,
  } as any);
  console.log(`   success=${result.success}, outputs=${result.outputs.length}`);
} catch (err: any) {
  const first = err?.errors?.[0] ?? err;
  console.log(`   빌드 거부됨: ${String(first?.message ?? first).split("\n")[0]}`);
}
console.log(`   out/ 디렉터리 생성 여부: ${await Bun.file(join(outdir, "index.js")).exists()}`);

// 7. 오류 수정 후 다시 실행
//    - index.ts / user.test.ts 의 id 타입 수정
//    - bun check 는 @types/bun 이 없으면 'bun:test' 를 TS2307 로 잡는다.
//      실무에서는 `bun add -d @types/bun`, 여기서는 오프라인 재현을 위해 최소 선언만 추가
await Bun.write(join(root, "src/index.ts"), FIXED);
await Bun.write(
  join(root, "src/bun-test-shim.d.ts"),
  `declare module "bun:test" {
  export function test(name: string, fn: () => void | Promise<void>): void;
  export function expect<T>(value: T): { toBe(expected: T): void };
}
`,
);
await Bun.write(
  join(root, "src/user.test.ts"),
  (await Bun.file(join(root, "src/user.test.ts")).text()).replace('id: "1"', "id: 1"),
);

console.log("\n-> [E] 오류 수정 후 재검사");
const e1 = await sh(["check", "--no-pretty", "--timing"]);
console.log(`   bun check 종료 코드: ${e1.code}`);
console.log("   " + e1.out.split("\n").join("\n   "));
const e2 = await sh(["run", "--check", "src/index.ts"]);
console.log(`   bun run --check 출력: ${e2.out.split("\n").pop()}`);
const e3 = await sh(["test", "--check"]);
console.log(`   bun test --check: 종료 코드 ${e3.code}, ${e3.out.match(/\d+ pass/)?.[0] ?? e3.out}`);

// 8. tsconfig 를 고치지 않고 더 엄격한 옵션 시험
console.log("\n-> [F] bun check --noUncheckedIndexedAccess (tsconfig 수정 없이 옵션 덮어쓰기)");
await Bun.write(
  join(root, "src/index.ts"),
  FIXED + `\nconst names = ["Ada"];\nconst first: string = names[0];\nconsole.log(first);\n`,
);
const f = await sh(["check", "--no-pretty", "--noUncheckedIndexedAccess"]);
console.log(`   종료 코드: ${f.code}`);
console.log("   " + f.out.split("\n").join("\n   "));

rmSync(root, { recursive: true, force: true });
console.log("\nbun check 파이프라인 검증 완료!\n");
```

### 예제 2. Bun.FetchSession 연결 풀 격리와 프록시 환경

로컬 업스트림 서버가 클라이언트 소켓 포트를 돌려주게 해 **같은 포트 = 같은 TCP 연결**로 풀 격리를 확인하고, 로컬 포워드 프록시로 `NO_PROXY`의 `host:port` 매칭, `proxy: false`, `ALL_PROXY` 대체를, `CONNECT`를 407로 거부하는 프록시로 `ERR_PROXY_TUNNEL`을 검증합니다.

```typescript
/**
 * [예제 2] Bun.FetchSession 연결 풀 격리 & NO_PROXY / proxy:false / ERR_PROXY_TUNNEL
 * 실행: bun run src/02_fetch_session_proxy.ts
 */
import { createServer } from "node:net";

console.log("=== 2. Bun.FetchSession 연결 풀 격리 & 프록시 환경 개선 ===\n");

// 0. 셸/CI/사내망이 주입한 프록시 변수 정리. 소문자(http_proxy, no_proxy)가 남아 있으면
//    대문자 변수를 바꿔도 결과가 달라지지 않으므로 반드시 양쪽 다 지운다.
const PROXY_VARS = ["HTTP_PROXY", "HTTPS_PROXY", "ALL_PROXY", "NO_PROXY"];
const inherited = PROXY_VARS.flatMap((k) => [k, k.toLowerCase()]).filter((k) => process.env[k]);
for (const k of PROXY_VARS) {
  delete process.env[k];
  delete process.env[k.toLowerCase()];
}
console.log(`-> 상속된 프록시 변수 ${inherited.length}개 제거: ${inherited.join(", ") || "(없음)"}\n`);

const body = (r: Response | Promise<Response>): Promise<any> => Promise.resolve(r).then((x) => x.json());

// 1. 업스트림 서버: 요청을 보낸 클라이언트 소켓의 포트를 돌려줌 → 포트가 같으면 같은 TCP 연결
function startUpstream(name: string) {
  return Bun.serve({
    port: 0,
    fetch(req, server) {
      const ip = server.requestIP(req);
      return Response.json({ name, clientPort: ip?.port, via: req.headers.get("x-via") ?? "direct" });
    },
  });
}
const upstreamA = startUpstream("A");
const upstreamB = startUpstream("B");
const urlA = `http://localhost:${upstreamA.port}/`;
const urlB = `http://localhost:${upstreamB.port}/`;

// 2. 세션별 연결 재사용 / 격리 검증
const sessionOne = new Bun.FetchSession({ keepAlive: { idleTimeout: 30, maxIdleSockets: 8 } });
const sessionTwo = new Bun.FetchSession({ keepAlive: { idleTimeout: 30, maxIdleSockets: 8 } });

async function ports(fetcher: (u: string) => Promise<Response>, n: number) {
  const seen: number[] = [];
  for (let i = 0; i < n; i++) seen.push((await body(fetcher(urlA))).clientPort);
  return seen;
}

console.log("-> [A] 세션 단위 연결 풀");
const p1 = await ports((u) => sessionOne.fetch(u), 5);
const p2 = await ports((u) => fetch(u, { session: sessionTwo } as any), 5);
const p3 = await ports((u) => fetch(u), 5);
console.log(`   sessionOne.fetch × 5  → 클라이언트 포트 ${[...new Set(p1)].join(",")} (연결 ${new Set(p1).size}개)`);
```

### 예제 3. Bun.ModuleGraph 멀티 테넌트 격리 (실험적)

같은 앱 파일을 테넌트별 그래프로 로드해 모듈 상태 격리, 그래프 소유 서버·타이머, `ModuleGraph.current`, `onError` 수집, `dispose()`와 `using` 정리를 확인합니다.

```typescript
/**
 * [예제 3] (실험적) Bun.ModuleGraph 로 한 프로세스에서 멀티 테넌트 앱 인스턴스 운영
 * 실행: bun run src/03_module_graph_tenants.ts
 */
import { mkdirSync, rmSync } from "node:fs";
import { join } from "node:path";

console.log("=== 3. Bun.ModuleGraph 멀티 테넌트 격리 (실험적 API) ===\n");

const dir = join(import.meta.dir, "temp_graph_app");
rmSync(dir, { recursive: true, force: true });
mkdirSync(dir, { recursive: true });

// 1. 테넌트 앱: 모듈 최상위 상태(카운터, 캐시), 타이머, HTTP 서버를 가진 평범한 모듈
await Bun.write(
  join(dir, "store.ts"),
  `export const cache = new Map<string, number>();
export let hits = 0;
export function hit() { return ++hits; }
`,
);
await Bun.write(
  join(dir, "app.ts"),
  `import { cache, hit } from "./store";

const tenant = process.env.TENANT ?? "unknown";
export let ticks = 0;
let server: ReturnType<typeof Bun.serve> | undefined;

export function start() {
  setInterval(() => { ticks++; }, 10);
  server = Bun.serve({
    port: 0,
    fetch() { return Response.json({ tenant, hits: hit() }); },
  });
  return server.port;
}

export function handle(key: string) {
  cache.set(key, (cache.get(key) ?? 0) + 1);
  return { tenant, hits: hit(), cacheSize: cache.size };
}

export function failLater() {
  setTimeout(() => { throw new Error("tenant " + tenant + " crashed in a timer"); }, 5);
}
`,
);

// 2. 테넌트별 그래프 생성: process 를 테넌트 전용 객체로 바꿔 끼우고, 오류는 그래프 단위로 수집
const errors: string[] = [];
function createTenant(name: string) {
  const tenantProcess = Object.create(process, {
    env: { value: { ...process.env, TENANT: name } },
  });
  return new Bun.ModuleGraph({
    globals: { process: tenantProcess },
    onError: (error: any, kind: string) => errors.push(`[${name}] ${kind}: ${error?.message ?? error}`),
  } as any);
}

const graphA = createTenant("acme");
const graphB = createTenant("globex");

const t0 = performance.now();
const appA: any = await graphA.import(join(dir, "app.ts"));
const t1 = performance.now();
const appB: any = await graphB.import(join(dir, "app.ts"));
const t2 = performance.now();

console.log("\n-> [A] 모듈 상태 격리");
console.log("   acme   : " + JSON.stringify(graphA.run(() => appA.handle("x"))));
console.log("   acme   : " + JSON.stringify(graphA.run(() => appA.handle("y"))));
console.log("   globex : " + JSON.stringify(graphB.run(() => appB.handle("x"))));
console.log(`   appA === appB ? ${appA === appB}`);

// 4. graph.run 안에서 연 서버·타이머는 그 그래프 소유가 됨
console.log("\n-> [B] 그래프 소유 리소스 (서버, 타이머)");
const portA = graphA.run(() => appA.start());
const portB = graphB.run(() => appB.start());
console.log("   acme   서버 응답: " + JSON.stringify(await (await fetch(`http://localhost:${portA}/`)).json()));
console.log("   globex 서버 응답: " + JSON.stringify(await (await fetch(`http://localhost:${portB}/`)).json()));

// 5. Bun.ModuleGraph.current: 호출자가 어느 그래프 컨텍스트에 있는지
const inside = graphA.run(() => (Bun.ModuleGraph as any).current === graphA);
const outside = (Bun.ModuleGraph as any).current;
console.log(`\n-> [C] ModuleGraph.current — run() 안: ${inside}, 바깥: ${outside ?? "null"}`);

await Bun.sleep(50);

for (const e of errors) console.log("   " + e);

const ticksBefore = appA.ticks;
graphA.dispose();
await Bun.sleep(60);
let aliveA = true;
try {
  await fetch(`http://localhost:${portA}/`, { signal: AbortSignal.timeout(300) });
} catch {
  aliveA = false;
}
const aliveB = (await fetch(`http://localhost:${portB}/`)).ok;
console.log("\n-> [E] graphA.dispose() 이후");
console.log(`   acme 서버 응답 가능: ${aliveA}, globex 서버 응답 가능: ${aliveB}`);

// 8. using 으로 블록 종료 시 자동 dispose
{
  using tmp = createTenant("initech");
  const app: any = await tmp.import(join(dir, "app.ts"));
  console.log(`\n-> [F] using 스코프 테넌트: ${JSON.stringify(tmp.run(() => app.handle("z")))}`);
}

graphB.dispose();
rmSync(dir, { recursive: true, force: true });
console.log("\n⚠️  ModuleGraph 는 보안 샌드박스가 아닙니다. 신뢰할 수 없는 코드 격리에는 별도 프로세스/컨테이너를 쓰세요.");
console.log("ModuleGraph 멀티 테넌트 검증 완료!\n");
```

### 예제 4. 문자열 → 코드 생성 차단 플래그 검증

문자열이 코드가 되는 경로 5가지(와 대조군인 일반 `JSON.parse`)를 플래그 없음 / 기본 / `=strict`에서 시도하고, `--compile-exec-argv`로 플래그를 내장한 실행 파일이 `BUN_OPTIONS`로 낮춰지지 않는지 확인합니다.

```typescript
/**
 * [예제 4] --disallow-code-generation-from-strings(=strict) 로 eval / new Function 봉쇄
 * 실행: bun run src/04_disallow_codegen.ts
 */
import { mkdirSync, rmSync } from "node:fs";
import { join } from "node:path";

console.log("=== 4. 문자열 → 코드 생성 차단 플래그 검증 ===\n");

const dir = join(import.meta.dir, "temp_codegen");
rmSync(dir, { recursive: true, force: true });
mkdirSync(dir, { recursive: true });

// 1. 문자열이 코드가 되는 7가지 경로를 하나씩 시도하는 프로브 스크립트
const probe = join(dir, "probe.ts");
await Bun.write(
  probe,
  `import vm from "node:vm";
import { Worker } from "node:worker_threads";
const results: Record<string, string> = {};
async function attempt(name: string, fn: () => unknown) {
  try {
    const v = await fn();
    results[name] = "허용 (" + String(v) + ")";
  } catch (e: any) {
    results[name] = "차단 " + e.name;
  }
}
await attempt("eval", () => eval("1 + 1"));
await attempt("new Function", () => new Function("return 1 + 1")());
await attempt("vm.runInNewContext", () => vm.runInNewContext("1 + 1"));
// 번들러가 빌드 시점에 data: URL 을 인라인하지 않도록 런타임에 문자열을 조립
const dataUrl = ["data:text/javascript", "export default 42"].join(",");
await attempt("import(data:)", async () => (await import(dataUrl)).default);
await attempt("Worker eval", () => new Promise((res, rej) => {
  try {
    const w = new Worker("require('node:worker_threads').parentPort.postMessage(7)", { eval: true });
    const timer = setTimeout(() => { w.terminate(); rej(Object.assign(new Error("no reply"), { name: "Timeout" })); }, 1500);
    w.once("message", (v) => { clearTimeout(timer); res(v); w.terminate(); });
    w.once("error", (e) => { clearTimeout(timer); rej(e); });
  } catch (e) { rej(e); }
}));
await attempt("일반 코드 (JSON.parse)", () => JSON.parse("{\\"ok\\":true}").ok);
console.log(JSON.stringify(results));
`,
);

async function run(label: string, args: string[], env: Record<string, string> = {}) {
  const proc = Bun.spawn([process.execPath, ...args], {
    stdout: "pipe",
    stderr: "pipe",
    env: { ...process.env, ...env },
  });
  const out = (await proc.stdout.text()).trim().split("\n").pop()!;
  await proc.exited;
  console.log(`-> ${label}`);
  try {
    for (const [k, v] of Object.entries(JSON.parse(out))) console.log(`   ${k.padEnd(22)} ${v}`);
  } catch {
    console.log("   " + out + (await proc.stderr?.text?.() ?? ""));
  }
  console.log();
}

// 2. 플래그 없음 / 기본 모드 / strict 모드 비교
await run("플래그 없음", [probe]);
await run("--disallow-code-generation-from-strings (Node 호환: eval·new Function 차단)", [
  "--disallow-code-generation-from-strings",
  probe,
]);
await run("--disallow-code-generation-from-strings=strict (Bun 전용: vm·data: import·Worker eval 까지 차단)", [
  "--disallow-code-generation-from-strings=strict",
  probe,
]);

// 3. 컴파일된 실행 파일에 플래그를 내장 → 항상 적용, BUN_OPTIONS 로 낮출 수 없음
const exe = join(dir, process.platform === "win32" ? "probe.exe" : "probe-bin");
const build = Bun.spawnSync([
  process.execPath,
  "build",
  "--compile",
  probe,
  "--outfile",
  exe,
  "--compile-exec-argv=--disallow-code-generation-from-strings=strict",
]);
console.log(`-> bun build --compile --compile-exec-argv=...=strict  (종료 코드 ${build.exitCode})\n`);

async function runExe(label: string, env: Record<string, string> = {}) {
  const proc = Bun.spawn([exe], { stdout: "pipe", stderr: "pipe", env: { ...process.env, ...env } });
  const out = (await proc.stdout.text()).trim().split("\n").pop()!;
  await proc.exited;
  const r = JSON.parse(out);
  console.log(`-> ${label}`);
  console.log(`   eval=${r["eval"]}, vm=${r["vm.runInNewContext"]}, import(data:)=${r["import(data:)"]}, Worker eval=${r["Worker eval"]}\n`);
}
await runExe("컴파일 바이너리 실행 (내장 플래그)");
await runExe('BUN_OPTIONS="--disallow-code-generation-from-strings" 로 낮추기 시도', {
  BUN_OPTIONS: "--disallow-code-generation-from-strings",
});

rmSync(dir, { recursive: true, force: true });
console.log("코드 생성 차단 플래그 검증 완료!\n");
```

### 예제 6. Bun.serve If-Range, CompressionStream level, node:http 대용량 응답

```typescript
  port: 0,

    "/dynamic/big.bin": () => {

      return new Response(file, { headers: { "Last-Modified": new Date(file.lastModified).toUTCString() } });

async function resume(url: string, validator: string) {
  const r = await fetch(url, { headers: { Range: "bytes=1000-", "If-Range": validator } });
  const body = await r.arrayBuffer();
  return { status: r.status, bytes: body.byteLength, contentRange: r.headers.get("content-range") };
}

console.log("-> [A] Range + If-Range 다운로드 재개");

  const past = new Date(Date.now() - 3_600_000);

  console.log(`   [${kind}] 파일 미변경 + If-Range → ${unchanged.status}, ${unchanged.bytes} bytes, ${unchanged.contentRange}`);

  // 수정 시각을 현재로 바꿔 '파일이 바뀐' 상태 재현
  const now = new Date();
  utimesSync(bigPath, now, now);
  const changed = await resume(url, lastModified);
  console.log(`   [${kind}] 파일 변경 후 같은 If-Range → ${changed.status}, ${changed.bytes} bytes${changed.status === 200 ? " (전체 재전송 ✅)" : " (옛 조각과 새 조각이 섞일 위험 ❌)"}`);
}
fileServer.stop(true);

// 2. CompressionStream level: 압축률 ↔ 속도 트레이드오프
// ---------------------------------------------------------------------------
console.log("\n-> [B] CompressionStream({ level })");
const payload = new TextEncoder().encode(
  JSON.stringify(
    Array.from({ length: 8000 }, (_, i) => ({ id: i, title: `상품 ${i}`, price: (i * 37) % 1000, tags: ["bun", "fast", "http"] })),
  ),
);

  const t = performance.now();
  const stream = new Blob([payload]).stream().pipeThrough(new CompressionStream(format as any, level === undefined ? undefined : ({ level } as any)));
  const out = await new Response(stream).arrayBuffer();
  return { ms: performance.now() - t, kb: out.byteLength / 1024 };
}

for (const [format, levels] of [
  ["gzip", [1, 6, 9]],
  ["brotli", [1, 4, 11]],
  ["zstd", [1, 3, 19]],
] as const) {

    const r = await compress(format, level);
    console.log(`   ${format.padEnd(6)} level ${String(level).padStart(2)} → ${r.kb.toFixed(1).padStart(7)} KB, ${r.ms.toFixed(1).padStart(7)} ms`);
  }
}

console.log(`   brotli 기본값(level 생략, 기존과 동일한 11) → ${brDefault.kb.toFixed(1)} KB, ${brDefault.ms.toFixed(1)} ms`);

  try {
    new CompressionStream(format as any, { level: bad } as any);
    console.log(`   ${format} level ${bad}: 허용됨`);
  } catch (e: any) {
    console.log(`   ${format} level ${bad}: ${e.name} — ${e.message}`);
  }
}

// 3. node:http 대용량 응답: 16 KB 초과 응답을 tick 당 한 번의 write 로 전송
// ---------------------------------------------------------------------------
console.log("\n-> [C] node:http 대용량 응답 처리량 (같은 프로세스 fetch 부하, 상대 비교용)");

const chunk2k = Buffer.alloc(2 * 1024, "b");
const body64k = Buffer.alloc(64 * 1024, "c");

const nodeServer = http.createServer((req, res) => {
  res.setHeader("content-type", "application/octet-stream");
  if (req.url === "/4x16k") {
    for (let i = 0; i < 4; i++) res.write(chunk16k);
    res.end();
  } else if (req.url === "/40x2k") {
    for (let i = 0; i < 40; i++) res.write(chunk2k);
    res.end();
  } else {
    res.end(body64k);
  }

async function load(path: string, durationMs = 1500, concurrency = 32) {

  const until = performance.now() + durationMs;
  await Promise.all(
    Array.from({ length: concurrency }, async () => {
      while (performance.now() < until) {
        const r = await fetch(`http://localhost:${nodePort}${path}`);
        await r.arrayBuffer();
        done++;
      }
    }),
  );
  return Math.round(done / (durationMs / 1000));
}

for (const [label, path] of [
  ["4 × res.write(16 KB)", "/4x16k"],
  ["40 × res.write(2 KB)", "/40x2k"],
  ["res.end(64 KB)", "/end64k"],

rmSync(dir, { recursive: true, force: true });
console.log("\nHTTP 계층 개선 검증 완료!\n");
```

## 4. ALL-IN-ONE 실무 종합 프로덕션 서버 구현체

이 코드는 Bun v1.4.3의 **핵심 기능(`Bun.FetchSession` 업스트림 풀 격리, `Promise.allSettled` 대량 팬아웃, `CompressionStream` 레벨 협상, 정적 자산 `If-Range` 이어받기, `Bun.ModuleGraph` 테넌트 플러그인, 코드 생성 차단)**을 하나의 API 게이트웨이로 통합한 소스 코드입니다. `bun run --check`로 타입 검사를 통과해야만 기동되고, `--disallow-code-generation-from-strings=strict`로 문자열 코드 실행이 봉쇄된 상태에서 동작합니다.

```typescript
/**
 * [종합 프로덕션 서버] Bun v1.4.3 ALL-IN-ONE 게이트웨이
 * 실행(권장): bun run --check --disallow-code-generation-from-strings=strict src/10_production_server.ts
 *
 *  - Bun.FetchSession     : 업스트림별 전용 연결 풀 (keep-alive, 프록시/TLS 설정 격리)
 *  - Promise.allSettled   : 대량 업스트림 팬아웃 (거부 다발도 선형 시간)
 *  - CompressionStream    : Accept-Encoding 협상 + brotli level 4 (동적 응답용)
 *  - Bun.serve routes     : 정적 파일 Range / If-Range 이어받기
 *  - Bun.ModuleGraph      : 테넌트별 플러그인 격리 로딩 (실험적)
 *  - 코드 생성 차단 여부를 /health 로 노출
 */
import { mkdirSync, rmSync } from "node:fs";
import { join } from "node:path";

const workdir = join(import.meta.dir, "temp_prod");
rmSync(workdir, { recursive: true, force: true });
mkdirSync(join(workdir, "plugins"), { recursive: true });
for (const k of ["HTTP_PROXY", "HTTPS_PROXY", "ALL_PROXY", "NO_PROXY"]) {
  delete process.env[k];
  delete process.env[k.toLowerCase()];
}

// ─────────────────────────────────────────────────────────────────────────────
// 1. 가짜 업스트림 2개 (인벤토리 / 가격) — 실제 환경에서는 사내 API
// ─────────────────────────────────────────────────────────────────────────────
const inventory = Bun.serve({
  port: 0,
  fetch(req, server) {
    const id = Number(new URL(req.url).searchParams.get("id"));
    if (id % 7 === 0) return new Response("out of service", { status: 503 });
    return Response.json({ id, stock: (id * 13) % 50, conn: server.requestIP(req)?.port });
  },
});
const pricing = Bun.serve({
  port: 0,
  fetch(req) {
    const id = Number(new URL(req.url).searchParams.get("id"));
    return Response.json({ id, price: 1000 + ((id * 37) % 500) });
  },
});

// ─────────────────────────────────────────────────────────────────────────────
// 2. 업스트림별 FetchSession: 풀을 섞지 않고, 장애 업스트림이 다른 풀에 영향 주지 않음
// ─────────────────────────────────────────────────────────────────────────────
const sessions = {
  inventory: new Bun.FetchSession({ keepAlive: { idleTimeout: 30, maxIdleSockets: 16 } }),
  pricing: new Bun.FetchSession({ keepAlive: { idleTimeout: 30, maxIdleSockets: 16 } }),
};
const upstream = {
  inventory: (id: number) => sessions.inventory.fetch(`http://localhost:${inventory.port}/?id=${id}`),
  pricing: (id: number) => sessions.pricing.fetch(`http://localhost:${pricing.port}/?id=${id}`),
};

async function getJson(res: Promise<Response>): Promise<any> {
  const r = await res;
  if (!r.ok) throw new Error(`upstream ${r.status}`);
  return r.json();
}

// ─────────────────────────────────────────────────────────────────────────────
// 3. 테넌트 플러그인: 같은 파일을 테넌트마다 독립 모듈 상태로 로드
// ─────────────────────────────────────────────────────────────────────────────
await Bun.write(
  join(workdir, "plugins/discount.ts"),
  `let applied = 0;
const rate = Number(process.env.DISCOUNT_RATE ?? "0");
export function apply(price: number) {
  applied++;
  return { price: Math.round(price * (1 - rate)), rate, applied };
}
`,
);
const tenantGraphs = new Map<string, { graph: any; plugin: any }>();
async function tenantPlugin(tenant: string) {
  let entry = tenantGraphs.get(tenant);
  if (!entry) {
    const rate = tenant === "vip" ? "0.2" : "0.05";
    const graph = new Bun.ModuleGraph({
      globals: { process: Object.create(process, { env: { value: { ...process.env, DISCOUNT_RATE: rate } } }) },
      onError: (e: any, kind: string) => console.error(`[tenant:${tenant}] ${kind}`, e?.message),
    } as any);
    entry = { graph, plugin: await graph.import(join(workdir, "plugins/discount.ts")) };
    tenantGraphs.set(tenant, entry);
  }
  return entry;
}

// ─────────────────────────────────────────────────────────────────────────────
// 4. 압축 협상: zstd > br > gzip, brotli 는 level 4 로 동적 응답 지연 억제
// ─────────────────────────────────────────────────────────────────────────────
function compressJson(req: Request, data: unknown, init: ResponseInit = {}) {
  const body = new Blob([JSON.stringify(data)]);
  const accept = req.headers.get("accept-encoding") ?? "";
  const headers = new Headers(init.headers as Bun.HeadersInit);
  headers.set("content-type", "application/json");
  headers.set("vary", "accept-encoding");
  const pick = accept.includes("zstd")
    ? (["zstd", { level: 3 }] as const)
    : accept.includes("br")
      ? (["brotli", { level: 4 }] as const)
      : accept.includes("gzip")
        ? (["gzip", { level: 6 }] as const)
        : null;
  if (!pick || body.size < 1024) return new Response(body, { ...init, headers });
  headers.set("content-encoding", pick[0] === "brotli" ? "br" : pick[0]);
  return new Response(body.stream().pipeThrough(new CompressionStream(pick[0] as any, pick[1] as any)), { ...init, headers });
}

// ─────────────────────────────────────────────────────────────────────────────
// 5. 게이트웨이 서버
// ─────────────────────────────────────────────────────────────────────────────
const assetPath = join(workdir, "catalog.bin");
await Bun.write(assetPath, new Uint8Array(512 * 1024).map((_, i) => i % 256));

let codegenBlocked = false;
try {
  new Function("return 1")();
} catch {
  codegenBlocked = true;
}

const gateway = Bun.serve({
  port: 0,
  routes: {
    "/health": () =>
      Response.json({ status: "ok", bun: Bun.version, codegenBlocked, tenants: [...tenantGraphs.keys()] }),
    "/assets/catalog.bin": Bun.file(assetPath),
    "/api/products": async (req) => {
      const url = new URL(req.url);
      const count = Math.min(Number(url.searchParams.get("count") ?? 50), 500);
      const tenant = req.headers.get("x-tenant") ?? "default";
      const ids = Array.from({ length: count }, (_, i) => i + 1);

      const [stocks, prices] = await Promise.all([
        Promise.allSettled(ids.map((id) => getJson(upstream.inventory(id)))),
        Promise.allSettled(ids.map((id) => getJson(upstream.pricing(id)))),
      ]);
      const { graph, plugin } = await tenantPlugin(tenant);

      const items = ids.map((id, i) => {
        const s = stocks[i];
        const p = prices[i];
        const priced = p.status === "fulfilled" ? graph.run(() => plugin.apply(p.value.price)) : null;
        return {
          id,
          stock: s.status === "fulfilled" ? s.value.stock : null,
          price: priced?.price ?? null,
          degraded: s.status === "rejected",
        };
      });
      const degraded = items.filter((x) => x.degraded).length;
      return compressJson(req, { tenant, count, degraded, items }, { headers: { "x-degraded": String(degraded) } });
    },
  },
  fetch() {
    return new Response("Not Found", { status: 404 });
  },
});

const base = `http://localhost:${gateway.port}`;
console.log(`[Gateway] Bun ${Bun.version} 게이트웨이 구동: ${base}\n`);

// ─────────────────────────────────────────────────────────────────────────────
// 6. 자체 검증
// ─────────────────────────────────────────────────────────────────────────────
console.log("-> 1. 헬스체크:", JSON.stringify(await (await fetch(`${base}/health`)).json()));

const t = performance.now();
const raw = await fetch(`${base}/api/products?count=300`, {
  headers: { "x-tenant": "vip", "accept-encoding": "br" },
  decompress: false,
} as any);
const compressedBytes = (await raw.arrayBuffer()).byteLength;
console.log(
  `-> 2. /api/products (vip, br): ${raw.status}, content-encoding=${raw.headers.get("content-encoding")}, ` +
    `압축 전송 ${compressedBytes} bytes, degraded=${raw.headers.get("x-degraded")}, ${(performance.now() - t).toFixed(1)}ms`,
);

const decoded: any = await (await fetch(`${base}/api/products?count=10`, { headers: { "x-tenant": "vip" } })).json();
const plain: any = await (await fetch(`${base}/api/products?count=10`, { headers: { "x-tenant": "default" } })).json();
console.log(`-> 3. 테넌트별 할인 플러그인: vip id=1 price=${decoded.items[0].price}, default id=1 price=${plain.items[0].price}`);

const first = await fetch(`${base}/assets/catalog.bin`);
const lm = first.headers.get("last-modified")!;
await first.arrayBuffer();
const resumed = await fetch(`${base}/assets/catalog.bin`, { headers: { Range: "bytes=4096-", "If-Range": lm } });
console.log(`-> 4. 정적 자산 이어받기: ${resumed.status}, ${resumed.headers.get("content-range")}, ${(await resumed.arrayBuffer()).byteLength} bytes`);

const conns = new Set<number>();
for (let i = 0; i < 20; i++) conns.add(((await (await upstream.inventory(1)).json()) as any).conn);
console.log(`-> 5. inventory 세션 연결 재사용: 순차 20회 요청 → TCP 연결 ${conns.size}개`);

console.log("-> 6. 헬스체크(테넌트 로드 후):", JSON.stringify(await (await fetch(`${base}/health`)).json()));

// 7. 정리
gateway.stop(true);
inventory.stop(true);
pricing.stop(true);
sessions.inventory.close();
sessions.pricing.close();
for (const { graph } of tenantGraphs.values()) graph.dispose();
rmSync(workdir, { recursive: true, force: true });
console.log("\n종합 게이트웨이 테스트 성공 및 종료 완료!\n");
```

## 6. 설치, 업그레이드 및 마이그레이션 권고사항

### 1) 즉시 업그레이드 명령어
현재 Bun이 설치되어 있는 경우 터미널에서 다음 명령어를 실행하면 최신 v1.4.3으로 업그레이드됩니다:
```bash
bun upgrade
```

신규 설치 시:
```bash
# macOS / Linux
curl -fsSL https://bun.sh/install | bash

# npm
npm install -g bun

# Windows (PowerShell)
powershell -c "irm bun.sh/install.ps1|iex"

# Scoop
scoop install bun

# Homebrew
brew tap oven-sh/bun
brew install bun

# Docker
docker pull oven/bun:1.4.3
docker run --rm --init --ulimit memlock=-1:-1 oven/bun:1.4.3
```

시스템 설치를 건드리지 않고 특정 버전만 시험하려면 GitHub 릴리즈의 바이너리를 받아 경로로 직접 실행합니다(본 문서의 검증 방식):

### 2) 프로덕션 마이그레이션 권고사항
- **모든 TypeScript 프로젝트:** CI의 `tsc --noEmit` 단계를 `bun check`로 바꾸는 것을 검토하세요. 먼저 공식 diff 절차(`tsc` 7.0.2 출력과 `bun check --no-pretty` 출력 비교)로 차이가 없는지 확인한 뒤 전환하는 것이 안전합니다. 로컬 개발 스크립트는 `bun run --check --watch`, 테스트는 `bun test --check`로 게이트를 걸 수 있습니다. 단, 에디터 LSP는 여전히 TypeScript가 담당합니다.
- **`tsconfig.json`과 타입 패키지:** `bun check`를 쓰려면 프로젝트 루트에 `tsconfig.json`을 두고, `@types/bun`을 설치한 뒤 `"types": ["bun"]`을 명시하세요. npm의 `@types/bun`이 1.4.3을 반영하기 전까지는 `Bun.FetchSession` / `Bun.ModuleGraph`용 타입 보강 파일이 필요합니다.
- **유휴 시간이 긴 서버(사내 도구, 관리자 API, 서버리스 컨테이너):** 업그레이드만으로 유휴 CPU와 메모리가 줄어듭니다. 별도 코드 변경이 필요 없습니다.
- **여러 외부 API를 호출하는 서비스:** 업스트림별로 `Bun.FetchSession`을 두어 TLS(CA)·프록시·keep-alive를 분리하세요. `session.fetch`는 bind되어 있으므로 SDK의 `fetch` 주입 옵션에 그대로 넘기면 됩니다.
- **사내 프록시 환경:** `NO_PROXY`에 CIDR·와일드카드·`host:port`를 쓸 수 있게 됐습니다. 프록시 인증 실패가 이제 `ERR_PROXY_TUNNEL`로 **reject**되므로, 응답 상태 코드로 407을 처리하던 코드는 `catch`에서 `err.code === "ERR_PROXY_TUNNEL"`과 `err.status`를 보도록 바꿔야 합니다. 소문자 `http_proxy`/`no_proxy`가 대문자 설정을 가리지 않는지도 점검하세요.
- **보안 민감 서비스:** `--disallow-code-generation-from-strings=strict`를 `--compile-exec-argv`로 실행 파일에 내장하는 것을 권장합니다. 의존성 중 `new Function`을 쓰는 라이브러리(일부 템플릿 엔진, 스키마 검증기의 코드 생성 모드 등)가 있으면 기동 시 `EvalError`가 나므로 스테이징에서 먼저 확인하세요.
- **압축 미들웨어:** `CompressionStream("brotli")`의 기본값은 여전히 quality 11로 매우 느립니다. 동적 응답에는 `{ level: 4 }` 안팎을 명시하세요. 1.4.0~1.4.2에서 범위 밖 레벨을 넘기던 코드는 1.4.3에서 `RangeError`가 나므로 업그레이드 전에 값을 점검해야 합니다.
- **파일 다운로드 서버:** `If-Range`가 지원되므로 대용량 파일은 정적 `Bun.file` 라우트로 내보내는 것이 가장 간단합니다. 동적 핸들러에서 `new Response(Bun.file())`를 반환한다면 `Last-Modified`를 직접 넣어야 이어받기 검증이 동작합니다.
- **Postgres(`Bun.SQL`) 사용자:** 트랜잭션 콜백에서 쿼리 오류를 삼키면 이제 `sql.begin()`이 `ERR_POSTGRES_COMMIT_ROLLED_BACK`으로 reject됩니다. 롤백을 성공으로 오인하던 코드가 드러나므로 오류 처리를 점검하세요.
- **대형 CLI 배포자:** `--compile --bytecode --format=esm`만으로 시작 시간이 줄고, 실사용 프로필로 `--bytecode-order`를 적용하면 추가로 크게 줄어듭니다. 작은 CLI에서는 효과가 거의 없으므로(예제 7) 빌드 파이프라인 복잡도와 비교해 결정하세요.
- **멀티 테넌트 실험:** `Bun.ModuleGraph`는 실험적 API이며 보안 샌드박스가 아닙니다. 신뢰할 수 있는 자체 코드의 상태 격리 용도로만 쓰고, 고객이 올린 코드 실행에는 프로세스·컨테이너 격리를 유지하세요.
- **1.4.1 / 1.4.2에서 번들 회귀를 겪은 프로젝트:** `--splitting` 순환 출력 순서, `--minify-syntax` 후 `ReferenceError`, `require()` 중간 값 문제가 정리됐으므로 워크어라운드를 제거하고 재빌드해 보세요.

## 7. 사실 검토 및 출처

- **공식 수치와 실측 수치의 구분:** 2장의 표 중 "공식"으로 표시한 값은 Bun 블로그와 Jarred Sumner 공개 자료(Linux x64 또는 16코어 Apple silicon, v1.4.2 대비)이고, "본 문서 실측"은 이 문서의 예제를 macOS arm64에서 Bun 1.4.0과 1.4.3으로 실행한 값입니다. 측정 환경과 비교 대상이 다르므로 배율이 일치하지 않는 것이 정상입니다.
