# Deno vs Bun — 지원 범위 · 외부 디펜던시 0 · 성능(Express/Gin/Axum 포함)

> 전제: **외부 라이브러리 / npm·JSR 패키지 설치 0**  
> - Deno = 런타임 내장 API만 (`deno add` / npm import 없이)  
> - Bun = 런타임 내장 API만 (`bun add` / npm import 없이)  
> 웹서버·JSON·파일·WebSocket 중심으로, 성능은 **공개 벤치 경향 + 상대 순위**로 정리 (절대 RPS는 환경마다 크게 변함)

범례: ✅ 네이티브 실무 가능 · ⚠️ 제한·버전 의존·직접 구현 · ❌ 사실상 외부 필요

## 1. 한 줄 결론

| 질문 | 답 |
|---|---|
| 패키지 없이 HTTP JSON·파일 서버? | **Deno·Bun 둘 다 ✅** |
| 패키지 없이 WebSocket? | **둘 다 ✅** |
| Node 호환·npm 감각? | **Bun**이 더 가깝 |
| 권한·보안 기본값? | **Deno** (명시적 권한) |
| TS 내장? | **둘 다 ✅** |
| SQLite 내장? | **둘 다 ✅** (Deno는 **2.2+** `node:sqlite` / Bun은 `bun:sqlite`) |
| HTTP 속도 (JS 런타임끼리) | **Bun ≈ Deno**, 버전·벤치에 따라 앞뒤 바뀜. 둘 다 **Express보다 훨씬 빠름** |
| 네이티브 프레임워크와 | 마이크로벤치에서 **Axum·(Go net/http·Gin)** 급과 어깨를 나란히 하거나 약간 뒤·앞. **부하·코어 수·메모리**에선 보통 Rust/Go가 유리한 경우 많음 |

## 2. 런타임이 다른 점

| | **Deno** | **Bun** |
|---|---|---|
| 엔진 | V8 | JavaScriptCore |
| 설계 키워드 | 웹 표준 · **보안(권한)** · TS | **속도** · **Node 호환** · 올인원 |
| 패키지 문화 | URL/JSR, Deno 2에서 npm 호환 강화 | npm/`package.json`이 기본 감각 |
| 기본 보안 | 파일·넷·환경 **플래그로 허용** | Node처럼 기본적으로 넓게 허용 |
| HTTP 서버 | `Deno.serve` | `Bun.serve` |
| 설치 단위 | `deno` 바이너리 | `bun` 바이너리 |
| 단일 실행 파일 | ✅ `deno compile` (런타임 임베드) | ✅ `bun build --compile` (비교적 성숙) · 아니면 `bun`+소스 |
| TS 실행 시 타입 검사 | 기본으로 **타입체크 가능** (`deno check` / run 옵션) | 실행은 **타입 제거(트랜스파일)** 위주 · 검사는 별도 |

```text
Express + Axios 스택 (피할 패턴)
  node + npm i express axios ...

외부 0 패턴
  deno run --allow-net server.ts     # Deno.serve
  bun server.ts                      # Bun.serve
```

## 4. 최소 웹서버 코드

### Deno (의존 0)

```ts
// server.ts
Deno.serve({ port: 8080, hostname: "0.0.0.0" }, async (req) => {
  const url = new URL(req.url);

  if (url.pathname === "/health") {
    return Response.json({ ok: true, runtime: "deno" });
  }

  if (url.pathname === "/echo" && req.method === "POST") {
    return Response.json(await req.json());
  }

  if (url.pathname === "/upload" && req.method === "POST") {
    const form = await req.formData();
    const file = form.get("file");
    if (!(file instanceof File)) return new Response("file required", { status: 400 });
    await Deno.writeFile(`data/${file.name}`, new Uint8Array(await file.arrayBuffer()));
    return Response.json({ name: file.name, size: file.size });
  }

  return new Response("not found", { status: 404 });
});
```

```bash
mkdir -p data
deno run --allow-net --allow-read --allow-write server.ts
```

### Bun (의존 0)

```ts
// server.ts
Bun.serve({
  port: 8080,
  hostname: "0.0.0.0",
  async fetch(req) {
    const url = new URL(req.url);

    if (url.pathname === "/health") {
      return Response.json({ ok: true, runtime: "bun" });
    }

    if (url.pathname === "/echo" && req.method === "POST") {
      return Response.json(await req.json());
    }

    if (url.pathname === "/upload" && req.method === "POST") {
      const form = await req.formData();
      const file = form.get("file");
      if (!(file instanceof File)) return new Response("file required", { status: 400 });
      await Bun.write(`data/${file.name}`, file);
      return Response.json({ name: file.name, size: file.size });
    }

    return new Response("not found", { status: 404 });
  },
});
```

```bash
mkdir -p data
bun server.ts
```

## 5. 성능 — Deno vs Bun

### 5.1 대략적 위치

```text
HTTP JSON “가벼운 핸들러” 처리량 (개념)

  Axum / 잘 짠 Go    █████████████████  (멀티코어·메모리에서 자주 상위)
  Bun.serve           ████████████████   (JS 계열 최상위권)
  Deno.serve          ████████████████   (최근 버전에서 Bun과 접전·역전 사례)
  Node 내장 http      ████████
  Express             ██████             (미들웨어 스택까지 가면 더 내려감)
```

### 5.2 공개 측정 예시 (절대값 아님 · 상대 감각용)

**A. JS 런타임끼리 (단일 코어 · JSON 엔드포인트 예시, 2026 블로그 측정)**  
출처 경향: [Botmonster — Bun vs Deno vs Node 2026](https://botmonster.com/web-dev/bun-vs-deno-vs-nodejs-javascript-runtime-2026/)

| 런타임 | 대략 RPS (해당 글의 한 측정) | 콜드 스타트 | 유휴 메모리(해당 글) |
|---|---|---|---|
| Deno ~2.9 | **~133k** req/s | ~14 ms | ~51 MB |
| Bun ~1.3 | **~122k** req/s | ~11 ms | ~36 MB |
| Node ~24 | **~48k** req/s | ~21 ms | ~49 MB |

→ 같은 날·같은 머신에서도 **버전만 바뀌면 Deno↔Bun 1위가 뒤집힘**. “항상 Bun이 더 빠르다”는 옛 슬로건은 더 이상 절대 진리가 아님.

**B. 실무 감각**

| 지표 | 경향 |
|---|---|
| 순수 hello/JSON RPS | Bun ≈ Deno ≫ Node/Express |
| 콜드 스타트 | Bun이 아주 살짝 빠른 측정 많음 |
| 메모리 | Bun이 더 낮게 나오는 측정 많음 |
| 멀티코어 스케일 | JS 핸들러는 기본적으로 **프로세스당 이벤트 루프** → `Worker`/멀티 프로세스 필요. (세부 네이티브 I/O 스레딩이 있어도 “Go처럼 자동 전코어”는 아님) Go/Rust가 유리한 경우 많음 |
| 테스트 러너 속도 | Bun이 매우 빠른 측정 많음 |

## 6. 수치 비교 — Express · Gin · Axum 등과

> **주의:** 아래 숫자는 **서로 다른 글·다른 하드웨어·다른 워크로드**를 모아 “자릿수 감각”만 주는 것입니다.  
> 프레임워크(Elysia/Gin) vs 런타임 내장(`Bun.serve`)을 한 표에 넣었으므로 **공정 1:1이 아닙니다.**  
> 당신 머신에서 `oha`/`wrk`로 다시 재는 것이 정답입니다.

### 6.1 상대 배율로 먼저 보기 (가장 안전)

같은 상자·가벼운 JSON/hello 계열에서 자주 나오는 **상대감**:

| 스택 | Express(Node) 대비 | 비고 |
|---|---|---|
| Express | **1×** (기준) | 미들웨어 쌓이면 더 느려짐 |
| Node `http` 내장 | ~1.5–3× | Express보다 가벼움 |
| Deno.serve / Bun.serve | ~**3–8×+** | 벤치에 따라 더 벌어지기도 |
| Gin / Go `net/http` | ~**5–15×+** | 멀티코어에서 특히 |
| Axum | ~**5–20×+** | 종종 왕좌, 메모리 최저권 |

Express가 “느린” 이유: 런타임만이 아니라 **미들웨어 파이프·호환 레이어** 비용이 큼.  
Bun/Deno 내장 서버는 그 층을 거의 안 탑니다.

### 6.2 인용 가능한 개별 측정 예

**예1 — hello 계열 RPS (한 아티클의 wrk 결과, 환경 상이)**  
([learn-nodejs-hard-way 재현 논의](https://github.com/ishtms/learn-nodejs-hard-way/blob/master/chapters/ch00-nodejs-faster-than-you-think.md) 등)

| 스택 | 보고된 RPS 대략 |
|---|---|
| Axum (Rust) | ~**209k** |
| Elysia on Bun | ~**149k** |
| Express | ~**29k–50k** (측정마다 편차) |

→ Axum > Bun 생태계 프레임워크 ≫ Express.

**예2 — JSON API, 단일 스레드 vs 멀티코어 (LinkedIn/개인 벤치 요지, Axum·Gin·Bun/Elysia)**  

| 조건 | 경향 |
|---|---|
| 머신 전체 코어 | **Rust(Axum) > Go(Gin) > Bun** |
| CPU 1코어 핀 · 단순 직렬화 | Bun이 Rust에 **근접하거나 순간 역전**한 사례 있음 |
| 메모리 | Axum ≪ Go ≪ Bun (예: 수 MiB vs 수십 MiB) |

**예3 — 마이크로서비스 부하 테스트 일부 (2026 컬렉션 글)**  
Bun이 Express 대비 성공 RPS·지연에서 **수 배** 유리하고, 같은 한도에서 Rust(Axum 등)와 **비슷한 천장**에 붙는 장면이 보고됨. Go는 그 사이~근접.

**예4 — 동일 시나리오 다언어 랩 (Gin·Axum·Fastify 등)**  
[backend-decision-lab](https://github.com/gustavoguarda/backend-decision-lab) 요지: 시나리오 평균 순위에서 **Gin·Axum이 상위**, Node(Fastify)는 I/O에선 선방·CPU 바운드에서 급락.

### 6.3 한 장 요약 표 (감각용)

| 스택 | 외부 디펜던시 0? | 전형적 HTTP 속도 띠 | 메모리 | 멀티코어 |
|---|---|---|---|---|
| **Bun.serve** | ✅ | 매우 높음 (JS 최상위) | 중 | 프로세스 스케일 필요 |
| **Deno.serve** | ✅ | 매우 높음 (Bun과 접전) | 중~약높 | 동일 |
| Node `http` | ✅ | 중 | 중 | 동일 |
| **Express** | ❌ (express) | 낮~중 | 중 | 동일 |
| **Go net/http** | ✅ | 매우 높음 | 낮~중 | **자연 스케일** |
| **Gin** | ❌ (gin) | 매우 높음 | 낮~중 | 자연 스케일 |
| **Axum** | ❌ (axum+tokio 등) | **최고권** | **최저권** | 우수 |

당신 제약(**디펜던시 0**)만 보면:

```text
속도 후보군 (외부 0)
  Bun.serve / Deno.serve / Go net/http

Express·Gin·Axum은 “프레임워크 디펜던시”가 생기는 축
  → 폐쇄망·패키지 금지와는 별개 선택
```

Gin/Axum을 쓰려면 보통 모듈 다운로드가 필요합니다.  
**속도만** 보면 Axum·Go가 여전히 안전한 상단이고, **디펜던시 0 + TS**면 Deno/Bun이 Express를 압도합니다.

| 함정 | 설명 |

| hello world ≠ 비즈니스 API | DB·파일·암호가 붙으면 순위 재편 |
| Express에 미들웨어 10개 | 불공정하게 느려 보임 |
| Elysia vs `Bun.serve` | 같은 Bun이어도 프레임워크 비용 다름 |
| 단일 코어 vs 전 코어 | Bun/Deno에 불리·유리 반전 가능 |
| 루프백 + 같은 CPU | 절대 RPS 과장 |
| 버전 | Deno/Bun은 **마이너만으로 RPS 10%+** 흔들림 |

**직접 재기 (권장):**

```bash
# 서버: Deno 또는 Bun /health
oha -n 100000 -c 100 http://127.0.0.1:8080/health
# 또는
wrk -t4 -c100 -d15s http://127.0.0.1:8080/health
```

같은 날 Express / `go` nethttp / (여유 있으면) Axum sample을 같은 `oha`로 찍으면 당신 환경의 표가 완성됩니다.

## 10. 보충 — 문서에 없던 중요 차이

초판에 빠져 있어 실무에서 자주 걸리는 항목입니다.

### 10.1 TypeScript: “실행” vs “검사”

| | Deno | Bun |
|---|---|---|
| `.ts` 실행 | ✅ | ✅ |
| 실행 시 타입 에러로 **실패** | 설정에 따라 ✅ (`deno check` / 검사 포함 실행) | 기본은 **타입을 지우고 실행** → 잘못된 타입이어도 런타임까지 갈 수 있음 |
| 함의 | 폐쇄망 CI 없이도 타입 안전에 유리 | 속도·편의 ↑ · 타입은 에디터/`tsc`에 맡기는 편 |

### 10.2 Deno `@std` / JSR은 “내장”이 아님

- `jsr:@std/yaml`, `@std/path` 등은 **공식이나 외부 모듈**.
- 폐쇄망·`deno add` 불가 전제에서는 **가져오는 순간 외부 디펜던시**.
- 웹서버만이면 `Deno.serve` + Web API만으로 충분 → `@std`를 안 쓰면 됨.

### 10.3 SQLite API가 다름 (둘 다 설치 0)

| | Deno (≥2.2) | Bun |
|---|---|---|
| 모듈 | `node:sqlite` (`DatabaseSync`) | `bun:sqlite` (`Database`) |
| npm install | 불필요 | 불필요 |
| 코드 호환 | 이름·메서드가 달라 **복붙 1:1 불가** | |

### 10.4 Deno KV는 “안정·만능 DB”가 아님

- 로컬 CLI에서 쓰려면 버전에 따라 **`--unstable-kv`** 등이 필요.
- 로컬 백엔드는 SQLite 계열, Deploy는 FoundationDB 등 **환경이 다름**.
- 일반 SQL이 필요하면 `node:sqlite` / 파일 DB를 쓰는 편이 예측 가능.

### 10.5 권한 UX

```bash
# Deno: 최소 권한 예
deno run --allow-net --allow-read=./data --allow-write=./data server.ts

# Bun: 플래그 없이 기동 (편의 ↑, 실수 시 파일시스템 노출 면적 ↑)
bun server.ts
```

폐쇄망 **내부툴**이면 Bun 편의가 크고, **권한 감사**가 필요하면 Deno가 맞음.

### 10.6 단일 바이너리

- Deno: `deno compile`로 배포 산출물 만들기 익숙.
- Bun: `bun build --compile`도 실사용 가능 (초판의 “실험적만”은 **과소평가**).
- 그래도 OS/CPU별 산출물은 각각 필요 (이전 Go/Bun 크로스 문서와 동일).

### 10.7 예제 코드 보안

§4 업로드 예제의 `file.name` 그대로 저장은 **경로 조작**에 취약.  
실사용 시 basename/UUID로 저장할 것 (Deno·Bun 공통).

### 10.8 성능 표의 공정성

- §6의 Express 대비 배율·RPS는 **서로 다른 벤치를 섞은 감각 표**.
- Elysia(Bun 위 프레임워크) ≠ `Bun.serve` 내장.
- Gin ≠ 가장 얇은 Go `net/http` (비슷한 띠, 오버헤드 있을 수 있음).

### 10.9 멀티프로세스

JS 런타임도 `Worker`·여러 프로세스·리버스 프록시로 스케일 가능.  
“스케일 불가”가 아니라 **Go처럼 기본 한 프로세스가 전 코어를 자연스럽게 먹진 않는다**는 뜻.

## 11. 사실 검토 · 정정

| 초판 표현 | 판정 | 정정 |
|---|---|---|
| SQLite “Deno 2+ 내장” | ⚠️ 부정확 | **Deno ≥2.2**의 **`node:sqlite`**. Deno 전용 `Deno.sqlite` 모듈이 아님 |
| Deno KV ✅ | ⚠️ 과장 | **unstable 플래그·환경 의존** → ⚠️ 로 격하 |
| Deno YAML “⚠️/버전” | ⚠️ 애매 | 디펜던시 0이면 사실상 **내장 YAML 없음** (`@std/yaml`은 외부) → Bun만 ✅ |
| Bun 단일 바이너리 “실험적” | ⚠️ 과소 | `bun build --compile` 사용 가능 → 문구 완화 |
| “항상 이벤트 루프 하나뿐” | ⚠️ 단순화 | Worker/네이티브 I/O는 있으나 **Go식 자동 전코어는 아님**으로 재서술 |
| Bun ≈ Deno ≫ Express | ✅ 경향 OK | 버전·벤치에 따라 Deno가 Bun을 앞서기도 함 (본문 유지) |
| vs Axum/Gin 접전~열세 | ✅ 경향 OK | 단일 코어·순수 JSON에선 Bun이 앞선 **사례**도 있음 (본문에 이미 있음) |
| 외부 0으로 JSON·파일·WS | ✅ | Deno·Bun 모두 맞음 |
| Node 호환은 Bun 우세 | ✅ | Deno 2에서 격차 감소 (본문 반영) |
| 권한 모델 Deno만 | ✅ | Bun도 실험적 보안 플래그가 생길 수 있으나 **기본 철학은 Deno** |
| §6 절대 RPS 표 | ✅ 주의 문구 있음 | “자릿수 감각”으로만 읽을 것 — **틀린 숫자라기보다 비공정 비교** |

**남아 있는 한계 (틀린 말은 아니나 한계):**

- 벤치 숫자는 시간이 지나면 바뀜 → 문서 날짜·출처 링크 기준.
- Postgres/`Bun.sql`·Redis·S3는 **버전 확인 필수** (⚠️ 유지가 맞음).
- “Gin/Axum이 디펜던시 필요”는 Cargo/Go module 기준 ✅.

## 부록 — 차이 한눈에 (정정 반영)

| | Deno | Bun |
|---|---|---|
| 외부 0 HTTP / WS / 파일·JSON | ✅ | ✅ |
| 외부 0 SQLite | ✅ (`node:sqlite` ≥2.2) | ✅ (`bun:sqlite`) |
| 보안 기본 | 강함(권한) | Node형 |
| Node 호환 | 중~상 (Deno 2↑) | 상 |
| YAML 내장 | ❌~외부 std | ✅ |
| password 고수준 | 약함 | ✅ `Bun.password` |
| KV | ⚠️ unstable·환경 | — |
| TS 타입검사 UX | 강함 | 실행≠검사 |
| `@std`/JSR 함정 | 있음 | 적음 |
| vs Express 속도 | 훨씬 빠름 | 훨씬 빠름 |
| vs Gin/Axum | 접전~열세 (조건 의존) | 동 |

> **정리 (재확인):** 웹서버(JSON·파일·WS) + 외부 0이면 Deno·Bun **지원 범위는 거의 동등**하고, 초판 결론은 유지됩니다.  
> 보충·정정 핵심은 **SQLite API 이름/버전, KV·YAML의 “내장” 과장 여부, TS 검사 차이, Deno `@std`가 외부라는 점, Bun compile 과소평가**입니다.  
> 속도 결론(Express ≪ Deno/Bun, Axum·Go는 상단·조건부 접전)도 경향으로 **유효**하되, 표의 RPS는 직접 재측정하세요.
