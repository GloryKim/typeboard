# NAT Loopback(Hairpin NAT)의 개념과 내부망에서의 공인 IP 접속 문제

## 요약

NAT Loopback은 Hairpin NAT라고도 불리며, 같은 NAT 경계 안의 클라이언트가 공인 IP 또는 그 IP에 매핑된 포트로 내부 서버에 접속할 때 패킷이 공유기에서 “나갔다 다시 안으로” 꺾여 돌아오도록 처리하는 기능이다. 일반적인 포트 포워딩은 인터넷에서 WAN으로 들어오는 트래픽을 가정하지만, 내부 단말이 동일한 공인 주소로 접속하면 출발지와 목적지가 모두 NAT 내부에 존재하므로 별도의 반사(reflection) 경로가 필요하다.

많은 가정용·통신사 지급 공유기는 이 경로를 구현하지 않거나 기본 비활성 상태다. 그 결과 외부(LTE, 다른 네트워크)에서는 `공인IP:포트` 또는 DDNS 도메인으로 접속이 되지만, 같은 Wi-Fi·유선 LAN에서는 타임아웃·연결 거부가 발생한다. 내부에서 사설 IP로 직접 접속하면 정상인 경우가 전형적이다.

근본 해결은 공유기에서 Hairpin/NAT Reflection을 켜는 방법과, 애초에 내부 클라이언트가 공인 IP를 목적지로 쓰지 않게 만드는 방법(Split DNS, 내부 호스트명, VPN 오버레이)으로 나뉜다. 서비스 URL을 하나로 유지해야 한다면 Split DNS가 실무적으로 가장 안정적이다.

## 1. 문제 상황: 공인 IP로 내부끼리 통신하려는 이유

홈 서버, NAS, 개발용 리버스 프록시, IoT 게이트웨이, 사내 테스트 서버를 운영할 때 흔히 다음을 한다.

1. 공유기에 포트 포워딩(또는 UPnP)을 설정한다. 예: WAN `443` → `192.168.0.20:443`
2. DDNS로 `home.example.com`을 공인 IP에 연결한다.
3. 클라이언트·앱·스크립트·브라우저 북마크에 `https://home.example.com` 하나만 넣는다.

외부에서는 의도대로 동작한다. 그러나 같은 LAN의 PC·휴대폰·다른 서버가 동일한 URL로 접속하면 실패하는 경우가 많다. 사용자는 “포트 포워딩이 잘못됐다”, “방화벽이 막았다”, “DNS가 깨졌다”로 오해하기 쉽지만, 실제로는 **포트 포워딩 규칙 자체는 정상이고, LAN→공인IP→LAN 반사 경로만 없는 상태**인 경우가 많다.

이 구성이 자주 선택되는 이유는 실용적이다.

- 외부와 내부에서 설정을 나누고 싶지 않다.
- TLS 인증서가 공인 도메인에 발급되어 있어 사설 IP로 접속하면 인증서 이름 불일치가 난다.
- 모바일 앱·IoT 펌웨어에 엔드포인트 URL이 하나뿐이다.
- 클라우드 없이 집/사무실 공인 주소를 API 베이스로 쓰고 싶다.

즉 문제는 “공인 IP로 내부 IP끼리 통신하려는 설계” 자체와, 그 설계를 NAT 장비가 지원하지 않는 현실의 불일치다.

## 2. 용어와 관련 개념

| 용어 | 의미 |
| --- | --- |
| NAT | 사설 주소와 공인 주소(및 포트) 사이를 변환하는 주소 변환 |
| DNAT / 포트 포워딩 | 목적지의 공인 IP:포트를 내부 사설 IP:포트로 바꾸는 변환. 외부→내부 서버 접속에 사용 |
| SNAT / Masquerade | 출발지 사설 IP를 WAN 주소로 바꾸는 변환. 내부→인터넷 통신에 사용 |
| NAT Loopback / Hairpin NAT | 내부 클라이언트가 WAN 공인 주소를 목적지로 할 때, 패킷을 다시 내부 서버로 돌려보내는 반사 처리 |
| NAT Reflection | pfSense 등에서 쓰는 유사 개념. 포트 포워딩 규칙을 LAN 측에도 적용해 반사시키는 설정 |
| Split DNS / Split-horizon DNS | 같은 도메인을 질의 위치에 따라 공인 IP 또는 사설 IP로 다르게 응답하는 DNS 구성 |
| Double NAT | 공유기 뒤에 또 다른 NAT(통신사 CGNAT, 상위 공유기)가 있는 구조. Hairpin 문제와 별개로 포트 포워딩 자체를 어렵게 만듦 |

Hairpin이라는 이름은 패킷 경로가 머리핀처럼 꺾여 같은 인터페이스(또는 같은 NAT 도메인)로 되돌아가는 모습에서 왔다. Loopback은 “루프백 인터페이스”와 혼동되기 쉬우나, 여기서는 **NAT 장비 상에서의 루프백(반사)**을 뜻한다. `127.0.0.1`과는 무관하다.

## 3. 정상 포트 포워딩과 Hairpin 경로의 차이

### 3.1 외부 클라이언트의 정상 경로

```text
인터넷 클라이언트
  → 목적지: 공인IP:443
  → 공유기 WAN에서 DNAT: 192.168.0.20:443
  → 내부 서버가 응답
  → 공유기가 응답 패킷의 출발지를 다시 공인IP:443처럼 보이게 역변환
  → 인터넷 클라이언트로 반환
```

이 경로에서 출발지는 NAT 밖이다. 공유기는 “WAN으로 들어온 패킷을 LAN으로 넘긴다”는 익숙한 모델로 처리한다.

### 3.2 내부 클라이언트가 공인 IP를 쓸 때의 이상적 Hairpin 경로

```text
내부 클라이언트 192.168.0.10
  → 목적지: 공인IP:443   (라우팅상 보통 기본 게이트웨이=공유기)
  → 공유기가 “이 목적지는 내 WAN 주소 + 포트포워딩 대상”임을 인식
  → DNAT: 192.168.0.20:443
  → (필요 시) 출발지도 보정: 192.168.0.10 → 공유기 LAN 주소 등으로 SNAT
  → 서버 192.168.0.20이 응답
  → 공유기가 반사 세션에 맞게 역변환하여 클라이언트 192.168.0.10으로 반환
```

핵심은 DNAT만으로는 부족한 경우가 많다는 점이다. 서버가 응답을 **클라이언트 사설 IP로 직접** 보내면, 클라이언트의 TCP 스택 입장에서는 “내가 보낸 목적지는 공인 IP인데, 응답 출발지는 사설 IP”가 되어 세션이 성립하지 않을 수 있다. 그래서 많은 Hairpin 구현은 내부 반사 트래픽에 대해 **추가 SNAT(또는 동등한 상태 추적)**를 수행해, 클라이언트 눈에 보이는 상대 주소를 공인 IP(또는 기대하는 주소)로 유지한다.

Hairpin을 지원하지 않는 공유기의 전형적인 실패 모드는 다음과 같다.

```text
내부 클라이언트 → 공인IP:443 전송
  → 공유기가 WAN으로 내보내려 하거나, 로컬 배달에 실패하거나,
    DNAT는 하지만 응답 경로/상태 추적이 깨짐
  → 연결 타임아웃, RST, 또는 간헐적 한쪽만 통신
```

장비·펌웨어마다 세부 증상은 다르지만, “외부만 되고 내부만 안 된다”는 관측 패턴은 공통적이다.

## 4. 패킷 관점에서 왜 깨지는가

같은 L3 서브넷의 두 호스트가 사설 IP로 통신할 때는 ARP로 직접 도달한다. Hairpin 문제는 **목적지가 같은 서브넷의 사설 IP가 아니라, NAT 바깥으로 보이는 공인 주소**일 때 발생한다.

1. 클라이언트의 라우팅 테이블은 `공인IP`를 “직접 연결 대역”이 아니라 “기본 게이트웨이로 보낼 대상”으로 본다.
2. 패킷은 공유기로 전달된다.
3. 공유기는 이 패킷을 (a) 인터넷으로 포워딩할지, (b) 자신의 WAN 주소에 대한 로컬/포워딩 규칙으로 처리할지 결정해야 한다.
4. 포트 포워딩 규칙이 “WAN 인터페이스로 ingress한 트래픽”에만 걸려 있으면, LAN에서 온 동일 목적 패킷에는 규칙이 적용되지 않는다.
5. 설령 DNAT가 되어 서버에 도착해도, 응답의 출발지/목적지 튜플이 클라이언트의 TCP 상태와 맞지 않으면 핸드셰이크가 실패한다.

따라서 “포트 포워딩을 켰는데도 LAN에서 공인 IP로 안 된다”는 것은 논리적으로 모순이 아니다. **규칙의 적용 방향(WAN ingress)과 실제 트래픽 방향(LAN → WAN 주소)이 다르기 때문**이다.

TLS를 쓰는 경우 문제가 더 헷갈린다. 인증서는 `home.example.com`에 발급되어 있으므로, 내부에서 `https://192.168.0.20`으로 접속하면 네트워크는 열려도 브라우저가 이름 불일치를 낸다. 사용자는 “HTTPS가 깨졌다”고 느끼고 공인 도메인을 고집하게 되고, 그 결과 다시 Hairpin 경로에 의존하게 된다.

## 5. 증상과 진단 절차

### 5.1 전형적 증상

- LTE/다른 네트워크: `https://home.example.com` 성공
- 집 Wi-Fi: 같은 URL 실패(스피너, 타임아웃, 간헐 실패)
- 집 Wi-Fi에서 `http://192.168.0.20:포트` 또는 서버의 사설 IP로는 성공
- `ping` 공인 IP는 공유기/ISP 정책에 따라 응답하거나 막힐 수 있어 판단 근거로 부적절
- 서버 로그에 외부 접속은 보이지만, LAN 클라이언트의 공인 IP 접속 시도는 안 보이거나 이상하게 보임

### 5.2 최소 진단 순서

1. **외부 검증**: 휴대폰 데이터(Wi-Fi 끔)로 공인 도메인/포트 접속이 되는지 확인한다. 되면 포트 포워딩과 서버 리슨은 대체로 정상이다.
2. **내부 사설 IP 검증**: LAN에서 서버의 `192.168.x.x:포트`로 직접 접속한다. 되면 서버·방화벽·서비스는 내부에서 살아 있다.
3. **내부 공인 IP/도메인 검증**: LAN에서 `공인IP:포트`와 `도메인:포트`를 각각 시도한다. 도메인만 실패하면 DNS/Split 이슈 가능성도 있고, 공인 IP도 실패하면 Hairpin 부재 가능성이 높다.
4. **DNS 확인**: `dig home.example.com` 또는 `nslookup`으로 LAN에서 도메인이 공인 IP로 해석되는지 본다. Hairpin 미지원 환경에서 공인 IP로 해석되는 것이 실패의 직접 원인이다.
5. **공유기 기능 확인**: 관리 UI에서 NAT Loopback, Hairpin NAT, NAT Reflection, “내부에서 WAN 주소 접근 허용” 유사 항목을 찾는다. OpenWrt는 방화벽 zone/redirect 설정, pfSense는 NAT Reflection 옵션으로 명시되는 경우가 많다.
6. **이중 NAT/CGNAT 구분**: WAN 주소가 `100.64.0.0/10`이거나, 인터넷에서 보이는 공인 IP와 공유기 WAN IP가 다르면 CGNAT·상위 NAT 이슈가 겹친다. 이 경우 “외부에서도” 포트 포워딩이 안 될 수 있으므로 Hairpin만의 문제가 아니다. CGNAT 진단은 `docs/network`의 CGNAT 노트를 참고한다.

### 5.3 오진하기 쉬운 것들

- **CORS, 앱 버그, 인증 쿠키 도메인**: 네트워크는 열렸는데 앱만 실패하는 경우와 구분한다. TCP/TLS 단계부터 실패하면 앱 이슈가 아니다.
- **AP 격리(Client isolation)**: 게스트 Wi-Fi에서 단말 간 통신을 막는 설정은 Hairpin과 별개로 사설 IP 접속도 막는다. 사설 IP도 안 되면 격리를 의심한다.
- **IPv6 / Happy Eyeballs**: 도메인이 AAAA를 갖고 클라이언트가 IPv6로 먼저 가면, IPv4 Hairpin과 무관한 경로로 실패·성공이 갈릴 수 있다. A/AAAA와 실제 연결 주소를 함께 본다.
- **DNS 재바인딩 보호**: 일부 DNS 필터·브라우저·보안 장비가 “공인 이름이 사설 IP로 해석되는 것”을 막는다. Split DNS를 도입할 때 이 보호 기능과 충돌할 수 있다.

## 6. 해결 방법

해결은 “반사 경로를 장비에 만들 것인가”와 “내부에서는 공인 주소를 목적지로 쓰지 않게 할 것인가”로 나뉜다.

### 6.1 공유기에서 Hairpin NAT / NAT Reflection 활성화

가능한 환경이라면 가장 직접적이다. 포트 포워딩 규칙을 LAN 출발 트래픽에도 적용하고, 필요 시 반사 세션용 SNAT를 수행한다.

적용 시 확인할 점:

- 포트 포워딩 규칙마다 Reflection을 켜야 하는 장비와, 전역 옵션인 장비가 있다.
- “NAT + proxy” 방식과 “순수 NAT” 방식의 구현 차이가 있다. 전자는 성능·연결 추적 부담이 다를 수 있다.
- 공유기 CPU가 약한 환경에서 대량 내부 트래픽을 공인 주소로 돌리면 불필요한 NAT 부하가 생긴다. 기능적으로는 되어도 설계상 최선은 아닐 수 있다.
- 통신사 임대 공유기는 UI에 항목이 없거나, 켜도 불완전한 경우가 많다. 그때는 공유기 교체(브리지 모드 + 자체 라우터) 또는 아래의 DNS/오버레이 방식을 쓴다.

Hairpin을 켜도 **상위 CGNAT**이 있으면 “인터넷에서 집 서버로 들어오는 접속” 자체는 여전히 안 될 수 있다. Hairpin은 “이미 포트 포워딩이 유효한 전제에서 LAN 반사”를 고치는 기능이다.

### 6.2 Split DNS (권장되는 실무 해법)

같은 이름을 쓰되, 내부 DNS만 사설 IP를 돌려준다.

```text
외부 DNS:  home.example.com → 203.0.113.10   (공인)
내부 DNS:  home.example.com → 192.168.0.20   (사설)
```

클라이언트의 URL은 항상 `https://home.example.com`이다. LAN에서는 패킷이 공유기의 WAN 주소를 거치지 않고 서버로 직접 가므로 Hairpin이 필요 없다. TLS 인증서의 CN/SAN과도 이름이 일치한다.

구현 위치 예:

- 공유기 자체 DNS / Dnsmasq 호스트 오버라이드
- Pi-hole, AdGuard Home, CoreDNS, unbound 로컬 존
- 회사 내 스플릿 호라이즌을 지원하는 AD DNS / 내부 리졸버
- Docker/`extra_hosts`, Kubernetes CoreDNS stub 등 환경별 오버라이드

주의점:

- 모든 단말이 그 내부 DNS를 쓰도록 DHCP로 배포해야 한다. 단말이 `1.1.1.1`/`8.8.8.8`을 하드코딩하면 Split이 무시되고 다시 공인 IP로 해석된다.
- DoH/DoT를 쓰는 브라우저·OS는 시스템 DNS를 우회할 수 있다. 필요하면 DoH를 끄거나, 게이트웨이에서 통제한다.
- VPN 연결 시 “어느 DNS를 쓰는지”에 따라 내부/외부 해석이 섞인다. VPN DNS 정책을 함께 설계한다.
- DNS 재바인딩 보호가 사설 응답을 드롭하면 Split DNS가 실패한다. 해당 도메인을 예외로 넣는다.

### 6.3 내부에서는 사설 주소·내부 호스트명 사용

URL을 둘로 나누어도 되는 개인·소규모 환경에 적합하다.

- 내부: `http://192.168.0.20:8080`, `https://nas.lan`, `http://server.local`
- 외부: `https://home.example.com`

mDNS(`.local`), 공유기 로컬 도메인, 고정 `/etc/hosts`로 이름을 줄 수 있다. 다만 인증서, 쿠키 도메인, CORS, 모바일 앱의 단일 베이스 URL 제약과 충돌하기 쉽다. 개발·관리 접속용으로는 충분하고, 제품화된 클라이언트에는 Split DNS나 VPN이 낫다.

### 6.4 호스트 파일·기기별 오버라이드 (임시)

특정 PC의 `/etc/hosts` 또는 Windows `hosts`에 `192.168.0.20 home.example.com`을 넣는 방법이다. 즉시 검증에는 좋지만 단말이 늘수록 깨진다. “이 PC에서만 된다”는 상태가 되어 원인 파악을 오히려 어렵게 만들 수 있으므로, 진단 후 Split DNS로 올리는 것이 좋다.

### 6.5 VPN · 오버레이 네트워크

WireGuard, Tailscale, Headscale, ZeroTier, Nebula 등으로 **공인 IP hairpin을 우회**하고, 오버레이가 부여한 안정적인 사설/CGNAT 주소로 서로 붙는다.

이 방식의 이점:

- 가정용 공유기의 Hairpin 지원 여부에 의존하지 않는다.
- CGNAT·이중 NAT 환경에서도 “외부에서 집 서버로” 접근하는 문제를 함께 완화할 수 있다(릴레이/DERP 포함 시).
- 포트 포워딩으로 서비스를 인터넷에 직접 노출하지 않아도 된다.

대가:

- 클라이언트에 VPN/에이전트 설치 또는 프로비저닝이 필요하다.
- 브라우저만으로 불특정 다수에게 여는 공개 웹 서비스에는 적합하지 않을 수 있다.
- ACL·키 배포·디바이스 분실 대응 등 접근 통제를 별도로 운영해야 한다.

### 6.6 애플리케이션·아키텍처 쪽에서 피하는 방법

인프라를 고치기 어렵다면 설계로 우회한다.

- **클라이언트가 먼저 나가는 연결**: 내부 장치가 공인 클라우드/중계 서버로 WebSocket·SSE·MQTT를 맺고, 서버가 그 연결로 명령을 내린다. CGNAT 노트에서 다루는 역방향 연결 모델과 같은 계열이다.
- **환경별 베이스 URL**: 앱이 네트워크 위치(또는 사용자 설정)에 따라 내부/외부 엔드포인트를 고른다. 운영 부담이 커지므로 소규모에 한정한다.
- **리버스 프록시를 LAN과 WAN에 분리 바인딩**: 내부용 리스너와 외부용 리스너를 나누되, 인증·TLS 정책은 통일한다.

인터넷에 포트를 열어 Hairpin만으로 내부 트래픽까지 태우는 구성은, 기능이 되어도 **내부 대용량 전송이 공유기 NAT를 불필요하게 경유**하게 만든다. 가능하면 내부 트래픽은 사설 경로로 두는 편이 지연·대역·장애 지점 측면에서 유리하다.

## 7. 선택 가이드

| 상황 | 우선 선택 |
| --- | --- |
| 외부 포트 포워딩은 되고, LAN에서만 공인 도메인 실패 | Split DNS 또는 Hairpin 활성화 |
| URL·인증서를 하나로 유지해야 함 | Split DNS |
| 공유기 UI에 Loopback/Reflection 있음 | Hairpin ON + 동작 검증 |
| 통신사 공유기·설정 불가 | 브리지 후 자체 라우터, 또는 Split DNS/VPN |
| 외부에서도 포트 포워딩 자체가 안 됨 | CGNAT/이중 NAT부터 진단. Hairpin만으로는 해결 안 됨 |
| 불특정 다수 공개 서비스가 아니라 가족·팀만 접속 | VPN 오버레이로 노출면 축소 |
| 빠른 임시 확인 | hosts 오버라이드 후, 원인 확정 시 정식 해법으로 이전 |

실무적으로는 **Split DNS를 기본**, Hairpin은 “장비가 지원하고 트래픽량이 작을 때의 보조”, VPN은 “원격·다중 사이트·노출 최소화”에 두는 구성이 균형이 좋다.

## 8. 보안과 운영상의 주의

Hairpin을 켠다고 해서 새로운 인터넷 공격면이 크게 늘지는 않는 경우가 많다. 이미 WAN 포트 포워딩으로 노출된 서비스를 LAN에서도 같은 주소로 쓰게 할 뿐이기 때문이다. 다만 다음을 구분해야 한다.

- **노출 자체의 위험**: 공인으로 연 관리자 UI, 약한 암호, 구버전 서비스는 Hairpin과 무관하게 위험하다. 가능하면 VPN·SSO·MFA 뒤로 옮긴다.
- **내부에서 공인 URL을 쓰는 습관**: 내부 사용자가 항상 공인 경로만 쓰면, DNS 장애·인증서 갱신·공유기 NAT 장애가 내부 업무까지 한 번에 멈춘다. Split DNS나 내부 헬스체크를 두면 장애 반경을 줄일 수 있다.
- **로그의 출발지 IP**: Hairpin 구현이 SNAT를 쓰면 서버 로그에 클라이언트 사설 IP 대신 공유기 주소만 남을 수 있다. 감사·레이트리밋·IP 허용 목록을 쓸 때 왜곡이 생긴다. Split DNS 경로에서는 실제 사설 출발지가 보이므로 운영이 단순한 경우가 많다.
- **게스트 네트워크**: 게스트 VLAN에서 본망 서버로 Hairpin/포워딩을 허용할지는 정책 문제다. “손님 Wi-Fi에서도 집 서버 URL이 되게” 만드는 것이 항상 바람직하지는 않다.

## 9. 정리용 체크리스트

1. 외부에서 공인 도메인/포트가 되는가?
2. 내부에서 사설 IP:포트가 되는가?
3. 내부에서 공인 IP:포트가 되는가?
4. 내부 DNS가 도메인을 무엇으로 해석하는가?
5. 공유기에 NAT Loopback/Reflection이 있는가?
6. WAN IP와 인터넷에 보이는 공인 IP가 같은가?(CGNAT 여부)
7. 단일 URL이 필수인가, 내부/외부를 나눌 수 있는가?
8. 장기적으로 Split DNS·VPN·역방향 연결 중 무엇으로 운영 부담을 줄일 것인가?

1·2가 성공하고 3이 실패하면 Hairpin 부재를 강하게 의심한다. 1이 실패하면 먼저 포트 포워딩·방화벽·CGNAT을 보고, Hairpin은 나중 문제다.

## 결론

NAT Loopback(Hairpin NAT)은 같은 NAT 도메인의 단말이 공인 IP·포워딩된 포트로 내부 서버에 접속할 수 있게 패킷을 반사시키는 기능이다. “공인 IP로 내부끼리 통신”하려는 구성에서, 외부만 되고 내부만 안 되는 현상은 포트 포워딩 설정 오류라기보다 **반사 경로 미지원**인 경우가 많다.

장비에서 Hairpin을 켤 수 있으면 증상을 직접 없앨 수 있다. 그러나 URL과 인증서를 유지하면서 경로를 단순하게 만들려면, 내부 DNS가 사설 IP를 반환하는 Split DNS가 더 견고하다. 공인 노출을 줄이거나 CGNAT까지 넘어야 한다면 VPN 오버레이나 클라이언트가 먼저 붙는 역방향 연결 모델을 검토한다. 진단은 외부 공인 접속, 내부 사설 접속, 내부 공인 접속, DNS 해석 결과를 분리해 확인하는 것이 핵심이다.
