# 자바스크립트 엔진과 런타임: 언어를 실행하는 층과 호스트가 여는 층

## 요약

자바스크립트 엔진은 ECMA-262가 정의한 언어를 실행하는 프로그램이다. 소스를 파싱하고, 바이트코드로 해석하고, 자주 도는 함수만 기계어로 올린다. 자바스크립트 런타임은 그 엔진을 안에 넣고, 파일·네트워크·DOM·타이머처럼 언어 명세 밖에 있는 능력을 붙인 호스트다. Chrome과 Node.js는 같은 V8을 쓰지만 서로 다른 런타임이다. 브라우저 탭은 디스크를 읽지 못하고, Node 프로세스는 읽는다. 차이는 컴파일러가 아니라 호스트가 열어 준 API와 그 API를 스케줄하는 이벤트 루프에 있다.

이 경계는 성능, 보안, 코드가 옮겨 가는 범위를 동시에 정한다. 성능의 상한은 엔진의 최적화 단계가 만들고, 프로세스가 만질 수 있는 세계의 경계는 런타임이 만든다. Deno는 그 경계를 기본 거부로 뒤집었고, Bun은 엔진 자체를 JavaScriptCore로 바꿔 런타임 선택이 구현체 선택이기도 하다는 것을 보여 준다. 엔진만 있으면 식은 계산된다. 파일, 네트워크, 이벤트, 화면이 필요하면 런타임이 필요하다.

## 1. 명세가 그어 둔 선

ECMA-262는 값, 객체, 함수, 실행 컨텍스트, 모듈을 정의한다. 입출력은 정의하지 않는다. `fs`, `document`, `fetch`, `setTimeout`은 이 문서 밖에 있다. 엔진은 명세 안의 언어를 구현하고, 런타임은 그 엔진을 임베드한 뒤 호스트 객체를 전역에 심는다. Nicholas Zakas의 구분은 이 한 줄로 충분하다. 런타임은 ECMAScript 호스트다.

호출 스택과 힙은 엔진이 코드를 돌리는 동안 유지하는 구조다. 힙은 객체가 사는 메모리이고, 호출 스택은 실행 컨텍스트가 쌓이는 곳이다. 함수가 호출되면 프레임이 쌓이고, 반환되면 빠진다. 이 두 구조만으로 동기 코드는 끝까지 돈다. 타이머가 울리거나 소켓이 도착했을 때 어떤 콜백을 다음에 올릴지는 스택 밖의 일이다. MDN이 정리한 에이전트 모델은 여기에 작업 큐를 더한다. 스택이 비면 큐에서 다음 작업을 꺼내 빈 스택 위에 다시 올린다. HTML은 이 루프를 이벤트 루프라고 부르고 태스크와 마이크로태스크로 나눈다. 서버 런타임은 같은 아이디어를 자기 방식으로 구현한다. 루프의 구체적 순서는 엔진 구현체가 아니라 호스트 명세의 몫이다.

```text
ECMA-262  값, 객체, 호출, Promise 잡
엔진      파싱, 바이트코드, 최적 기계어, 힙, 호출 스택
런타임    호스트 API + 바깥 이벤트를 잡으로 바꾸는 루프
```

> 출처: [MDN, JavaScript execution model](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Execution_model), [Nicholas Zakas, JavaScript engines and JavaScript runtimes](https://humanwhocodes.com/blog/2024/03/javascript-engines-runtimes/)

## 2. 엔진: 소스에서 기계어까지

엔진은 소스를 한 번에 전부 기계어로 바꾸지 않는다. 시작을 빨리 하고, 뜨거운 함수만 비싸게 최적화한다. V8의 공식 개요가 적는 단계는 다섯 층이다.

| 단계 | 이름 | 하는 일 |
| --- | --- | --- |
| 파싱 | Parser | 소스를 추상 구문 트리로 만든다 |
| 해석 | Ignition | 트리에서 바이트코드를 만들고 레지스터 기반으로 실행하며, 나중에 쓸 타입 피드백을 모은다 |
| 기준 컴파일 | Sparkplug | 최적화 없이 바이트코드를 곧장 기계어로 바꿔 해석보다 빠르게 만든다 |
| 중간 최적화 | Maglev | Sparkplug보다 나은 코드를 TurboFan보다 빨리 만든다 |
| 최상위 최적화 | TurboFan / Turboshaft | 뜨거운 함수의 최고 성능 기계어. 2025년 3월 기준 자바스크립트 백엔드는 Sea of Nodes 대신 Turboshaft의 제어 흐름 그래프 IR을 탄다 |

Ignition이 모은 피드백이 어긋나면 최적화된 코드는 버리고 아래 단계로 돌아간다. 그래서 같은 함수도 처음 몇 번과 수천 번째의 실행 경로가 다르다. "엔진은 자바스크립트를 기계어로 바꾸는 블랙박스"라는 설명은 최상위 단계만 말한 것이다. 대부분의 코드는 한동안 바이트코드와 기준 기계어로 산다.

많이 쓰이는 엔진은 세 개다. 언어 명세를 각자 구현하고, 최적화 파이프라인의 이름은 다르며, 호스트 API는 포함하지 않는다.

| 엔진 | 주로 들어가는 곳 |
| --- | --- |
| V8 | Chrome, Node.js, Deno |
| SpiderMonkey | Firefox |
| JavaScriptCore | Safari, Bun |

같은 소스가 세 엔진에서 같은 값을 내는 것은 ECMA-262가 맞춰 준 결과다. 같은 시간 안에 끝나는 것은 명세가 보장하지 않는다. 숨은 클래스, 인라인 캐시, 어떤 단계에서 최적화가 떨어지는지는 구현체마다 다르다.

> 출처: [V8 docs, High-Level Overview](https://github.com/v8/v8/blob/main/docs/overview.md), [V8 블로그, Land ahoy: leaving the Sea of Nodes, 2025-03-25](https://v8.dev/blog/leaving-the-sea-of-nodes)

## 3. 런타임: 엔진 밖에 붙는 세계

런타임이 추가하는 것은 함수 목록만이 아니다. 그 함수가 완료됐을 때 콜백을 어느 큐에 넣을지의 규칙이다. 브라우저의 웹 API는 DOM, 타이머, `fetch`, 저장소다. Node.js는 파일 시스템, 소켓, 자식 프로세스, 스트림을 더하고 I/O 완료는 libuv가 알린다. Deno는 웹 플랫폼 API를 서버 쪽으로 가져오면서 파일과 네트워크를 권한 뒤로 숨긴다. 표준이 "런타임은 이것만 추가해야 한다"고 정하지 않았기 때문에 셋의 HTTP 클라이언트와 모듈 해석은 서로 다르다. Node의 `fetch`는 나중에 따라온 API이고, Deno는 처음부터 웹 API를 기본으로 두었다.

`setTimeout`은 이 경계를 한 호출로 보여 준다. 엔진은 `setTimeout(fn, 1000)`이라는 호출 식을 평가한다. 그 이름이 가리키는 함수는 런타임이 전역에 넣어 둔 호스트 함수다. 호스트는 타이머를 등록하고, 시간이 지난 뒤 콜백을 태스크 큐에 넣는다. 콜 스택이 비어야 그 태스크가 실행된다. 지연 시간이 0이어도 현재 스택이 끝날 때까지 콜백은 기다린다.

```text
엔진: setTimeout 호출 식을 평가하고, 등록이 끝나면 다음 줄을 계속 실행
런타임: 타이머를 보관
스택이 빈 뒤: 마이크로태스크를 비우고, 그다음 타이머 태스크를 스택에 올린다
```

큐는 한 종류가 아니다. HTML 이벤트 루프에서 `Promise.then`과 `queueMicrotask`는 마이크로태스크다. `setTimeout`, I/O, 클릭은 태스크다. 스택이 빌 때마다 마이크로태스크 큐를 먼저 비우고, 그다음 태스크를 하나 가져온다. 브라우저는 그 사이에 렌더링 기회를 둔다. Node의 루프는 libuv 단계(timers, poll, check 등)로 쪼개져 있고 화면은 없다. 순서를 가정한 코드는 엔진이 같아서 옮겨지지 않는다. 호스트의 큐 규칙이 맞아야 옮겨진다.

```javascript
setTimeout(() => console.log("task"), 0);
Promise.resolve().then(() => console.log("microtask"));
console.log("stack");
// stack → microtask → task
```

`console.log`도 언어 문법이 아니다. 호출 모양은 엔진이 평가하고, 출력이 어디로 가는지는 호스트가 정한다. 브라우저의 개발자 도구, Node의 stdout, 테스트 러너의 수집기는 같은 호출의 다른 호스트 바인딩이다.

## 4. 같은 V8이 서로 다른 권한을 가지는 이유

Chrome과 Node.js는 V8을 공유한다. 아래 코드의 문법 분석과 숫자 연산은 같은 엔진 코드 경로를 탄다. 파일이 열리는지는 런타임이 결정한다.

```javascript
import { readFile } from "node:fs/promises";
const text = await readFile("./note.txt", "utf8");
```

Node에서는 프로세스가 그 경로를 읽을 권한이 있으면 동작한다. 브라우저에 이 모듈 해석과 파일 API는 없다. 페이지의 자바스크립트가 사용자 디스크를 열면 안 되기 때문이다. 브라우저의 보안 경계는 출처(origin)와 엔진 밖의 샌드박스다. Node의 역사적 기본값은 그 반대다. 프로세스는 파일과 네트워크를 처음부터 쓸 수 있고, 제한은 운영체제 사용자 권한에 맡긴다.

Deno는 같은 V8 위에서 기본값을 뒤집었다. 권한 플래그 없이 띄우면 파일과 네트워크와 환경 변수는 닫혀 있다. `--allow-read`, `--allow-net`처럼 실행할 때 명시해야 열린다. 엔진이 더 안전해진 것이 아니다. 호스트가 엔진에 넘겨주는 능력의 기본값을 거부로 바꾼 것이다. 2026년 10월 Deno 팀의 런타임 개발 종료 일정은 이 모델의 사업 이야기이고, 권한 모델 자체는 런타임 설계의 예로 남는다.

Bun은 경계를 한 번 더 밀다. 서버 쪽 API를 제공한다는 점에서는 Node, Deno와 같은 종류의 런타임이지만 안의 엔진은 JavaScriptCore다. "V8이면 동작이 같다"는 전제는 서버 런타임 사이에서도 깨진다. 언어 값은 명세가 맞추고, 처리량과 일부 경계 동작은 엔진이, 파일과 네트워크의 모양은 런타임이 정한다.

| 런타임 | 엔진 | 호스트가 여는 것 | 기본 권한 |
| --- | --- | --- | --- |
| 브라우저 | V8, SpiderMonkey, JavaScriptCore | DOM, 타이머, `fetch`, 저장소 | 출처 샌드박스. 파일 시스템 없음 |
| Node.js | V8 | `fs`, `net`, `http`, 스트림, 자식 프로세스. libuv가 I/O 완료를 알림 | 프로세스 사용자가 할 수 있는 일은 기본 허용 |
| Deno | V8 | 웹 플랫폼 API와 서버 API. 파일·네트워크는 권한 뒤 | 기본 거부. 플래그로 연다 |
| Bun | JavaScriptCore | 서버 API, 번들러, 패키지 매니저를 한 실행 파일에 | Node에 가깝게 열리고, 엔진은 다르다 |

## 5. 성능, 보안, 코드가 살아남는 범위

성능에 엔진이 미치는 영향은 단계의 높이다. 한 번 돌고 끝나는 스크립트는 Ignition과 Sparkplug가 지배하고, 컴파일 비용이 본전인 서버 핸들러는 Maglev와 Turboshaft까지 올라간다. 타입이 흔들려 최적화가 떨어지면 최상위 기계어는 폐기되고 아래 단계로 돌아온다. 이 비용은 어느 런타임에 심었는지와 별개로 V8 또는 JavaScriptCore 안에서 발생한다.

성능에 런타임이 미치는 영향은 기다리는 방식이다. 같은 JSON 파싱은 엔진 문제다. 만 개의 파일을 동시에 읽는 일은 스레드 풀 크기, 비동기 I/O 구현, 권한 검사, HTTP 스택의 문제다. 벤치마크가 "자바스크립트가 빠르다"고 말할 때 그 문장은 엔진 문장과 런타임 문장으로 갈라야 한다.

보안도 같은 선에서 갈라진다. 엔진 취약점은 언어 구현의 메모리 안전 문제이고, 샌드박스를 벗어나는 문제일 때 심각해진다. 호스트 취약점은 API를 너무 많이 열어서 생긴다. Node 서비스가 요청 경로를 `readFile`에 그대로 넘기면 V8은 명세대로 문자열을 넘겼을 뿐이다. 디스크를 연 쪽은 런타임이고, 경로를 검증하지 않은 쪽은 애플리케이션이다. Deno의 권한 플래그는 이 실수를 프로세스 시작 시점으로 끌어올린다. 브라우저의 출처 경계는 같은 역할을 탭에 대해 한다.

코드를 쓰는 방식은 이 선이 저장소 어디에 있는지로 드러난다.

```text
언어로 남는 것  : 값 변환, 자료구조, 순수 함수, Promise 조합
호스트로 새는 것 : 경로, 소켓, DOM, 타이머 지연에 기댄 순서, 전역 이름
옮겨 가는 단위  : 언어 부분은 엔진을 바꿔도 남고, 호스트 부분은 어댑터가 필요하다
```

브라우저와 서버가 소스를 공유하려면 공유 부분에서 `document`와 `node:fs`가 동시에 빠져 있어야 한다. 테스트 러너는 그 자체로 작은 런타임이라, 타이머와 파일과 콘솔을 바꿔 끼운다. 모킹이 잘 되는 자리는 언어가 아니라 호스트 경계다.

## 6. 실행 위치를 정하기 전에 보는 점검표

| 영역 | 점검 항목 |
| --- | --- |
| 명세 | 이 호출이 ECMA-262 안에 있는가, 호스트가 심은 이름인가? |
| 엔진 | 병목이 파싱과 컴파일과 숨은 클래스인가, I/O 대기인가? |
| 큐 | 순서가 마이크로태스크인가, 태스크인가? 그 순서를 이 호스트가 보장하는가? |
| 권한 | 파일과 네트워크가 기본 허용인가, 기본 거부인가, 출처로 막히는가? |
| 이식 | 다음 런타임에 같은 전역 이름이 있는가? 없으면 어댑터 자리가 있는가? |
| 최적화 | 뜨거운 함수의 타입이 안정적인가, 호출마다 모양이 바뀌는가? |
| 출력 | `console`과 타이머를 언어 기능으로 가정하고 테스트하고 있는가? |

## 결론

자바스크립트가 브라우저와 서버와 데스크톱에 있다는 말은, 언어가 그 장소들을 알고 있다는 뜻이 아니다. 엔진은 명세 안의 식을 실행하고, 런타임이 그 엔진을 어떤 세계에 심었는지가 장소다. V8이라는 같은 상자가 Chrome에서는 DOM과 출처 샌드박스 안에 있고, Node에서는 libuv와 함께 디스크와 소켓 앞에 있고, Deno에서는 그 디스크와 소켓이 권한 뒤에 있다. Bun은 상자 자체를 JavaScriptCore로 바꾼다.

코드를 읽다가 `setTimeout`과 `readFile`과 `document`가 보이면 그 줄은 엔진을 잠시 나가 호스트에 부탁하는 줄이다. 부탁이 끝나는 순서, 실패하는 권한, 옮겨 가지 않는 범위는 컴파일러 단계표보다 호스트를 먼저 봐야 답이 나온다.
