# Python 3.15로 본 동적 언어의 시작 시간 최적화와 점진적 성능 개선

## 요약

Python 3.15.0은 2026년 10월 9일 안정판으로 출시됐다. 기여자 1,012명이 커밋 5,643개를 반영했다. 언어 차원에서는 처음 사용할 때까지 모듈 로딩을 미루는 명시적 지연 임포트(`lazy import`), 바꿀 수 없는 딕셔너리 `frozendict`, 고유 표식 값을 만드는 `sentinel`, 컴프리헨션 안의 `*`·`**` 언패킹이 추가됐다. 텍스트 입출력의 기본 인코딩은 OS와 무관하게 UTF-8이 됐다. 구현 차원에서는 실험적 JIT가 x86-64 Linux에서 7~8%, AArch64 macOS에서 11~12% 빨라졌고, 실행 중인 프로세스에 재시작 없이 붙는 샘플링 프로파일러 Tachyon과 프레임 포인터 기본 활성화, 자유 스레딩 빌드용 안정 ABI `abi3t`가 들어갔다.

이번 릴리스의 성격은 혁명보다 누적에 가깝다. 지연 임포트는 대형 애플리케이션의 시작 시간이라는 오래된 불만을 문법으로 해결했고, UTF-8 기본값은 Windows 비영어권 사용자의 고질적인 인코딩 오류를 없앴다. JIT는 여전히 실험적이지만 "실행을 기록하는" 방식으로 바꾸면서 방향을 되찾았다. 한편 macOS 27.0에서는 IDLE과 tkinter 대화상자가 멈추는 문제가 있어 Tk 기반 앱 사용자는 주의가 필요하다. 3.15 출시와 함께 Python 3.10은 지원 종료 대상이 됐다.

## 2. 시작 시간 문제와 지연 임포트

### 2.1 왜 시작이 느린가

모듈을 import하면 Python은 파일을 찾고, 디스크에서 읽고, 바이트코드로 컴파일하고, 최상위 코드를 실행한다. 의존성이 깊은 애플리케이션은 이 과정에만 몇 초가 걸리는데, 실제 실행에서는 그중 일부만 쓰는 경우가 많다. 개발자들은 import를 함수 안으로 옮기거나 `importlib`로 필요할 때 로딩하는 식으로 우회했지만, 코드가 읽기 어려워지고 import 문이 코드베이스 곳곳에 흩어졌다.

### 2.2 `lazy` 소프트 키워드

3.15는 `lazy`라는 새 소프트 키워드로 이 문제를 문법 차원에서 해결한다. 지연 임포트로 표시하면 Python은 모듈을 즉시 로딩하지 않고 가벼운 프록시 객체를 만든다. 실제 로딩은 그 이름에 처음 접근할 때 투명하게 일어난다.

```python
lazy import json
lazy from pathlib import Path

print("Starting up...")              # json, pathlib은 아직 로딩 안 됨

data = json.loads('{"key": "value"}')  # 여기서 json 로딩
p = Path(".")                          # 여기서 pathlib 로딩
```

import를 파일 맨 위에 모아 두는 관례를 유지하면서도 실제로 쓰는 모듈만 비용을 낸다. 로딩에 실패하면 import 선언 시점이 아니라 처음 사용하는 시점에 예외가 나고, traceback에는 사용 위치와 원래 import 위치가 함께 표시된다.

코드를 고치지 않고 전역으로 켜려면 `python -X lazy_imports=all` 또는 `PYTHON_LAZY_IMPORTS=all`을 쓴다. 선택적으로 켜려면 필터 함수를 등록한다.

```python
import sys

def myapp_filter(importing, imported, fromlist):
    return imported.startswith("myapp.")

sys.set_lazy_imports_filter(myapp_filter)
sys.set_lazy_imports("all")

import myapp.slow_module  # lazy (필터에 해당)
import json               # eager (필터에 해당하지 않음)
```

3.15 미만도 지원해야 하는 라이브러리는 `__lazy_modules__ = ["json", "pathlib"]`를 정의하면 일반 `import` 문이 같은 의미의 지연 임포트로 동작한다.

### 2.3 제약과 opt-in 설계

`lazy`는 모듈 최상위에서만 쓸 수 있다. 함수, 클래스 본문, `try/except/finally` 안에서 쓰면 `SyntaxError`가 난다. `lazy from module import *`와 `lazy from __future__ import ...`도 허용되지 않는다. HN에서는 "왜 전역 기본값으로 켜지 않느냐"는 질문이 나왔는데, 기존 코드 중 import 시점의 부작용에 의존하는 경우가 많아 명시적으로 켜는 방식이 택해졌다.

## 3. 일상 코드를 바꾸는 변화

### 3.1 UTF-8 기본 인코딩

```python
open("data.txt").read()   # 3.14까지: OS 로케일 인코딩 (한국어 Windows는 cp949)
                          # 3.15부터: 항상 UTF-8
```

`encoding`을 명시하지 않은 텍스트 입출력에만 적용되고 명시한 값은 그대로 쓴다. 한국어 Windows에서 `open()`이 cp949로 읽어 `UnicodeDecodeError`가 나던 문제가 사라진다. 기존 로케일 인코딩이 필요하면 `encoding="locale"`을 쓰고, 여러 버전과 호환하려면 여전히 `encoding="utf-8"`을 명시하는 것이 가장 안전하다.

### 3.2 컴프리헨션 언패킹

```python
>>> lists = [[1, 2], [3, 4], [5]]
>>> [*L for L in lists]              # = [x for L in lists for x in L]
[1, 2, 3, 4, 5]

>>> dicts = [{'a': 1}, {'b': 2}, {'a': 3}]
>>> {**d for d in dicts}             # 뒤에 오는 값이 덮어씀
{'a': 3, 'b': 2}
```

이중 for 컴프리헨션이나 `itertools.chain.from_iterable()`을 대신하며, 집합 컴프리헨션과 제너레이터 표현식, 비동기 제너레이터 표현식에도 적용된다.

### 3.3 `frozendict`와 `sentinel`

`frozendict`는 생성 후 변경할 수 없는 딕셔너리다. 키와 값이 모두 해시 가능하면 `frozendict` 자체도 딕셔너리 키나 집합 원소로 쓸 수 있다. 삽입 순서는 유지하지만 동등성 비교는 순서에 영향을 받지 않는다. `dict`의 하위 클래스가 아니므로 `isinstance(x, dict)` 검사는 통과하지 못한다. 받는 쪽은 `isinstance(x, (dict, frozendict))`나 `collections.abc.Mapping`으로 검사해야 한다. PEP 814의 공동 저자는 Victor Stinner와 한국인 CPython 코어 개발자 나동희(Donghee Na)다.

```python
>>> a = frozendict(x=1, y=2)
>>> a['z'] = 3
TypeError: 'frozendict' object does not support item assignment
>>> a == frozendict(y=2, x=1), hash(a) == hash(frozendict(y=2, x=1))
(True, True)
```

`sentinel`은 "인자가 들어오지 않음"과 "`None`이 들어옴"을 구분할 때 쓰는 고유 표식 값이다. 기존 관용구 `MISSING = object()`는 repr이 알아보기 어렵고 복사하거나 pickle하면 동일성이 깨졌다. `sentinel`은 복사해도 동일성이 유지되고 repr이 간결하며 타입 표현식에서 `|` 연산자와 함께 쓸 수 있다.

### 3.4 다른 언어 습관을 잡아 주는 오류 메시지

```python
>>> [1, 2, 3].push(4)
AttributeError: 'list' object has no attribute 'push'. Did you mean '.append'?
>>> 'hello'.toUpperCase()
AttributeError: 'str' object has no attribute 'toUpperCase'. Did you mean '.upper'?
```

JavaScript, Java, Ruby, C#의 흔한 메서드 이름 표를 보고 Python의 대응 메서드를 제안한다. 여러 언어를 오가는 개발자에게 특히 유용하다.

### 3.5 `.start` 파일

지금까지는 `.pth` 파일의 `import` 줄이 인터프리터 시작 시 임의 코드를 실행했고, 무엇이 실행되는지 확인하기 어려웠다. `.start` 파일은 시작 시 호출할 함수를 `pkg.mod:callable` 형식으로 명시하게 해 시작 과정의 감사 가능성을 높인다. `.pth`의 `import` 줄은 조용히 deprecated 처리됐다.

## 4. 성능: JIT와 프로파일링

### 4.1 실험적 JIT의 방향 전환

| 플랫폼 | 비교 대상 | 향상(pyperformance 기하평균) |
| --- | --- | --- |
| x86-64 Linux | 표준 CPython 인터프리터 | 7~8% |
| AArch64 macOS | 꼬리 호출 인터프리터 | 11~12% |

JIT는 여전히 실험적이고 평균값이라 작업에 따라 느려질 수도 있다. 핵심 변화는 트레이스를 "예측(projection)"하던 방식에서 실제 실행을 "기록(recording)"하는 방식으로 바꾼 것이다. 개발자 Ken Jin에 따르면 첫 시제품은 오히려 6% 느렸는데, Mark Shannon의 제안을 잘못 이해한 덕분에 dual dispatch라는 구조를 찾았다. 디스패치 테이블을 두 개 두되 추적용 테이블의 모든 항목이 `TRACE_RECORD` 명령어 하나를 가리키게 해서, 인터프리터 크기는 명령어 1개만큼만 늘고 기본 인터프리터 속도는 유지된다.

```text
기본 모드 : opcode → 일반 디스패치 테이블 → 해당 명령어 실행
추적 모드 : opcode → 추적 테이블 → TRACE_RECORD (기록 후 원래 명령어로) → 트레이스 완성 → JIT 최적화
```

추적 오버헤드는 특화 인터프리터 대비 3~5배 수준으로, 메타 트레이싱을 쓰는 PyPy의 900~1000배와 비교하면 매우 가볍다. 여기에 기본 레지스터 할당, 상수 전파, 참조 카운트 최적화가 더해졌다. 공식 배포본도 바뀌어 Windows 64비트는 꼬리 호출 인터프리터를 쓰고, macOS 설치본은 자유 스레딩 빌드를 기본으로 함께 설치한다.

### 4.2 profiling 패키지와 Tachyon

새 `profiling` 패키지는 기존 `cProfile`을 옮긴 결정적 추적기 `profiling.tracing`과 새 통계적 샘플링 프로파일러 `profiling.sampling`(Tachyon)을 묶는다. `cProfile` 이름은 별칭으로 유지되고 `profile` 모듈은 3.17에서 제거된다.

Tachyon은 실행 중인 프로세스에 코드 수정이나 재시작 없이 붙어 주기적으로 스택을 수집한다. 대상 프로세스 밖에서 샘플링하므로 오버헤드가 사실상 없고 최대 1,000,000Hz까지 샘플링할 수 있다. PID로 붙는 `attach`, 스크립트를 실행하는 `run`, 멈춘 프로세스의 전체 스레드 스택을 찍는 `dump`를 지원한다. 측정 모드는 실제 경과 시간(`wall`), CPU 시간(`cpu`), GIL 보유 시간(`gil`), 예외 처리 중(`exception`)으로 나뉜다. 결과는 HTML 플레임 그래프, 소스 줄별 히트맵, Firefox Profiler 형식, `top`처럼 생긴 실시간 TUI(`--live`)로 볼 수 있고, `--async-aware`로 코루틴 단위 분석도 가능하다. 프로파일러와 대상 프로세스는 같은 마이너 버전이어야 한다.

### 4.3 프레임 포인터 기본 활성화

CPython은 지원 플랫폼에서 `-fno-omit-frame-pointer` 등으로 빌드되어 `perf`, 디버거, 크래시 분석, eBPF 도구가 Python과 네이티브 코드가 섞인 호출 스택을 빠르고 안정적으로 추적한다. C, C++, Rust 확장도 같은 플래그를 유지해야 한다. 네이티브 컴포넌트 하나라도 프레임 포인터 없이 빌드되면 전체 스택 추적이 끊긴다.

## 5. 타입 시스템과 C 확장

타입 힌트 쪽에서는 세 가지가 추가됐다. PEP 728은 TypedDict에 선언하지 않은 추가 키를 금지하거나 추가 키의 값 타입을 지정하게 한다. PEP 747의 TypeForm은 `int`, `str | None`, `list[int]` 같은 타입 표현식 자체를 인자로 받는 API에 정확한 타입을 붙이게 한다. PEP 800은 함께 상속할 수 없는 클래스 관계를 타입 검사기에 표현한다.

C 확장 쪽의 핵심은 `abi3t`다. 기존 안정 ABI `abi3`는 GIL 빌드용이었고, `abi3t`는 자유 스레딩 빌드에서도 여러 Python 버전에 걸쳐 쓸 수 있는 바이너리를 만들게 한다. `cryptography`는 3.15 이상용으로 플랫폼마다 `abi3.abi3t` 휠 하나만 배포한다. `PyObject`가 불투명 타입이라 GIL 빌드와 자유 스레딩 빌드가 같은 휠을 쓸 수 있기 때문이다. HN에는 abi3 휠 하나로 바꾼 뒤 CI 작업이 약 20개에서 4개로 줄었다는 사례가 올라왔다. 다만 기존 확장이 자동으로 호환되지는 않으며 소스 수정이 필요할 수 있다. 이 밖에 C에서 bytes 객체를 만드는 PyBytesWriter(PEP 782)와 종료 중인 인터프리터 접근으로 생기는 멈춤·충돌을 막는 API(PEP 788)가 추가됐다.


### 6.2 macOS 27.0의 IDLE·tkinter 문제

IDLE이나 tkinter 앱에서 About IDLE, Settings, Open Module처럼 대화상자를 여는 메뉴를 누르면 앱이 멈출 수 있고 강제 종료가 필요할 수 있다. 원인은 macOS 27.0의 운영체제 동작 변경이며, 모든 Tk 버전과 이에 의존하는 현행 Python 전부에 영향을 주는 것으로 추정된다. Tk 기반 앱에 의존한다면 해결책이 나올 때까지 macOS 업그레이드를 미루거나 실제 작업 흐름을 먼저 테스트하라는 권고가 나왔다. 진행 상황은 CPython 이슈 #158053에서 확인할 수 있다.

## 7. 커뮤니티 반응

여러 라이브러리를 관리하는 개발자들은 새 버전의 진짜 가치가 옛 버전의 지원 종료에 있다고 말했다. 3.10이 빠지면서 예외 그룹, `tomllib`, `Self` 타입 같은 3.11 기능을 마음 놓고 쓸 수 있게 됐다는 것이다. 반대로 "새 버전이 나왔다는 이유로 기존 사용자 호환성을 깨는 정책은 싫다"는 의견도 있었다.

최신 macOS와 Xcode를 설치해도 시스템 Python은 여전히 3.9.6이라는 지적이 나왔고, 어차피 uv 등으로 따로 설치해야 한다면 바로 3.15를 설치하라는 조언이 붙었다. Python에 LTS가 없다 보니 기업 배포판이 자체적으로 10년씩 지원한다는 현실도 정리됐다. 3.14는 Ubuntu 26.04, 3.12는 RHEL 10과 Ubuntu 24.04, 3.9는 RHEL 9, 3.6은 2029년 지원이 끝나는 RHEL 8에 들어 있다. Tachyon 시연용 10MB 넘는 GIF 두 개가 문서 폴더에 추가돼 XZ 소스 타르볼이 3.14보다 약 50% 커졌다는 관찰도 있었다.

## 결론

Python 3.15는 화려한 한 방보다 오래된 불편을 하나씩 걷어내는 릴리스다. 지연 임포트는 대형 애플리케이션과 CLI의 시작 시간이라는 고질적인 문제를 문법으로 풀었고, UTF-8 기본값은 비영어권 사용자의 인코딩 오류를 기본 설정에서 없앴다. `frozendict`, `sentinel`, 컴프리헨션 언패킹, 다른 언어 습관을 잡아 주는 오류 메시지는 일상 코드를 조금씩 편하게 만든다. 성능 쪽에서 JIT는 아직 실험적이지만, 실행을 기록하는 방식으로 바꾸고 오버헤드를 극적으로 낮추면서 지속 가능한 방향을 찾았다. Tachyon과 프레임 포인터는 "어디가 느린가"를 운영 환경에서 바로 확인하게 해 준다. 동적 언어를 빠르게 만드는 방법은 하나가 아니다. 타입을 근거로 미리 컴파일하는 접근이 있는 한편, Python은 실행을 관찰하고 필요한 것만 늦게 하는 쪽을 택했다.
