# 티빙 침해사고 사례로 본 클라우드 자격 증명 관리와 접근 통제

## 요약

2026년 티빙 침해사고는 개발자가 보유한 접속키가 탈취된 뒤 내부 시스템 접근과 정보 유출로 이어진 사례다. 과학기술정보통신부 조사 결과에 따르면, 공격자는 개발자 접속키를 이용해 내부 시스템에 침투했으며, 개발 프로젝트 361건과 최대 3,954만 개의 계정 관련 정보가 영향을 받았다. 사고의 본질은 특정 클라우드 서비스의 취약점이라기보다 장기 자격 증명, 과도한 권한, 부실한 모니터링 및 미조치 취약점이 결합된 자격 증명 관리 실패에 있다.

이 사례에서 가장 우선해야 할 개선은 애플리케이션과 개발자가 사용하는 장기 액세스 키를 제거하고, 역할(Role) 기반의 단기 자격 증명으로 전환하는 것이다. 이와 함께 최소 권한, 저장소 비밀 탐지, 다중 인증, 이상 행위 탐지, 로그 보존 및 사고 대응 절차를 하나의 운영 체계로 설계하는걸 검토해야 한다.

## 1. 사고 개요와 확인된 사실

정부의 2026년 9월 3일 조사 결과는 공격자가 개발자가 보유한 접속키를 탈취하여 티빙 내부 시스템에 침투하고 정보를 유출했다고 설명한다. 기술 자산 측면에서는 소스코드가 포함된 개발 프로젝트 361건이 유출됐으며, 이용자 정보 측면에서는 활성·비활성·테스트 계정을 합쳐 3,954만 개 계정이 영향 범위에 포함됐다. 계정별 보유 정보는 달랐고, 성명·생년월일·휴대전화번호·이메일·연계정보(CI) 등 최대 20개 항목, 70종의 정보가 유출된 것으로 발표됐다. 비밀번호와 환불 계좌번호는 암호화되어 있었다.

조사는 키 관리 체계 미비, 비정상 행위 모니터링 부재, 부족한 정보보호 인력, 로그 관리 미흡, 2024년 모의해킹에서 확인된 취약점의 미조치를 문제점으로 지적했다. 또한 침해사고 인지 시점은 2026년 5월 31일 10시 10분, 신고 시점은 6월 1일 15시 8분으로 발표됐다. 따라서 이 사례를 설명할 때는 인프라 구성이나 공격 세부 경로를 추정하기보다, 조사 결과로 확인된 사실과 개선 과제를 구분하는 것이 중요하다.

## 2. 사고가 확대된 구조

접속키가 소스 저장소, CI/CD 설정, 개발자 단말 또는 공유 문서에 남아 있으면 공격자는 코드 취약점을 찾지 않아도 정상 사용자처럼 클라우드 API를 호출할 수 있다. 키에 데이터베이스 조회, 객체 저장소 읽기, 비밀 값 열람, 권한 변경과 같은 넓은 권한이 부여되어 있으면 단일 자격 증명 탈취가 대규모 유출로 확대된다.

핵심 위험은 다음과 같이 연결된다.

```text
장기 접속키 노출 또는 탈취
  → 정상 API 호출로 위장한 내부 접근
  → 과도한 IAM 권한 사용
  → 개인정보·소스코드·운영 자산 접근
  → 탐지 지연 및 피해 범위 확대
```

암호화도 키 관리와 분리해서 볼 수 없다. 데이터가 암호화되어 있더라도 복호화 권한 또는 키 접근 권한까지 동일한 자격 증명으로 획득할 수 있다면 방어 효과는 제한적이다. 반대로 데이터베이스 비밀번호를 해시로 저장하는 것은 중요하지만, 개인정보 유출 전반을 막는 대책은 아니다. 개인정보 자체, 접근 토큰, API 키, 복구 정보 역시 별도의 보호 대상이다.

## 3. 보안 책임과 IAM의 역할

클라우드의 공동 책임 모델에서 클라우드 제공자는 물리 인프라와 기반 서비스의 보안을 담당하지만, 고객은 계정 관리, IAM 정책, 애플리케이션 구성, 데이터 접근 제어, 로깅 및 모니터링을 책임진다. 따라서 클라우드를 사용한다는 사실만으로 접근 통제가 안전해지지는 않는다.

IAM은 사람과 워크로드가 어떤 리소스에 어떤 작업을 수행할 수 있는지를 제어하는 체계다. 안전한 IAM 설계는 다음 원칙을 따른다.

- 사람·서비스·자동화 작업의 신원을 분리한다.
- 기본 권한은 거부하고, 업무 수행에 필요한 권한만 명시적으로 부여한다.
- 읽기·쓰기·삭제·권한 변경을 분리하고, 운영 환경 접근은 별도로 승인한다.
- 개인 사용자에게 공유 계정이나 공용 키를 배포하지 않는다.
- 권한 부여, 변경, 사용 이력을 로그로 남기고 정기적으로 검토한다.

## 4. 우선 적용해야 할 기술 통제

### 4.1 장기 액세스 키 제거

애플리케이션에는 정적 액세스 키를 코드, 환경 파일, 컨테이너 이미지에 넣지 않는다. 클라우드 워크로드에는 역할을 연결하고, 보안 토큰 서비스가 발급하는 단기 자격 증명을 사용한다. 예를 들어 가상 머신, 컨테이너, 서버리스 함수에는 실행 역할을 부여하고, 필요한 리소스에 한정된 정책을 연결한다. 사람의 운영 접근은 SSO·연합 인증과 MFA를 사용하며, 임시 권한 상승과 만료 시간을 적용한다.

단기 자격 증명은 유출 가능성을 없애지는 않지만, 사용 기간과 권한 범위를 제한해 피해 창을 줄인다. 장기 키가 불가피한 예외는 소유자, 목적, 권한, 만료일, 회전 주기, 보관 위치를 등록하고 정기적으로 재검토해야 한다.

### 4.2 최소 권한과 환경 분리

개발·검증·운영 환경은 계정 또는 프로젝트 단위로 분리한다. 개발자 계정이 운영 데이터 전체에 상시 접근할 필요는 없다. 운영 접근이 필요한 경우에도 읽기 전용, 특정 서비스, 특정 시간대로 제한하고 별도 승인 절차를 둔다.

권한 정책은 와일드카드 권한을 줄이고, 리소스 범위와 작업을 구체적으로 지정한다. 특히 `iam:*`, `kms:*`, 전체 객체 저장소 읽기, 전체 데이터베이스 접근처럼 권한 확장 또는 대량 반출로 이어질 수 있는 권한은 별도의 통제를 적용한다.

### 4.3 비밀 정보의 저장소 유입 방지

비밀 값은 전용 비밀 관리 서비스에 보관하고, 애플리케이션은 역할을 통해 필요한 시점에만 읽는다. 저장소에는 키·토큰·비밀번호를 커밋하지 않도록 사전 커밋 검사와 서버 측 비밀 탐지를 적용한다. 이미 커밋된 비밀 값은 파일 삭제만으로 해결되지 않으므로 즉시 폐기·교체하고, 저장소 이력·빌드 로그·배포 산출물·개발자 단말까지 노출 범위를 조사해야 한다.

### 4.4 탐지와 대응

정상 자격 증명을 악용한 공격은 방화벽만으로 식별하기 어렵다. 다음 신호를 수집·경보화해야 한다.

- 평소와 다른 지역·시간대·IP에서의 인증 및 API 호출
- 단기간의 대량 조회·다운로드·스냅샷 생성
- 권한 정책, 역할 신뢰 정책, 접근키의 생성·변경·비활성화
- 비밀 관리 서비스, 객체 저장소, 데이터베이스에 대한 비정상 접근
- 로그 중단, 감사 설정 변경, 보존 기간 단축

감사 로그는 중앙 저장소로 전송하고, 운영자가 임의로 삭제하거나 변경하기 어렵게 보존해야 한다. 경보는 담당자 연락망, 키 비활성화, 세션 폐기, 네트워크 격리, 증적 보전으로 이어지는 대응 절차와 함께 운용한다.

## 5. CI/CD와 개발 도구의 보안 설계

CI/CD는 생산성을 높이지만, 배포 권한과 비밀 값이 집중되는 고위험 경로이기도 하다. 파이프라인에는 저장소별·환경별 역할을 분리하고, OIDC 등 연합 인증을 이용해 실행 시점에 단기 자격 증명을 발급하는 방식을 우선한다. 배포용 장기 키를 CI 변수에 장기간 보관하는 방식은 지양한다.

코드 생성 도구와 자동화 도구를 사용할 때도 동일한 원칙이 적용된다. 생성된 코드에 예시 키를 실제 값으로 치환해 넣지 않으며, 설정 파일·터미널 출력·오류 추적 도구·채팅 기록에 비밀 값이 남지 않도록 검토한다. 자동화 계정은 사람이 사용하는 계정과 분리하고, 해당 작업에 필요한 최소 권한만 부여한다.

## 6. 운영 점검표

| 영역 | 점검 항목 |
| --- | --- |
| 자격 증명 | 장기 액세스 키의 전수 목록, 소유자·만료일·회전 이력이 있는가? |
| 워크로드 | 모든 실행 환경이 역할 기반 단기 자격 증명을 사용하는가? |
| 사람 접근 | SSO와 MFA가 강제되고, 운영 권한은 시간 제한·승인 절차를 거치는가? |
| 권한 | 서비스·환경·행위별 최소 권한이 적용되며 와일드카드 권한을 검토하는가? |
| 비밀 관리 | 저장소·이미지·로그에서 비밀 탐지를 수행하고 발견 즉시 교체하는가? |
| 탐지 | 인증, 권한 변경, 대량 반출, 로그 설정 변경을 중앙에서 탐지하는가? |
| 복구 | 키 폐기, 세션 무효화, 권한 회수, 증적 보전, 신고·통지 절차를 훈련했는가? |

## 결론

접속키 유출 사고의 대응은 키 하나를 교체하는 데서 끝나지 않는다. 장기 자격 증명을 줄이고, 역할 기반 단기 자격 증명과 최소 권한을 기본값으로 만들며, 저장소·CI/CD·운영 계정 전반에서 비밀 값의 생성·보관·사용·폐기를 관리해야 한다. 여기에 모니터링, 로그 보존, 취약점 조치, 정기적인 권한 검토가 결합될 때 단일 개발자 계정 또는 단일 키의 탈취가 전사적 사고로 확대되는 것을 막을 수 있다.
