# 대용량 데이터셋(1TB급) 이동 전략 보고서

> 집 PC → 개발 서버로 학습용 데이터셋을 옮기기 위한 실측 기반 분석 보고서.
> 원본 실측 노트(`readme.md`)의 측정값과 시나리오를 검산·정리하고, 병목의 근본 원인과
> 권장 전송 전략을 정리한다.

---

## 1. 요약 (Executive Summary)

집 PC에 있는 대용량 학습 데이터셋(약 1TB, 일부 400GB 단위)을 개발 서버로
옮기려는 상황이다. 가능한 경로는 크게 세 가지다.

1. **외장하드로 물리적 수송** (오프라인 sneakernet)
2. **집 → NAS 원격 업로드 → NAS에서 개발서버으로 내부 다운로드**
3. **개발서버에서 외부 데이터를 직접 다운로드**

실측 결과, 3번(직접 다운로드)은 개발서버 망의 QoS/방화벽 정책 때문에 **약 4MB/s로 제한되고
장시간 세션이 강제로 끊긴다.** 반면 1번(외장하드)은 **총 4시간 30분(+이동)**, 2번(NAS 경유)은
**총 약 30시간**으로, 데이터 크기가 클수록 물리적 수송이 압도적으로 유리하다.

| 순위 | 시나리오 | 1TB 총 소요(순수 전송) | 특징 |
|------|----------|------------------------|------|
| 1 | 외장하드 직접 수송 | **약 4시간 30분** + 이동시간 | 가장 빠르고 확실, 끊김 위험 없음 |
| 2 | 집→NAS 업로드 후 개발서버 내부 다운 | **약 30시간(≈1.25일)** | 걸어두고 방치 가능, 업로드 안정성 전제 |
| 3 | 개발서버에서 외부 직접 다운로드 | 사실상 불가(≈70시간+끊김) | QoS 4MB/s 제한 + 세션 강제 종료 |

**결론:** 1TB 이상은 외장하드 수송을 1순위로, NAS 경유를 백업/무인 야간 전송용으로 권장한다.

## 2. 실측 대역폭 정리

원본 노트에서 측정된 구간별 전송 속도를 표로 정리하고, 초당 바이트(MB/s)를
비트레이트(Mbps)로 환산했다. (1 byte = 8 bit 기준, 1 MB/s ≈ 8 Mbps)

| 구간 | 실측 속도 (MB/s) | 환산 (Mbps) | 비고 |
|------|------------------|-------------|------|
| 같은 공유기에 물린 PC 간 (LAN) | 40 ~ 70 | 320 ~ 560 | 가정용 유선 LAN 수준 |
| 집 → NAS 업로드 (원격) | 10 | ≈ 80 | 가정 인터넷 업로드 상한에 근접 |
| NAS → 개발서버 (개발서버 망 내부) | 125 | ≈ 1000 | **1GbE(1 Gbps) 회선 포화 수준** |
| 외장하드 (USB 3.0 실측) | 100 ~ 130 | 800 ~ 1040 | HDD 물리 속도 한계에 근접 |
| 집에서 데이터 받기(다운로드) | 최대 69 | ≈ 552 | 가정 인터넷 다운로드 실측 |
| 개발서버 에서 직접 다운로드 | ≈ 4 (제한) / 끊김 | ≈ 32 | QoS·방화벽에 의한 인위적 제한 |

### 관찰 포인트

- **NAS→개발서버의 125 MB/s는 1 Gbps 회선을 거의 100% 쓰고 있는 값**이다.
  (125 MB/s × 8 = 1,000 Mbps = 1 Gbps) → 개발서버 내부망은 기가비트 유선으로 매우 건강하다.
- **USB 3.0의 인터페이스 규격은 5 Gbps(≈600 MB/s)** 이지만, 실측 100~130 MB/s는
  인터페이스가 아니라 **외장 HDD(회전식 디스크)의 물리적 순차 읽기/쓰기 속도**가 병목이라는 뜻이다.
  (SSD 기반 외장 드라이브를 쓰면 이 구간은 300~1000 MB/s까지 빨라질 수 있다.)
- **집 업로드 10 MB/s vs 집 다운로드 69 MB/s의 큰 비대칭**은 전형적인 가정용 인터넷 특성
  (비대칭 회선: 다운로드는 넓고 업로드는 좁음)이다. 그래서 집→NAS "업로드"가 전체 병목이 된다.
- **개발 서버로 직접 다운로드 4MB/s**만 유독 낮다. 이는 회선 성능 문제가 아니라 **정책적 제한**이라는
  강한 신호다(같은 개발서버 망 내부 전송은 125 MB/s가 나오므로).

## 3. 소요 시간 산출 방법과 검산

### 3.1 계산식

$$
\text{전송 시간(초)} = \frac{\text{데이터 크기(MB)}}{\text{전송 속도(MB/s)}}
$$

본 보고서는 원본 노트와 동일하게 **1TB = 1,000,000 MB (십진, SI 단위)** 로 계산한다.
운영체제가 표시하는 값은 보통 **1TiB = 1,048,576 MB (2진)** 이므로, 실제 파일이
"1TB"라고 표시되면 계산값보다 **약 7~10% 더 걸릴 수 있다.** (아래 표는 SI 기준)

### 3.2 속도별 1TB 전송 시간 (검산표)

| 속도 (MB/s) | 1TB 소요 시간 | 계산 |
|-------------|----------------|------|
| 4 | 약 69.4시간 (≈2.9일) | 1,000,000 / 4 = 250,000초 |
| 10 | **약 27시간 47분** | 1,000,000 / 10 = 100,000초 |
| 40 | 약 6시간 57분 | 1,000,000 / 40 = 25,000초 |
| 69 | 약 4시간 1분 | 1,000,000 / 69 ≈ 14,493초 |
| 100 | 약 2시간 47분 | 1,000,000 / 100 = 10,000초 |
| 123 | **약 2시간 15분** | 1,000,000 / 123 ≈ 8,130초 |
| 125 | **약 2시간 13분** | 1,000,000 / 125 = 8,000초 |
| 130 | 약 2시간 8분 | 1,000,000 / 130 ≈ 7,692초 |

원본 노트의 "27시간 47분", "2시간 13분", "2시간 15분" 값이 위 검산과 **정확히 일치**한다.

## 4. 시나리오별 상세 분석 (1TB 기준)

### 4.1 시나리오 A — 외장하드 직접 수송 (최우선 추천)

| 단계 | 작업 | 속도 | 소요 |
|------|------|------|------|
| 1 | 집 PC → 외장하드 쓰기 | ≈123 MB/s | 약 2시간 15분 |
| 2 | (물리적 이동) | — | 이동 시간 |
| 3 | 외장하드 → 개발서버 읽기 | ≈123 MB/s | 약 2시간 15분 |
| — | **순수 전송 합계** | — | **약 4시간 30분** |

- **장점:** 네트워크 차단·세션 끊김 위험이 전혀 없다. 가장 확실하고 빠르다.
- **한계/주의:**
  - 외장 HDD 속도가 병목(100~130 MB/s). **SSD 외장 드라이브를 쓰면 절반 이하로 단축** 가능.
  - 물리적 이동 시간·분실/충격 위험이 추가된다(백업본 유지 권장).
  - 복사 후 **무결성 검증(체크섬)** 을 반드시 수행해야 한다(§6.1).

### 4.2 시나리오 B — 집 → 개발서버랑 동일 망의 NAS 업로드 후 개발서버 내부 다운로드

| 단계 | 작업 | 속도 | 소요 |
|------|------|------|------|
| 1 | 집 PC → NAS (원격 업로드) | ≈10 MB/s | 약 27시간 47분 |
| 2 | NAS → 개발서버 (개발서버 망 내부) | ≈125 MB/s | 약 2시간 13분 |
| — | **총 작업 시간** | — | **약 30시간 (≈1.25일)** |

- **장점:** 퇴근 전 집 PC에서 업로드를 걸어두면 사람이 지켜볼 필요가 없다.
  전제 조건(10 MB/s가 끊김 없이 유지)만 충족되면 다음 날 무렵 완료된다.
- **병목:** 전체의 90% 이상이 **집 업로드 구간(27시간 47분)** 이다. 여기가 곧 총 시간이다.
- **핵심 주의:** 업로드가 27시간 이상 단일 세션으로 유지되어야 하므로 **재개(resume) 가능한
  전송 도구(§6.2)** 가 사실상 필수다. 중간에 끊기면 처음부터 다시 받는 참사를 막아야 한다.

### 4.3 시나리오 C — 개발서버에서 외부 데이터를 직접 다운로드 (비권장)

- 실측상 **약 4MB/s로 제한**되고, 장시간 대용량 세션은 **강제 종료(RST)** 된다.
- 만약 유지된다고 가정해도 1TB에 약 69시간, 400GB에 약 28시간이 걸리며,
  현실적으로는 **세션이 중간에 끊겨 완료 자체가 어렵다.**
- 근본 원인은 아래 §5에서 상세히 분석한다.

## 5. 병목의 근본 원인 분석

### 5.1 왜 개발서버(컴퓨터 A) 직접 다운로드는 4MB/s로 제한되고 끊기나

**(1) 네트워크 장비(QoS/방화벽)의 대역폭 제어**
개발서버 망(1번망) 내부 라우터·방화벽에 사용자/IP별 대역폭을 약 **30~35 Mbps(실효 약 4MB/s)**
로 묶는 QoS(Quality of Service) 정책이 걸려 있을 가능성이 높다.
(4 MB/s × 8 = 32 Mbps → QoS 상한과 정확히 맞아떨어진다.)
같은 개발서버 망 내부 전송(NAS→개발서버)은 125 MB/s가 나오므로, 회선이 아니라 **외부 트래픽에만
적용되는 정책적 제한**임이 분명하다.

**(2) TCP 세션 타임아웃 + Stateful Inspection 방화벽**
400GB를 4MB/s로 받으면 단일 TCP 세션을 **약 28시간** 유지해야 한다.
개발서버 망 보안 장비는 이런 장시간·대용량 단일 세션을 이상 징후로 판단하거나,
메모리상의 세션 테이블(NAT Table)이 가득 차 **강제로 연결을 끊는다(RST 패킷 발송).**
→ 그래서 "다운로드 안됨/끊김" 현상이 반복된다.

### 5.2 왜 집 → NAS 업로드(3번 과정)는 끊김 없이 잘 되나

**(1) 트래픽 방향·포트 정책의 차이**
- 개발서버가 외부에서 받는 트래픽은 "Outbound 요청에 대한 Inbound 응답"으로 방화벽의 감시 대상이다.
- 반대로 외부(집)에서 NAS로 **보내는** 트래픽은 NAS 전용 포트(SSH, SFTP, WebDAV 등)로 들어오므로
  일반 웹 세션 제한·QoS 타깃에서 **제외되어 있을 수 있다.**

**(2) NAS의 파일 전송 프로토콜 안정성**
NAS는 대용량 파일 전송을 기본 전제로 설계되어, 패킷 손실 시 재전송(Retransmission) 조율이나
세션 유지(Keep-Alive) 능력이 일반 PC의 웹/VSCode 전송보다 훨씬 뛰어나다.

**(3) 10 MB/s라는 "적절한" 대역폭**
10 MB/s(≈80 Mbps)는 라우터·보안 장비에 순간 과부하를 주지 않고 **안정적으로 흐를 수 있는
최적 레이트 구간**이라, 차단되지 않고 지속 유지된다.
(4MB/s는 QoS가 억지로 눌러 끊는 방향, 10MB/s는 자연스럽게 흐르는 방향이라는 대비.)

### 5.3 한 줄 정리

> 문제는 회선 속도가 아니라 **"외부에서 안으로 당기는(pull) 트래픽"에 걸린 정책적 제한**이다.
> 그래서 "밖에서 안으로 밀어넣는(push, 집→NAS 업로드)" 또는 "물리적 수송(외장하드)"이 통한다.

## 6. 실무 권장 사항 및 리스크 관리

### 6.1 무결성 검증(체크섬)은 필수

물리 수송이든 네트워크 전송이든, 완료 후 원본과 사본의 해시를 비교해야 한다.
(대용량 복사 중 무음 손상(silent corruption)·중단 후 부분 복사 방지)

```bash
# Linux(개발서버) / macOS
sha256sum dataset.tar        # 또는 md5sum (빠르지만 충돌 위험은 이론상 존재)

# Windows (PowerShell)
Get-FileHash .\dataset.tar -Algorithm SHA256
```

양쪽 값이 같아야 전송 성공으로 간주한다.

### 6.2 재개 가능한 전송 도구 사용 (NAS 경유 시)

27시간 이상 걸리는 업로드는 반드시 **중단 후 이어받기(resume)** 를 지원하는 도구로 한다.

```bash
# rsync: 부분 전송/이어받기/무결성 검증에 강함
rsync -avP --partial --append-verify ./dataset/ user@nas:/volume1/dataset/

# rclone: 클라우드/NAS 대상, 체크섬·재시도·병렬 청크 지원
rclone copy ./dataset remote:dataset --progress --transfers=4 --checkers=8

# scp/sftp만 가능하면 tmux/nohup으로 세션 유지
nohup rsync -avP ... &   # 또는 tmux 안에서 실행하여 SSH 끊겨도 지속
```

- `--partial`/`--append-verify`로 중간에 끊겨도 처음부터 다시 받지 않는다.
- 세션 자체가 끊길 수 있으므로 서버 쪽 `tmux`/`screen` 안에서 돌리는 것을 권장.

### 6.3 하나의 큰 파일 vs 잘게 쪼개기

- **아주 큰 단일 파일**은 한 번 끊기면 손해가 크다. 반대로 파일 수가 너무 많으면
  파일당 오버헤드로 느려진다.
- 절충: **tar로 묶되 적당한 청크(예: 수 GB 단위)로 분할**하면, 끊겨도 실패한 청크만 다시 받는다.

```bash
# 5GB 단위로 분할 + 재조립
tar cf - dataset/ | split -b 5G - dataset.tar.part_
cat dataset.tar.part_* | tar xf -
```

### 6.4 압축은 데이터 성격에 따라 판단

- 텍스트/JSON/로그 위주면 압축(gzip/zstd)으로 전송량을 크게 줄일 수 있다.
- **이미 압축된 미디어(mp4, jpg, webdataset 등)** 는 압축 이득이 거의 없고 CPU만 소모하므로
  `tar`(무압축)로 묶기만 하는 것이 낫다.

### 6.5 리스크 요약

| 리스크 | 영향 | 대응 |
|--------|------|------|
| 외장하드 분실/충격 손상 | 데이터 유실 | 원본은 집에 유지, 이동 중 백업본 확보 |
| NAS 업로드 27시간 중 끊김 | 재전송으로 시간 폭증 | rsync `--partial`, tmux/nohup |
| 방화벽 세션 강제 종료(직접 다운) | 완료 불가 | 직접 pull 방식 자체를 지양 |
| 1TB vs 1TiB 단위 오차 | 예상보다 7~10% 지연 | 여유 시간 확보하여 일정 산정 |
| 복사 중 무음 손상 | 학습 데이터 오염 | 완료 후 SHA256 검증 |

## 7. 의사결정 가이드

- **급하고 확실해야 한다 / 데이터가 500GB 이상** → **외장하드 수송(시나리오 A).**
  가능하면 **SSD 외장 드라이브**로 전송 시간을 추가 단축.
- **사람이 못 지켜본다 / 야간·주말에 걸어두고 싶다** → **NAS 업로드(시나리오 B)** 를
  rsync 재개 옵션 + tmux로 무인 실행.
- **개발서버에서 직접 인터넷 다운로드** → **지양.** 꼭 필요하면 IT 부서에 QoS/방화벽 예외(특정
  포트·목적지·세션 타임아웃 완화)를 요청하고, 그 전까지는 A 또는 B로 우회.

## 8. 향후 개선 아이디어 (선택)

- **개발서버 망 QoS 예외 신청:** 특정 업무용 IP/포트에 한해 대역폭 상한·세션 타임아웃을 완화받으면
  직접 다운로드도 회선 성능(수백 Mbps)으로 끌어올릴 수 있다.
- **NAS 업로드 병렬화:** 단일 세션 10MB/s가 정책상 상한이 아니라면, 여러 세션으로 분할 업로드
  (`rclone --transfers`)해 총 처리량을 높일 수 있다. (단, QoS가 사용자/IP 단위면 효과 제한적.)
- **정기 데이터 동기화 체계화:** 반복적으로 옮긴다면 NAS를 중간 허브로 두고 `rsync` cron/스케줄러로
  증분 동기화(변경분만 전송)하면 매번 전체를 옮길 필요가 없다.
- **외장 저장매체 SSD 전환:** 향후에도 물리 수송을 쓸 계획이면 USB 3.x/Thunderbolt SSD로 교체 시
  쓰기·읽기 각각 2시간 15분 → 30분~1시간 수준으로 단축 가능.

## 부록 A. 단위 환산 참고

| MB/s | Mbps (×8) | 1TB 전송 시간(SI) |
|------|-----------|-------------------|
| 4 | 32 | 69.4시간 |
| 10 | 80 | 27.8시간 |
| 40 | 320 | 6.9시간 |
| 69 | 552 | 4.0시간 |
| 100 | 800 | 2.8시간 |
| 125 | 1000 (1 Gbps) | 2.2시간 |

- 1 Byte = 8 bit. 인터넷 회선 광고는 보통 **Mbps(비트)**, 파일 복사 표시는 **MB/s(바이트)**.
  같은 링크라도 숫자가 8배 차이 나 보이는 이유다.
- SI(십진) 1TB = 10¹² B, 2진 1TiB = 2⁴⁰ B ≈ 1.0995 TB. OS 표시는 대개 2진.

## 부록 B. 원본 실측 노트 대비 검산 결과

| 원본 노트 값 | 검산 | 판정 |

| NAS→개발서버 2시간 13분 | 1,000,000 ÷ 125 = 8,000초 = 2h13m | ✅ 일치 |

| 400GB @ 4MB/s ≈ 28시간 | 400,000 ÷ 4 = 100,000초 = 27.8h | ✅ 일치 |
| QoS 30~35Mbps ≈ 4MB/s | 4 MB/s × 8 = 32 Mbps | ✅ 일치 |
