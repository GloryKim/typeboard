## 1. 영상에서 던진 질문

### 개념

제목이 말하는 것:

> DB 문자열 컬럼을 `255`로 잡는 건 **단순 버릇(관습)** 이 아니다.  
> 그 뒤에는 **저장 방식·과거 제한·인덱스 한도** 같은 기술적 이유가 있다.

현장에서 자주 보는 스키마:

```sql
name        VARCHAR(255) NOT NULL,
email       VARCHAR(255) NOT NULL,
title       VARCHAR(255),
description VARCHAR(255),  -- 긴 본문이면 부적절한 경우가 많음
```

질문이 두 겹이다.

| 질문 | 짧은 답 |
|---|---|
| 왜 하필 255인가? | `2^8 - 1` 경계, 길이 메타데이터, 옛 VARCHAR 최대값, utf8×767바이트 인덱스 한도와 맞물림 |
| 그럼 오늘도 무조건 255? | **아니다.** 도메인 최대 길이를 먼저 정하고, 문자셋·인덱스·행 크기·엔진 한도를 검증한다 |

이 보고서는 “255를 까라”가 아니라, **왜 그 숫자가 튀했는지**와 **지금은 어떻게 고를지**를 분리해서 적는다.

### 체크포인트

- [ ] “255 = 매직 넘버 국룰”과 “255 = 기술 한계의 흔적”을 구분
- [ ] 영상 제목의 ‘관습이 아니다’를 ‘이유 없이 쓰지 말자’가 아니라 ‘이유가 있었다’로 읽기

## 2. CHAR vs VARCHAR — 255를 말하기 전에

### 개념

| 타입 | 저장 | 언제 |
|---|---|---|
| `CHAR(N)` | 고정 길이(저장 시 패딩). MySQL에서 `N`은 문자 수, 상한 **255** | 길이가 거의 고정인 코드(국가코드 등) |
| `VARCHAR(N)` | 가변 길이 + **길이 프리픽스** | 길이가 들쭉날쭉한 일반 문자열 |
| `TEXT` / `BLOB` 계열 | 값이 커지면 오프페이지 저장 경향, 인덱스·임시테이블 제약이 더 큼 | 긴 본문 |

`VARCHAR(255)`의 `255`는 MySQL에서 **최대 문자 수(characters)** 선언이지, **바이트 수**가 아니다.  
실제 바이트는 **문자셋의 문자당 최대 바이트 × 문자 수**로 불어난다.

```text
선언: VARCHAR(255)
latin1   → 최대 약 255 bytes 데이터
utf8mb3  → 최대 약 255 × 3 bytes
utf8mb4  → 최대 약 255 × 4 bytes  (이모지 포함 가능)
+ 길이 프리픽스 1 또는 2 bytes
```

참고: MySQL의 옛 이름 `utf8`은 실질적으로 **utf8mb3**(최대 3바이트/문자)다. 이모지까지 쓰려면 **utf8mb4**.

### 체크포인트

- [ ] `255`가 “255바이트”가 아니라 “최대 255문자”임을 말하기
- [ ] CHAR / VARCHAR / TEXT 역할 구분
- [ ] `utf8` ≈ utf8mb3, 이모지는 utf8mb4

## 3. 이유 1 — 길이 프리픽스 1바이트 vs 2바이트

### 개념 (영상·매뉴얼이 말하는 “진짜 이유”의 핵심 축)

MySQL은 `VARCHAR` 값을 대략 이렇게 저장한다.

```text
[ length prefix ][ actual bytes ... ]
```

[공식 매뉴얼](https://dev.mysql.com/doc/refman/8.4/en/storage-requirements.html) 요지:

- 컬럼 값이 **최대 0~255바이트만 필요하면** → 길이 프리픽스 **1바이트** (`L + 1`)
- 값이 **255바이트를 넘을 수 있으면** → 길이 프리픽스 **2바이트** (`L + 2`)

프리픽스는 “지금 row에 들어 있는 길이”만이 아니라,  
**그 컬럼 선언상 허용되는 최대 바이트**가 255를 넘을 수 있는지에 좌우된다.

단바이트 문자셋(`latin1` 등)에서는:

| 선언 | 최대 데이터 바이트(대략) | 길이 프리픽스 |
|---|---|---|
| `VARCHAR(255)` | 255 | **1바이트** |
| `VARCHAR(256)` | 256 | **2바이트** |

매뉴얼 예시와 같은 감각: `VARCHAR(255) latin1`의 `'abcd'`는 데이터 4 + 프리픽스 1 = 5바이트.  
같은 255를 `ucs2`(문자당 2바이트)로 쓰면 최대 510바이트라 **프리픽스가 2바이트**가 된다.

그래서 “애매하면 255”가 **한 세대 동안** 합리적으로 들렸다.

- 필요한 상한을 모를 때, 1바이트 프리픽스 구간의 **최대치**를 고른다.
- `VARCHAR(1000)`처럼 크게 잡으면, 실제 데이터가 짧아도 **스키마 때문에** 2바이트 프리픽스로 갈 수 있다.

다만 **utf8mb4**에서는 `VARCHAR(255)`만 해도 최대 `255×4 = 1020`바이트라, 프리픽스가 **이미 2바이트**다.  
→ “255면 무조건 1바이트 프리픽스”는 **문자셋에 따라 거짓**이다. (6절)

### 숫자 감각

```text
2^8 - 1 = 255
→ 1바이트로 표현 가능한 최대 부호 없는 정수
→ “길이 ≤ 255”를 1바이트 메타데이터로 담기 좋은 경계
```

`TINYINT UNSIGNED` 최댓값도 255라서 헷갈리기 쉽지만,  
컬럼 길이 255와 TINYINT 255는 **다른 이야기**를 같은 숫자로 공유할 뿐이다.

### 체크포인트

- [ ] VARCHAR = 데이터 + 길이 프리픽스
- [ ] 프리픽스 기준이 “문자 수 255”가 아니라 **바이트 255**임을 말하기
- [ ] utf8mb4에서는 255여도 2바이트 프리픽스인 경우가 많음

## 4. 이유 2 — 옛 MySQL에서 VARCHAR 최대가 255

### 개념

MySQL **5.0.3 이전**에는 `VARCHAR` 최대 길이가 **255**였다.  
그 시절 “문자열 상한을 크게” 잡으려면 사실상 `VARCHAR(255)`가 천장에 가까웠다.

이후 선언 가능 상한이 커졌지만(아래 7절 **행 크기** 제약 안),

- 오래된 튜토리얼·ORM 기본값·복사한 스키마
- “일단 최대에 가깝게”

가 남아 **습관처럼 255**가 전파되었다.

영상 제목의 “관습이 아닙니다”는 이렇게 읽으면 된다.

> 처음엔 **엔진 한도·저장 포맷**에서 나온 숫자였고,  
> 한도가 풀린 뒤에도 숫자가 살아남아 **관습처럼 보이게** 된 것이다.  
> 아무 이유 없는 랜덤이 아니라, **이유가 있었던 숫자의 잔상**이다.

주의: “지금은 `VARCHAR(65535)`까지”라고만 말하면 오해다.  
**행 전체 65,535바이트**를 여러 컬럼이 나눠 쓰고, 멀티바이트면 문자 수 상한이 더 줄어든다. (7절)

### 체크포인트

- [ ] 5.0.3 이전 최대 255 사실을 한 줄로
- [ ] “선언 가능 상한”과 “행 크기 때문에 실제로 쓸 수 있는 상한”을 분리

## 5. 이유 3 — 인덱스 키 767바이트와 255·191

### 개념

InnoDB(구 기본, COMPACT/REDUNDANT 계열)에서 **인덱스 키 프리픽스** 한도가 오랫동안 **767바이트**였다.

문자셋별 “인덱스에 올리는 최대 문자 수” 감각:

| 문자셋 | 문자당 최대 바이트 | 767바이트 안에 들어가는 대략 문자 수 |
|---|---|---|
| `utf8` / `utf8mb3` | 3 | `floor(767/3) = 255` |
| `utf8mb4` | 4 | `floor(767/4) = 191` |

그래서:

- utf8 시절: `VARCHAR(255)` + UNIQUE/INDEX가 **한도 직전**(255×3=765 ≤ 767)에 들어갔다.
- utf8mb4로 바꾸면: `VARCHAR(255)` 인덱스 → 255×4=1020 > 767 → **`ERROR 1071: Specified key was too long`**
- 응급처방으로 많이 쓰인 값: **`VARCHAR(191)`** (191×4=764 ≤ 767)

즉 255는 “예쁜 숫자”이기도 하지만, **utf8 × 767바이트 인덱스 한도의 거의 최대 문자 수**이기도 했다.

### 현대 MySQL

- `ROW_FORMAT=DYNAMIC` / `innodb_large_prefix` / MySQL 8 기본 등으로 인덱스 한도가 **3072바이트**로 넉넉해진 환경이 많다.
- 그 경우 `utf8mb4 VARCHAR(255)` **단일** 인덱스가 한도에 안 걸릴 수 있다.
- 그래도 **복합 인덱스**에서는 컬럼 바이트 합이 다시 터질 수 있다.

```text
예: (a VARCHAR(255), b VARCHAR(255)) utf8mb4
최악 합 ≈ 255×4 + 255×4 = 2040  (한도 설정에 따라 OK/NG)
세 컬럼이면 더 쉽게 3072를 위협
```

### 예시 SQL

```sql
-- utf8mb4 + 옛 767 한도 환경에서 실패하기 쉬운 패턴
CREATE TABLE users (
  id BIGINT PRIMARY KEY,
  email VARCHAR(255) NOT NULL,
  UNIQUE KEY uk_email (email)
) CHARACTER SET utf8mb4;

-- 완화 후보 (장단 있음 — 12절)
-- email VARCHAR(191) NOT NULL
-- 또는 PREFIX: UNIQUE KEY uk_email (email(191))  -- 의미적 함정 주의
```

### 체크포인트

- [ ] 255 ≈ 767/3, 191 ≈ 767/4 관계를 적을 수 있는지
- [ ] utf8mb4 전환 시 인덱스 에러가 왜 나는지 설명
- [ ] 단일 키 OK여도 복합 키는 다시 계산

## 6. 문자셋이 끼어들면 255의 의미가 바뀐다

### 개념

같은 `VARCHAR(255)`라도:

| 문자셋 | 최대 데이터 바이트(대략) | 길이 프리픽스 | 767 인덱스에 전체 키 |
|---|---|---|---|
| latin1 | 255 | 1 | 가능 |
| utf8mb3 | 765 | 2 (최대 >255바이트) | 거의 딱 맞음 |
| utf8mb4 | 1020 | 2 | 옛 한도에선 불가 → 191 등 |

오해 교정:

1. “255면 항상 디스크에 길이 1바이트만 더 쓴다” → **문자셋에 따라 아님**  
2. “255면 항상 인덱스 OK” → **utf8mb4 + 옛 767이면 아님**  
3. “255문자 = 255바이트” → **멀티바이트에선 아님**

### 체크포인트

- [ ] 스키마 리뷰 시 `CHARACTER SET` / collation을 같이 보기
- [ ] 신규지·특수문자가 필요하면 utf8mb4가 기본에 가깝다

## 7. 행 크기 65,535바이트 — VARCHAR 상한의 또 다른 천장

### 개념

MySQL 내부 행 표현에는 **최대 행 크기 약 65,535바이트** 제약이 있다(엔진이 더 큰 row를 지원해도 API 한계로 흔히 이 숫자가 등장).  
`BLOB`/`TEXT`는 이 한도에 **포인터 수준만** 기여하고 본문은 다른 영역에 두는 식으로 처리되는 경우가 많다.

그래서:

- `VARCHAR`를 아주 크게 여러 개 두면 **테이블 생성이 실패**하거나, 문자셋 때문에 선언 가능한 문자 수가 줄어든다.
- utf8mb4면 문자당 최대 4바이트 → 이론상 한 컬럼 선언 상한이 대략 `65535/4 ≈ 16383` 문자 근처로 잡히는 설명이 매뉴얼에 있다.
- “`VARCHAR(65535)` 한 방에”는 **다른 컬럼이 없을 때조차** 현실적으로 까다롭다.

255 이야기와 연결:

> 255는 “행 한도를 걱정하지 않고도 인덱스·프리픽스와 맞추기 쉬운 **작은 안전 구간**”에 있었다.  
> 큰 VARCHAR를 남발하면 255 문제가 아니라 **행 크기** 문제로 먼저 터진다.

### 체크포인트

- [ ] VARCHAR 상한 = 엔진 선언 한도 ∩ 행 크기 ∩ 문자셋
- [ ] 긴 필드는 TEXT/별도 저장을 먼저 검토

## 8. “관습이 아니다”를 어떻게 읽어야 하나

### 개념

영상 카피를 오해하면:

- (잘못된 읽기) “255를 쓰면 무조건 정답이다 / 관습을 따르라”  
- (올바른 읽기) “사람들이 255를 고른 데는 **저장 프리픽스·옛 최대값·인덱스 바이트**라는 이유가 있었다”

동시에 인정해야 할 사실:

- 그 이유들이 **오늘날 모든 엔진·모든 컬럼에 그대로 최적인 것은 아니다**  
- 이유를 모른 채 복붙하는 순간, 그것은 **다시 관습**이 된다  

학습 목표:

1. 255의 **역사·기술 배경** 이해하기  
2. 현재 프로젝트의 **도메인 길이 + 문자셋 + 인덱스 + 행 크기**로 숫자를 **다시 고르기**

### 체크포인트

- [ ] “이유 있는 관습”과 “맹목적 복붙”을 구분하는 문장 쓰기

## 9. 지금(2020년대)에도 255가 최선인가

### 개념

| 상황 | 권장 감각 |
|---|---|
| 이메일 | 경로/주소 길이 관행상 **254~320옥텟** 이야기가 분분. 실무에선 `VARCHAR(255)`가 흔하고 대체로 충분. 앱에서 형식·길이 검증 병행 |
| 이름·닉네임 | 서비스 정책(예: 30~50자). 255는 과한 경우 많음 |
| URL | 브라우저·프록시 한도(2048 등) 고려. 255는 짧을 수 있음 |
| 본문·설명 | `TEXT`/`MEDIUMTEXT` 또는 객체 스토리지. `VARCHAR(255)` 억지 금지 |
| UNIQUE 키 | utf8mb4 + 구형 767이면 191/해시 유니크 검토 (프리픽스 UNIQUE는 12절) |
| MySQL 8 + DYNAMIC | 단일 255 인덱스 부담이 예전보다 작음. 복합키는 계산 |

이메일 “표준 254자”는 RFC 해석·구현마다 표현이 조금씩 다르다.  
중요한 실무 포인트는 **DB 255에만 맡기지 말고 앱에서 검증**하는 것이다.

**임시 테이블·정렬·메모리** 일부 경로에서는 선언 길이가 버퍼 추정에 쓰인다는 설명이 엔진·버전별로 있다.  
“255면 RAM이 무조건 절약”을 절대법칙처럼 외우지 말고, **사용 엔진 문서**를 확인한다.

### 체크포인트

- [ ] 컬럼 비즈니스 최대 길이를 먼저 적고 타입을 고른다
- [ ] UNIQUE/인덱스 컬럼은 바이트 한도를 별도 검증

## 10. VARCHAR vs TEXT — 255를 키울지 TEXT로 갈지

### 개념

| | `VARCHAR(N)` | `TEXT` |
|---|---|---|
| 상한 | N 문자 (행 크기 제약) | 타입별 (TINY/TEXT/MEDIUM/LONG) |
| 인덱스 | 전체 또는 프리픽스 | 보통 **프리픽스 길이 지정** 필요(구버전·설정에 따라) |
| 기본값 | 지정 가능 | 구버전에서 기본값 제약 있었음(버전 확인) |
| 용도 | 짧은~중간 필드 | 본문·로그·JSON 문자열 등 |

판단 휴리스틱:

- 최대 길이가 **명확하고 수백 자 이하** → `VARCHAR(N)`  
- 상한이 없거나 수천 자 이상 → `TEXT` 계열  
- “일단 2000자로 VARCHAR” → 행 크기·인덱스부터 계산. 막히면 TEXT

InnoDB는 긴 VARCHAR도 row format에 따라 오프페이지로 나갈 수 있어, “VARCHAR면 항상 인라인”은 과장이다.  
그래도 **의도(짧은 식별자 vs 본문)** 를 타입으로 드러내는 가치는 있다.

### 체크포인트

- [ ] 본문에 VARCHAR(255)를 쓰지 않기
- [ ] TEXT에 UNIQUE를 걸 때 제약·프리픽스를 확인

## 11. 실무에서 길이를 고르는 절차

### 절차

```text
1) 도메인: 이 필드에 들어올 수 있는 최대 문자 수는?
2) 문자셋: utf8mb4 인가? (거의 예)
3) 인덱스: PK/UNIQUE/INDEX/복합키에 올라가는가?
4) 엔진 한도: 767 vs 3072, 복합 인덱스 바이트 합
5) 행 크기: 같은 row의 다른 VARCHAR와 합산
6) 선언: VARCHAR(N) 또는 TEXT
7) 앱 검증: DB보다 먼저 길이·형식 체크
8) 모니터링: “Data too long” / 1071 발생 여부
```

### 안티패턴

```sql
-- 전부 255
username VARCHAR(255),
bio      VARCHAR(255),
content  VARCHAR(255)
```

`bio`/`content`는 보통 255로 부족하거나, username은 255가 과도하다.

## 12. 프리픽스 인덱스·UNIQUE의 함정

### 개념

```sql
UNIQUE KEY uk_email (email(191))
```

옛 767 한도를 피하려고 자주 쓰였지만:

| 문제 | 설명 |
|---|---|
| 유일성 범위 | **앞 191문자만** 유일. 뒤가 다른 두 값은 한쪽이 거절될 수 있음 |
| 이메일 | 로컬파트가 긴 주소에서 잘못된 충돌 가능 |
| 검색 | `ORDER BY email` 등에서 인덱스 활용이 기대와 다를 수 있음 |

더 안전한 대안 감각:

1. MySQL 8 + DYNAMIC으로 **전체 컬럼** UNIQUE가 한도 안인지 확인  
2. `email`을 합리적인 N(예: 255)으로 두고 한도 OK인지 확인  
3. 불가피하면 `email_hash` BINARY(32) UNIQUE + 원문은 별도 컬럼  
4. 도메인상 191자면 충분한 필드만 `VARCHAR(191)`

### 체크포인트

- [ ] 프리픽스 UNIQUE를 “만능 해결”로 쓰지 않기
- [ ] 이메일·슬러그 등 전체 일치 유일성이 중요하면 전체 키/해시 검토

## 13. sql_mode · 잘림 · 마이그레이션

### 개념

구버전·느슨한 `sql_mode`에서는 길이 초과 시 **에러 대신 잘라 넣고 경고**만 하는 설정이 있었다.  
지금은 `STRICT_TRANS_TABLES` 등이 기본에 가깝고, 초과 시 **에러**가 나는 편이 일반적이다.

실무:

- 배포 환경 `sql_mode` 확인  
- 앱에서 먼저 막아 UX 메시지 제공  
- `ALTER ... MODIFY col VARCHAR(새N)` 는 테이블 크기·락·복제 지연을 동반할 수 있음  

길이 **축소** 마이그레이션:

```text
1) 현재 MAX(CHAR_LENGTH(col)) 조회
2) 새 상한보다 긴 row 정리/거부
3) ALTER
4) 앱 상수 동시 변경
```

길이 **확대**는 상대적으로 안전하지만, 인덱스·행 크기 재검증이 필요하다.

### 체크포인트

- [ ] STRICT 모드에서 “조용한 잘림”이 기본이 아님을 알기
- [ ] 축소 ALTER 전 MAX 길이 조사

### 스키마 스케치

```sql
CREATE TABLE accounts (
  id            BIGINT PRIMARY KEY AUTO_INCREMENT,
  email         VARCHAR(255) NOT NULL,
  display_name  VARCHAR(50)  NOT NULL,
  bio           VARCHAR(500) NULL,
  UNIQUE KEY uk_accounts_email (email)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 ROW_FORMAT=DYNAMIC;
```

### Rust 쪽 길이 검증 (DB보다 먼저)

```rust
use thiserror::Error;

#[derive(Debug, Error)]
enum AccountError {
    #[error("email too long (max {max})")]
    EmailTooLong { max: usize },
    #[error("display_name too long (max {max})")]
    NameTooLong { max: usize },
}

const EMAIL_MAX: usize = 255;
const NAME_MAX: usize = 50;

fn validate_email(email: &str) -> Result<(), AccountError> {
    // 유니코드 scalar 개수. MySQL utf8mb4 "문자"와 100% 동일하진 않을 수 있어
    // 팀에서 grapheme/바이트 중 어떤 기준으로 맞출지 합의할 것.
    if email.chars().count() > EMAIL_MAX {
        return Err(AccountError::EmailTooLong { max: EMAIL_MAX });
    }
    Ok(())
}

fn validate_display_name(name: &str) -> Result<(), AccountError> {
    if name.chars().count() > NAME_MAX {
        return Err(AccountError::NameTooLong { max: NAME_MAX });
    }
    Ok(())
}
```

바이트·인덱스 예산:

```rust
fn max_bytes_for_varchar_chars(chars: usize, bytes_per_char: usize) -> usize {
    chars.saturating_mul(bytes_per_char)
}

fn demo_utf8mb4_index_budget() {
    let worst_255 = max_bytes_for_varchar_chars(255, 4);
    assert_eq!(worst_255, 1020);

    let old_limit = 767usize;
    assert!(worst_255 > old_limit);
    assert_eq!(old_limit / 4, 191);

    let modern_limit = 3072usize;
    assert!(worst_255 <= modern_limit);

    // 복합 인덱스 감각
    let composite = worst_255 + worst_255; // 두 VARCHAR(255)
    assert_eq!(composite, 2040);
    assert!(composite <= modern_limit);
}
```

### sqlx insert 스케치

```rust
use sqlx::MySqlPool;

pub async fn insert_account(
    pool: &MySqlPool,
    email: &str,
    display_name: &str,
) -> Result<(), AccountError> {
    validate_email(email)?;
    validate_display_name(display_name)?;

    sqlx::query(
        r#"
        INSERT INTO accounts (email, display_name)
        VALUES (?, ?)
        "#,
    )
    .bind(email)
    .bind(display_name)
    .execute(pool)
    .await
    .map_err(|e| {
        // 학습용: 실제로는 sqlx::Error 를 앱 에러로 매핑
        tracing::error!(error = %e, "insert failed");
        AccountError::EmailTooLong { max: EMAIL_MAX } // placeholder — 실서비스에선 전용 에러
    })?;

    Ok(())
}
```

(위 `map_err` placeholder는 학습용이다. 실서비스에선 DB 에러 코드를 구분해 매핑한다.)

## 15. PostgreSQL·다른 DB와의 차이

### PostgreSQL

- `VARCHAR(n)` / `TEXT`가 흔하고, MySQL식 “255 → 길이 프리픽스 1바이트” 스토리를 **그대로 가져오면 안 된다**
- 길이 제한은 도메인 제약에 가깝고, 긴 값은 TOAST 등 다른 메커니즘
- “습관적 VARCHAR(255)”는 이식된 MySQL 스키마·ORM 영향인 경우가 많다
- Postgres에서는 길이 몰라도 되면 `TEXT` + CHECK로 상한을 거는 패턴도 흔하다

### SQL Server / Oracle 등

- 타입 이름·바이트/문자 단위·인덱스 한도가 제각각
- **255가 만국 공통 물리 상수인 것처럼 외우지 말 것**

이 영상·이 보고서의 기술 축은 **MySQL VARCHAR 생태계**에 가장 잘 맞는다.

### 체크포인트

- [ ] 팀 DB가 Postgres면 MySQL 255 신화를 그대로 적용하지 않기

## 16. 자주 하는 실수

1. **모든 문자열을 VARCHAR(255)**  
2. **255 = 255바이트로 착각** (utf8mb4면 최대 ~1020바이트)  
3. **utf8 → utf8mb4만 하고 UNIQUE(255) 유지** (구형 767에서 1071)  
4. **“프리픽스 1바이트” 때문에 utf8mb4에도 무조건 255** (이미 2바이트인 경우가 많음)  
5. **프리픽스 UNIQUE로 유일성을 전부 해결했다고 착각**  
6. **앱 검증 없이 DB에만 맡김**  
7. **VARCHAR(255)에 게시글 본문**  
8. **Postgres에 MySQL 255 이유를 그대로 강의**  
9. **큰 VARCHAR 여러 개로 행 크기 65,535를 무시**  
10. **255를 쓰면 항상 성능이 좋다고 믿음** (쿼리·인덱스 설계가 훨씬 큼)

## 17. 정리 표

| 층위 | 255와 관련 | 한 줄 |
|---|---|---|
| 비트 | `2^8 - 1` | 1바이트로 담는 최대값 경계 |
| 저장 | 길이 프리픽스 | **바이트** 255 초과 가능 여부로 1·2바이트 |
| 역사 | MySQL < 5.0.3 | VARCHAR 최대가 255 |
| 인덱스 | 767바이트 | utf8에서 255자 ≈ 한도 직전 |
| utf8mb4 | 191 | 767/4. 255는 옛 한도에서 인덱스 실패 가능 |
| 현대 | 3072 등 | 단일 키는 완화, 복합키·행 크기는 별도 |
| 행 | 65,535바이트 | 큰 VARCHAR 남발의 또 다른 천장 |
| 실무 | 컬럼별 N | 이메일≈255, 닉네임 작게, 본문은 TEXT |

영상 한 줄 재진술:

> DB 컬럼 255는 아무 생각 없는 유행이 아니라,  
> **가변 문자열 메타데이터·옛 상한·인덱스 바이트 한도**가 겹쳐 만들어진 숫자다.  
> 다만 **지금도 무조건 255**인 것은 아니며, 이유를 안 뒤 **다시 선택**해야 한다.
