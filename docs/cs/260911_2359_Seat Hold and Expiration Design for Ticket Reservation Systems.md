# 티켓 예매 시스템의 좌석 선점과 만료 처리 설계: 임시 점유(HELD), 지연 만료, 결제 대기(PAYMENT_PENDING)

## 요약

본 보고서는 선착순 티켓 예매 시스템에서 좌석 하나를 결제가 끝날 때까지 잠시 잡아 두는 문제, 즉 좌석의 선점과 만료 처리를 다룬다. 출발점은 이전 예매 시스템 설계에서 "만료된 HELD 좌석의 회수는 별도 설계가 필요하다"고만 표시하고 넘어간 부분에 대해 제기된 질문이다. 사용자가 좌석을 선택해 놓고 아무것도 하지 않은 채 떠나면, 언제 누가 HELD를 AVAILABLE로 되돌리는 갱신을 실행해야 하는가? 1분마다 HELD 좌석을 갱신하는 스케줄러가 필요한가?

좌석 상태를 AVAILABLE(판매 가능)과 SOLD(판매 완료) 두 가지로만 두면, 몇 분이 걸리는 결제 진행 구간을 표현할 수 없다. 이 구간을 AVAILABLE로 두면 중복 예매가 생기고, SOLD로 두면 결제 실패나 이탈 시 팔리지 않은 좌석이 팔린 것으로 남아 판매 기회를 잃는다. 그래서 특정 사용자가 일정 시간 동안 갖는 임시 점유권인 HELD 상태를 둔다. HELD를 도입하면 두 가지 질문이 생긴다. 누가 HELD를 얻는가(동시성 처리)와 언제 HELD를 끝내는가(만료 처리)다.

동시성 처리는 상태 확인과 상태 변경을 하나의 쿼리에서 수행하는 **원자적 조건부 갱신**으로 해결한다. 만료 처리는 분산 시스템의 **리스(lease)** 개념으로 이해할 수 있다. 다만 저장된 만료 시각은 스스로 상태를 바꾸지 못하므로, 조회나 선점 시점에 만료 시각을 함께 판정하는 **지연 만료(lazy expiration)** 를 기본으로 하고, 남은 좌석을 주기적으로 정리하는 **능동 만료(active expiration)** 스케줄러를 보조로 조합하는 방식을 권장한다.

그러나 동시 선점을 막는 것만으로 중복 판매 문제가 끝나지 않는다. 결제 승인이 만료 시각 이후에 도착하거나, 타임아웃으로 결과를 아예 받지 못하면, 만료를 판정하는 쪽과 결제를 확정하는 쪽이 서로의 상태를 모르기 때문에 이미 결제된 좌석이 다른 사용자에게 다시 선점될 수 있다. 이를 막으려면 결제 요청을 시작하는 순간 좌석을 **PAYMENT_PENDING(결제 대기)** 상태로 옮겨, 회수해도 되는 상태(HELD)와 회수하면 안 되는 상태(PAYMENT_PENDING)를 구분해야 한다. PAYMENT_PENDING은 PG(결제 대행사)의 콜백으로 마무리하고, 오래 남은 건은 PG의 결제 상태 조회 API로 확인한다. 예매 시스템의 가장 큰 리스크는 중복 판매이므로, 결과가 불확실할 때는 좌석을 풀기보다 보수적으로 더 잡아 두는 편이 비즈니스적으로 안전하다.

## 1. 문제 정의

### 1.1 배경: 이전 설계에서 남겨진 과제

이전의 콘서트 티켓 예매 시스템 설계에서는 하나의 좌석을 두고 여러 사람이 동시에 선점하려는 동시성 문제를 다뤘다. 여러 기법이 있었지만 최종적으로 **원자적 조건부 갱신**을 채택했고, 이를 쿼리로 구성했다. 그 설계에는 다음 한 줄이 회색 주석으로만 표시되어 있었다.

```text
※ 만료된 HELD 좌석 회수는 별도 설계 필요
```

즉 선점(HELD)을 얻는 방법은 정했지만, 선점이 끝나는 방법은 설명하지 않은 상태였다.

### 1.2 제기된 질문

이 표시를 두고 다음과 같은 질문이 제기되었다.

| 번호 | 질문 |
| --- | --- |
| 1 | 만료된 HELD 좌석 회수는 별도 설계가 필요하다고 되어 있는데, 보통 어떻게 회수하는가? |
| 2 | 사용자가 좌석을 선택해 놓고 아무것도 하지 않은 채 나가 버리면, 어느 시점에 HELD를 AVAILABLE로 변경하는 갱신을 실행해야 하는가? |
| 3 | 1분에 한 번씩 HELD 좌석을 갱신하는 스케줄러가 필요한가? |

본 보고서는 이 질문에 답하면서, 예매 시스템에서 좌석의 선점과 만료를 어떻게 처리할지에 대한 하나의 설계 관점을 정리한다.

### 1.3 좌석 하나를 둘러싼 시나리오

여러 사람이 좌석을 선점하려고 경쟁하는 가운데, 사용자 A가 101번 좌석을 먼저 선점했다고 하자. A는 이후 다른 좌석을 추가로 선점할 수도 있고, 이것을 선택했다가 저것을 선택하는 식으로 바꿀 수도 있다. 그리고 최종적으로 결제까지 완료되어야 실제로 좌석이 팔린 것이 된다.

```text
[좌석 선택] ───────── 결제 진행 ───────── [결제 완료]
     │                                        │
  A가 101번 선점                           실제 판매 성립
     └──────────── 이 구간의 101번은 누구의 것인가? ────┘
```

처음 좌석을 선택한 시점부터 결제가 완료될 때까지 101번 좌석은 누구의 것이어야 하는가? A가 선택했으므로 A의 좌석이라고 보는 것이 자연스럽다. 그러나 다음 상황에서는 답이 간단하지 않다.

| 상황 | 질문 |
| --- | --- |
| 사용자 이탈 | A가 결제를 하지 않고 그냥 떠났다면 101번은 어떻게 되어야 하는가? |
| 서버 장애 | 처리 도중 서버가 다운되면 101번은 어떻게 되어야 하는가? |
| 응답 유실 | A가 결제를 했는데 결제 응답을 받지 못하면 어떻게 해야 하는가? |

### 1.4 일반화된 문제

이 문제는 **특정 리소스의 선점부터 최종 완료까지 시간이 걸리는 시스템**에서 리소스의 선점과 만료를 어떻게 설계할 것인가로 일반화된다. 본 보고서는 그에 대한 한 가지 접근법을 다룬다.

## 2. 좌석 상태 모델의 출발점

### 2.1 가장 단순한 두 상태 모델

가장 단순한 형태는 좌석 상태를 두 가지로 두는 것이다.

| 상태 | 의미 |
| --- | --- |
| AVAILABLE | 누구든지 선점할 수 있는 좌석 |
| SOLD | 결제까지 완료되어 판매된 좌석 |

```text
AVAILABLE ──(결제 완료)──▶ SOLD
```

좌석은 비어 있거나 팔렸거나 둘 중 하나의 상태만 가진다. 매우 단순하지만 문제가 있다.

### 2.2 결제 진행 구간의 문제

결제에는 시간이 걸린다. 선점 가능한 좌석과 이미 팔린 좌석 사이에 **결제 진행**이라는 단계가 들어가며, 이 단계는 몇 분 이상 걸릴 수 있다. 이 중간 단계를 두 상태 중 하나로 표현하려고 하면 어느 쪽이든 문제가 생긴다.

| 결제 진행 구간을 표현하는 방식 | 결과 | 문제 |
| --- | --- | --- |
| AVAILABLE로 둔다 | 결제 진행 중에 다른 사람이 같은 좌석을 다시 선점할 수 있다 | 중복 예매 |
| SOLD로 둔다 | 결제 실패, 결제 포기, 사용자 이탈 시에도 좌석이 판매 완료로 남는다 | 팔리지 않은 좌석이 팔린 것으로 기록되어 판매 기회 상실 |

결제 진행 구간은 "아직 팔리지 않았지만, 다른 사람에게 줘서도 안 되는" 상태다. 두 상태 모델로는 이를 표현할 수 없다.

### 2.3 중간 상태 HELD의 도입

그래서 일반적으로 중간 단계를 별도 상태로 두는 것이 좋다. 좌석을 잡아 두는 행위를 홀드(hold)라 하고, 그 상태를 **HELD**라고 한다.

```text
AVAILABLE ──(선점)──▶ HELD ──(결제 완료)──▶ SOLD
```

HELD는 **특정 사용자가 일정 시간 동안 가지고 있는 임시 점유권**이다. 소유권(SOLD)이 아니라 점유권이며, 영구적이지 않고 시간 제한이 있다는 점이 핵심이다.

### 2.4 HELD가 남기는 두 가지 질문

임시 점유권인 HELD 상태를 두면 두 가지를 설계해야 한다.

| 번호 | 질문 | 문제 영역 | 내용 |
| --- | --- | --- | --- |
| 1 | 누가 HELD를 얻는가? | 동시성 처리 | A와 B처럼 여러 사용자가 같은 좌석을 동시에 선택하면 누구에게 줄 것인가 |
| 2 | 언제 HELD를 끝내는가? | 만료 처리 | 결제가 정상 완료되면 문제없지만, 사용자 이탈이나 결제 실패 시 어떻게 되돌릴 것인가 |

본 보고서의 주제는 두 번째인 만료 처리다. 다만 만료 처리는 동시성 처리 위에서 동작하므로, 순서대로 동시성 처리부터 정리한다.

## 3. 동시성 처리: 누가 HELD를 얻는가

### 3.1 읽기와 쓰기 사이의 경쟁 상태

두 사용자 A와 B가 101번 좌석을 동시에 예매하려 한다. 각 사용자는 먼저 좌석이 판매 가능한지 조회하고, 가능하면 HELD로 쓰기를 한다. 문제는 읽기와 쓰기가 별개의 단계라는 데 있다.

```text
시간  사용자 A                         사용자 B
────  ───────────────────────────      ───────────────────────────
T1    101번 조회 → AVAILABLE
T2                                     101번 조회 → AVAILABLE (A가 아직 쓰기 전)
T3    101번 쓰기 → HELD(A)  ✔ 성공
T4                                     101번 쓰기 → HELD(B)  ✔ 성공 (A를 덮어씀)
```

T2는 A가 읽은 뒤 쓰기 전의 찰나다. 이때 B가 좌석을 조회하면 A가 아직 쓰기 전이므로 좌석은 여전히 AVAILABLE이다. 그래서 B도 선점하려고 쓰기를 한다. 그 사이 A가 이미 HELD로 바꿨지만, B가 나중에 다시 HELD로 바꾸면 A의 선점을 덮어쓴다. A도 선점에 성공했고 B도 선점에 성공했지만 좌석은 하나뿐이다. 이것이 일반적인 다중 사용자 환경의 동시성 문제다.

### 3.2 해법 비교

이 동시성 문제는 보통 데이터베이스 락으로 처리한다.

| 해법 | 동작 | 장점 | 단점 |
| --- | --- | --- | --- |
| 비관적 락 | 조회할 때 잠그고, 쓸 때까지 다른 사용자가 중복으로 쓰지 못하게 한다 | 가장 보편적이고 직관적이다 | 경합이 몰리면 락 대기 시간이 길어져 병목이 되기 쉽다 |
| 분산 락 | 데이터베이스 외부의 락 저장소로 좌석 단위 잠금을 건다 | 대안이 될 수 있다 | 인프라가 복잡해진다 |
| 조건부 업데이트 | 하나의 쿼리 안에서 상태를 확인하고 그 상태일 때만 갱신한다 | 판단과 선점을 하나로 묶어 원자적으로 수행한다 | 갱신 결과(영향받은 행)를 반드시 해석해야 한다 |

선착순 예매는 인기 좌석에 요청이 순간적으로 몰리는 대표적인 고경합 환경이다. 그래서 본 설계에서는 낙관적 방식의 일종인 **조건부 업데이트**로 동시성 문제를 처리하기로 결정했다.

### 3.3 조건부 업데이트 쿼리

조건부 업데이트는 "좌석이 판매 가능한 상태인가"라는 판단과 "내가 선점하겠다"는 쓰기를 하나로 합친다. 좌석을 갱신하되 상태를 함께 보고, 상태가 AVAILABLE일 때만 HELD로 바꾼다. 이때 만료 시각도 함께 기록하며, 본 설계에서는 현재 시각으로부터 7분 동안 잡아 두는 것으로 가정한다. 아래 쿼리는 PostgreSQL 문법을 기준으로 한다.

```sql
UPDATE seats
   SET status     = 'HELD',
       hold_id    = :hold_id,
       held_by    = :user_id,
       held_until = now() + interval '7 minutes'
 WHERE seat_no = :seat_no
   AND status  = 'AVAILABLE'
RETURNING seat_no, hold_id, held_until;
```

### 3.4 결과 해석

| 쿼리 결과 | 의미 | 처리 |
| --- | --- | --- |
| 행이 반환됨(1행) | 조건을 만족해 선점에 성공했다 | 선점 성공 응답, 결제 단계로 진행 |
| 행이 없음(0행) | 조건을 만족하지 못했다. 다른 사람이 이미 선점했다 | "이미 선택된 좌석" 응답, 다른 좌석 선택 유도 |

### 3.5 원자성이 보장되는 이유

이 쿼리는 **읽고, 판단하고, 쓰는** 세 단계를 하나의 쿼리 안에서 수행한다. 데이터베이스는 단일 UPDATE 문을 원자적으로 실행하며, 같은 행을 갱신하려는 다른 트랜잭션은 그 사이에 끼어들 수 없다. 3.1의 T2처럼 "읽은 뒤 쓰기 전"이라는 틈이 애초에 존재하지 않으므로, 두 사용자가 동시에 같은 좌석을 선점하는 일은 안전하게 차단된다. 동시에 같은 좌석을 갱신하려 한 두 요청 중 하나는 1행을, 다른 하나는 0행을 받는다.

## 4. 좌석 테이블 스키마

### 4.1 컬럼 구성

HELD 상태를 두는 좌석 테이블은 다음과 같이 구성한다.

| 컬럼 | 타입(예) | 의미 |
| --- | --- | --- |
| `seat_no` | BIGINT | 좌석 번호 |
| `status` | VARCHAR / ENUM | 좌석 상태: AVAILABLE, HELD, SOLD (임시 점유권인 HELD가 중간에 포함됨) |
| `hold_id` | UUID 등 | 선점 트랜잭션에 대한 고유값 |
| `held_by` | BIGINT | 누가 선점했는지, 사용자 ID 참조값 |
| `held_until` | TIMESTAMP | 선점이 유지되는 시각(앞의 7분 만료 시각) |

```text
seats
┌──────────┬───────────┬──────────┬──────────┬─────────────────────┐
│ seat_no  │ status    │ hold_id  │ held_by  │ held_until          │
├──────────┼───────────┼──────────┼──────────┼─────────────────────┤
│ 101      │ HELD      │ h-7f3a…  │ 3001     │ 2026-09-11 18:07:00 │
│ 102      │ AVAILABLE │ NULL     │ NULL     │ NULL                │
│ 103      │ SOLD      │ h-91c2…  │ 3005     │ (확정 후 의미 없음)   │
└──────────┴───────────┴──────────┴──────────┴─────────────────────┘
```

### 4.2 각 컬럼의 역할

- `status`는 좌석의 생명주기를 나타낸다. 이후 9장에서 PAYMENT_PENDING이 추가된다.
- `hold_id`는 "누가"가 아니라 "어느 선점인가"를 식별한다. 같은 사용자가 같은 좌석을 놓았다가 다시 잡으면 `held_by`는 같지만 `hold_id`는 달라진다. 따라서 결제 요청, 결제 콜백, 선점 해제를 특정 선점 건에 정확히 연결하는 기준이 된다(참고 설계, 9.3과 13.2 참고).
- `held_by`는 선점자를 기록해, 결제 단계 진입이나 선점 해제를 선점한 본인만 할 수 있도록 조건을 거는 데 쓴다.
- `held_until`은 임시 점유권의 만료 시각이다. 이 값은 기록일 뿐 스스로 상태를 바꾸지 않는다는 점이 만료 처리 문제의 핵심이다(5.4).

### 4.3 타입 선택에 대한 참고

좌석 번호가 BIGINT로 되어 있는데, 좌석이 아주 많지 않은 공연장에서는 다소 낭비일 수 있다. 메모리와 저장 장치 가격이 많이 내려가 크게 문제가 될 소지는 없지만, 이왕이면 데이터 규모에 맞는 타입을 골라 아끼는 편이 좋다.

이로써 동시성 처리 문제는 해결되었다. 이제 본 주제인 만료 처리로 넘어간다.

## 5. 만료의 본질: HELD는 리스(lease)다

### 5.1 시간 제한이 있는 임시 권리

HELD는 시간 제한이 있는 임시 권리다. 분산 시스템에서는 일정 시간 동안 자원 사용 권한을 부여하고, 그 시간이 지나면 권한이 사라지게 만드는 구조를 **리스(lease)** 라고 부른다. HELD는 좌석에 대한 리스다.

| 리스의 구성 요소 | 좌석 선점에서의 대응 |
| --- | --- |
| 자원 | 좌석 |
| 권한 보유자 | `held_by`(선점한 사용자), `hold_id`(선점 건) |
| 권한 기간 | `held_until`(선점 만료 시각) |
| 권한 소멸 | 만료 시각 경과 후 좌석을 다시 판매 가능으로 취급 |

리스 구조의 장점은 권한 보유자가 명시적으로 권한을 반납하지 않아도 시간이 지나면 권한이 사라진다는 데 있다. 1.3에서 제기한 "사용자가 떠난 경우"와 "서버가 다운된 경우"가 바로 이에 해당한다. 사용자는 떠나면서 아무 요청도 보내지 않고, 다운된 서버는 정리 작업을 할 수 없다. 그러나 만료 시각이 데이터베이스에 기록되어 있으므로, 누가 해제를 하지 않더라도 만료 시각이 지나면 좌석을 회수할 근거가 남는다.

### 5.2 선점 시간이 필요한 이유

임시로 잡아 두는 시간은 얼마로 두어야 하는가? 결제는 시간이 많이 걸리는 작업이다.

| 결제 과정에서 일어날 수 있는 일 | 시간을 늘리는 이유 |
| --- | --- |
| 결제창 이동 | 예매 화면에서 결제 화면으로 전환 |
| 카드 인증 | 카드사 인증 절차, 인증 앱으로 전환 |
| 한도 초과 | 카드 한도 부족으로 다른 카드로 교체 |
| 간편 결제 | 비밀번호 입력 실패와 재시도 |

실제 PG 승인 자체는 짧게 끝날 수 있지만, 그 앞단에서 사용자가 결제를 완료하는 과정 자체는 꽤 시간이 걸린다. 그리고 이 시간 동안 선점은 유지되어야 한다. 사용자가 좌석을 선점한 뒤 결제가 완료될 때까지 좌석을 다른 사람에게 빼앗기면 안 되기 때문이다.

### 5.3 선점 시간의 결정 기준

선점 시간을 몇 분으로 둘지에 대한 정해진 표준값은 없다. 다음 요소를 보고 알맞은 값을 정한다.

| 기준 | 고려 내용 |
| --- | --- |
| 결제 행동 | 결제 수단, 인증 방식, 사용자가 결제를 끝내는 데 걸리는 실제 시간 |
| 비즈니스 정책 | 공정성, 회전율, 상품 특성 |
| 시스템 특성 | 트래픽 규모, 좌석 수, 결제 연동 구조 |

참고 사례로 인터파크는 좌석 선택 단계에서 최대 10분, 결제 진행 단계에서 7분의 선점 시간을 둔다고 안내한다. 또한 상품 유형이나 정책에 따라 이 시간이 달라지거나 아예 제한이 없을 수도 있다고 안내한다.

| 단계 | 선점 시간(인터파크 안내 기준) |
| --- | --- |
| 좌석 선택 단계 | 최대 10분 |
| 결제 진행 단계 | 7분 |
| 예외 | 상품 유형·정책에 따라 달라지거나 제한 없음 |

본 설계의 쿼리는 선점 시간을 7분으로 가정한다.

### 5.4 만료 시각은 스스로 동작하지 않는다

7분이라는 선점 시간이 지나면 어떻게 되는가? 별도로 구현하지 않는 한 **아무 일도 일어나지 않는다.** `held_until`은 저장해 둔 값일 뿐이며 스스로 상태를 바꾸지 못한다. 만료 시각이 지나도 `status`는 여전히 HELD로 남는다.

```text
18:00:00  101번 HELD, held_until = 18:07:00
18:07:00  만료 시각 도달 → (아무 일도 일어나지 않음)
18:30:00  101번 status는 여전히 HELD
```

따라서 만료를 확인해 상태를 바꾸는 로직을 별도로 추가해야 한다. 1.2의 질문도 바로 이 지점에 관한 것이다.

## 6. 좌석 상태 전이와 트리거

### 6.1 상태 전이 목록

좌석 상태가 어떻게 바뀌는지 경우를 나눠 보면 다음과 같다.

| 번호 | 전이 | 조건 | 트리거 |
| --- | --- | --- | --- |
| 1 | AVAILABLE → HELD | 누구든지 선착순으로 먼저 접근해 선점 | 사용자 행동(좌석 선택) |
| 2 | HELD → SOLD | 선점한 사용자가 결제까지 완료 | 사용자 행동(결제 완료) |
| 3 | HELD → AVAILABLE | 결제 실패, 사용자의 결제 취소, 결제 명시적 거절 | 사용자 행동(실패·취소·거절) |
| 4 | HELD → AVAILABLE | 선점 시간(7분) 경과 | **시간 경과** — 누가 바꿀 것인가? |

```text
                 ① 선점(선착순)
   AVAILABLE ────────────────────▶ HELD ───② 결제 완료──▶ SOLD
       ▲                            │
       │   ③ 결제 실패·취소·거절      │
       ├────────────────────────────┤
       │   ④ 만료 시각 경과(?)        │
       └────────────────────────────┘
```

### 6.2 사용자 행동 트리거와 시간 트리거

1~3번 전이는 **사용자의 행동이 트리거**다. 사용자의 요청이 들어오면 그 요청을 처리하는 과정에서 상태를 바꾸면 된다. 상태를 바꿀 주체와 시점이 분명하다.

반면 4번 전이는 아무도 요청을 보내지 않는다. 떠난 사용자는 요청을 보내지 않고, 시간이 흘렀다는 사실은 이벤트가 아니다. 그래서 4번 전이는 "누가, 언제 바꿀 것인가"를 별도로 정해야 하며, 이것이 **만료 처리 전략**이다.

## 7. 만료 처리 전략

### 7.1 지연 만료(Lazy Expiration)

지연 만료는 만료 시각을 일단 그대로 두고, **좌석을 조회하거나 다른 사람이 선점을 시도할 때** 만료 시각을 보고 판매 가능 상태로 인식하는 방식이다. 상태를 미리 바꾸지 않고, 상태가 필요한 순간에 만료 여부를 판정한다.

```text
18:07:00  101번 만료 시각 도달 → 아무것도 하지 않음 (status = HELD 유지)
18:09:12  사용자 C가 101번 선점 시도
          → status = HELD 이지만 held_until(18:07:00) < now(18:09:12)
          → 사실상 AVAILABLE로 판정 → C의 선점 성공
```

### 7.2 능동 만료(Active Expiration)

능동 만료는 별도의 스케줄러를 두는 방식이다. 주기적으로 돌면서 만료된 좌석을 찾아 다시 판매 가능 상태로 바꿔 주는 워커를 운영한다.

```text
[스케줄러] 매 N초/분마다
   → status = HELD 이고 held_until < now 인 좌석 검색
   → AVAILABLE로 갱신
```

능동 만료는 시간차가 생길 수 있다. 스케줄러가 도는 시각과 만료 시각이 정확히 일치하지 않기 때문이다. 스케줄러가 1분 주기라면 만료 후 최대 1분 가까이 좌석이 HELD로 남아, 그동안 선점 가능한 좌석이 선점 불가로 보인다.

### 7.3 두 전략의 비교

| 항목 | 지연 만료 | 능동 만료 |
| --- | --- | --- |
| 판정 시점 | 조회·선점 요청 시점 | 스케줄러 실행 시점 |
| 정확성 | 요청 시점의 현재 시각으로 정확히 판정 | 실행 주기만큼 시간차 발생 |
| 추가 구성 요소 | 없음(쿼리 조건만 변경) | 스케줄러·워커 운영 필요 |
| 저장된 상태 | 만료 후에도 HELD로 남을 수 있음 | 실행 후에는 실제 상태와 일치 |
| 주의점 | 조회·통계·집계에서 만료 시각을 함께 봐야 함 | 주기 설정, 중복 실행, 대량 갱신 부하 |

실무에서는 지연 만료를 사용하는 편이 좋다. 판정이 요청 시점에 이뤄지므로 결과가 보다 명확하다.

### 7.4 지연 만료의 주의점

지연 만료를 쓰면 데이터베이스에 저장된 `status` 값과 실제 의미가 다를 수 있다. 따라서 상태를 읽는 모든 곳에서 만료 시각을 함께 고려해야 한다.

| 영역 | 주의점 |
| --- | --- |
| 좌석 조회 | 좌석 배치도에 HELD로 저장된 좌석 중 만료된 것은 선택 가능으로 보여 줘야 한다 |
| 통계·집계 | "선점 중인 좌석 수"를 셀 때 `status = 'HELD'`만 보면 만료된 좌석까지 포함된다. 만료 시각도 함께 봐야 한다 |
| 비인기 좌석 | 다른 사람이 조회하거나 선점 요청을 하기 전까지 만료 시각이 그대로 남고 상태도 HELD로 유지된다. 이를 감안해야 한다 |

비인기 좌석은 지연 만료의 약점을 가장 잘 보여 준다. 아무도 찾지 않는 좌석은 판정할 기회가 오지 않으므로, 만료된 지 오래되어도 HELD로 남는다.

### 7.5 권장: 지연 만료와 능동 만료의 조합

지연 만료를 사용하더라도 스케줄러를 함께 돌리는 것을 생각해 볼 수 있으며, 둘을 적절히 조합해 사용하는 것을 권장한다.

| 역할 | 담당 전략 | 목적 |
| --- | --- | --- |
| 정확한 판정 | 지연 만료 | 좌석을 조회하거나 선점할 때 현재 상태를 만료 시각까지 보고 정확하게 판단 |
| 잔여 정리 | 능동 만료(스케줄러) | 주기적으로 남은 만료 좌석을 정리해 저장된 상태를 실제와 맞춤 |

이 조합에서 스케줄러는 **정확성을 책임지지 않는다.** 정확성은 지연 만료가 보장하고, 스케줄러는 저장된 상태를 정돈하는 보조 역할만 한다. 따라서 스케줄러가 늦게 돌거나 한 번 실패해도 좌석 판매의 정확성에는 영향이 없다.

### 7.6 지연 만료를 반영한 선점 쿼리

지연 만료를 적용하면 3.3의 선점 조건문을 변경해야 한다. 기존에는 상태가 AVAILABLE인지만 봤지만, 이제는 **HELD 상태이면서 만료 시각이 지났는지**도 조건에 포함한다.

```sql
UPDATE seats
   SET status     = 'HELD',
       hold_id    = :hold_id,
       held_by    = :user_id,
       held_until = now() + interval '7 minutes'
 WHERE seat_no = :seat_no
   AND (
         status = 'AVAILABLE'
      OR (status = 'HELD' AND held_until < now())
   )
RETURNING seat_no, hold_id, held_until;
```

이렇게 하면 HELD 상태지만 만료된 좌석도 다시 판매 가능 좌석으로 취급되어 선점할 수 있다. 판정과 갱신이 여전히 하나의 쿼리 안에 있으므로, 만료된 좌석을 두 사용자가 동시에 노려도 한 명만 성공한다.

만료 시각 비교에는 애플리케이션 서버의 시계가 아니라 데이터베이스의 `now()`를 쓰는 편이 안전하다(참고 설계). 여러 애플리케이션 서버의 시계가 조금씩 어긋나 있어도, 만료 시각의 기록과 판정이 같은 시계를 기준으로 이뤄지기 때문이다.

### 7.7 조회와 집계에 지연 만료 반영(참고 설계)

7.4의 주의점에 따라, 좌석 배치도 조회에서는 저장된 상태 대신 판정된 상태를 반환한다.

```sql
SELECT seat_no,
       CASE
         WHEN status = 'HELD' AND held_until < now() THEN 'AVAILABLE'
         ELSE status
       END AS effective_status
  FROM seats
 WHERE event_id = :event_id;
```

집계도 마찬가지로, 선점 중인 좌석은 `status = 'HELD' AND held_until >= now()` 조건으로 센다.

### 7.8 잔여 정리 스케줄러(참고 설계)

보조 스케줄러는 만료된 HELD 좌석만 골라 정리한다.

```sql
UPDATE seats
   SET status = 'AVAILABLE', hold_id = NULL, held_by = NULL, held_until = NULL
 WHERE status = 'HELD'
   AND held_until < now();
```

운영 시 고려 사항은 다음과 같다.

| 항목 | 고려 내용 |
| --- | --- |
| 조건 | 반드시 `status = 'HELD'`를 조건에 둔다. 이 조건은 9장의 PAYMENT_PENDING 좌석을 회수 대상에서 자연스럽게 제외한다 |
| 인덱스 | `(status, held_until)` 인덱스로 만료 대상을 빠르게 찾는다 |
| 대량 갱신 | 만료 대상이 많으면 일정 건수씩 나눠 갱신해 락과 부하를 분산한다 |
| 중복 실행 | 여러 인스턴스에서 동시에 돌아도 조건부 갱신이므로 결과는 같다. 다만 불필요한 경합을 줄이려면 한 인스턴스만 실행하도록 한다 |
| 주기 | 정확성은 지연 만료가 책임지므로 짧은 주기가 필수는 아니다 |

### 7.9 제기된 질문에 대한 답

| 질문 | 답 |
| --- | --- |
| 만료된 HELD 좌석은 보통 어떻게 회수하는가? | 지연 만료를 기본으로 한다. 조회·선점 시점에 `held_until`을 함께 판정해, 만료된 HELD를 판매 가능으로 취급한다 |
| 어느 시점에 HELD → AVAILABLE 갱신을 실행하는가? | 별도의 갱신 시점을 기다리지 않는다. 다음 사용자의 선점 쿼리가 판정과 선점을 동시에 수행한다 |
| 1분마다 도는 스케줄러가 필요한가? | 정확성을 위해 필수는 아니다. 다만 비인기 좌석의 잔여 HELD를 정리하고 저장 상태를 실제와 맞추기 위해 보조로 함께 두는 것을 권장한다 |

## 8. 만료와 결제 확정이 겹치는 순간

### 8.1 만료 직전에 승인된 결제

지연 만료와 스케줄러로 HELD 회수는 해결되었다. 그런데 선점 만료와 결제 완료가 겹치는 순간에는 어떻게 되는가?

```text
18:06:59  PG에서 사용자 A의 결제 승인 완료
18:07:00  101번 HELD 만료 시각 도달
18:07:00+ 인기 좌석이므로 다른 사용자들이 즉시 선점 시도 → 사용자 B 선점 성공
18:07:02  PG의 승인 결과가 우리 서버에 도착 (만료 시각 이후)
```

인기 좌석이라면 HELD가 만료되자마자 다른 사용자가 선점을 시도하고, 선점해 간다. 그런데 결제 승인은 만료 직전에 났지만, 승인 결과가 우리에게 도달한 것은 만료 시각 이후다.

```text
사용자 A  ──선점──┬──────── 결제 진행 ────────┬──────────────▶
                 │                         (PG 승인 18:06:59)
                 │                    만료 18:07:00
                 │                          │   B 선점
                 │                          ▼     │
사용자 B  ───────┼──────────────────────────────── 선점 성공 ──▶
                 │                                   ▲
PG 응답  ────────┴───────────────────────────────────┘ 18:07:02 도착
```

결과적으로 A는 결제를 완료했는데 좌석을 확보하지 못하고, B는 다른 사람이 결제한 좌석을 선점하게 된다. 중복 판매가 발생할 수 있다.

### 8.2 이 순간의 좌석은 누구의 것인가

이 시점에 101번 좌석은 A의 관점에서는 SOLD인가, B의 관점에서는 AVAILABLE인가? 두 관점이 모두 각자의 근거를 가진다.

| 관점 | 근거 | 결론 |
| --- | --- | --- |
| A(결제 측) | PG에서 결제가 승인되었다 | 이미 팔린 좌석(SOLD) |
| B(만료 측) | 선점 만료 시각이 지났다 | 판매 가능한 좌석(AVAILABLE) |

### 8.3 원인: 판정 주체의 분리

이 문제는 밀리초 단위의 시간 정밀도 문제가 아니다. 시계를 아무리 정밀하게 맞춰도 해결되지 않는다. 원인은 **만료를 판정하는 쪽과 결제를 확정하는 쪽이 서로 분리되어 있다**는 데 있다. 각자가 상대의 상태를 모른다.

| 판정 주체 | 아는 것 | 모르는 것 |
| --- | --- | --- |
| 만료 판정(우리 데이터베이스) | `held_until`이 지났다는 사실 | 그 좌석에 대해 결제가 진행 중이거나 이미 승인되었다는 사실 |
| 결제 확정(외부 PG) | 결제가 승인되었다는 사실 | 우리 쪽 선점이 이미 만료되어 다른 사용자에게 넘어갔다는 사실 |

### 8.4 타임아웃: 결과를 모르는 상태

8.1은 결제 승인 결과가 만료 시각보다 늦게 콜백으로 도착한 경우다. 결과가 아예 오지 않는 경우도 있다. PG 결제는 성공했는데 네트워크가 지연되어 타임아웃이 나는 경우다.

```text
우리 서버 ──결제 요청──▶ PG
                         │ 내부적으로 승인 성공
우리 서버 ◀──── (응답 지연) ┘
    │
    └─ 타임아웃 발생 → 결과를 받지 못함
```

PG는 외부 시스템이다. PG 내부에서는 성공했지만 우리는 상태를 받지 못했다. 우리 입장에서 타임아웃을 실패로 단정할 수는 없다. 네트워크가 지연되었을 뿐, **성공인지 실패인지 모르는 상태**다.

| 우리가 관측한 것 | 실제 PG 상태 가능성 |
| --- | --- |
| 타임아웃 | 승인 성공, 승인 실패, 아직 처리 중, 요청 미도달 |

이 상태에서 만료 시각이 되면 어떻게 해야 하는가? 타임아웃 사례를 시간 순서로 보면 다음과 같다.

```text
1. PG에서는 이미 승인이 끝났다.
2. 우리 서버에는 그 결과가 아직 도착하지 않았다.
3. 선점 만료 시각이 지났다.
4. 좌석이 회수되었다(지연 만료 또는 스케줄러).
5. 다른 사용자가 이 좌석을 다시 선점했다.
6. → 중복 판매 가능
```

### 8.5 동시 선점 방지만으로는 끝나지 않는다

3장의 조건부 업데이트는 두 사용자가 **동시에** 같은 좌석을 선점하는 것을 막았다. 그러나 중복 판매 문제는 그것으로 끝나지 않는다.

| 중복 판매 경로 | 3장으로 막히는가 |
| --- | --- |
| 두 사용자의 동시 선점 | 막힌다(조건부 업데이트) |
| 승인 결과가 만료 시각보다 늦게 도착 | 막히지 않는다 |
| 타임아웃으로 승인 결과가 아예 오지 않음 | 막히지 않는다 |

## 9. PAYMENT_PENDING: 회수해도 되는 상태와 안 되는 상태의 구분

### 9.1 상태를 서로 알게 만든다

8장의 문제는 판정하는 양쪽이 서로의 상태를 모르기 때문에 생긴다. 그렇다면 **상태를 서로 알게 만들면** 된다. 이를 위해 상태를 하나 더 둔다. **PAYMENT_PENDING(결제 대기)** 이다.

```text
AVAILABLE ──선점──▶ HELD ──결제 요청 시작──▶ PAYMENT_PENDING ──결제 확정──▶ SOLD
```

사용자는 좌석을 선점한 뒤, **만료 시각 이전에** HELD에서 PAYMENT_PENDING으로 상태를 바꿀 수 있다. PG에 결제를 요청하기 직전에 이 전이를 수행하면, "이 좌석에 대해 결제가 시작되었다"는 사실이 좌석 상태에 기록된다. 만료 판정 측이 결제 측의 상태를 알 수 있게 된 것이다.

### 9.2 만료 시점의 처리 구분

중간 과정을 두면, 만료 시각이 되었을 때 좌석이 어느 상태에 있느냐에 따라 처리가 갈린다.

| 만료 시점의 상태 | 의미 | 만료 시 처리 |
| --- | --- | --- |
| HELD | PAYMENT_PENDING으로 넘어가지 않았다. 즉 PG 자체를 호출하지 않았다 | 결제가 일어날 수 없으므로 즉시 회수 |
| PAYMENT_PENDING | 결제 요청이 시작되었다 | 회수하지 않고 결제 결과를 추가로 확인 |

7장의 만료 회수 로직(지연 만료 조건과 정리 스케줄러)은 모두 `status = 'HELD'`를 조건으로 확인한다. PAYMENT_PENDING으로 바뀐 좌석은 이 조건에 걸리지 않으므로, 만료 시각이 지나도 회수되지 않는다. 즉 HELD 만료 시각이 되었을 때 **회수해도 되는 상태와 회수하면 안 되는 상태가 구분**된다.

### 9.3 PAYMENT_PENDING 전이 쿼리(참고 설계)

HELD에서 PAYMENT_PENDING으로의 전이도 조건부 업데이트로 수행한다. 본인의 선점 건이고, 아직 만료되지 않았을 때만 전이한다.

```sql
UPDATE seats
   SET status = 'PAYMENT_PENDING'
 WHERE seat_no    = :seat_no
   AND status     = 'HELD'
   AND hold_id    = :hold_id
   AND held_until > now()
RETURNING seat_no, hold_id;
```

| 결과 | 의미 | 처리 |
| --- | --- | --- |
| 1행 | 만료 전에 결제 단계로 진입했다 | PG에 결제 요청 |
| 0행 | 이미 만료되었거나 다른 사용자에게 넘어갔다 | PG를 호출하지 않고 "선점 시간 만료" 안내 |

이 순서가 중요하다. **상태 전이에 성공한 뒤에만 PG를 호출**하므로, PG에 결제 요청이 나간 좌석은 반드시 PAYMENT_PENDING 상태다. 반대로 HELD 상태에서 만료된 좌석은 PG 호출이 한 번도 일어나지 않았음이 보장되므로 안심하고 회수할 수 있다. 8.1과 8.4의 사례에서 A의 좌석은 결제 요청 시점에 이미 PAYMENT_PENDING이므로, 18:07:00에 만료 시각이 지나도 B가 선점할 수 없다.

### 9.4 상태 전이 전체 구조

```text
                         ① 선점(선착순, 조건부 업데이트)
        ┌──────────────────────────────────────────────┐
        │                                              ▼
   AVAILABLE ◀───── ③ 취소·만료(결제 시작 전) ─────── HELD
        ▲                                              │
        │                                              │ ② 결제 요청 시작(만료 전)
        │                                              ▼
        └──── ⑤ 결제 실패·거절·미시도 확인 ──── PAYMENT_PENDING
                                                       │
                                                       │ ④ 결제 성공 확인
                                                       ▼
                                                     SOLD
```

| 상태 | 회수 가능 여부 | 다음 상태로 가는 계기 |
| --- | --- | --- |
| AVAILABLE | 해당 없음 | 선착순 선점 |
| HELD | 만료 시 회수 가능 | 결제 요청 시작, 취소, 만료 |
| PAYMENT_PENDING | 만료되어도 회수 불가 | PG 콜백, PG 상태 조회 결과 |
| SOLD | 회수 불가(환불·취소는 별도 업무 흐름) | 없음 |

## 10. PAYMENT_PENDING의 마무리

PAYMENT_PENDING은 최종적으로 SOLD 또는 AVAILABLE 중 하나로 바뀌어야 한다. 그 처리 경로는 정상 경로와 예외 경로로 나뉜다.

### 10.1 정상 경로: PG 콜백

가장 정상적이고 가장 많이 일어나는 경로는 PAYMENT_PENDING으로 전이된 뒤 사용자가 실제로 결제를 완료하고, PG로부터 콜백을 받는 것이다. 콜백에는 결제 성공, 거절 등 여러 결과값이 담긴다. 그 결과에 따라 좌석 상태를 SOLD 또는 AVAILABLE로 바꾼다.

| PG 콜백 결과 | 좌석 처리 |
| --- | --- |
| 결제 성공 | PAYMENT_PENDING → SOLD |
| 결제 거절·실패 | PAYMENT_PENDING → AVAILABLE |
| 사용자 결제 취소 | PAYMENT_PENDING → AVAILABLE |

참고 설계로서, 콜백 처리도 현재 상태와 선점 건을 조건으로 거는 조건부 업데이트로 수행한다.

```sql
UPDATE seats
   SET status = 'SOLD'
 WHERE seat_no = :seat_no
   AND status  = 'PAYMENT_PENDING'
   AND hold_id = :hold_id;
```

### 10.2 예외 경로: 오래 남은 PAYMENT_PENDING

예외 상황도 생길 수 있다. 선점 만료 시각이 한참 지났는데도 좌석이 계속 PAYMENT_PENDING에 머무는 경우다. 콜백이 유실되었거나, 8.4처럼 타임아웃이 났거나, 사용자가 결제창을 닫고 떠났을 수 있다.

일반적으로 PG사는 해당 결제 건의 진행 상태를 확인할 수 있는 **결제 상태 조회 API**를 제공한다. 이런 예외에서는 PG에 한번 조회해 보고, 그 결과에 따라 처리한다.

| PG 조회 결과 | 판단 | 좌석 처리 |
| --- | --- | --- |
| 결제 성공 | 승인 완료, 결과만 전달되지 않았다 | SOLD로 변경 |
| 결제 실패·거절 | 결제가 성립하지 않았다 | AVAILABLE로 원복 |
| 정상 진행 중 | 아직 결제가 끝나지 않았다 | PAYMENT_PENDING 유지, 이후 다시 조회 |
| 결제 시도 없음 | 승인 자체가 시도되지 않았고, 사용자가 결제창을 닫고 떠났다 | AVAILABLE로 원복 |
| 조회 실패·불명확 | 여전히 결과를 알 수 없다 | PAYMENT_PENDING 유지(10.3), 재조회 |

### 10.3 예외 처리 흐름

```text
[PAYMENT_PENDING 점검 작업]
  ├─ 대상: status = PAYMENT_PENDING 이고 held_until이 일정 시간 이상 지난 좌석
  ├─ PG 결제 상태 조회 API 호출
  │     ├─ 성공       → SOLD
  │     ├─ 실패·거절   → AVAILABLE
  │     ├─ 미시도      → AVAILABLE
  │     ├─ 진행 중     → 유지, 다음 주기에 재조회
  │     └─ 불명확      → 유지, 재조회 (몇 차례)
  └─ 재조회 한도 초과 → 운영자 확인 대상으로 분류(참고 설계)
```

일반적으로는 10.1의 정상 경로로 거의 모든 건이 마무리된다. 다만 예외가 생길 수 있으므로, 이처럼 PG를 몇 차례 조회해 보는 로직을 추가해야 할 수 있다. 이 점검 작업은 7.8의 HELD 정리 스케줄러와 대상이 다르다. HELD 정리는 데이터베이스 안에서 끝나지만, PAYMENT_PENDING 점검은 외부 PG를 조회해야 한다.

### 10.4 보수적 원칙: 중복 판매가 가장 큰 리스크다

예매 시스템에서 가장 큰 리스크는 **중복 판매**다. 두 사람이 같은 좌석을 선택하고 결제까지 성공해 버리는 경우가 가장 위험하고, 고객 응대(CS) 측면에서도 가장 어려운 경우다. 누구의 결제를 회수해야 하는지 정해야 하고, 이는 곧 고객 불만으로 이어진다.

| 선택 | 잘못되었을 때의 결과 | 피해 성격 |
| --- | --- | --- |
| 확실하지 않은 PAYMENT_PENDING을 AVAILABLE로 바꾼다 | 실제로 결제가 성공했다면 중복 판매 | 고객 불만, CS 부담, 신뢰 하락 |
| 결제 성공이 확실하지 않아도 좀 더 잡아 둔다 | 실제로 결제가 실패했다면 좌석이 잠시 팔리지 않음 | 회사의 판매 기회 일부 손실 |

따라서 확실하지 않은데 PAYMENT_PENDING을 판매 가능 상태로 바꾸는 것보다는, 결제 성공이 확실하지 않더라도 **보수적으로 조금 더 잡아 두는 것**이 비즈니스적으로 더 안전하다.

## 11. 설계의 변형과 선택 기준

### 11.1 정답이 정해진 설계는 아니다

지금까지의 좌석 선점과 만료 처리 설계는 하나의 접근법이며 정답이 정해진 것은 아니다. 규모나 특성에 따라 설계는 얼마든지 달라질 수 있다.

### 11.2 좌석과 예약의 분리

모델 자체를 분리할 수 있다. 좌석은 해당 좌석의 선점 여부만 알 수 있도록 하고, 구체적인 예약 상황은 **Reservation(예약)** 이라는 별도 모델로 분리한다.

| 모델 | 책임 |
| --- | --- |
| Seat(좌석) | 좌석이 현재 점유되어 있는지 여부 |
| Reservation(예약) | 누가, 언제, 어떤 결제 건으로, 어떤 단계에 있는지 등 구체적인 예약 상황 |

```text
Seat                         Reservation
┌─────────┬────────────┐     ┌──────────┬─────────┬───────────────┬──────────┐
│ seat_no │ occupied   │◀────│ seat_no  │ user_id │ status        │ expires  │
└─────────┴────────────┘     └──────────┴─────────┴───────────────┴──────────┘
                                         (HELD / PAYMENT_PENDING / CONFIRMED ...)
```

### 11.3 단계의 분리

5.3의 인터파크 사례처럼 좌석 선점 단계와 결제 단계를 분리할 수 있다. 결제 단계도 더 세분화해 분리하고, 단계마다 각각의 만료 시간을 둘 수 있다.

```text
[좌석 선점 단계] ── 만료 시간 1 (예: 최대 10분)
        ▼
[결제 단계] ── 만료 시간 2 (예: 7분)
   ├─ 결제 수단 선택 ── 만료 시간 2-1
   └─ 결제 승인 대기 ── 만료 시간 2-2
```

### 11.4 선택 기준: 비즈니스의 핵심 리스크

어떤 구조를 선택할지에는 다음 기준이 필요하다.

1. **해당 비즈니스의 핵심 리스크가 무엇인지** 파악한다. 예매 시스템에서는 중복 판매가 가장 큰 리스크다. 고객 불만이 엄청나기 때문이다. 반면 실제 결제가 완료되지 않았는데 좌석이 PAYMENT_PENDING으로 남아 있는 것은 회사 입장에서 약간의 손해일 수 있지만, 고객 불만으로 이어지지는 않는다.
2. 그 리스크를 해소할 수 있는 **가장 단순한 구조로 시작**한다.
3. 필요해지고, 시스템 규모가 늘어나고, 복잡성이 증가할 때 **단계를 나누거나 테이블을 나누는** 방식을 적용한다.

| 단계 | 구조 | 적용 시점 |
| --- | --- | --- |
| 시작 | 단일 좌석 테이블 + HELD·PAYMENT_PENDING 상태 + 조건부 업데이트 | 핵심 리스크(중복 판매)를 막는 최소 구조 |
| 확장 1 | 선점 단계와 결제 단계 분리, 단계별 만료 시간 | 정책이 세분화될 때 |
| 확장 2 | 좌석과 예약 모델 분리 | 예약 정보가 복잡해지고 규모가 커질 때 |

## 12. 추가로 고려할 두 가지 트레이드오프

### 12.1 선점 시간의 길이: 안전한 판매와 회전율

앞에서 선점 시간을 7분으로 가정했지만, 선점 시간을 어떻게 정할지에도 정해진 답은 없다.

| 선택 | 장점 | 단점 |
| --- | --- | --- |
| 길게 잡는다 | 안전한 판매. 사용자가 결제 중 실수하거나 문제가 생겨도 선점이 오래 유지되어 결제 완료를 보장해 준다 | 이탈한 사용자의 좌석이 오래 묶인다 |
| 짧게 잡는다 | 회전율. 중간에 떠났거나 결제를 제대로 하지 못한 사용자를 정리하고 다른 사람에게 좌석을 준다 | 결제를 진행 중인 사용자가 시간 부족으로 놓칠 수 있다 |

열차 승차권 예매는 3분이다. 3분 동안 예약을 완료하지 않거나 다른 일을 하고 있으면, 선착순으로 먼저 들어왔더라도 바로 튕겨 낸다. 회전율을 우선한 정책이다.

### 12.2 결제 결과가 불명확할 때: 보류와 해제

결제는 결과가 불명확할 때가 있다. 그래서 10장에서 PG에 재조회해야 한다고 했다. 이때도 두 가지 선택이 있다.

| 선택 | 동작 | 장점 | 단점 |
| --- | --- | --- | --- |
| 만료 보류 | 결과를 확실히 확인할 때까지 만료를 보류한다 | 안전한 판매 | 좌석이 잠시 묶인다 |
| 해제 후 환불 | 명확하지 않으면 일단 풀어서 다른 사람에게 기회를 주고, 나중에 결제 완료가 확인되면 환불로 정리한다 | 회전율 | 중복 판매 위험, 환불 처리와 고객 불만 |

### 12.3 권장 선택

예매 시스템에서 해제 후 환불은 리스크가 매우 클 수 있으므로 선택하지 않는 편이 낫다. 10.4의 원칙과 같다. 다만 어느 쪽이든 정답이 있는 것은 아니며, 서비스가 무엇을 더 중요하게 생각하느냐에 따라 달라질 수 있다.

## 13. 연관 개념과 적용 범위

### 13.1 이 도메인의 핵심 키워드

"결제하는 동안 좌석을 잡아 준다"는 요구는 다음 설계 주제와 연결된다.

| 키워드 | 본 설계에서의 의미 | 다룬 장 |
| --- | --- | --- |
| 동시성 제어 | 여러 사용자가 같은 좌석을 동시에 선점할 때 한 명만 성공시키는 것 | 3장 |
| 상태 모델 | AVAILABLE·HELD·PAYMENT_PENDING·SOLD와 그 전이 규칙 | 2, 6, 9장 |
| 만료 판정 | 리스 만료를 누가, 언제 판정할 것인가(지연·능동 만료) | 5, 7장 |
| 레이스 컨디션 | 읽기와 쓰기 사이의 틈, 만료와 결제 확정의 경합 | 3, 8장 |
| 타임아웃 | 외부 시스템의 결과를 모르는 상태와 그 처리 | 8, 10장 |
| 멱등성 | 같은 요청이 여러 번 처리되어도 결과가 한 번 처리한 것과 같아야 하는 성질 | 13.2 |

### 13.2 멱등성과의 연결(참고 설계)

결제 연동에서는 같은 결과가 여러 번 도착할 수 있다. PG가 콜백을 재전송하거나, 콜백과 상태 조회 결과가 동시에 도착하거나, 타임아웃 후 재시도가 일어난다. 본 설계의 조건부 업데이트는 이런 중복에 대해 자연스럽게 멱등하게 동작한다.

| 상황 | 동작 |
| --- | --- |
| 성공 콜백이 두 번 도착 | 첫 번째는 `status = 'PAYMENT_PENDING'` 조건을 만족해 SOLD로 바뀐다. 두 번째는 이미 SOLD이므로 0행이 되어 아무 변화가 없다 |
| 콜백과 PG 조회 결과가 동시에 도착 | 먼저 처리된 쪽만 상태를 바꾸고, 나머지는 0행으로 끝난다 |
| 다른 선점 건의 늦은 콜백 | `hold_id`가 현재 선점 건과 다르므로 좌석 상태를 바꾸지 않는다 |

이때 0행이 나왔다고 무조건 오류로 처리하지 않고, 현재 상태가 이미 원하는 결과(SOLD)인지 확인해 같은 응답을 돌려주면 된다. PG에 결제를 요청할 때도 `hold_id` 같은 고유값을 주문 식별자로 넘기면, 재시도 시 같은 결제가 두 번 승인되는 일을 막고 상태 조회의 기준으로도 쓸 수 있다.

### 13.3 다른 도메인으로의 확장

이 문제는 예매 시스템 좌석만의 문제가 아니다. **한정된 자원을 잠시 동안 잡아 두는** 모든 비즈니스와 도메인에서 같은 문제가 생길 수 있다.

| 도메인 | 선점 대상 | 대응 관계 |
| --- | --- | --- |
| 공연·스포츠 예매 | 좌석 | 본 보고서의 대상 |
| 커머스 | 재고 | 장바구니·주문 단계의 재고 임시 차감 |
| 사내 시스템 | 회의실 | 예약 확정 전 시간대 임시 점유 |
| 주차 | 주차면 | 입차 전 주차면 선점 |
| 한정판 판매 | 한정판 상품 | 결제 전 구매권 임시 확보 |

모든 경우에 같은 질문이 반복된다. 누가 자원을 얻는가(동시성), 언제 자원을 돌려놓는가(만료), 외부 확정 결과와 만료가 겹치면 어떻게 하는가(결제 대기 상태와 결과 확인)다.

## 14. 점검표

| 영역 | 점검 항목 |
| --- | --- |
| 상태 모델 | 결제 진행 구간을 AVAILABLE이나 SOLD가 아닌 별도 상태(HELD)로 표현했는가? |
| 동시성 | 좌석 선점이 상태 확인과 갱신을 한 쿼리에서 수행하는 조건부 업데이트로 이뤄지는가? |
| 결과 해석 | 조건부 업데이트의 영향받은 행 수(1행/0행)로 선점 성공과 실패를 구분하는가? |
| 스키마 | 상태, 선점 고유값(`hold_id`), 선점자(`held_by`), 만료 시각(`held_until`)을 모두 기록하는가? |
| 선점 시간 | 결제 행동, 비즈니스 정책, 시스템 특성을 근거로 선점 시간을 정했는가? |
| 만료 동작 | 만료 시각이 스스로 상태를 바꾸지 않는다는 점을 전제로 만료 로직을 별도로 두었는가? |
| 지연 만료 | 선점 조건에 `status = 'HELD' AND held_until < now()`를 포함해 만료 좌석을 판매 가능으로 취급하는가? |
| 조회·집계 | 좌석 조회와 통계에서 저장된 상태가 아니라 만료 시각까지 반영한 상태를 쓰는가? |
| 보조 스케줄러 | 비인기 좌석의 잔여 HELD를 정리하는 스케줄러가 있고, 정확성은 지연 만료가 책임지는가? |
| 시계 | 만료 시각의 기록과 판정이 같은 시계(데이터베이스 시각)를 기준으로 하는가? |
| 결제 대기 | PG 호출 전에 만료 전 조건으로 HELD → PAYMENT_PENDING 전이를 수행하는가? |
| 회수 범위 | 만료 회수 로직이 HELD만 대상으로 하고 PAYMENT_PENDING은 건드리지 않는가? |
| 콜백 처리 | PG 콜백 결과에 따라 PAYMENT_PENDING을 SOLD 또는 AVAILABLE로 조건부 갱신하는가? |
| 예외 점검 | 오래 남은 PAYMENT_PENDING을 PG 상태 조회 API로 확인하는 로직이 있는가? |
| 보수적 원칙 | 결과가 불확실한 결제 대기 좌석을 판매 가능으로 서둘러 풀지 않는가? |
| 멱등성 | 중복 콜백, 재시도, 늦게 도착한 다른 선점 건의 콜백이 상태를 잘못 바꾸지 않는가? |
| 확장 | 핵심 리스크를 막는 가장 단순한 구조에서 시작하고, 필요할 때 단계나 모델을 분리할 계획이 있는가? |

## 결론

좌석 선점은 "좌석을 잠시 잡아 둔다"는 비즈니스 요구를 상태와 규칙으로 바꾸는 문제다. 두 상태(AVAILABLE, SOLD)로는 몇 분이 걸리는 결제 진행 구간을 표현할 수 없으므로, 특정 사용자의 시간 제한 임시 점유권인 HELD를 둔다. HELD를 누가 얻을지는 상태 확인과 갱신을 한 쿼리로 묶은 원자적 조건부 갱신으로 정한다.

HELD는 분산 시스템의 리스와 같다. 리스 덕분에 사용자가 떠나거나 서버가 다운되어도 회수할 근거가 남는다. 다만 만료 시각은 기록일 뿐 스스로 상태를 바꾸지 않는다. 그래서 조회와 선점 시점에 만료 시각을 함께 판정하는 지연 만료를 기본으로 하고, 비인기 좌석에 남은 HELD를 정리하는 스케줄러를 보조로 조합한다. 1분마다 도는 스케줄러는 정확성을 위해 꼭 필요하지 않으며, 저장된 상태를 정돈하는 역할로 충분하다.

동시 선점을 막는 것만으로 중복 판매가 끝나지는 않는다. 결제 승인이 만료 이후에 도착하거나 타임아웃으로 결과를 모르는 경우, 만료를 판정하는 쪽과 결제를 확정하는 쪽은 서로의 상태를 모른다. 결제 요청을 시작하기 전에 좌석을 PAYMENT_PENDING으로 옮기면, 회수해도 되는 좌석(결제를 시작하지 않은 HELD)과 회수하면 안 되는 좌석(결제가 시작된 PAYMENT_PENDING)이 구분된다. PAYMENT_PENDING은 PG 콜백으로 마무리하고, 오래 남은 건은 PG 상태 조회로 확인한다.

설계 선택의 기준은 비즈니스의 핵심 리스크다. 예매 시스템에서 가장 큰 리스크는 중복 판매이므로, 결과가 불확실할 때는 좌석을 풀어 회전율을 얻기보다 조금 더 잡아 두는 보수적인 선택이 안전하다. 그 리스크를 막는 가장 단순한 구조에서 시작하고, 규모와 복잡성이 커질 때 단계나 모델을 나눈다. 이 접근은 좌석뿐 아니라 재고, 회의실, 주차면, 한정판 상품처럼 한정된 자원을 잠시 잡아 두는 모든 도메인에 그대로 적용된다.
