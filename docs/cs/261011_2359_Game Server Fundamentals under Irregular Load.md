# 게임 서버의 기초 이론: 불규칙한 부하, 데이터 접근, 완료 통지

## 요약

게임 서버에서 기초 이론을 검증한다는 말은 용어를 맞히는 시험이 아니다. 네트워크와 소켓, 멀티스레드, 불규칙하게 몰리는 부하, 디자인 패턴으로 읽는 코드, RDBMS, 그리고 시스템 프로그래밍의 완료 통지까지를 한 구조로 설명할 수 있는지를 본다. 게임 서비스에는 평시와 피크의 격차가 크고, 그 피크는 일정표대로 오지 않는다. 접속이 한 번에 몰리면 스레드가 락에 줄 서고, 소켓 버퍼가 차고, DB 쿼리가 게임 루프를 붙잡는다. 이 순간을 버티는 도구가 락프리 큐이고, Windows에서는 I/O 완료 포트(IOCP)와 Registered I/O(RIO)이며, Linux에서는 epoll이다. 셋은 모두 "많은 연결을 적은 스레드로 본다"는 목표는 같고, 커널이 알려 주는 사건의 종류가 다르다.

C와 C++ 서버가 관계형 데이터베이스를 만질 때 자주 서는 자리는 ODBC다. 자바의 JDBC, MyBatis, JPA보다 낮다. 핸들, 바인딩, 진단 레코드, 트랜잭션을 호출하는 쪽이 직접 다룬다. 클린 코드와 디자인 패턴은 이 층 위에 이름을 붙이는 일이다. 세션의 상태, 패킷의 분기, DB로 나가는 작업이 한 클래스에 엉키면 부하가 몰린 날 고칠 자리가 없다.

## 1. 기초 이론을 검증한다는 말

검증은 구현 경험을 말로 다시 푸는 능력이다. 소켓을 열어 봤는지, 스레드를 붙여 봤는지, 쿼리를 날려 봤는지만으로는 부족하다. 부하가 평시의 몇 배로 붙었을 때 어디가 먼저 막히는지, 그 막을 곳을 어떤 동기화와 어떤 I/O 모델로 피하는지, 그 선택을 다른 사람이 읽게 코드로 남겼는지를 설명해야 한다.

층은 아래에서 위로 쌓인다.

```text
불규칙한 접속과 패킷
  → 소켓과 메시지 경계
    → 스레드와 공유 상태
      → 락 또는 락프리 큐
        → IOCP / RIO / epoll 중 하나의 완료·준비 통지
          → 그 통지 밖에서 도는 DB 작업 (ODBC)
            → 이 경계를 패턴과 읽기 쉬운 코드로 고정
```

위를 모르면 아래의 API 이름은 암기표가 된다. IOCP를 호출 순서대로 외워도, 완료 핸들러 안에서 SQL을 동기로 실행하면 포트가 지켜 주려던 스레드 수가 무너진다. 기초를 안다는 것은 이 연결을 말로 닫을 수 있다는 뜻이다.

## 2. 네트워크와 소켓

소켓은 프로세스와 커널 네트워크 스택 사이의 핸들이다. 게임 서버가 주로 보는 것은 TCP와 UDP다. TCP는 바이트 스트림이다. `recv`가 돌아온 길이는 클라이언트가 `send`한 메시지 하나와 일치하지 않는다. 절반만 올 수도 있고, 두 메시지가 한 번에 올 수도 있다. 그래서 길이 헤더나 구분자로 프레임을 짜고, 소켓마다 수신 버퍼를 두어 다음 패킷이 완성될 때까지 이어 붙인다. UDP는 데이터그램이라 한 수신이 한 패킷인 경우가 많지만, 순서가 바뀌고 사라진다. 로그인과 거래처럼 잃어버리면 안 되는 경로는 TCP에 두고, 자주 죽고 새로 보내도 되는 위치 갱신은 UDP에 두는 식으로 갈라진다. 갈라진 뒤에도 서버는 두 입력을 같은 세션 상태로 합쳐야 한다.

블로킹 소켓에 연결마다 스레드를 두면 코드는 직선으로 읽힌다. `accept`하고 `recv`가 돌아올 때까지 잔다. 접속이 수천을 넘으면 스레드가 그 수만큼 생기고, 대부분은 커널 안에서 잔다. 깨울 때마다 스택을 바꾸고, 캐시가 식는다. 게임 서버는 보통 논블로킹 소켓으로 바꾼 뒤, 사건이 있는 소켓만 깨우는 다중화로 간다. Windows에서 그 사건이 "걸어 둔 수신이 끝났다"이면 IOCP나 RIO이고, Linux에서 그 사건이 "지금 읽으면 잠들지 않는다"이면 epoll이다.

불규칙한 부하는 이 선택 이전에 이미 소켓 옵션과 백로그를 건드린다. 점검이 끝나고, 이벤트가 시작하고, 패치 직후 로그인이 몰리면 `listen` 백로그를 넘는 SYN이 거절된다. 붙어 있는 연결은 서버가 `recv`를 제때 못 하면 수신 윈도우가 닫히고, 클라이언트 송신은 멈춘다. Nagle 알고리즘은 작은 패킷을 모아 보내 처리량을 올리지만, 조작 패킷의 지연을 키운다. 지연이 비싼 세션은 `TCP_NODELAY`로 그 뭉침을 끈다. 처리량이 비싼 대량 전송은 그대로 둔다. 옵션 하나의 이유까지 말할 수 있어야 소켓을 써 본 경험이다.

## 3. 멀티스레드와 불규칙한 부하

게임 서비스의 트래픽은 평균으로 설계하면 틀린다. 웹 요청도 출퇴근에 몰리지만, 게임은 그 몰림이 더 날카롭다. 월드 이벤트가 열리는 초, 서버 오픈, 접속 보상, 핫타임. 평시에는 코어가 한가하고, 그 몇 분 동안 로그인과 패킷과 쿼리가 같이 뛴다. 큐잉 지연은 사용률이 1에 가까워질수록 가파르게 늘어나므로, 평균 CPU가 30%라는 그래프는 피크의 대기열을 숨긴다. 피크를 평균 장비로 견디게 하려면 일을 나누고, 막을 수 없는 입구는 버리고, 게임 틱과 무관한 대기는 다른 스레드로 보낸다.

멀티스레드는 그 분리다. 흔히 받는 I/O 스레드와 월드를 진행하는 로직 스레드를 나눈다. I/O 스레드는 소켓 완료만 보고 패킷을 큐에 넣는다. 로직 스레드는 틱마다 큐를 비우고 상태를 고친다. DB 스레드는 쿼리 결과를 다른 큐로 돌려준다. 공유되는 것은 세션 맵, 큐, 객체 풀이다. 뮤텍스로 이 셋을 감싸면 정확해지기 쉽다. 피크에서 그 뮤텍스가 하나가 되면 모든 스레드가 같은 줄에 선다. 락 호송(convoy)이다. 우선순위가 낮은 스레드가 락을 쥔 채 밀리면 높은 쪽도 같이 멈춘다.

그래서 스레드를 안다는 것은 API를 호출해 봤다는 말이 아니다. 다음을 구분하는 일이다.

| 상황 | 맞는 질문 |
| --- | --- |
| 데이터 경쟁 | 두 스레드가 같은 세션 필드를 락 없이 쓰는가 |
| 락의 범위 | 락을 쥔 채 소켓이나 DB를 기다리는가 |
| 일관성 | 큐에서 뺀 패킷이 이미 끊긴 세션을 가리키는가 |
| 순서 | 같은 세션의 패킷이 로직 스레드 밖에서 순서가 바뀌는가 |
| 폭주 | 수신이 로직보다 빠를 때 큐를 버릴 기준이 있는가 |

같은 세션의 패킷 순서는 보통 로직 스레드 하나로 모아서 지킨다. I/O 스레드가 세션 객체를 직접 고치면 순서가 깨진다. 큐는 그 경계의 완충이다. 완충이 뮤텍스이면 피크에서 다시 한 줄이 된다. 그다음 질문이 락프리 큐다.

## 4. 디자인 패턴과 클린 코드

패턴은 장식이 아니다. 부하와 스레드 경계를 코드에서 보이게 하는 이름이다. 논할 수 있다는 말은 이름을 열거하는 일이 아니라, 왜 그 경계를 그 패턴으로 닫았는지와 그 비용이 무엇인지를 말하는 일이다.

세션은 상태가 있다. 핸드셰이크, 인증, 월드 입장, 플레이, 종료. 이 전이를 `if`가 흩어진 정수로 두면, 종료된 세션에 패킷을 처리하는 구멍이 리뷰에서 안 보인다. State로 전이를 모으면 허용되지 않은 입력은 한 자리에서 거절된다. 패킷 종류가 늘수록 한 함수의 `switch`는 읽히지 않는다. 핸들러를 타입이나 아이디로 찾는 표는 Command나 Strategy에 가깝다. 가상 호출 한 번의 비용과, 리뷰어가 핸들러 하나를 따로 읽을 수 있는 이득을 같이 말해야 한다. 객체 풀은 피크에서 할당을 없애려고 쓴다. 풀에서 뺀 객체를 다른 스레드가 아직 읽는 동안 반환하면, 패턴은 성능 기법이 아니라 사용 후 해제 버그의 공장이 된다.

SOLID를 이 서버에 대면 질문이 구체적이 된다. 세션 클래스가 소켓 버퍼와 SQL 문자열과 인벤토리 규칙을 같이 가지면 변경 이유가 셋이다. 네트워크 형식이 바뀔 때마다 게임 규칙이 다시 컴파일된다. 단일 책임은 그 셋을 가르라는 요구다. 의존 역전은 로직 스레드가 ODBC 핸들을 직접 잡지 않게 한다. 로직은 "이 쿼리를 나중에 실행하라"는 작업만 큐에 넣는다. DB 스레드가 ODBC를 안다. 이렇게 나누지 않으면 클린 코드는 이름 정렬이고, 피크 때의 구조는 그대로다.

남의 코드를 읽는 일은 같은 요구의 반대 방향이다. 레거시 서버는 이미 이 경계가 무너진 채로 돌아간다. 읽는 사람은 락을 쥔 채 호출되는 함수, 세션을 삭제하는 스레드, 패킷을 조립하다 만 버퍼를 찾아야 한다. 읽기 쉬운 코드를 쓴다는 것은 다음 사람이 그 검색을 짧게 끝내게 둔다는 것이다. 패턴을 논하는 자리는 리뷰다. "여기 Strategy를 썼다"가 아니라 "이 핸들러는 I/O 스레드에서 호출되면 안 된다"가 리뷰 문장이다.

## 5. RDBMS와 ODBC

게임 서버의 영속 데이터는 계정, 캐릭터, 인벤토리, 결제, 로그다. 관계는 있고, 트랜잭션이 필요하고, 그래서 RDBMS가 남는다. 경험은 접속 문자열을 붙여 봤다는 수준을 넘어야 한다. 격리 수준, 인덱스가 없을 때의 잠금, 트랜잭션을 연 채 게임 틱을 기다리는 일이 서버를 어떻게 세우는지까지다.

C와 C++에서 그 접속의 흔한 바닥은 ODBC다. Open Database Connectivity는 드라이버 관리자와 DBMS별 드라이버 사이의 C API다. 애플리케이션은 SQL Server인지 MySQL인지보다 핸들 셋에 의존한다.

```text
환경 핸들(SQLHENV)  →  연결 핸들(SQLHDBC)  →  문장 핸들(SQLHSTMT)
SQLSetEnvAttr으로 버전을 맞춘다
SQLDriverConnect로 붙는다
SQLPrepare로 문장을 준비한다
SQLBindParameter로 입력 파라미터를 묶는다
SQLExecute로 실행한다
SQLBindCol / SQLFetch로 행을 꺼낸다
실패하면 SQLGetDiagRec으로 SQLSTATE와 메시지를 읽는다
SQLEndTran으로 커밋하거나 롤백한다
```

자바 진영의 JDBC 위에 올라간 MyBatis나 JPA는 매핑과 세션과 캐시를 대신 쥔다. ODBC는 그 층을 기본으로 제공하지 않는다. 컬럼을 어느 버퍼에 받을지, 문자열 길이가 잘리면 무엇을 반환하는지, 진단 레코드를 몇 개나 읽어야 하는지, 문장 핸들을 재사용할지를 호출하는 코드가 안다. 사내에 이 호출을 감싼 래퍼가 있는 경우가 많다. 래퍼가 있어도 바닥이 ODBC이면, 지연과 에러와 커넥션 수명은 그 API의 규칙을 따른다.

게임 루프와의 결합이 핵심이다. `SQLExecute`가 디스크나 락을 기다리면 호출한 스레드가 잔다. 그 스레드가 IOCP 워커이거나 월드 틱이면, 소켓 완료가 밀리고 월드가 멈춘다. 그래서 쿼리는 작업 객체로 만들어 DB 스레드 풀에 넘긴다. 넘기는 통로가 3절의 큐다. 결과는 다시 로직 스레드의 큐로 돌아와, 세션이 아직 살아 있을 때만 적용한다. 쿼리를 기다리는 동안 세션이 끊기면 결과를 버려야 한다. 이 경쟁을 락프리 큐만으로 해결했다고 말하면 안 된다. 큐는 전달을 맡고, 세션의 수명 검사는 로직 스레드가 맡는다.

커넥션 풀은 피크 때 로그인이 동시에 `SQLDriverConnect`를 하지 않게 한다. 풀 크기보다 많은 쿼리가 오면 큐에서 기다린다. 풀을 무한히 키우면 DB의 최대 연결에서 거절된다. 경험으로 말할 내용는 풀의 상한, 문장 준비의 재사용, 트랜잭션 안에서 게임 로직을 호출하지 않는 규칙, 느린 쿼리 하나가 풀 전체를 점유하는 모습이다.

## 6. 락프리 큐를 만든다는 말

락프리 큐를 만들라는 요구는 헤더를 포함하라는 뜻이 아니다. 뮤텍스 없이 넣고 빼는 구조를 직접 짜 보고, 그 구조가 깨지는 메모리 순서를 봐야 한다. 게임 서버에서 가장 흔한 형태는 여러 I/O 스레드가 넣고, 로직 스레드 하나가 빼는 큐다. 그 전에 생산자 하나와 소비자 하나의 링을 끝까지 맞게 만들 수 있어야 한다. 하나가 맞으면, 생산자를 늘릴 때 무엇이 추가로 깨지는지가 보인다.

카운터를 인덱스로 쓰는 링은 가득 참과 비어 있음을 `head == tail` 하나로 구분하지 않아도 된다. 생산자는 `tail`만 올리고, 소비자는 `head`만 올린다. 용량은 2의 거듭제곱으로 두면 마스크로 자리를 계산한다.

```cpp
bool push(T v) {
    auto t = tail.load(std::memory_order_relaxed);
    auto h = head.load(std::memory_order_acquire);
    if (t - h == Capacity) return false;      // 가득 참
    slot[t & (Capacity - 1)] = std::move(v);  // 아직 공개하지 않은 칸
    tail.store(t + 1, std::memory_order_release);
    return true;
}

bool pop(T& out) {
    auto h = head.load(std::memory_order_relaxed);
    auto t = tail.load(std::memory_order_acquire);
    if (h == t) return false;                 // 비어 있음
    out = std::move(slot[h & (Capacity - 1)]);
    head.store(h + 1, std::memory_order_release);
    return true;
}
```

`release` 저장은 그 저장 이전의 버퍼 쓰기가 소비자의 `acquire` 로드 이후에 보이게 한다. 둘 다 `relaxed`이면 소비자는 `tail`이 오른 것을 보고도 아직 쓰이지 않은 칸을 읽을 수 있다. 이 버그는 평시에는 거의 안 나고, 코어가 바빠 재배치가 드러나는 피크에서 난다. 만들어 보라는 이유다.

이 링은 생산자가 둘이면 깨진다. 두 생산자가 같은 `tail`을 읽고 같은 칸에 쓴다. 여러 생산자는 그 칸의 소유를 CAS로 다퉈야 한다. CAS 큐는 ABA를 만난다. 노드 주소가 빠져나갔다가 같은 주소로 재사용되면 CAS는 성공하고 링크는 틀린 노드를 가리킨다. 주소를 함부로 재사용하지 못하게 하는 에폭이나 해저드 포인터가 따라온다. 그걸 없이 "락프리"라고 부른 큐는 뮤텍스 큐보다 위험하다. 서버 패킷 경로의 현실적인 선택은 둘이다. I/O 스레드마다 SPSC 링을 두고 로직 스레드가 여러 링을 폴링하거나, 검증된 MPSC 큐를 쓴다. 어느 쪽이든 가득 차면 정책을 정해야 한다. 로그인 폭주에서 무한히 쌓으면 메모리가 먼저 죽는다. 오래된 이동 패킷은 버리고, 거래 패킷은 연결을 끊는 식으로 종류를 나눈다.

락프리는 락이 없다는 뜻이 아니다. 진행 보장의 이름이다. 어떤 스레드가 스케줄에서 빠져도 다른 스레드의 연산이 유한 번에 끝난다는 쪽에 가깝다. 대기가 전혀 없다는 대기 부재(wait-free)와는 다르다. 이 차이를 말하면서 링의 `release`와 `acquire`를 가리킬 수 있으면, 큐를 만들었다는 문장이 성립한다.

## 7. Windows의 기본: IOCP

Windows에서 다수 소켓의 기본 모델은 I/O 완료 포트다. 프로액터다. 애플리케이션이 수신이나 송신을 먼저 걸어 두고, 커널이 그 연산이 끝났다고 완료 패킷을 포트에 넣는다. 워커는 `GetQueuedCompletionStatus`로 그 패킷을 받는다. 패킷에는 몇 바이트가 끝났는지, 어느 `OVERLAPPED`인지가 들어 있다. "지금 읽어도 된다"가 아니라 "걸어 둔 읽기가 끝났다"이다.

최소 순서는 다음과 같다.

```text
CreateIoCompletionPort로 포트를 만든다
WSASocket에 WSA_FLAG_OVERLAPPED를 준다
소켓을 포트에 묶으며 완료 키로 세션 식별자를 넘긴다
WSARecv에 OVERLAPPED와 버퍼를 채워 수신을 걸어 둔다
워커가 GetQueuedCompletionStatus에서 깨어난다
바이트 수를 프레임 조립기에 넘긴다
같은 소켓에 WSARecv를 다시 건다
```

다시 걸지 않으면 그 소켓의 완료는 거기서 멈춘다. 커널은 버퍼가 게시되어 있을 때만 받아 둔 데이터를 완료로 넘긴다. 피크에서 재게시가 늦으면 수신 윈도우가 닫힌다.

`CreateIoCompletionPort`의 동시 실행 스레드 수는 보통 코어 수에 맞춘다. 워커가 완료를 처리하다 잠들면 포트는 다른 스레드를 풀어 그 수를 채우려 한다. 그래서 완료 핸들러 안의 동기 ODBC, 파일 잠금, 긴 락은 워커를 늘리는 버그다. DB는 5절처럼 큐 밖으로 나간다. 핸들러가 하는 일은 버퍼를 프레임으로 자르고 로직 큐에 넣는 것까지다.

완료 키와 `OVERLAPPED`의 수명을 착각하면 풀에서 이미 반환한 세션을 워커가 만진다. 소켓을 닫아도 이미 걸린 수신의 완료는 나중에 도착한다. 그 완료를 받을 때까지 세션과 버퍼를 살리거나, 닫힘을 표시해 늦게 온 완료를 무시해야 한다. IOCP를 기본으로 안다는 것은 `GetQueuedCompletionStatus`의 인자 순서가 아니라 이 수명이다.

## 8. Registered I/O

RIO는 Windows 8과 Windows Server 2012부터 들어온 Winsock 확장이다. IOCP와 같이 프로액터지만, 버퍼와 요청 큐를 미리 커널에 등록해 연산마다 치르는 전환과 복사를 줄이려 한다. 작은 패킷이 매우 많은 게임 서버를 염두에 둔 경로다. IOCP를 대체하는 다른 운영체제가 아니다. 같은 Windows 안에서 더 낮은 오버헤드로 가는 선택이다.

```text
RIOCreateCompletionQueue로 완료 큐를 만든다
RIORegisterBuffer로 송수신에 쓸 메모리를 등록한다
소켓마다 RIOCreateRequestQueue로 요청 큐를 만든다
RIOReceive / RIOSend로 등록된 버퍼의 구간을 걸어 둔다
RIODequeueCompletion으로 끝난 연산을 직접 꺼낸다
필요하면 RIONotify로 이벤트나 IOCP에 깨움을 건다
```

완료를 보는 방법이 둘로 갈린다. 게임 루프가 이미 틱으로 돈다면 완료 큐를 그 틱에서 폴링한다. 깨어나는 스레드가 필요 없다. 사건이 올 때만 깨우고 싶으면 완료 큐에 알림을 걸고, 그 알림을 이벤트나 IOCP에 연결한다. 알림을 IOCP에 연결해도 데이터 경로는 등록된 버퍼다. 클래식 IOCP처럼 호출마다 새 버퍼 포인터를 넘기는 구조와 다르다.

등록된 버퍼는 완료가 오기 전에 해제하거나 다른 용도로 덮으면 안 된다. 슬롯이 떨어지면 수신을 더 걸 수 없다. IOCP에서 재게시를 잊는 버그와 같은 가족이다. RIO는 그 슬롯을 애플리케이션이 링처럼 직접 센다. 만들 일이 락프리 큐와 닮아 있다. 생산자는 커널이고 소비자는 게임 루프이며, 칸을 비우기 전에 다음 수신을 걸어야 한다.

IOCP를 기본으로 두고 RIO를 같이 보라는 말은 순서가 있다. 완료의 수명, 워커가 잠들면 안 되는 이유, 다시 걸어야 스트림이 산다는 이유를 IOCP에서 배운 뒤에야 RIO의 등록 버퍼가 같은 문제의 더 싼 형태인지 보인다. RIO만 따로 외우면 폴링 루프와 알림 루프를 고르는 이유가 사라진다.

## 9. Linux의 epoll, 그리고 셋의 차이

epoll은 Linux의 준비 통지다. 리액터다. `epoll_wait`가 돌아가는 이유는 걸어 둔 수신이 끝나서가 아니다. 그 fd에 대해 `recv`를 호출하면 당장에는 잠들지 않을 가능성이 생겼기 때문이다. 바이트 수는 `recv`가 돌아올 때 정해진다. 덜 오면 다시 기다린다. TCP 프레임 조립은 여기서도 필요하고, "완료된 바이트 수"가 커널 패킷에 실려 오지 않는다는 점만 IOCP와 다르다.

```text
epoll_create1로 관심 목록을 만든다
논블로킹 소켓을 epoll_ctl로 추가한다
epoll_wait가 준비된 fd 목록을 준다
EPOLLIN이면 recv로 비운다
EPOLLOUT이면 송신 버퍼에 쌓인 것을 send한다
레벨 트리거이면 조건이 참인 동안 다시 알려 준다
엣지 트리거이면 상태가 바뀐 순간만 알려 주므로 EAGAIN이 나올 때까지 비운다
```

엣지 트리거에서 한 번만 `recv`하고 돌아가면, 커널 버퍼에 데이터가 남아 있어도 다음 가장자리가 오기 전까지 깨워 주지 않는다. 피크에서 패킷이 붙어 들어오면 이 실수가 바로 멈춤으로 보인다. 레벨 트리거는 그 실수를 늦게 드러내고, 대신 처리할 준비도 되기 전에 자주 깨울 수 있다. 어느 쪽을 골랐는지와 `EAGAIN` 처리가 epoll을 아는 기준이다.

같은 목적을 놓고 셋을 비교하면 다음과 같다.

| | IOCP | RIO | epoll |
| --- | --- | --- | --- |
| 운영체제 | Windows | Windows 8 이후의 Windows | Linux |
| 모델 | 프로액터 | 프로액터. 버퍼를 미리 등록 | 리액터 |
| 통지의 내용 | 걸어 둔 `WSARecv`/`WSASend`가 끝났고, 바이트 수가 있다 | 등록된 요청이 끝났고, 완료 큐에 항목이 있다 | fd가 읽거나 쓸 수 있는 상태로 바뀌었다 |
| 버퍼 | 호출마다 `OVERLAPPED`와 버퍼를 넘긴다 | 등록해 고정한 구간의 슬롯을 돌린다 | 깨어난 뒤 사용자 버퍼로 `recv`/`send` 한다 |
| 누가 꺼내는가 | `GetQueuedCompletionStatus`를 도는 워커 | 틱에서 `RIODequeueCompletion`, 또는 이벤트·IOCP 알림 | `epoll_wait` 이후 그 자리에서 `recv` |
| 피크에서 깨지는 곳 | 핸들러가 잠들거나 수신을 다시 걸지 않음 | 슬롯 고갈, 완료 전 버퍼 해제 | 엣지 트리거에서 `EAGAIN`까지 비우지 않음 |
| 스레드와의 관계 | 동시 실행 수를 코어에 맞추고, 핸들러는 큐에 넣기만 한다 | 게임 스레드가 직접 폴링하면 깨우기 비용이 없다 | 대기 스레드가 준비된 fd만 처리한다 |

Windows 진영의 기본이 IOCP이고, 그 위의 저비용 경로가 RIO다. Linux 진영에서 같은 질문에 먼저 나오는 답이 epoll이다. "차이"는 성능 우열이 아니다. 커널이 완료를 통지하는지, 준비를 통지하는지다. 완료 통지에서는 버퍼가 연산이 끝나기 전에 살아 있어야 하고 바이트 수가 패킷에 있다. 준비 통지에서는 깨어난 뒤에 읽으며, 읽기 전에 버퍼를 커널에 맡겨 두지 않는다. 서버를 Windows에 둘지 Linux에 둘지에 따라 스레드가 기다리는 API가 바뀌고, 세션과 버퍼의 수명 규칙이 같이 바뀐다. 로직 스레드로 패킷을 넘기는 큐와, 그 큐 밖에서 DB를 처리하는 규칙은 어느 쪽에서나 같다.

Linux 5.1 이후의 io_uring은 제출 큐와 완료 큐, 등록 버퍼를 가져 RIO에 더 가깝다. epoll을 Linux의 유일한 I/O 모델로 외우면 이 경로가 빠진다. 다만 기존 게임 서버와 커널 호환에서 아직 설명의 기준점은 epoll이다. 셋을 비교한 뒤 io_uring을 "Linux의 완료 큐"로 한 문장 더 말할 수 있으면 충분하다.

## 10. 이 층이 한 서버에서 만나는 순서

로그인 폭주를 예로 층을 통과시키면 검증 질문이 닫힌다.

```text
접속이 평시의 여러 배로 들어온다
listen 백로그와 accept 루프가 먼저 받는다
소켓은 논블로킹으로 IOCP, RIO, epoll 중 하나에 등록된다
완료 또는 준비 통지가 워커를 깨운다
워커는 프레임만 조립하고 락프리 큐에 넣는다
워커는 SQL을 호출하지 않는다
로직 스레드는 큐를 비우며 세션 상태를 전이한다
인증 쿼리는 DB 스레드의 ODBC 풀로 넘어간다
결과가 로직 큐로 돌아왔을 때 세션이 살아 있으면 적용한다
큐가 가득 차면 종류별로 버리거나 연결을 닫는다
```

이 순서를 코드에서 읽으려면 패턴이 경계를 드러내야 한다. 세션 상태, 패킷 핸들러, 쿼리 작업이 한 함수에 있으면 위의 화살표가 검색되지 않는다. 클린 코드는 화살표를 파일 경계로 남기는 일이다.

## 11. 설계를 닫은 뒤에 구현으로 넘긴다

위 층은 구현하면서 발견하기에는 비싸다. 모호한 채로 코드를 생성하면 빈칸을 메우는 쪽이 버퍼 수명과 실패 정책을 정한다. 그 정책은 피크에서야 틀린 것이 드러난다. 그래서 구현 전에 요소와 절차와 실패 시의 행동을 문장으로 닫는다. 요소는 테스트 단위와 같고, 절차는 무엇을 먼저 만들지의 순서다. 화면이 있는 도구라면 화면 설계서 대신 동작하는 UI를 먼저 두어 합의의 대상으로 삼을 수 있다. 성능과 보안은 기능 목록 옆의 비기능 요구로 같이 적는다. 적히지 않은 요구는 구현 중에 즉석 결정이 된다.

운영 도구의 사례가 이 순서를 보여 준다. 서버 로그를 보고, 고치고, 빌드하고, JAR을 올리고, 프로세스를 재시작하는 일이 사람 손의 복붙으로만 이어지면, 그 루프 자체가 불규칙한 장애에 대한 대응 속도를 제한한다. 자동화하더라도 한 단계라도 실패하면 멈추고 사람이 로그를 본 뒤에 다음으로 간다. 자동 복구를 처음부터 넣으면 실패한 이유를 덮는 코드가 도구의 본체가 된다. 혼자 쓰는 도구라면 절차를 규칙 언어로 일반화할 이유도 없다. 언어와 런타임을 만드는 비용은 반복 몇 번의 자동화와 자릿수가 다르다. 정해진 순서는 그대로 코드에 둔다.

손작업에 필요한 능력은 SSH, SFTP, 로컬 프로세스, 파일이다. 브라우저 안의 자바스크립트는 그 호출을 열 수 없다. 페이지를 그리는 웹뷰와, 운영체제 API를 호출하는 네이티브 프로세스를 나누고 IPC로 잇는다. Tauri는 UI를 웹 기술로 두고 코어를 Rust로 두며, Windows에서는 시스템 WebView2가 Edge로 화면을 그린다. Electron처럼 Chromium을 앱에 넣지 않는다. 자바스크립트의 `invoke`가 네이티브 함수로 간다. 이 코어는 HTTP로 떠 있는 웹 서버가 아니다. 소켓과 파일을 여는 프로세스다. SSH와 SFTP는 Rust 크레이트로 이미 있으므로 프로토콜을 직접 구현할 목록에서 빠진다. 가능 여부를 먼저 확인하고 지우는 일이 설계의 산출물이다.

모델에게 이 설계를 맡길 때도 자리는 나뉜다. 한 대화는 요소와 실패 정책을 정하는 회의이고, 코드 생성은 그 문서가 끝난 뒤에 한다. 모호하면 구현하지 말고 되묻게 한다. 관심사에 맞장구치는 추천, 예를 들어 오래된 GUI 툴킷으로도 된다는 제안은 요구와 따로 둔다. 유일한 선택인지 묻고, 범위가 커지는 제안은 거절 이유를 문장으로 남긴다. 긴 응답은 읽는다. 합의는 문서에 두고, 대화 로그 전체를 다음 실행의 입력으로 다시 넣지 않는다. 로그는 닫힌 논쟁을 다시 연다. 실행으로 확인할 때는 프로세스가 뜬 것과, 명세에 있던 나머지 기능이 있는 것을 다른 칸에 적는다.

## 12. 점검표

| 영역 | 확인 |
| --- | --- |
| 부하 | 평시와 피크의 격차를 평균 CPU로 숨기지 않았는가 |
| 소켓 | TCP를 스트림으로 보고 프레임을 조립하는가. 백로그와 `TCP_NODELAY`의 이유가 있는가 |
| 스레드 | I/O, 로직, DB가 나뉘고, 락을 쥔 채 기다리는 경로가 없는가 |
| 큐 | SPSC의 `acquire`/`release`를 설명할 수 있는가. 생산자가 둘이면 무엇이 깨지는가 |
| 가득 참 | 패킷 종류별로 버릴 것과 끊을 것이 나뉘는가 |
| IOCP | 수신을 다시 거는가. 완료 핸들러가 동기 SQL을 호출하지 않는가. 닫힌 소켓의 늦은 완료를 무시하는가 |
| RIO | 등록 버퍼의 수명과 슬롯 고갈을 아는가. 폴링과 알림 중 무엇을 고르는지 말할 수 있는가 |
| epoll | 준비가 완료와 다르다는 것을 말할 수 있는가. 엣지 트리거면 `EAGAIN`까지 비우는가 |
| 차이 | 완료 통지와 준비 통지에서 버퍼를 누가 언제까지 소유하는지 말할 수 있는가 |
| ODBC | 핸들 셋과 진단 레코드와 풀의 상한을 알고, 쿼리가 어느 스레드에서 도는가 |
| 패턴 | 세션 상태, 패킷 분기, DB 작업이 서로 다른 변경 이유로 나뉘는가 |
| 설계 | 실패 시 멈출지 복구할지, 직접 만들 것과 라이브러리에 맡길 것이 문장으로 남았는가 |

## 결론

게임 서버의 기초는 네트워크, 스레드, 데이터베이스, 운영체제 I/O를 따로 외우는 과목이 아니다. 접속이 불규칙하게 몰릴 때 소켓이 스트림으로 들어오고, 그 스트림을 끝내는 통지가 Windows에서는 IOCP와 RIO, Linux에서는 epoll이며, 그 통지를 받은 스레드는 락프리 큐까지만 닿고, SQL은 ODBC를 아는 DB 스레드가 나중에 처리하며, 그 경계가 패턴으로 읽혀야 한다. 완료와 준비를 구분하지 못하면 버퍼를 언제 해제해도 되는지가 바뀌는데도 같은 코드 모양을 유지하게 된다. 큐의 메모리 순서를 만들지 않으면 평시에만 맞는 서버가 된다. 클린 코드는 그 서버를 다음 사람이 피크의 경로를 따라 읽을 수 있게 경계를 남기는 일이다.
