## 1. 채팅 시스템이란

### 개념

채팅 시스템은 “메시지를 저장하는 DB 앱”이 아닙니다. **연결이 살아있는 사용자에게는 즉시 이벤트를 밀어 주고**, **연결이 없는 사용자에게는 푸시로 깨우고**, **그 사이 모든 메시지는 영구(또는 장기) 저장**하는 실시간 분산 시스템입니다.

큰 축은 둘입니다.

| 축 | 질문 | 이 교재에서의 위치 |
|---|---|---|
| **전달(Delivery)** | 누가 어느 서버에 붙어 있는가? 그 서버까지 이벤트를 어떻게 가져가나? | §5–§14 |
| **저장(Persistence)** | 메시지·방·멤버십을 어디에, 어떤 키로 쌓고 읽을까? | §15–§22 |

한 줄로:

> 채팅 = **세션 라우팅(실시간)** + **영속 저장(이력)** + **오프라인 푸시(깨우기)**

### 왜 “일반 REST API”와 다른가

| 일반 API | 채팅 |
|---|---|
| 요청 → 응답 한 번 | 장수명 연결 위에서 **서버가 먼저** 이벤트를 push |
| 상태가 서버에 거의 없음 | **어느 서버에 누가 붙어 있는지**가 핵심 상태 |
| 스케일아웃이 비교적 단순 | 연결 상태가 노드에 묶여 **크로스 서버 전달**이 생김 |
| 실패 시 클라이언트가 재시도 | 실패 시 **푸시 폴백·세션 정리·재전달**이 얽힘 |

### 체크포인트

- [ ] 채팅을 “DB CRUD + 폴링”으로만 설명하지 않고, 세션·릴레이·푸시를 말할 수 있는지
- [ ] 전달 계층과 저장 계층을 분리해서 설계해야 하는 이유를 한 문장으로

## 2. 당근 채팅의 도메인 특징

### 개념

발표 시점 기준(스크립트)으로 보면 대략 이런 규모·도메인입니다.

발표 **전달 파트**(권영훈)와 **저장 파트**(김기현)의 숫자를 섞지 마세요.

| 출처 | 지표 | 의미 |
|---|---|---|
| 전달 파트 | MAU 약 **1,900만** | 서비스 월간 활성. 중고거래 등에서 채팅이 **필수 경로** |
| 저장 파트 | 유저 약 **3,900만** | 채팅이 다루는 유저 규모·영구 저장 전제 |

도메인 기능:

- 중고거래 / 중고차 / 부동산 / 알바 등 **1:1 채팅**
- 커뮤니티·모임용 **그룹 채팅**
- 가게 프로필 기준 **사장님·매니저 다중 수신(비즈니스 채팅)**
- **모든 채팅 메시지는 서버에 기본적으로 영구 저장**

도메인이 중요한 이유: “슬랙형 워크스페이스”와 “중고거래 1:1”은 **동시 접속 패턴·방 크기·읽음 표시·푸시 정책**이 다릅니다. 아키텍처는 이 도메인에 맞춰 진화합니다.

### 시나리오 맵

```text
┌─────────────┐   ┌──────────────────┐   ┌─────────────────────┐
│ 1:1 거래채팅  │   │ 비즈니스(사장님)   │   │ 모임 그룹 채팅       │
│ A ↔ B       │   │ 고객 → 사장+매니저 │   │ 10명 → 1,000명+    │
│ 단순 릴레이   │   │ 수신자 확장 조회   │   │ 배치·청크 필수      │
└─────────────┘   └──────────────────┘   └─────────────────────┘
```

### 체크포인트

- [ ] 우리 제품이 1:1 중심인지 / 대인원 그룹인지부터 말할 수 있는지
- [ ] “사장님 채팅”처럼 **수신자가 프로필 멤버십으로 확장**되는 케이스를 구분했는지

## 3. 전체 아키텍처 한눈에

### 개념

채팅은 보통 세 가지 큰 컴포넌트로 시작합니다.

```text
┌──────────────┐     ┌────────────────────┐     ┌──────────────┐
│  Client App  │◀───▶│   Chat Server(s)   │────▶│  Database    │
│ (WebSocket)  │     │  연결·이벤트·API    │     │ 방·멤버·메시지 │
└──────────────┘     └─────────┬──────────┘     └──────────────┘
                               │
                               ▼
                     ┌────────────────────┐
                     │   Push Server      │
                     │ (APNs / FCM 등)    │
                     └────────────────────┘
```

확장된 형태(발표에서 도달한 구조)는 대략 이렇게 됩니다.

```text
 Client ──WS──▶ Chat Server (세션 로컬 메모리)
                    │
                    │ 1) DB에 메시지 저장
                    │ 2) MQ에 "전달해줘" 이벤트 발행
                    ▼
              Message Queue
                    │
                    ▼
              Consumer Worker(s)
                    │
                    │ KV Store에서 user → server IP 조회
                    ├─ online  → Chat Server로 Relay 요청
                    └─ offline → Push Server로 알림 요청

              KV Store (공유 세션 위치)
              userId → connectedServerIp
```

| 컴포넌트 | 역할 | 상태성 |
|---|---|---|
| Chat Server | WS/TCP 연결 유지, 로컬 세션, 릴레이 수신 | **연결에 대해 stateful** |
| Database | 방·멤버십·메시지 영속 | durable |
| KV Store | “유저가 어느 서버에 붙었는지” | ephemeral, **100% 신뢰 금지** |
| Message Queue + Consumer | 크로스 서버 전달을 비동기로 분리 | 처리량에 따라 스케일 |
| Push Server | 오프라인(또는 세션 불일치) 깨우기 | 외부 의존 |

### Pub/Sub을 처음부터 안 쓴 이유 (예고)

유저마다 토픽을 두고 “방의 전원에게 publish”하면, **대인원 방에서 메시지 1건 = 멤버 수만큼 발행**이 됩니다. 발표에서는 이 비효율 때문에 **KV + 배치 릴레이** 쪽을 선택했다고 설명합니다. (§12–§13에서 자세히)

### 체크포인트

- [ ] 위 다이어그램을 보고 데이터 경로(저장)와 이벤트 경로(전달)를 구분해서 그릴 수 있는지
- [ ] Chat Server가 “무상태 API 서버”가 아닌 이유를 말할 수 있는지

## 4. 메시지 전달 3단계

### 개념

방 참여자 A, B가 **온라인**, C가 **오프라인**이라고 가정합니다. A가 메시지를 보내면 흐름은 세 단계입니다.

```text
① Persist     A → Chat Server → Database (메시지 저장)
② Fan-out     Chat Server → (온라인) B에게 실시간 이벤트
③ Push        (오프라인) C에게 푸시 알림
```

| 단계 | 성공 기준 | 실패 시 |
|---|---|---|
| Persist | DB에 메시지가 남음 | 재시도 / 클라이언트에 에러. **이력이 없으면 전달도 의미 없음** |
| Fan-out | 온라인 세션에 이벤트 도착 | 재릴레이 / 클라이언트가 재접속 후 history pull |
| Push | 오프라인 기기 알림 | OS/토큰 이슈. 앱 진입 시 history로 보정 |

중요한 설계 원칙:

> **저장은 동기적으로 확실히**, **전달·푸시·부수 효과는 가능한 한 비동기**로 빼면 API 응답성과 확장성이 좋아집니다. (저장 계층 최적화 §22와 맞물림)

### 의사 코드

```text
onSendMessage(sender, roomId, body):
  msg = db.insertMessage(roomId, sender, body)          // ①
  members = db.listMembers(roomId)
  for each member in members where member != sender:
    enqueue(DeliverToUser{ userId: member, message: msg }) // ②③는 컨슈머가 판단
  return Ack{ messageId: msg.id }  // 가능하면 여기서 빠르게 응답
```

### 체크포인트

- [ ] “온라인 fan-out”과 “오프라인 push”를 같은 파이프라인에서 분기하는 이유를 설명
- [ ] 클라이언트가 history를 pull하는 이유를 “전달 실패의 안전망”으로 말할 수 있는지

## 5. 서버 1대 — 1:1 채팅

### 개념

서버가 **한 대**뿐이면 세션은 전부 그 서버의 **로컬 메모리**에 있습니다.

```text
┌─────────────────────────────────────┐
│           Chat Server #1            │
│  Local Memory:                      │
│    userA → Session(connA)           │
│    userB → Session(connB)           │
└─────────────────────────────────────┘
         ▲                ▲
         │ WS             │ WS
       User A           User B
```

연결 시 (발표 표현 그대로의 핵심):

1. **당근 앱을 처음 열 때** 채팅 서버에 장수명 연결이 열린다 (특정 채팅방 입장 시점이 아님)
2. 서버는 `userId → session` 을 **로컬 맵**에 저장 → 이 정보가 있어야 해당 유저에게 이벤트 push 가능
3. 앱 종료·연결 끊김 시 맵에서 제거

메시지 전송 (A → B):

1. A의 요청을 받은 서버가 **DB에 메시지 저장**
2. **이 채팅방에 누가 있는지**(멤버십)를 조회
3. 수신자 B가 이 서버 로컬에 있으면 세션으로 이벤트 push  
   (발신자 A에게는 자기 메시지를 다시 안 보내도 됨)
4. 오프라인이면 이후 단계에서 푸시 (§4, §10)

### 로컬 세션 맵 스케치

```go
// 개념용 — 실제 프로덕션은 동시성·다중 기기 세션을 고려
type SessionStore struct {
    mu   sync.RWMutex
    byID map[string]net.Conn // userId → connection
}

func (s *SessionStore) Put(userID string, c net.Conn) {
    s.mu.Lock()
    defer s.mu.Unlock()
    s.byID[userID] = c
}

func (s *SessionStore) Get(userID string) (net.Conn, bool) {
    s.mu.RLock()
    defer s.mu.RUnlock()
    c, ok := s.byID[userID]
    return c, ok
}
```

### 서버 1대에서 충분한가

| 상황 | 판단 |
|---|---|
| 프로토타입 / 사내툴 / 동시접속 수백 | 충분할 수 있음 |
| 장애 시 SPOF | 서버 죽으면 **모든 실시간 연결 단절** |
| 트래픽 증가 | CPU·FD·메모리 한계 → 곧 수평 확장 필요 |

### 체크포인트

- [ ] “로컬 메모리 세션”이 실시간 전달의 출발점임을 이해
- [ ] 서버 1대 설계의 SPOF를 말할 수 있는지

## 6. 서버 2대 — 로컬 세션의 벽

### 개념

서버를 두 대로 늘리면 **로드밸런서가 연결을 sticky하게 붙이지 않는 한**, A와 B가 서로 다른 서버에 붙습니다.

```text
┌──────────────────┐          ┌──────────────────┐
│  Chat Server #1  │          │  Chat Server #2  │
│  Local: A→sess   │          │  Local: B→sess   │
└────────▲─────────┘          └────────▲─────────┘
         │                             │
       User A                        User B
```

A가 #1에 메시지를 보냄 → #1은 B에게 줘야 함 → 그런데 **B 세션은 #2의 로컬 메모리에만** 있음 → #1은 B에게 push 불가.

이것이 채팅 수평 확장의 **첫 번째 본질적 문제**입니다.

> 연결 상태는 노드에 귀속된다. 메시지 전달은 노드를 가로질러야 한다.

### 해결 후보 두 가지

| 방법 | 아이디어 | 장점 | 단점 |
|---|---|---|---|
| **공유 메모리 (KV)** | `userId → serverIp` 를 Redis 등에 저장. 대상 서버에 **릴레이 요청** | 대인원 배치/집계에 유리 | 릴레이 API·세션 정합성 관리 필요 |
| **Pub/Sub** | 유저(또는 방) 토픽을 구독. 발행하면 구독자가 수신 | 구현이 직관적 | 멤버 수만큼 발행·구독 fan-out 비용 |

발표에서는 **KV Store + 릴레이**를 중심으로 설명하고, Pub/Sub은 그룹방에서 비효율이 커진다고 합니다.

### 체크포인트

- [ ] “서버가 늘면 로컬 세션만으로는 부족하다”를 그림으로 설명
- [ ] KV vs Pub/Sub 선택 기준을 “방 크기·배치 가능성”으로 말할 수 있는지

## 7. 공유 메모리(KV Store)와 릴레이

### 개념

모든 Chat Server가 접근하는 **공유 KV**에 “지금 이 유저가 어느 서버에 붙어 있는지”를 둡니다.

```text
Connect:
  localMemory[userId] = session
  kv.set(userId, myServerIP)          // 예: "123" → "1.1.1.1"

Disconnect (정상):
  localMemory.delete(userId)
  kv.delete(userId)

Send A→B (서버 #1에서):
  save message to DB
  targetIP = kv.get(B)
  if targetIP == myIP:
      push to local session B
  else:
      http/rpc Relay(targetIP, B, message)   // 릴레이 요청
```

도식:

```text
  A ──▶ Server#1 ──persist──▶ DB
              │
              │ kv.get(B) → 2.2.2.2
              ▼
         Relay request ──▶ Server#2 ──push──▶ B
              │
         KV Store
         B → 2.2.2.2
```

### 릴레이 API 스케치

```go
// Server#2가 받는 내부 API
type RelayRequest struct {
    UserID  string          `json:"user_id"`
    Payload json.RawMessage `json:"payload"`
}

func (h *Handler) Relay(w http.ResponseWriter, r *http.Request) {
    var req RelayRequest
    // decode...
    conn, ok := h.sessions.Get(req.UserID)
    if !ok {
        // 세션 없음 → KV가 stale일 수 있음 (§10)
        w.WriteHeader(http.StatusNotFound)
        return
    }
    _ = writeEvent(conn, req.Payload)
    w.WriteHeader(http.StatusNoContent)
}
```

### 정상 종료 vs 비정상 종료

| 상황 | KV | 로컬 세션 |
|---|---|---|
| 앱 정상 종료 | delete | delete |
| 프로세스 kill / 서버 다운 | **남아 있을 수 있음** | 사라짐 |
| 네트워크 순단 후 재접속 | 새 IP로 overwrite | 새 세션 |

그래서 발표의 핵심 문장:

> **KV Store를 100% 신뢰하면 안 된다.**

stale 엔트리는 릴레이 실패 → 푸시 폴백 → KV 삭제로 치유합니다. (§10)

### 체크포인트

- [ ] connect/disconnect 시 로컬 + KV 둘 다 갱신하는 이유를 설명
- [ ] “릴레이”가 서버 간 내부 RPC임을 구분했는지 (클라이언트 API가 아님)

## 8. 서버 N대 — 그물망의 함정

### 개념

서버가 10대로 늘고, **각 서버가 서로를 직접 릴레이**하면 연결 토폴로지는 완전 그래프(그물망)에 가까워집니다.

```text
S1 ── S2 ── S3
 │ ╲  │ ╱  │
 │   ╲│╱   │
S4 ── S5 ── S6 ...
```

| 문제 | 설명 |
|---|---|
| 네트워크 복잡도 | 서버 수 N에 대해 잠재 링크 ~ O(N²) |
| 설정·보안 | 서버마다 서로를 알아야 함 (서비스 디스커버리·방화벽) |
| 장애 전파 | 한 노드 지연이 다른 노드의 동기 릴레이를 막을 수 있음 |
| 확장성 | “서버만 더 띄우면 된다”가 성립하기 어려움 |

원하던 그림은 이것입니다.

> Chat Server들은 **서로를 몰라도 되고**, **가운데 큐/워커만** 알면 된다.

## 9. 메시지 큐 + 컨슈머로 수평 확장

### 개념

**메시지 큐**: 이벤트를 순서대로(또는 파티션 단위로) 줄을 세우는 저장소.  
**컨슈머**: 줄에서 꺼내 실제로 “어디에 릴레이할지 / 푸시할지”를 수행하는 워커.

```text
A → Server#1
      │ persist DB
      │ publish Deliver{user:B, msg}
      ▼
   Message Queue
      │
      ▼
   Consumer
      │ kv.get(B) → Server#2
      │ async relay to Server#2
      ▼
   Server#2 → push → B
```

서버가 10대여도 Chat Server ↔ Chat Server 그물망은 사라지고, 대략 이런 형태가 됩니다.

```text
Chat Servers (N) ──publish──▶ Queue ──▶ Consumers (M) ──relay/push──▶ Chat Servers / Push
                     ▲                         │
                     └──── KV Store ◀──────────┘
```

| 조절 노브 | 의미 |
|---|---|
| Chat Server 수 N | 동시 WebSocket 연결·접속 트래픽 |
| Consumer 수 M | 전달 처리량 (큐 lag 보고 스케일) |
| Queue 파티션 | 처리 병렬도·키 기반 순서 보장 |

### 왜 릴레이를 비동기로 하나

발표에서 강조한 이유:

1. **컨슈머 처리량**: 서버 응답을 기다리지 않고 다음 이벤트로 넘어갈 수 있음
2. **책임 분리**: 릴레이 에러·재시도·푸시 폴백은 **채팅 서버 쪽 책임**으로 두고, 컨슈머는 “요청을 던지는” 쪽에 가깝게

```text
Consumer:
  ip = kv.get(user)
  if ip == nil:
      pushServer.notify(user, msg)      // 오프라인
  else:
      fireAndForget relay(ip, user, msg) // 응답 안 기다림 (개념)

Chat Server (relay 수신 시):
  if session missing:
      pushServer.notify(...)
      kv.delete(user)                   // stale 정리
```

### Kafka / Redis Streams / SQS 중 뭐를?

| 선택 | 잘 맞는 경우 |
|---|---|
| Kafka | 대용량, 재생·감사, 다른 팀 이벤트 공유, 검색 인덱싱 파이프라인 |
| Redis Streams | 이미 Redis KV를 쓰고, 운영 단순·중간 규모 |
| SQS + workers | 관리형·단순 큐, 순서 요구가 느슨 |

발표 저장 파트에서는 **Kafka**를 검색 인덱싱·팀 간 이벤트·크리티컬 비동기 태스크에 쓴다고 명시합니다. 전달 파트의 “메시지 큐”는 동일 계열로 이해하면 됩니다.

### 체크포인트

- [ ] N 서버 그물망 → Queue/Consumer 허브로 바뀌는 그림을 그릴 수 있는지
- [ ] Consumer 수를 “연결 수”가 아니라 “전달 처리량”으로 스케일하는지

## 10. 푸시 알림 — 언제, 누가 보내나

### 개념

푸시는 “오프라인 전용”만이 아닙니다. **세션 위치 정보의 불일치**를 보정하는 안전망이기도 합니다.

### 케이스 1 — 진짜 오프라인

```text
A online, B offline
A sends → Consumer kv.get(B) → miss
       → Push Server → B의 기기
```

### 케이스 2 — KV는 있는데 세션은 없음 (stale)

```text
A online, B 실제로는 offline
KV에는 잘못 B → Server#2 로 남아 있음

Consumer → Relay to #2
Server#2 localMemory에 B 없음
  → Push Server로 알림
  → KV에서 B 엔트리 삭제 요청
```

| 원인 | 결과 |
|---|---|
| 서버 다운으로 disconnect 훅 미실행 | KV에 유령 엔트리 |
| 비정상 종료 | 동일 |
| 네트워크 파티션 / 레이스 | 잠깐의 불일치 |

설계 함의:

1. **KV는 hint**, source of truth가 아님  
2. **로컬 세션이 최종 판정** (“지금 이 연결로 push 가능한가”)  
3. 실패 시 **푸시 + KV 정리**로 eventual consistency

### 푸시 중복·억제

실서비스에서는 추가로 고민합니다. (발표 범위 밖이지만 구축 시 필수)

- 이미 앱이 foreground면 푸시 생략
- 같은 방의 연속 메시지 묶음(collapse key)
- 알림 설정(방 mute)은 UserChat 설정에서 조회

### 체크포인트

- [ ] 푸시가 “오프라인”과 “stale KV” 두 경로에서 나온다고 설명
- [ ] KV delete를 누가(어느 컴포넌트가) 담당하는지 설계에 적어 두었는지

## 11. 비즈니스(사장님) 채팅

### 개념

고객이 가게 프로필의 “채팅 문의하기”로 메시지를 보내면, **사장뿐 아니라 매니저 등 프로필에 연결된 여러 유저**가 받아야 합니다.

UI 관점(스크립트):

- 일반 유저: 채팅 탭에 일반/비즈니스 구분 없음
- 사장·매니저: **비즈니스 탭**이 생기고, 관리 중인 가게 채팅이 모임

### 전달 흐름

```text
Customer → Chat Server#1
             │
             ▼
        Business Service
        profileId → [ownerId, managerId, ...]
             │
             ├─ publish Deliver{owner}
             └─ publish Deliver{manager}
             │
             ▼
          Consumers
             ├─ owner   @ Server#2 → relay
             └─ manager @ Server#3 → relay
```

핵심: **채팅방의 “논리적 수신자”와 “실제 userId 목록”이 1:1이 아닐 수 있다.**  
방/프로필 메타를 보고 **수신 userId를 펼친 뒤**, 기존 Deliver 파이프라인에 태웁니다.

### 스키마와의 연결

저장 계층의 `UserChat`(유저↔방 N:M)에 비즈니스 멤버가 들어가거나, 별도 Business Membership 서비스가 userId 목록을 줍니다. 전달 계층은 그 목록만 받으면 됩니다.

### 체크포인트

- [ ] “방 멤버 조회”가 단순 DB join이 아니라 도메인 서비스 호출일 수 있음을 이해
- [ ] 수신자 확장 후에도 §9의 Deliver 파이프라인을 재사용하는지

## 12. 그룹 채팅 — 유저 단위 발행의 한계

### 개념

모임방 인원 10명, 전원 온라인. 5명은 Server#2, 5명은 Server#3.

**유저마다 Deliver 이벤트를 하나씩** 발행하면:

| 단계 | 횟수 (인원 10) | 인원 1,000이면 |
|---|---|---|
| 멤버 조회 | 1 | 1 |
| MQ publish | 10 | **1,000** |
| KV lookup | 10 | **1,000** |
| Relay | 서버별로 분산 | **최대 1,000** |

메시지 **한 번**에 큐 트래픽이 멤버 수에 비례합니다. 1,000명 방에서 초당 메시지율만 올라가도 큐·컨슈머·KV가 먼저 녹습니다.

### Pub/Sub이었다면

유저 토픽에 각각 publish하는 구조는 같은 스케일 문제를 겪기 쉽고, **“유저 목록을 묶어서 한 번에 처리”**하는 최적화가 어렵습니다. 발표가 KV+배치를 선호한 이유입니다.

### 체크포인트

- [ ] “메시지 1건의 비용 ∝ 멤버 수”가 왜 위험한지 수치로 설명
- [ ] 다음 절의 배치가 어떤 카운터를 줄이는지 예상

## 13. 배치 전달과 청크 분할

### 개념

**아이디어 1 — 유저 ID를 묶는다**

```text
Before: publish(Deliver{u1}), publish(Deliver{u2}), ... publish(Deliver{u1000})
After:  publish(DeliverBatch{users:[u1..u500]})
        publish(DeliverBatch{users:[u501..u1000]})
```

컨슈머는:

1. 배치 userId 목록을 받음
2. KV를 **한 번에(또는 파이프라인으로)** 조회해 `serverIp → []userId`로 그룹핑
3. 서버별로 **한 번의 릴레이**에 여러 유저를 담아 전달

```text
Consumer(batch):
  locations = kv.mget(userIds)
  group = map[serverIP][]userID
  for each (ip, users) in group:
      relay(ip, users, message)
  for each user with no ip:
      push(user, message)
```

**아이디어 2 — 청크(chunk)로 나눈다**

1,000명을 한 배치에 넣으면 컨슈머 한 작업이 너무 길어져 **타임아웃**이 잦아집니다. 2,000·3,000명 방은 더 심합니다.

```text
1..1000 을 200명씩 5개 청크
  chunk1: 1..200
  chunk2: 201..400
  ...
  chunk5: 801..1000
```

| | 유저별 발행 | 배치+청크 |
|---|---|---|
| MQ 이벤트 수 | ~1000 | ~5 (청크 크기 200 기준) |
| 처리 시간 예측 | 어려움 | 청크 크기 ≈ 예산 가능 |
| 타임아웃 | 대형 방에서 빈번 | 감소 |
| 약간 늘어나는 것 | — | 이벤트 수(1→5)는 늘지만 **안정성 이득** |

청크 크기는 **타임아웃·p99 처리 시간·KV RTT**를 재며 튜닝합니다. “무조건 최댓값”이 아닙니다.

### 체크포인트

- [ ] 배치가 줄이는 것(publish/lookup 횟수)과 청크가 줄이는 것(한 작업의 꼬리 지연)을 구분
- [ ] 우리 서비스 예상 최대 방 인원으로 청크 크기를 가정해 보기

## 14. 전달 계층 정리 — 확장성·신뢰성·효율성

### 개념

발표가 전달 파트를 세 키워드로 닫습니다.  
단, **신뢰성** 구간은 원본 스크립트가 불명료하므로(§0), 같은 발표에서 반복된 장치로 재구성합니다.

| 키워드 | 발표에서 명확히 말한 수단 | 효과 |
|---|---|---|
| **확장성** | MQ + Consumer 비동기 | 요청 증가 시 Chat Server / Consumer **수평** 확장 |
| **신뢰성** *(재구성)* | 메시지 **DB 영속** + KV 불신 + **푸시 폴백** + stale KV 삭제 | 세션이 틀려도 “전달 실패 = 메시지 소실”이 되지 않음 |
| **효율성** | 유저 배치 + **청크(예: 200)** | 대인원 fan-out을 **예측 가능한 수행 시간**으로 |

한 줄 요약:

> **저장은 DB에, 위치는 KV hint에, 전달은 큐로 비동기화하고, 실패는 푸시로 보정하며, 대인원은 잘라서 보낸다.**

### 체크포인트

- [ ] 세 키워드를 각자 한 문장·한 메커니즘으로 매핑
- [ ] “확장만 되고 비효율인 시스템” vs “효율만 좋고 확장 안 되는 시스템” 반례를 말하는지

## 15. 저장 계층 — 왜 분리했나

### 개념

과거에는 여러 서비스가 **하나의 메인 RDB**를 공유했습니다. MAU가 급증하며 데이터·트래픽이 폭증했고, 인덱스·쿼리 튜닝·캐시로도 **물리 장비 한계**에 닿았습니다.

스케일업(머신 스펙 업)을 해도:

- 피크에 DB CPU ~90%까지 치솟는 경우
- AWS RDB 타입 기준 **올릴 수 있는 스펙이 얼마 안 남음**
- 채팅이 전체 DB 트래픽의 **약 60%**를 차지 → 채팅 부하가 **전사 장애**로, 그 반대도 가능

따라서:

1. **채팅 DB를 메인 DB에서 분리**
2. **확장 가능한 저장 구조로 재설계**
3. 실시간성이 중요하므로 **API 지연 최적화**를 병행

### 교훈

| 안티패턴 | 결과 |
|---|---|
| 모든 도메인이 한 DB | 한 팀의 hot path가 전사 SPOF |
| 스케일업만 반복 | 곧 천장 + 비용 급증 |
| 채팅을 “그냥 큰 테이블”로 | 메시지 폭증이 전체를 압도 |

### 체크포인트

- [ ] “채팅을 분리한 이유”를 트래픽 비율·장애 전파로 설명
- [ ] 저장 재설계와 API 최적화가 **동시에** 필요한 이유를 이해

## 16. 스키마 — Chat / UserChat / Message

### 개념

핵심은 세 테이블(실제로는 필드가 훨씬 많지만 골격만).

```text
Chat          채팅방 (제목, 썸네일, 타입, ...)
UserChat      유저 ↔ 방 N:M + 방별 설정
Message       메시지 (id, text, ...)
```

관계:

```text
Chat 1 ─── * UserChat * ─── 1 User
Chat 1 ─── * Message
```

방이 만들어지면:

1. `Chat`에 row 1개
2. 참여자 수만큼 `UserChat` row 추가

이 테이블로:

- “이 방에 누가 있나”
- “내가 참여 중인 방 목록”
- 알림 mute 등 **유저-방 설정**

을 표현합니다. 조회용 인덱스도 필수입니다.

### 최소 필드 예시

```sql
-- 개념용 SQL. 실제 DynamoDB는 다른 모델링 (§18)

CREATE TABLE chat (
  chat_id     BIGINT PRIMARY KEY,
  title       TEXT,
  thumbnail   TEXT,
  created_at  TIMESTAMPTZ
);

CREATE TABLE user_chat (
  user_id          BIGINT NOT NULL,
  chat_id          BIGINT NOT NULL,
  display_index    BIGINT,          -- 목록 정렬용 (§19)
  settings_json    JSONB,
  PRIMARY KEY (user_id, chat_id)
);
CREATE INDEX idx_user_chat_list ON user_chat (user_id, display_index DESC);

CREATE TABLE message (
  chat_id     BIGINT NOT NULL,
  message_id  BIGINT NOT NULL,
  sender_id   BIGINT NOT NULL,
  body        TEXT,
  created_at  TIMESTAMPTZ,
  PRIMARY KEY (chat_id, message_id)
);
```

### 체크포인트

- [ ] 왜 `Message`만으로 방 목록·멤버십을 표현하지 않는지
- [ ] `UserChat`이 “설정 저장소”이기도 한 이유를 설명

## 17. 샤딩 — 샤드 키 고르기

### 개념

메시지는 데이터가 가장 많습니다. 샤딩(물리 DB 인스턴스에 분산)이 필요합니다.

잘못된 읽기 패턴:

```text
메시지 조회 1번 → 모든 샤드에 scatter-gather → 확장성∅ + 성능↓↓
```

목표:

> **가능한 한 적은 샤드(이상적으로 1개)에서 읽히게** 데이터를 배치한다.

채팅에서 자연스러운 접근:

- 클라이언트가 **특정 채팅방**의 메시지 리스트를 요청
- 같은 방의 메시지들은 `message_id`는 달라도 **`chat_id`는 동일**

따라서:

| 데이터 | 샤드 키 | 이유 |
|---|---|---|
| 메시지, 방 내부 데이터 | **chat_id** | 방 메시지 조회 = 단일 샤드 |
| 유저 기반 데이터 (내 방 목록 등) | **user_id** | “내 것” 조회 = 단일 샤드 |

```text
chat_id=42 인 메시지들 ──▶ 전부 Shard X
user_id=7 의 UserChat들 ──▶ 전부 Shard Y
```

### 샤드 키를 잘못 고르면

| 키 | 문제 |
|---|---|
| `message_id`만 | 한 방 메시지를 여러 샤드에서 모아야 함 |
| `created_at` | 핫 파티션(최신 시간대) + 방 단위 locality 상실 |
| `user_id`로 메시지 저장 | 1:1은 운 좋으면 한곳, 그룹은 **발신자마다 분산** → 방 조회 지옥 |

### 체크포인트

- [ ] “읽기 패턴이 샤드 키를 결정한다”고 말할 수 있는지
- [ ] chat_id / user_id 이중 샤딩이 각각 어떤 쿼리를 위한 것인지

## 18. DynamoDB 선택과 파티션 키

### 개념

샤딩 구현 옵션:

| 방식 | 누가 샤딩을 아나 |
|---|---|
| 앱 레벨 샤딩 | 개발자가 라우팅·리밸런싱·장애를 짐 |
| 미들웨어 샤딩 | Proxy가 분배. 운영 복잡도 상당 |
| **관리형 자동 샤딩** | 파티션 키만 정하면 엔진이 분산 |

당근 채팅은 **AWS DynamoDB**를 선택했습니다. 이유(발표):

- 확장성
- **적은 인원으로 관리 가능**
- 파티션 키 설정 시 **자동 샤딩**
- 오토스케일링
- 관리형이라 DB 운영 비용 거의 배제

마이그레이션 이후: **트래픽으로 인한 DB 장애가 거의 없음**.

### 테이블 매핑 (개념)

| 논리 테이블 | Partition Key | Sort Key (예시) |
|---|---|---|
| Message | `chat_id` | `message_id` (또는 timestamp) |
| UserChat / 유저 데이터 | `user_id` | `chat_id` |

콘솔에서 테이블 생성 시 Partition Key만 지정해도, 그 키 기준으로 파티셔닝됩니다.

### DynamoDB를 쓸 때 주의

발표 범위 밖이지만 구축 시 중요:

- **핫 파티션**: 초대형 공개방 하나의 `chat_id`에 쓰기가 몰리면 그 파티션이 병목 → 청크/버퍼/쿨다운 등 도메인 완화
- **액세스 패턴 선행 설계**: RDB처럼 ad-hoc JOIN이 어렵습니다
- **단일 방 쿼리**는 강점, **글로벌 검색**은 OpenSearch 등으로 비동기 인덱싱 (Kafka 활용 §22)

### 체크포인트

- [ ] “파티션 키 = 샤드 키”로 DynamoDB를 설명할 수 있는지
- [ ] 관리형 선택 이유에 “인원 대비 운영”이 들어가는지

## 19. 채팅방 목록 정렬 — display_index

### 개념

채팅 목록 UI는 **새 메시지가 있는 방이 위로** 올라갑니다. 즉 “최근 메시지가 생긴 방 순” 정렬입니다.

구현 방법 중 발표가 택한 것:

> `UserChat.display_index`를 **새 메시지 ID 기반**으로 갱신하고, 목록 조회 시 이 필드로 정렬.

```text
onNewMessage(chatId, newMessageId):
  insert Message(chatId, newMessageId, ...)
  for each userId in members(chatId):
      update UserChat(userId, chatId).display_index = newMessageId
```

1:1이면 업데이트 2번.  
**1,000명 그룹이면 메시지 1건에 display_index 업데이트가 1,000번.**

이것을 메시지 전송 API 안에서 **순차 처리**하면 실시간 API의 응답이 무너집니다. → §20의 병렬·비동기.

### 목록 조회

```text
GET /chats
  → Query UserChat where user_id = me
  → ORDER BY display_index DESC
  → (필요 시) 각 방의 미리보기 메시지·뱃지 조인/배치 조회
```

### 체크포인트

- [ ] display_index가 “방의 최신성”을 유저별로 복제한 이유 (유저 샤드에서 목록을 읽으려고)
- [ ] 그룹방에서 쓰기 증폭(write amplification)을 인식하는지

## 20. 쓰기 병렬화 — 고루틴/멀티스레드

### 개념

메시지 전송 시 여러 write(멤버별 display_index 등)를 **핸들러에서 동시에** 날립니다.

```go
// 개념용: 멤버별 display_index 병렬 업데이트
func updateDisplayIndexes(ctx context.Context, chatID int64, msgID int64, members []int64) error {
    g, ctx := errgroup.WithContext(ctx)
    for _, uid := range members {
        uid := uid
        g.Go(func() error {
            return db.UpdateDisplayIndex(ctx, uid, chatID, msgID)
        })
    }
    return g.Wait()
}
```

발표 팀 스택은 **Go**라 고루틴을 사용. 런타임이 고루틴↔OS 스레드를 매핑하므로 “스레드 풀을 직접 관리”하는 부담이 적습니다.

| 언어 | 비슷한 수단 |
|---|---|
| Go | goroutine + errgroup |
| Rust | tokio::spawn / join_all |
| Java | virtual threads / CompletableFuture |
| Node | Promise.all (단, CPU Bound에는 한계) |

부분 실패: 개별 고루틴 업데이트가 실패할 수 있지만, **다음 메시지가 오면 다시 보정**되는 성질이라 발표에서는 크게 집착하지 않았다고 합니다. (도메인상 eventual OK인 write)

### 체크포인트

- [ ] “병렬 write로 응답 시간을 max(개별)에 가깝게” 만드는 그림을 이해
- [ ] 부분 실패를 허용할 수 있는 필드와 없는 필드(메시지 insert)를 구분

## 21. 읽기 병렬화 — 리소스 어그리게이션

### 개념

채팅방 메시지 조회 시 메시지 본문만이 아니라:

- 프로필 이미지
- 리액션
- (필요 시) 첨부 메타

등 **부가 리소스**가 붙습니다. 순차 조회하면:

```text
응답시간 ≈ t(messages) + t(profiles) + t(reactions) + ...
```

병렬이면:

```text
응답시간 ≈ max(t(messages), t(profiles), t(reactions), ...) + aggregate
```

```go
g, ctx := errgroup.WithContext(ctx)
var msgs []Message
var profiles map[int64]Profile
var reactions map[int64][]Reaction

g.Go(func() error { var err error; msgs, err = loadMessages(ctx, chatID); return err })
g.Go(func() error { var err error; profiles, err = loadProfiles(ctx, senderIDs); return err })
g.Go(func() error { var err error; reactions, err = loadReactions(ctx, chatID); return err })
if err := g.Wait(); err != nil { return err }

return aggregate(msgs, profiles, reactions)
```

- [ ] 읽기 경로의 “어그리게이션 포인트”를 핸들러로 모으는지
- [ ] N+1 순차 쿼리를 병렬·배치로 바꿨는지

## 22. 비동기 최적화 — 읽음 표시와 Kafka

### 개념

**읽음 표시(read receipt)** 흐름 예:

1. 클라이언트가 읽음 API 호출
2. 해당 메시지의 읽음 상태 **write**
3. 방 참여자 조회
4. 서버 간 이벤트로 **상대 클라이언트에 “읽음” 실시간 전달**

이 전부를 동기적으로 끝내고 응답하면 지연이 큽니다.

패턴:

```text
요청 유입
  │
  ├─ (동기) 꼭 지금 내구성 필요한 write만 수행
  ├─ 클라이언트에 먼저 200 응답
  │
  └─ (비동기) 나머지
        · 고루틴 워커로 백그라운드 업데이트
        · 또는 Kafka에 태스크 발행 → 컨슈머가 처리
```

| 수단 | 언제 |
|---|---|
| **고루틴** | 유실이 치명적이지 않고, 부하가 감당될 때 (빠른 경로) |
| **Kafka** | 고루틴 남발이 부담되거나, **유실이 크리티컬**, 또는 다른 팀/검색엔진과 공유 |

Kafka 추가 用途(발표):

- 검색 엔진 인덱싱
- 타 팀으로 도메인 이벤트 발행

### 읽음 API 의사 코드

```go
func ReadMessage(ctx context.Context, userID, chatID, messageID int64) error {
    if err := db.MarkRead(ctx, userID, chatID, messageID); err != nil {
        return err // 동기 필수
    }
    // 응답은 여기서 반환한다고 가정하고,
    // 아래는 비동기
    go notifyReadReceipts(userID, chatID, messageID)
    // 또는:
    // kafka.Publish(ReadReceiptTask{...})
    return nil
}
```

- [ ] “응답 경로에 남을 것 / 빼도 될 것”을 표로 나눠 봤는지
- [ ] 고루틴 vs Kafka 선택 기준에 **유실 비용**이 들어가는지

## 23. 기술 스택 선택 가이드

### 개념

발표 스택을 “정답”이 아니라 **제약 하의 선택**으로 읽습니다.

| 영역 | 발표에서 언급 | 대안 예시 |
|---|---|---|
| Chat Server 언어 | Go (고루틴) | Rust/Java/Node — 동시성 모델만 맞으면 |
| 장수명 연결 | (암시) WS 등 | WebSocket, gRPC stream, MQTT |
| 세션 위치 | KV Store | Redis Cluster |
| 전달 큐 | Message Queue | Kafka / Redis Streams / SQS |
| 저장 | DynamoDB | Cassandra, Scylla, 샤딩 MySQL(운영 비용↑) |
| 푸시 | Push Server | FCM, APNs, 자체 프록시 |
| 비즈니스 멤버십 | Business Server | 별도 membership 서비스 |

### 소규모에서 과한 것 / 꼭 필요한 것

| 규모 | 추천 |
|---|---|
| 토이·동시 100↓ | 서버 1대 + RDB + 로컬 세션 + 폴링/푸시 단순화 |
| 성장기 | Redis 세션 위치 + 릴레이, RDB 읽기 분리 |
| 대규모·대인원 방 | MQ+Consumer, 배치/청크, 저장 분리·샤딩, 비동기 API |

### 개념

```text
Phase 0  도메인·API 계약
         방 생성, 메시지 전송, history, 읽음, 푸시 토큰

Phase 1  싱글 서버
         WS + 로컬 세션 + RDB

Phase 2  멀티 서버 + KV

Phase 4  그룹·비즈니스
         수신자 확장, 배치 fan-out, 청크 튜닝

Phase 5  저장 분리·샤딩
         chat_id / user_id 키, 관리형 또는 앱 샤딩

Phase 6  API 지연 전쟁
```

### 26.2 로컬 세션 (다중 연결 대비)

```go
// --- file: internal/session/store.go ---
package session

import (
	"sync"

	"github.com/gorilla/websocket"
)

type Conn struct {
	DeviceID string
	WS       *websocket.Conn
	sendCh   chan []byte
}

type Store struct {
	mu   sync.RWMutex
	byID map[string]map[string]*Conn // userID → deviceID → Conn
}

func New() *Store {
	return &Store{byID: make(map[string]map[string]*Conn)}
}

func (s *Store) Put(userID, deviceID string, c *Conn) {
	s.mu.Lock()
	defer s.mu.Unlock()
	if s.byID[userID] == nil {
		s.byID[userID] = make(map[string]*Conn)
	}
	s.byID[userID][deviceID] = c
}

func (s *Store) Delete(userID, deviceID string) (empty bool) {
	s.mu.Lock()
	defer s.mu.Unlock()
	devs := s.byID[userID]
	if devs == nil {
		return true
	}
	delete(devs, deviceID)
	if len(devs) == 0 {
		delete(s.byID, userID)
		return true
	}
	return false
}

func (s *Store) HasUser(userID string) bool {
	s.mu.RLock()
	defer s.mu.RUnlock()
	return len(s.byID[userID]) > 0
}

// PushAll: 해당 유저의 모든 기기 세션에 전송 (§29)
func (s *Store) PushAll(userID string, data []byte) (okCount int) {
	s.mu.RLock()
	defer s.mu.RUnlock()
	for _, c := range s.byID[userID] {
		select {
		case c.sendCh <- data:
			okCount++
		default:
			// 버퍼 full → 해당 기기만 스킵 (백프레셔)
		}
	}
	return okCount
}
```

### 26.3 KV Store (위치 힌트 + TTL)

```go
// --- file: internal/kv/redis.go ---
package kv

import (
	"context"
	"time"

	"github.com/redis/go-redis/v9"
)

// 인터페이스만 보면 발표의 “공유 메모리”와 동일.
type Locator interface {
	Set(ctx context.Context, userID, serverAddr string) error
	Get(ctx context.Context, userID string) (string, error)
	MGet(ctx context.Context, userIDs []string) (map[string]string, error)
	Delete(ctx context.Context, userID string) error
	Touch(ctx context.Context, userID string) error // 하트비트로 TTL 연장 (§30)
}

type RedisLocator struct {
	rdb *redis.Client
	ttl time.Duration
}

func NewRedis(addr string, ttl time.Duration) *RedisLocator {
	return &RedisLocator{
		rdb: redis.NewClient(&redis.Options{Addr: addr}),
		ttl: ttl, // 예: 90s. 하트비트 30s마다 Touch
	}
}

func key(userID string) string { return "chat:sess:" + userID }

func (l *RedisLocator) Set(ctx context.Context, userID, serverAddr string) error {
	return l.rdb.Set(ctx, key(userID), serverAddr, l.ttl).Err()
}

func (l *RedisLocator) Get(ctx context.Context, userID string) (string, error) {
	return l.rdb.Get(ctx, key(userID)).Result()
}

func (l *RedisLocator) MGet(ctx context.Context, userIDs []string) (map[string]string, error) {
	keys := make([]string, len(userIDs))
	for i, u := range userIDs {
		keys[i] = key(u)
	}
	vals, err := l.rdb.MGet(ctx, keys...).Result()
	if err != nil {
		return nil, err
	}
	out := make(map[string]string, len(userIDs))
	for i, v := range vals {
		if s, ok := v.(string); ok && s != "" {
			out[userIDs[i]] = s
		}
	}
	return out, nil
}

func (l *RedisLocator) Delete(ctx context.Context, userID string) error {
	return l.rdb.Del(ctx, key(userID)).Err()
}

func (l *RedisLocator) Touch(ctx context.Context, userID string) error {
	return l.rdb.Expire(ctx, key(userID), l.ttl).Err()
}
```

```go
// --- file: internal/kv/memory.go ---
package kv

import (
	"context"
	"errors"
	"sync"
	"time"
)

type memEntry struct {
	addr string
	exp  time.Time
}

type MemoryLocator struct {
	mu  sync.RWMutex
	m   map[string]memEntry
	ttl time.Duration
}

func NewMemory(ttl time.Duration) *MemoryLocator {
	return &MemoryLocator{m: make(map[string]memEntry), ttl: ttl}
}

func (l *MemoryLocator) Set(_ context.Context, userID, serverAddr string) error {
	l.mu.Lock()
	defer l.mu.Unlock()
	l.m[userID] = memEntry{addr: serverAddr, exp: time.Now().Add(l.ttl)}
	return nil
}

func (l *MemoryLocator) Get(_ context.Context, userID string) (string, error) {
	l.mu.RLock()
	defer l.mu.RUnlock()
	e, ok := l.m[userID]
	if !ok || time.Now().After(e.exp) {
		return "", ErrNotFound
	}
	return e.addr, nil
}

func (l *MemoryLocator) MGet(ctx context.Context, userIDs []string) (map[string]string, error) {
	out := make(map[string]string, len(userIDs))
	for _, u := range userIDs {
		if addr, err := l.Get(ctx, u); err == nil {
			out[u] = addr
		}
	}
	return out, nil
}

func (l *MemoryLocator) Delete(_ context.Context, userID string) error {
	l.mu.Lock()
	defer l.mu.Unlock()
	delete(l.m, userID)
	return nil
}

func (l *MemoryLocator) Touch(_ context.Context, userID string) error {
	l.mu.Lock()
	defer l.mu.Unlock()
	e, ok := l.m[userID]
	if !ok {
		return ErrNotFound
	}
	e.exp = time.Now().Add(l.ttl)
	l.m[userID] = e
	return nil
}

var ErrNotFound = errors.New("session not found")
```

### 26.4 영속 저장 (스키마 동작)

```go
// --- file: internal/store/memory.go ---
package store

import (
	"context"
	"errors"
	"sort"
	"sync"
	"time"

	"chatlab/internal/id"
	"chatlab/internal/model"
)

var ErrDuplicate = errors.New("duplicate client_msg_id")

type Store struct {
	mu       sync.Mutex
	chats    map[string]struct{}
	members  map[string][]string            // chatID → userIDs
	messages map[string][]model.Message     // chatID → messages
	userChat map[string]map[string]int64    // userID → chatID → display_index(numeric)
	idem     map[string]string              // clientMsgID → messageID
}

func New() *Store {
	return &Store{
		chats:    make(map[string]struct{}),
		members:  make(map[string][]string),
		messages: make(map[string][]model.Message),
		userChat: make(map[string]map[string]int64),
		idem:     make(map[string]string),
	}
}

func (s *Store) CreateChat(chatID string, memberIDs []string) {
	s.mu.Lock()
	defer s.mu.Unlock()
	s.chats[chatID] = struct{}{}
	s.members[chatID] = append([]string{}, memberIDs...)
	for _, u := range memberIDs {
		if s.userChat[u] == nil {
			s.userChat[u] = make(map[string]int64)
		}
		s.userChat[u][chatID] = 0
	}
}

func (s *Store) ListMembers(_ context.Context, chatID string) ([]string, error) {
	s.mu.Lock()
	defer s.mu.Unlock()
	return append([]string{}, s.members[chatID]...), nil
}

// InsertMessage: 동기 필수 경로. display_index는 별도 병렬/비동기 (§19–§20)
func (s *Store) InsertMessage(_ context.Context, chatID, sender, body, clientMsgID string) (model.Message, error) {
	s.mu.Lock()
	defer s.mu.Unlock()
	if clientMsgID != "" {
		if mid, ok := s.idem[clientMsgID]; ok {
			for _, m := range s.messages[chatID] {
				if m.MessageID == mid {
					return m, ErrDuplicate // 호출측에서 기존 메시지 ACK
				}
			}
		}
	}
	msg := model.Message{
		ChatID:    chatID,
		MessageID: id.NewMessageID(),
		SenderID:  sender,
		Body:      body,
		CreatedAt: time.Now().UTC(),
		ClientMsg: clientMsgID,
	}
	s.messages[chatID] = append(s.messages[chatID], msg)
	if clientMsgID != "" {
		s.idem[clientMsgID] = msg.MessageID
	}
	return msg, nil
}

func (s *Store) UpdateDisplayIndex(_ context.Context, userID, chatID, messageID string) error {
	s.mu.Lock()
	defer s.mu.Unlock()
	if s.userChat[userID] == nil {
		s.userChat[userID] = make(map[string]int64)
	}
	// 학습용: messageID 문자열 대신 증가 카운터. 실서비스는 message_id 정렬 가능 값.
	s.userChat[userID][chatID] = time.Now().UnixNano()
	_ = messageID
	return nil
}

func (s *Store) ListChats(userID string) []string {
	s.mu.Lock()
	defer s.mu.Unlock()
	type pair struct {
		id  string
		idx int64
	}
	var ps []pair
	for cid, idx := range s.userChat[userID] {
		ps = append(ps, pair{cid, idx})
	}
	sort.Slice(ps, func(i, j int) bool { return ps[i].idx > ps[j].idx })
	out := make([]string, len(ps))
	for i := range ps {
		out[i] = ps[i].id
	}
	return out
}

func (s *Store) MessagesAfter(chatID, afterID string, limit int) []model.Message {
	s.mu.Lock()
	defer s.mu.Unlock()
	ms := s.messages[chatID]
	if afterID == "" {
		if len(ms) > limit {
			return append([]model.Message{}, ms[len(ms)-limit:]...)
		}
		return append([]model.Message{}, ms...)
	}
	var out []model.Message
	seen := false
	for _, m := range ms {
		if seen {
			out = append(out, m)
			if len(out) >= limit {
				break
			}
		}
		if m.MessageID == afterID {
			seen = true
		}
	}
	return out
}

func (s *Store) MarkRead(_ context.Context, userID, chatID, messageID string) error {
	// 동기 write만. 상대 알림은 비동기 (§22)
	_ = userID
	_ = chatID
	_ = messageID
	return nil
}
```

### 26.6 Chat Server — 연결·전송·청크 발행

```go
// --- file: internal/server/server.go ---
package server

import (
	"context"
	"encoding/json"
	"errors"
	"log"
	"net/http"
	"time"

	"chatlab/internal/kv"
	"chatlab/internal/model"
	"chatlab/internal/push"
	"chatlab/internal/queue"
	"chatlab/internal/session"
	"chatlab/internal/store"

	"github.com/gorilla/websocket"
	"golang.org/x/sync/errgroup"
)

const ChunkSize = 200 // 발표 예시와 동일 스케일

type Server struct {
	SelfAddr string
	Local    *session.Store
	KV       kv.Locator
	DB       *store.Store
	Q        queue.Publisher
	Push     push.Notifier
	Upgrader websocket.Upgrader
}

func (s *Server) HandleWS(w http.ResponseWriter, r *http.Request) {
	userID := r.URL.Query().Get("user_id")
	deviceID := r.URL.Query().Get("device_id")
	if userID == "" || deviceID == "" {
		http.Error(w, "user_id & device_id required", 400)
		return
	}
	conn, err := s.Upgrader.Upgrade(w, r, nil)
	if err != nil {
		return
	}
	c := &session.Conn{DeviceID: deviceID, WS: conn, sendCh: make(chan []byte, 64)}
	s.Local.Put(userID, deviceID, c)
	_ = s.KV.Set(r.Context(), userID, s.SelfAddr)

	go s.writePump(c)
	go s.readPump(userID, deviceID, c)
}

func (s *Server) writePump(c *session.Conn) {
	defer c.WS.Close()
	for data := range c.sendCh {
		_ = c.WS.SetWriteDeadline(time.Now().Add(10 * time.Second))
		if err := c.WS.WriteMessage(websocket.TextMessage, data); err != nil {
			return
		}
	}
}

func (s *Server) readPump(userID, deviceID string, c *session.Conn) {
	defer func() {
		empty := s.Local.Delete(userID, deviceID)
		if empty {
			_ = s.KV.Delete(context.Background(), userID)
		}
		close(c.sendCh)
		c.WS.Close()
	}()
	c.WS.SetReadLimit(1 << 20)
	for {
		_, data, err := c.WS.ReadMessage()
		if err != nil {
			return
		}
		var frame model.WSFrame
		if err := json.Unmarshal(data, &frame); err != nil {
			continue
		}
		switch frame.Type {
		case "ping":
			_ = s.KV.Touch(context.Background(), userID) // §30
			ack, _ := json.Marshal(model.WSFrame{Type: "pong"})
			c.sendCh <- ack
		case "send":
			// payload: {chat_id, body, client_msg_id}
			s.handleSendFrame(userID, frame.Payload, c)
		case "read":
			s.handleReadFrame(userID, frame.Payload)
		}
	}
}

type sendPayload struct {
	ChatID      string `json:"chat_id"`
	Body        string `json:"body"`
	ClientMsgID string `json:"client_msg_id"`
}

func (s *Server) handleSendFrame(sender string, raw interface{}, c *session.Conn) {
	b, _ := json.Marshal(raw)
	var p sendPayload
	_ = json.Unmarshal(b, &p)
	msg, err := s.Send(context.Background(), sender, p.ChatID, p.Body, p.ClientMsgID)
	frame := model.WSFrame{Type: "ack", Payload: msg}
	if err != nil && !errors.Is(err, store.ErrDuplicate) {
		frame = model.WSFrame{Type: "error", Payload: err.Error()}
	}
	out, _ := json.Marshal(frame)
	c.sendCh <- out
}

// Send = 발표의 “저장 후 전달 이벤트 발행”
func (s *Server) Send(ctx context.Context, from, chatID, body, clientMsgID string) (model.Message, error) {
	msg, err := s.DB.InsertMessage(ctx, chatID, from, body, clientMsgID)
	if err != nil && !errors.Is(err, store.ErrDuplicate) {
		return model.Message{}, err
	}
	if errors.Is(err, store.ErrDuplicate) {
		return msg, err // 이미 저장된 메시지 — 재전달은 정책에 따라
	}

	members, err := s.DB.ListMembers(ctx, chatID)
	if err != nil {
		return msg, err
	}

	// display_index 병렬 업데이트 (§20) — 전송 ACK와 분리하려면 go로 빼도 됨
	g, gctx := errgroup.WithContext(ctx)
	for _, uid := range members {
		uid := uid
		g.Go(func() error {
			return s.DB.UpdateDisplayIndex(gctx, uid, chatID, msg.MessageID)
		})
	}
	_ = g.Wait() // 부분 실패 허용 정책이면 에러 무시 가능 (발표와 동일)

	// 발신자 제외 수신자 → 청크 단위로 큐 발행 (§13)
	var recipients []string
	for _, uid := range members {
		if uid != from {
			recipients = append(recipients, uid)
		}
	}
	for _, chunk := range chunkStrings(recipients, ChunkSize) {
		_ = s.Q.Publish(model.DeliverBatch{
			ChatID:  chatID,
			Message: msg,
			UserIDs: chunk,
		})
	}
	return msg, nil
}

func chunkStrings(in []string, n int) [][]string {
	if n <= 0 {
		n = 200
	}
	var out [][]string
	for i := 0; i < len(in); i += n {
		j := i + n
		if j > len(in) {
			j = len(in)
		}
		out = append(out, in[i:j])
	}
	return out
}

func (s *Server) handleReadFrame(userID string, raw interface{}) {
	b, _ := json.Marshal(raw)
	var p struct {
		ChatID    string `json:"chat_id"`
		MessageID string `json:"message_id"`
	}
	_ = json.Unmarshal(b, &p)
	ctx := context.Background()
	if err := s.DB.MarkRead(ctx, userID, p.ChatID, p.MessageID); err != nil {
		return
	}
	// 응답은 이미 ping/별도 ACK 가능. 상대 알림은 비동기 (§22)
	go s.fanoutReadReceipt(userID, p.ChatID, p.MessageID)
}

func (s *Server) fanoutReadReceipt(reader, chatID, messageID string) {
	members, err := s.DB.ListMembers(context.Background(), chatID)
	if err != nil {
		return
	}
	payload, _ := json.Marshal(model.WSFrame{
		Type: "read",
		Payload: map[string]string{
			"chat_id":    chatID,
			"message_id": messageID,
			"reader_id":  reader,
		},
	})
	for _, uid := range members {
		if uid == reader {
			continue
		}
		_ = s.Q.Publish(model.DeliverBatch{
			ChatID:  chatID,
			Message: model.Message{ChatID: chatID, MessageID: messageID, Body: string(payload), SenderID: reader},
			UserIDs: []string{uid},
		})
	}
	log.Printf("read-receipt enqueued reader=%s chat=%s", reader, chatID)
}
```

```go
	"encoding/json"

	UserIDs []string      `json:"user_ids"` // 배치 릴레이

// HandleRelay: Consumer → Chat Server
// 로컬에 세션 없는 유저는 stale → 푸시 + KV 삭제 (§10)
func (s *Server) HandleRelay(w http.ResponseWriter, r *http.Request) {
	var req RelayRequest
	if err := json.NewDecoder(r.Body).Decode(&req); err != nil {
		http.Error(w, err.Error(), 400)
		return
	}
	data, _ := json.Marshal(model.WSFrame{Type: "message", Payload: req.Message})

	var missing []string
	for _, uid := range req.UserIDs {
		n := s.Local.PushAll(uid, data)
		if n == 0 {
			missing = append(missing, uid)
		}
	}
	for _, uid := range missing {
		s.Push.Notify(uid, req.Message)
		_ = s.KV.Delete(r.Context(), uid)
	}
	w.WriteHeader(http.StatusNoContent)
}
```

### 26.8 Consumer — KV 조회·서버별 그룹핑·비동기 릴레이

```go
// --- file: internal/consumer/worker.go ---
package consumer

import (
	"bytes"
	"context"
	"encoding/json"
	"log"
	"net/http"
	"time"

	"chatlab/internal/kv"
	"chatlab/internal/model"
	"chatlab/internal/push"
	"chatlab/internal/queue"
)

type Worker struct {
	Q      *queue.MemoryQueue
	KV     kv.Locator
	Push   push.Notifier
	Client *http.Client
}

func (w *Worker) Run(ctx context.Context) {
	for {
		select {
		case <-ctx.Done():
			return
		case batch := <-w.Q.Ch:
			w.handle(ctx, batch)
		}
	}
}

func (w *Worker) handle(ctx context.Context, batch model.DeliverBatch) {
	locs, err := w.KV.MGet(ctx, batch.UserIDs)
	if err != nil {
		log.Printf("kv mget err: %v", err)
		return
	}
	// serverAddr → userIDs
	groups := map[string][]string{}
	var offline []string
	for _, uid := range batch.UserIDs {
		addr, ok := locs[uid]
		if !ok || addr == "" {
			offline = append(offline, uid)
			continue
		}
		groups[addr] = append(groups[addr], uid)
	}
	for _, uid := range offline {
		w.Push.Notify(uid, batch.Message)
	}
	// 비동기 릴레이: 응답을 길게 기다리지 않음 (발표)
	for addr, users := range groups {
		addr, users := addr, users
		go w.relayFireAndForget(addr, users, batch.Message)
	}
}

func (w *Worker) relayFireAndForget(addr string, users []string, msg model.Message) {
	body, _ := json.Marshal(map[string]interface{}{
		"user_ids": users,
		"message":  msg,
	})
	req, err := http.NewRequest(http.MethodPost, "http://"+addr+"/internal/relay", bytes.NewReader(body))
	if err != nil {
		return
	}
	req.Header.Set("Content-Type", "application/json")
	ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
	defer cancel()
	req = req.WithContext(ctx)
	resp, err := w.Client.Do(req)
	if err != nil {
		// 실패 시 푸시 폴백 (서버 책임이지만 데모에선 워커도 보조)
		for _, uid := range users {
			w.Push.Notify(uid, msg)
		}
		return
	}
	resp.Body.Close()
}
```

## 27. 클라이언트 연결 수명·재접속·gap fill

### 개념

발표는 “앱 켤 때 연결”까지 말했지만, 실서비스는 **끊김이 일상**입니다. 실시간 푸시만 믿으면 메시지 구멍이 납니다.

```text
Connect → Authenticate → Sync(gap fill) → Live events
    ↑                                         │
    └────────── reconnect (backoff) ◀─────────┘
```

| 단계 | 할 일 |
|---|---|
| 최초/재접속 | `GET /v1/history?chat_id=&after_id=마지막수신ID` |
| 라이브 | WS `message` 프레임 수신 |
| 하트비트 | `ping` / `pong` + 서버는 KV TTL Touch (§30) |
| 백오프 | 1s, 2s, 4s… jitter (서버 폭풍 방지) |

```go
// 클라이언트 의사코드
func syncAndListen(chatID, lastID string, ws *WS) {
    gap := httpGet("/v1/history?chat_id="+chatID+"&after_id="+lastID)
    ui.Apply(gap)
    for frame := range ws.Frames {
        if frame.Type == "message" {
            ui.ApplyOne(frame.Payload)
            lastID = frame.Payload.MessageID
        }
    }
}
```

**신뢰성의 실제 정의:** DB에 있는 한, 실시간 실패는 **history pull로 회복** 가능해야 한다. 푸시는 “깨우기”이지 유일 전달 경로가 아니다.

### 체크포인트

- [ ] 재접속 시 반드시 gap fill을 하는가
- [ ] “푸시 도착 = 메시지 수신”으로 UI를 만들지 않는가 (앱 진입 후 history)

## 28. 메시지 ID·순서·멱등성

### 개념

발표는 message_id로 display_index를 갱신한다고만 했고, **ID 발급·중복 전송**은 생략했습니다. 구축 시 필수입니다.

| 문제 | 증상 | 대응 |
|---|---|---|
| 클라이언트 재시도 | 같은 문구 2번 저장 | `client_msg_id` 멱등 키 (§26 InsertMessage) |
| 시계 역전 | 목록 정렬 깨짐 | 서버 발급 단조 ID (snowflake/ULID) |
| 파티션 내 순서 | 같은 방 메시지 역전 | chat_id 파티션 키 + 단일 작성자 경로 / per-chat sequencer |
| at-least-once 전달 | WS 중복 수신 | 클라이언트 message_id dedupe |

```text
Client                  Server
  |-- send (client_msg_id=X) -->|
  |                             | insert if X unseen
  |<--------- ack (msg_id) -----|
  |-- send again (X) ---------->|
  |<--------- ack (same) -------|  // ErrDuplicate지만 같은 메시지 반환
```

방 안 순서 보장의 현실 단위:

- **같은 chat_id 안**에서 클라이언트가 message_id 정렬로 렌더
- 서버는 가능하면 **방 단위 직렬화**(샤드 단일 파티션 쓰기)로 강하게 보장

### 체크포인트

- [ ] 전송 API에 idempotency key가 있는가
- [ ] display_index에 쓰는 ID가 **정렬 가능**한가

## 29. 다중 기기 세션

### 개념

발표 예시는 `userId → session` 1개처럼 보이지만, 모바일+웹이 흔합니다.

```text
user A
  ├─ device phone → Server#1
  └─ device web   → Server#2   // 같은 유저, 서로 다른 서버 가능
```

| 설계 | 의미 |
|---|---|
| KV 값 | `userId → [ {device, server}, ... ]` 또는 device별 키 |
| 릴레이 | 유저의 **모든 기기 위치**로 fan-out |
| disconnect | **해당 device만** 제거. 마지막 device일 때만 KV 삭제 (§26) |

```go
// KV 값 예시 (JSON)
// chat:sess:A = [{"device":"phone","addr":"10.0.0.1:8080"},{"device":"web","addr":"10.0.0.2:8080"}]
```

푸시 정책: 같은 유저가 **어느 기기든 foreground 세션이 있으면** 푸시 억제할 수 있음.

### 체크포인트

- [ ] userId당 세션 1개 가정이 우리 제품에 맞는지 검토
- [ ] device 단위 disconnect가 KV를 통째로 지우지 않는지

## 30. KV TTL·하트비트·세션 정합성

### 개념

발표의 stale KV는 **서버 다운·비정상 종료**가 원인입니다. 운영에서는 TTL+하트비트가 1차 방어입니다.

```text
Connect:  SET user→addr EX 90
Every 30s ping: EXPIRE 90 (Touch)
Server crash: TTL 만료 → 자동 삭제 (유령 엔트리 수명 상한)
Relay miss:   즉시 Delete + Push   (능동 치유)
```

| 장치 | 역할 |
|---|---|
| TTL | 유령 엔트리의 **최대 생존 시간** |
| Touch | 정상 연결 유지 |
| Relay miss 삭제 | TTL을 기다리지 않는 **즉시 치유** |
| 로컬 세션 | 최종 판정자 |

주의: TTL만 길고 Touch가 없으면, 앱이 백그라운드에서 소켓만 죽은 채 KV가 남아 잘못된 릴레이가 납니다.

### 체크포인트

- [ ] KV TTL < “유령을 견딜 최대 시간”으로 설정했는가
- [ ] ping 주기가 TTL의 1/2~1/3인가

## 31. 관측성·SLO

### 개념

확장·청크·비동기는 **지표 없이** 튜닝할 수 없습니다.

| 지표 | 보는 이유 |
|---|---|
| WS 동시 접속 수 / 서버 | Chat Server 스케일 |
| 큐 lag / consumer lag | Consumer 스케일, 청크 크기 |
| 릴레이 4xx·타임아웃 비율 | stale KV·네트워크 |
| 푸시 시도 중 “KV miss 비율” | 오프라인 vs 버그 |
| 전송 API p50/p99 | display_index·동기 구간 |
| history QPS | 재접속 폭풍, gap fill 의존도 |
| DynamoDB throttle / hot partition | 초대형 방 chat_id |

예시 SLO (팀마다 조정):

```text
Send ACK p99 < 200ms   (Persist + enqueue까지)
Live delivery p99 < 1s (같은 리전 온라인)
Queue lag < 2s
Relay success > 99% (실패분은 푸시·history로 회복)
```

### 체크포인트

- [ ] 청크 크기를 lag·릴레이 p99로 튜닝할 계획이 있는가
- [ ] “전달 실패”를 메시지 유실과 분리해서 알람 치는가

## 부록 A. 용어 빠른 사전

| 용어 | 의미 |
|---|---|
| Session | 장수명 연결 핸들. 보통 서버 로컬 (device 단위 권장) |
| KV Store | userId → serverAddr 힌트. **truth 아님** |
| Relay | Consumer/타 서버 → Chat Server 내부 push 요청 |
| Consumer | 큐 이벤트를 처리하는 워커 |
| Fan-out | 한 메시지를 여러 수신자에게 퍼뜨림 |
| Chunk | 수신자 목록을 타임아웃 예산으로 자른 단위 (예: 200) |
| Shard / Partition Key | 물리 분산 기준 키 |
| display_index | 유저별 채팅 목록 정렬 키 (새 message_id 기반) |
| Stale | 실제 세션과 불일치하는 KV |
| Gap fill | 재접속 시 after_id 이후 history pull |
| Idempotency key | client_msg_id 등 중복 전송 방지 키 |
