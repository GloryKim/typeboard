# 쿠버네티스: 구글이 공개한 클러스터 제어와 그 복잡성의 대가

## 요약

컨테이너는 애플리케이션을 기계에서 떼어 냈다. 그다음 문제는 떼어 낸 애플리케이션을 기계 수백 대 위에서 누가 배치하고, 죽으면 누가 다시 살리고, 주소가 바뀌면 누가 찾아 주느냐다. 구글은 이 문제를 내부 시스템 Borg로 10년 넘게 풀고 있었고, 그 후속인 Omega에서 제어 평면을 나누는 법을 시험한 뒤, 2014년에 바깥 개발자를 위한 형태로 Kubernetes를 공개했다. 2015년 1.0과 함께 Cloud Native Computing Foundation의 시드 기술로 넘어가면서 클러스터 운영의 사실상 표준이 됐다.

표준이 된 뒤에 업계에는 다른 말이 붙었다. 쿠버네티스는 구글이 독을 풀었다는 말이다. 구글 규모에서 정당한 해법, 즉 선언된 상태와 관찰된 상태를 맞추는 제어 루프가, 서버 몇 대와 애플리케이션 하나로 충분한 조직에는 애플리케이션보다 큰 운영 대상이 된다는 뜻이다. 주니어 엔지니어는 프로덕션의 전제로 클러스터를 요구하고, 작은 팀의 기술 책임자는 단일 프로세스 슈퍼바이저나 기존 웹 프레임워크로 충분하다고 맞선다. 둘 다 일부만 맞다. 이 보고서는 구글이 실제로 푼 문제, 그 해법의 개론, 그리고 그 해법이 독이 되는 조건을 한 자리에 놓는다.

## 1. 기계 한 대를 떠나면 생기는 문제

프로세스 하나를 한 기계에서 돌릴 때 운영자가 보는 세계는 좁다. 바이너리 경로, 포트, 로그 파일, 재시작 정책이면 충분하다. 기계가 여러 대이고 프로세스가 자주 죽거나 옮겨 다니면 질문의 종류가 바뀐다.

```text
누가 이 프로세스를 어느 기계에 올릴 것인가
기계가 죽으면 복제본은 어디로 다시 태어나는가
복제본의 IP가 바뀔 때 호출자는 어떤 이름을 부르는가
새 버전은 한 대씩 교체되는가, 전부 같이 죽는가
남는 CPU를 다른 작업이 써도 앞단 지연이 무너지지 않는가
```

이 질문들은 애플리케이션 코드 밖에 있다. 패키징이 아무리 깔끔해도 배치, 복구, 이름 붙이기, 자원 공유는 별도 시스템이다. 구글은 이 층을 컨테이너 관리라고 불렀고, 컨테이너 관리만으로는 끝나지 않는다는 것도 같은 경험에서 배웠다.

## 2. 구글이 안에서 푼 것: Borg, Omega, Kubernetes

구글의 첫 통합 컨테이너 관리 시스템은 Borg다. 그 전에는 오래 도는 서비스를 Babysitter가, 배치 작업을 Global Work Queue가 맡았다. Borg는 둘을 한 클러스터에 올렸다. 사용자용 서비스는 스파이크와 장애 대비로 자원을 넉넉히 예약하고, 평소에 비는 몫을 배치 작업이 가져다 쓴다. 지연에 민감한 프로세스와 CPU를 많이 먹는 프로세스가 한 기계에 있으려면 커널 수준 격리가 필요하고, 구글은 Linux 컨테이너 구현에 직접 기여하며 그 격리를 만들었다. EuroSys 2015에 공개된 Borg 논문의 규모는 수만 대 기계로 이뤄진 클러스터 여럿 위에서, 수천 가지 애플리케이션의 수십만 개 작업을 돌리는 수준이다.

Borg 위에는 이름 서비스, 로드밸런싱, 수평·수직 오토스케일, 롤아웃, 모니터링, 쿼터가 팀마다 따로 자랐다. 성공한 도구는 널리 퍼졌고, 각자 다른 API와 규약을 가졌다. 논문 저자들은 이 생태계가 배포 복잡도를 키웠다고 적는다. 오케스트레이션은 시작이지 끝이 아니었다.

Omega는 그 생태계의 소프트웨어 공학을 고치려는 후속작이다. 클러스터 상태를 Paxos 기반 저장소 한곳에 두고, 스케줄러를 포함한 제어 평면 구성요소가 그 저장소를 낙관적 동시성으로 직접 읽고 쓰게 했다. Borgmaster 하나에 몰려 있던 기능이 대등한 컴포넌트로 갈라졌다. Omega의 여러 아이디어는 이후 Borg로 다시 흡수됐다.

Kubernetes는 세 번째다. Borg와 Omega가 구글 내부 전용이었다면, Kubernetes는 리눅스 컨테이너에 대한 외부 관심이 커지고 구글이 퍼블릭 클라우드를 팔기 시작한 시점에 오픈소스로 설계됐다. 이름은 키잡이를 뜻하는 그리스어에서 왔고, k8s는 K와 s 사이의 여덟 글자를 센 약자다. Omega처럼 공유 저장소가 중심에 있지만, 신뢰된 제어 평면만 저장소를 직접 만지던 방식은 버렸다. 모든 상태는 버전과 검증과 정책을 거는 도메인 REST API를 통과한다. 설계 목표는 컨테이너가 주는 활용률을 유지하면서, 클러스터 위에서 복잡한 분산 시스템을 배포하고 운영하기 쉽게 만드는 것이었다.

2016년 ACM Queue에 실린 Burns, Grant, Oppenheimer, Brewer, Wilkes의 회고는 세 시스템의 차이를 API 경계로 요약한다. Borgmaster는 모든 연산의 의미를 아는 단일 컴포넌트다. Omega는 저장소만 중심에 있고 의미는 클라이언트로 밀려난다. Kubernetes는 가운데다. 컴포넌트는 느슨하게 갈라져 있어도, API 서버가 불변 조건과 기본값과 버전을 강제한다.

| 시스템 | 시기와 성격 | 상태의 위치 | 외부 노출 |
| --- | --- | --- | --- |
| Borg | 장기 서비스와 배치를 한 클러스터에 혼재. 구글의 주 시스템으로 남음 | Borgmaster 안의 복제 저장소 | 내부 전용 |
| Omega | Borg 생태계의 구조를 다시 짜려는 후속 | Paxos 저장소를 제어 평면이 직접 접근 | 내부 전용 |
| Kubernetes | 외부 개발자의 배포 경험을 목표로 한 재설계 | etcd. 접근은 API 서버만 | 2014년 공개, 2015년 CNCF 기증 |

> 출처: [Verma 외, EuroSys 2015, Large-scale cluster management at Google with Borg](https://research.google/pubs/large-scale-cluster-management-at-google-with-borg/), [Burns 외, ACM Queue 2016, Borg, Omega, and Kubernetes](https://queue.acm.org/doi/full/10.1145/2898442.2898444), [Kubernetes 블로그, Borg: The Predecessor to Kubernetes](https://kubernetes.io/blog/2015/04/borg-predecessor-to-kubernetes/)

## 3. 이미지와 스케줄은 다른 층이다

Docker가 2013년 전후에 퍼뜨린 것은 격리 기술 자체가 아니다. 격리와 이미지를 한 단위로 묶어, 의존성이 거의 커널 시스템 콜 경계 안에 들어오는 패키지를 레지스트리로 주고받게 만든 일이다. 구글 내부의 대응물은 Midas Package Manager였고, Borg 컨테이너는 호스트에 깔린 베이스 이미지에 일부 의존했다. Docker 계열 이미지 포맷은 그 의존을 더 줄여 개발 환경과 운영 환경의 차이를 좁혔다.

이미지가 풀지 않는 것이 클러스터 문제다. 이미지 하나는 프로세스 트리를 상자에 넣는다. 상자가 어느 노드에 올라갈지, 노드가 사라지면 상자를 어디서 다시 만들지, 상자 앞의 안정된 주소는 누가 유지할지는 이미지 포맷 밖의 일이다. 단일 호스트의 컨테이너 런타임, 여러 호스트의 스케줄러, 그 위의 이름과 배포 정책은 층이 다르다. 쿠버네티스는 가운데와 위층을 표준 객체로 고정한 시스템이다. 아래층의 컨테이너 실행은 CRI로 분리되어 있고, 흔히 containerd나 CRI-O가 맡는다. 이미지 포맷이 Docker와 같다는 사실과, 노드에서 Docker 엔진이 돌아간다는 사실은 같은 문장이 아니다.

## 4. 쿠버네티스 개론

### 4.1 클러스터는 두 종류의 기계다

클러스터는 제어 평면과 워커로 나뉜다. 제어 평면은 원하는 상태를 저장하고 그 상태를 향해 행동을 고른다. 워커는 그 결정에 따라 컨테이너를 실제로 돌린다. 프로덕션에서는 제어 평면을 여러 대에 두고 장애 도메인을 나누는 것이 보통이다. 관리형 쿠버네티스(GKE, EKS, AKS 등)는 이 제어 평면의 쿼럼과 업그레이드를 클라우드 사업자가 맡는다. 그 경우에도 워커와 그 위의 객체 모델은 사용자 책임으로 남는다.

| 구성요소 | 놓이는 곳 | 하는 일 |
| --- | --- | --- |
| kube-apiserver | 제어 평면 | 클러스터의 유일한 문. 인증, 인가, 검증, 기본값, 버전을 거친 뒤에만 상태를 바꾼다 |
| etcd | 제어 평면 | 클러스터 상태의 일관된 키-값 저장소. Raft로 쿼럼을 맞춘다 |
| kube-scheduler | 제어 평면 | 아직 노드가 없는 Pod을 자원, 제약, 선호에 따라 노드에 묶는다 |
| kube-controller-manager | 제어 평면 | Deployment, ReplicaSet, Node, Job, Endpoint 등 컨트롤러의 조정 루프를 돌린다 |
| cloud-controller-manager | 제어 평면 | 로드밸런서, 라우트, 노드 수명을 클라우드 API와 맞춘다. 없는 클러스터도 있다 |
| kubelet | 워커 | 노드 에이전트. API에서 받은 Pod 명세를 컨테이너 런타임으로 실행하고 상태를 보고한다 |
| 컨테이너 런타임 | 워커 | 이미지를 받아 컨테이너를 시작하고 멈춘다 |
| kube-proxy | 워커 | Service의 가상 주소를 실제 Pod으로 잇는다. CNI 구현이 이 역할을 대체하기도 한다 |

### 4.2 원하는 상태와 조정 루프

쿠버네티스 객체의 공통 뼈대는 메타데이터, spec, status 세 칸이다. 메타데이터는 이름, UID, 리소스 버전, 레이블처럼 모든 객체에 같은 모양으로 붙는다. spec은 사용자가 선언한 원하는 상태다. status는 시스템이 관찰한 현재 상태이며 읽기 전용이다.

컨트롤러는 상태 기계의 다음 단계를 외워서 진행하지 않는다. 원하는 개수와 관찰된 개수의 차이를 보고, 차이를 줄이는 행동을 하고, 다시 관찰한다. 컨트롤러가 죽어도 저장소에 남은 spec과 status만 있으면 재시작 후 같은 차이를 다시 계산한다. Burns 등이 말한 설계 선택은 중앙의 하나의 오케스트라가 아니라, 작은 제어 루프 여러 개의 안무다. 예상하지 못한 장애에  brittle 한 중앙 상태 기계를 피하려는 선택이다.

```text
사용자: spec을 API 서버에 제출
API 서버: 검증 후 etcd에 기록
컨트롤러: spec과 status의 차이를 계산
스케줄러: Pod에 노드를 기록
kubelet: 그 노드에서 컨테이너를 실행하고 status를 갱신
컨트롤러: 차이가 0이 될 때까지 반복
```

차이가 0인 시간은 짧다. 노드가 사라지고, 프로브가 실패하고, 누군가 spec의 복제본 수를 바꾸면 루프가 다시 돈다. 쿠버네티스의 안정성은 "한 번 배포하면 가만히 있는 시스템"이 아니라 "어긋남을 계속 수선하는 시스템"에서 온다.

### 4.3 워크로드 객체

가장 작은 배포 단위는 Pod이다. Borg의 alloc에 해당한다. 한 Pod 안의 컨테이너는 같은 노드에 같이 스케줄되고, 네트워크 네임스페이스와 따라서 IP 하나를 공유하며, 볼륨으로 파일을 공유할 수 있다. 주 프로세스 옆에 로그를 빼는 프로세스를 두는 패턴이 대표적이다. 구글은 Borg에서 최상위 컨테이너가 alloc 없이 도는 경우를 허용했다가 불편이 컸고, Kubernetes는 컨테이너가 항상 Pod 안에 있게 고정했다.

Pod IP를 하나씩 준 것도 Borg에서 배운 부정 교훈이다. Borg는 한 기계의 IP를 컨테이너가 공유하고 스케줄러가 포트를 나눠 줬다. 컨테이너가 기계를 옮기면 포트가 바뀌어 DNS, URL, 기성 소프트웨어가 모두 흔들렸다. Kubernetes는 네트워크 신원을 애플리케이션 신원과 맞추기 위해 Pod마다 IP를 준다. 애플리케이션은 80번 같은 잘 알려진 포트를 그대로 쓴다. 이 IP는 Pod이 다시 만들어지면 바뀐다. 바뀌지 말아야 할 주소는 Pod이 아니라 Service가 맡는다.

복제와 업데이트는 Pod 위의 컨트롤러가 맡는다.

| 객체 | 보장 |
| --- | --- |
| ReplicaSet | 레이블로 고른 Pod을 원하는 개수만큼 유지 |
| Deployment | ReplicaSet을 세대별로 교체. 롤링 업데이트와 롤백 |
| StatefulSet | 순서와 안정된 네트워크 이름, 안정된 스토리지가 필요한 복제 |
| DaemonSet | 대상 노드마다 Pod 하나. 로그 에이전트, CNI 노드 컴포넌트 |
| Job, CronJob | 끝나야 하는 작업, 그리고 그 작업의 주기 실행 |
| Service | 레이블 셀렉터에 맞는 Pod 집합에 안정된 이름과 부하 분산 |
| Ingress, Gateway | 클러스터 밖 HTTP 경로를 Service에 연결. 구현체는 별도 컨트롤러 |
| ConfigMap, Secret | 이미지에 넣지 않는 설정과 자격 증명 |
| Namespace | 이름과 권한과 쿼터의 경계 |

레이블은 Borg의 Job 벡터를 대체한다. Borg는 같은 작업의 태스크를 0부터 번호를 매긴 벡터로만 묶었고, 롤링 업데이트의 재시작 순서가 샤딩 인덱스와 부딪히거나, 역할과 카나리 여부를 이름에 인코딩해 정규식으로 해석하는 일이 생겼다. Kubernetes의 레이블은 아무 키-값이나 붙일 수 있고, 셀렉터는 그 위의 동적 집합이다. 한 Pod이 여러 집합에 속할 수 있다. Service가 트래픽을 보낼 집합과, ReplicaSet이 개수를 맞출 집합은 레이블로 느슨하게 만난다. 오동작하는 Pod에서 Service가 보는 레이블만 떼면 트래픽에서는 빠지고 프로세스는 살아 있어 그 자리에서 디버그할 수 있다. ReplicaSet은 부족한 개수를 보고 대체 Pod을 만든다.

최소 선언은 아래 두 객체다. Deployment가 Pod 템플릿의 복제본 둘을 유지하고, Service가 `app=hello`인 Pod으로 80번 포트를 넘긴다.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: hello
spec:
  replicas: 2
  selector:
    matchLabels:
      app: hello
  template:
    metadata:
      labels:
        app: hello
    spec:
      containers:
        - name: app
          image: hello:1.4.2
          ports:
            - containerPort: 8080
---
apiVersion: v1
kind: Service
metadata:
  name: hello
spec:
  selector:
    app: hello
  ports:
    - port: 80
      targetPort: 8080
```

사용자가 만지는 숫자는 두 개다. 복제본 수와 이미지 태그다. 어느 노드의 몇 번 IP인지는 spec에 없다. 그 값은 status로 관찰될 뿐이다.

### 4.4 요청이 지나가는 길

클러스터 안의 다른 Pod이 `http://hello`를 호출하면 클러스터 DNS가 Service의 가상 IP를 돌려준다. kube-proxy 또는 CNI의 데이터 플레인이 그 가상 IP를 현재 준비된 Pod의 IP와 포트로 바꾼다. Pod이 교체되어도 Service 이름은 그대로다. 클러스터 밖에서는 Service 타입을 LoadBalancer로 두거나, Ingress·Gateway 컨트롤러가 외부 로드밸런서와 인증서를 연결한다. 외부 주소, Service, Pod IP는 세 개의 다른 수명이다. 이 셋을 한 주소로 착각하면 장애 분석이 어긋난다.

```text
클라이언트
  → 외부 로드밸런서 또는 Ingress
    → Service (가상 IP, 셀렉터)
      → 준비된 Pod IP
        → 컨테이너 포트
```

준비됐다는 판정은 프로브가 한다. 구글 Borg의 `/healthz`가 이 자리의 원형이다. 라이브니스 프로브가 실패하면 kubelet이 컨테이너를 다시 시작하고, 레디니스 프로브가 실패하면 Service가 그 Pod을 부하 분산에서 뺀다. 프로세스가 살아 있다는 사실과 트래픽을 받아도 된다는 사실은 일부러 분리돼 있다.

## 5. 왜 독이라고 불리는가

### 5.1 공개된 것은 커널이고, 남긴 것은 생태계다

Borg의 체감 가치는 스케줄러 단독이 아니었다. 이름 서비스, 마스터 선출, 애플리케이션을 아는 로드밸런싱, 오토스케일, 롤아웃, 워크플로, 모니터링이 붙은 다음이었다. 그 도구들은 팀의 필요에 따라 유기적으로 자랐고, API가 제각각이라 배포를 더 어렵게 만들었다. Kubernetes는 객체마다 같은 메타데이터와 spec, status를 갖게 해서 그 난립을 줄이려 했다. 학습 비용과 범용 도구 작성 비용은 실제로 줄었다.

난립은 클러스터 밖으로 다시 자랐다. 인그레스 구현체, 인증서 발급기, 시크릿 동기화, 정책 엔진, 서비스 메시, GitOps 컨트롤러, 노드 오토스케일러, 배포 가능한 관측 스택이 각각 합리적 이유로 추가된다. 합이 애플리케이션과 별개인 두 번째 분산 시스템이 된다. 구글 안에는 그 시스템을 직업으로 갖는 사람과 내부 플랫폼이 있었다. 공개된 배포본은 제어 루프와 객체 모델을 담고, 그 주위의 인력은 가져오지 않는다. "독을 풀었다"는 말은 제어 루프가 결함이 있다는 뜻이 아니다. 구글 규모의 용량으로 맞춘 약이 용량 표시 없이 유통됐다는 뜻이다.

### 5.2 설정은 구글도 끝내지 못한 문제다

2016년 회고에서 저자들이 가장 많은 두뇌와 잉크와 코드가 들어갔다고 밝힌 문제는 설정이다. 컨테이너 관리 시스템이 아직 하지 않는 일은 전부 설정 쪽으로 밀린다. 재시작 정책의 기본값, 플래그 검증, 이미지 버전, 릴리스 절차, 템플릿 라이브러리가 그렇게 설정 언어로 들어온다. 데이터에 계산이 필요해지는 순간 설정 언어는 튜링 완전을 향해 가고, 본래 피하려던 "설정이 코드"가 더 약한 언어로 다시 나타난다. 디버거와 테스트는 빈약하다.

쿠버네티스 실무는 이 문단을 거의 그대로 재현했다. YAML은 데이터로 충분하다는 전제에서 출발했고, 환경별 차이, 복제본 계산, 시크릿 주입이 필요해지자 Helm과 Kustomize와 각종 생성기가 계산을 맡았다. 계산과 데이터를 분리하라는 논문의 권고는 맞다. 그 분리를 팀이 실제로 유지하는 비용은 논문이 경고한 그 비용이다. 작은 서비스의 운영 복잡도는 애플리케이션 저장소가 아니라 클러스터 매니페스트 저장소에서 먼저 커진다.

같은 논문은 의존성 관리도 미해결로 남겼다. 서비스를 세운다는 것은 모니터링, 저장소, 배포 파이프를 같이 세운다는 뜻인데, 관리 시스템이 그 의존을 자동으로 올려 주지는 않는다. 수동으로 적은 의존 정보는 금세 썩고, 호출 추적으로 복원한 의존 정보는 "하필 그 인스턴스여야 했는가, 아무 인스턴스나 됐는가"를 구분하지 못한다. 새 애플리케이션을 올리는 일이 여전히 어려운 이유는 스케줄러가 없어서가 아니다. 부수 시스템을 같이 세워야 하기 때문이다.

### 5.3 채용 시장의 기본값이 된 뒤의 마찰

클러스터가 이력서의 기본 항목이 된 뒤에는 기술 선택과 무관한 압력이 생긴다. 경력이 짧은 엔지니어는 프로덕션이면 쿠버네티스라고 학습하고, 그 전제를 팀의 기본값으로 가져온다. 애플리케이션 하나, 배포 주기, 장애 시 사람 개입이 감당되는 작은 조직의 기술 책임자는 반대 압력을 말한다. 단일 언어의 웹 애플리케이션과 프로세스 슈퍼바이저, 또는 플랫폼이 프로세스를 대신 살려 주는 PaaS로 충분한데 왜 클러스터를 전제로 하느냐는 질문이다.

이 마찰은 무지가 아니다. 두 사람이 다른 실패 비용을 보고 있다. 주니어가 학습한 실패는 노드가 사라지고 복제본이 스스로 돌아와야 하는 실패다. 작은 팀의 실제 실패는 스키마 실수, 느린 쿼리, 잘못된 배포 한 건인 경우가 많다. 후자를 고치는 데 제어 평면 쿼럼, CNI, 인증서 회전, RBAC는 새 장애 면을 더할 뿐 기존 장애를 줄이지 않는다. 쿠버네티스를 배운 사람일수록 그 새 장애 면이 익숙해서, 익숙함을 필요와 혼동하기 쉽다.

독성의 실체는 기능 목록이 아니라 상시 비용이다.

```text
개념 비용 : Pod, Service, Ingress의 수명이 다르다는 것을 팀이 공유해야 한다
운영 비용 : etcd 쿼럼, 업그레이드 순서, CNI, CSI, 인증서, 권한
진단 비용 : 한 호스트의 로그 대신 이벤트, 프로브, 엔드포인트, 네트워크 정책을 따라간다
사회 비용 : "클러스터가 없는 프로덕션"을 미숙함으로 보는 채용과 리뷰 문화
```

관리형 제어 평면은 첫 번째와 두 번째의 일부를 돈으로 바꾼다. 객체 모델과 진단 비용과 사회 비용은 청구서 밖에 남는다.

## 6. 용량이 맞을 때와 맞지 않을 때

쿠버네티스가 비용을 회수하는 자리는 기계 장애를 정상 상태로 두고, 서비스가 여럿이고, 배포가 자주 겹치고, 팀을 넘어 같은 배치 규칙을 재사용해야 할 때다. 롤링 업데이트, 레디니스에 따른 트래픽 제거, 노드 추가만으로 용량을 늘리는 일, 배치 작업과 온라인 서비스의 한 클러스터 공유는 이 객체 모델이 Borg에서 가져와 잘 푸는 문제다. 플랫폼 팀이 있거나 관리형 쿠버네티스로 제어 평면을 넘긴 조직에서는 애플리케이션 팀이 spec만 다루게 만들 수 있다. 그 상태가 구글이 내부에서 누리던 상태에 가깝다.

용량이 맞지 않는 자리는 서비스 수와 사람 수와 장애 유형이 작은 곳이다. 프로세스가 한 종류이고, 재시작은 슈퍼바이저로 충분하고, 외부 트래픽은 로드밸런서 하나면 되고, 토요일에 엔드포인트와 CNI를 볼 사람이 없다. 이 조건에서는 단일 가상 머신, 프로세스 슈퍼바이저, 단일 호스트의 컨테이너 런타임, 또는 배포와 도메인과 TLS를 대신해 주는 PaaS가 운영 표면이 더 작다. 수평 확장이 필요해진 뒤에도 바로 클러스터로 갈 필요는 없다. 복제본 몇 개와 앞단 로드밸런서로 한 단계를 더 둘 수 있다.

| 신호 | 클러스터가 비용을 회수하는 쪽 | 클러스터가 새 시스템이 되는 쪽 |
| --- | --- | --- |
| 서비스 수 | 여러 팀이 여러 서비스를 같은 규칙으로 배포 | 서비스 하나 또는 소수 |
| 장애 모델 | 노드 손실이 일상, 사람 개입 없이 복귀해야 함 | 주 장애가 애플리케이션 결함과 배포 실수 |
| 배포 | 하루에도 여러 번, 무중단이 요구됨 | 배포 빈도가 낮고 짧은 중단이 허용됨 |
| 사람 | 플랫폼을 직업으로 갖는 사람이 있음 | 애플리케이션 개발자가 클러스터까지 혼자 봄 |
| 활용률 | 서비스와 배치를 한 기계에 섞어 남김을 줄여야 함 | 기계 한두 대의 유휴 CPU가 비용 문제가 아님 |

중간 지대는 관리형 클러스터다. 제어 평면의 독성, 즉 etcd와 업그레이드와 마스터 쿼럼은 크게 줄고, 객체 모델의 독성, 즉 spec을 읽고 프로브를 해석하고 애드온을 고르는 일은 남는다. 관리형을 쓴다는 문장은 "쿠버네티스를 운영하지 않는다"가 아니라 "제어 평면의 일부를 구매했다"에 가깝다.

## 7. 도입 전에 보는 점검표

| 영역 | 점검 항목 |
| --- | --- |
| 실패 | 지금 두려워하는 실패가 노드 소실인가, 애플리케이션 결함인가? |
| 사람 | 클러스터의 업그레이드와 CNI와 권한을 볼 이름이 달력에 있는가? |
| 서비스 경계 | 서비스가 둘 이상이고, 팀 사이 배포 규칙을 공유해야 하는가? |
| 제어 평면 | 관리형으로 쿼럼을 넘길 것인가, 직접 etcd를 책임질 것인가? |
| 주소 | 외부 주소, Service, Pod IP의 수명을 팀이 구분해 설명할 수 있는가? |
| 프로브 | 프로세스 생존과 트래픽 수신 가능을 다른 프로브로 나눌 수 있는가? |
| 설정 | 환경별 차이가 데이터로 남는가, 템플릿 언어의 계산으로 새는가? |
| 애드온 | 인그레스, 인증서, 시크릿, 메시에 각각 담당과 업그레이드 주기가 있는가? |
| 대안 | 슈퍼바이저, 복제본 몇 개의 로드밸런서, PaaS로 이번 분기의 요구가 끝나는가? |
| 사회 신호 | 클러스터를 고르는 이유가 장애 모델인가, 이력서와 관례인가? |

여섯 번째 줄까지 답이 없으면 객체 모델을 배울 이유는 있어도, 이번 서비스의 런타임으로 올릴 이유는 약하다. 학습과 운영을 분리하는 편이 비용이 작다. 로컬 클러스터나 문서 속의 예제로 조정 루프를 이해하고, 프로덕션 런타임은 서비스의 실제 실패에 맞는 더 작은 시스템을 둔다.

## 결론

구글이 푼 문제는 선명하다. 기계를 직접 고르는 데이터센터를, 애플리케이션을 단위로 선언하고 어긋나면 수선하는 데이터센터로 바꾸는 일이다. Borg가 그 문제를 내부에서 풀었고, Omega가 제어 평면을 나누었고, Kubernetes가 그 결과를 검증 가능한 API와 Pod, Service, 레이블, 조정 루프로 외부에 공개했다. 이미지 포맷이 포장지를 표준화했다면, 쿠버네티스는 포장지를 여러 기계 위에 올려 두고 살리는 제어를 표준화했다.

독이라는 말은 그 표준의 결함을 가리키지 않는다. 용량을 가리킨다. 구글은 오케스트레이션이 시작일 뿐이고, 설정 언어는 약한 프로그래밍 언어가 되기 쉬우며, 의존 시스템을 같이 세우는 문제는 아직 열려 있다고 2016년에 이미 적었다. 그 문단이 예고한 생태계가 산업 표준 주위에 그대로 자랐다. 노드 장애가 일상이고 플랫폼을 볼 사람이 있는 조직에게 이 생태계는 약이다. 애플리케이션 하나와 개발자 몇이 전부인 조직에게는, 약 성분과 같은 물질이 운영 부담이 된다. 쿠버네티스를 아는 일은 제어 루프를 이해했다는 뜻이다. 쿠버네티스를 띄우는 일은 그 루프가 수선해 줄 실패를 지금 가지고 있다는 뜻이어야 한다.
