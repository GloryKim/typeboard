## 1. 한 줄 정의

**Graph Engineering**은 LLM 한 번의 “루프”에 문제를 맡기는 대신, **노드(node)와 엣지(edge)로 이루어진 워크플로 그래프**를 설계해서 문제를 푸는 방식이다.

비유로 말하자면, **조직도(organizational chart)** 다.  
차트의 각 칸이 “누가 무엇을 하는지”이고, Graph Engineering에서는 그 칸이 **에이전트 노드**, **함수(결정론적 로직) 노드**, 그 외 처리 단위가 된다. 엔지니어가 **무엇을, 어떤 순서로, 다음에 무엇이 일어나는지**를 미리 정의하여 문제를 해결해나가는 엔지니어링이다.

---

## 2. 왜 “그래프”인가

포인트는 세 가지다.

1. **구조** — 노드와 엣지로 워크플로를 표현한다.
2. **순서** — 입력이 들어오면 어떤 노드를 지나 어떤 출력이 나오는지가 정의되어 있다.
3. **정보 전달** — 그래프를 **순회(traverse)** 할 때, 메모리나 상태(정보를) 다음 노드로 넘긴다.

Google **Agent Development Kit (ADK)** 로 멀티에이전트나 워크플로를 만들 때도, 에이전트들·노드들 사이에 **공유 상태(shared state)** 가 있다고 한다.. 즉 그래프는 단순한 그림이 아니라, **상태와 제어 흐름을 옮기는 실행 모델**이다.

---

## 3. 용어 정리: Harness · Loop · Graph

혼동하기 쉬워서 직접 구분한 세 개념이다.


| 용어          | 정의                                          | 의미                                  |
| ----------- | ------------------------------------------- | ----------------------------------- |
| **Harness** | 모델 **주변의 모든 것** — tools, memory, guardrails | 모델이 돌아가는 **울타리·환경**                 |
| **Loop**    | 그 harness **안에서** 에이전트가 도는 **사이클**          | 추론 → 결정 → 도구 선택 → 다시 추론… 목표 충족까지 반복 |
| **Graph**   | 조직도처럼 **노드·엣지로 짜인 워크플로**                    | 에이전트 노드, 함수 노드 등을 배치한 **전체 설계도**    |


정리하면:

- **Loop** = 한 에이전트(또는 한 단위)가 harness 안에서 목표를 향해 도는 **내부 반복**
- **Graph** = 여러 노드를 연결해 **전체 문제 해결 경로**를 만든 것
- **Harness** = 그 모든 것이 붙는 **도구·메모리·가드레일 인프라**

Graph Engineering은 이 셋 중 **그래프(워크플로)를 설계하는 쪽**에 초점을 둔다.

---

## 4. 지식 그래프(Knowledge Graph)와는 다른 것

Graph Engineering을 **지식 그래프·데이터 모델**로 오해했분은 다음과 같다.


| 용어                    | 강조점                                                        |
| --------------------- | ---------------------------------------------------------- |
| **Knowledge Graph**   | **데이터** — 무엇이 무엇과 연결되는지(지식 표현)                             |
| **GraphRAG**          | (이름에 graph가 들어가지만) 검색·생성 맥락의 다른 계열 용어로 언급                  |
| **Graph Engineering** | **행동(behavior)** — 무엇이 들어가고, **어떤 순서**로, **다음에 무엇이** 일어나는지 |


같은 “graph” 단어라도:

- Knowledge Graph → **지식·데이터 구조**
- Graph Engineering → **에이전트/워크플로 제어 흐름**

이 보고서는 후자만 다룬다. Knowledge Graph 구현 세부(Neo4j 등)는 없다.

---



## 5. Loop Engineering과의 차이


|                | Loop Engineering                 | Graph Engineering                    |
| -------------- | -------------------------------- | ------------------------------------ |
| 형태             | **하나의 실행 루프**가 목표에 도달할 때까지 계속 돈다 | **워크플로 그래프**를 만들고, 노드·엣지로 문제를 푼다     |
| 적합한 경우 (영상 비유) | 단순한 작업 — 예: **한 문단 요약**          | 복잡한 작업 — 예: **50페이지 PDF**, 여러 산출물·단계 |
| 제어             | “될 때까지 루프”                       | “이 노드 → 저 노드”가 **미리 정의**             |


영상 결론에 가까운 선택 기준:

- **워크플로를 미리 알고 있으면** → Graph Engineering
- **단순·단일 목표 루프**면 → Loop Engineering으로도 충분할 수 있음

---



## 6. Agent Swarm과의 차이

둘 다 **에이전트 오케스트레이션 패턴**이지만, under the hood가 다르다고 말한다.

### Graph Engineering

- **엔지니어가 각 노드**를 정의한다.
- 워크플로의 **각 단계**에서 무엇이 일어나는지, **데이터가 어떤 모양**인지까지 정한다.
- 특정 노드의 에이전트는 **이전 단계 전체를 알 필요가 없다** (노드에 필요한 입력만).
- 얻는 것: **예측 가능성(predictability)**, **디버깅 용이성(debuggability)**, **제어(control)**
- 잘 맞는 문제: **엄격히 정의 가능한** 프로세스 (아래 PR 리뷰 예)



### Agent Swarm

- 각 에이전트에 **성격(personality)** 만 주고, **문제를 던져** 협업하게 한다.
- 워크플로를 노드·엣지로 전부 고정하지 않는다.
- 잘 맞는 문제: **모호(ambiguous)** 하고, 유연한 탐색이 필요한 경우

선택 기준 (영상 요약):

- **이미 워크플로를 알고 있다** (예: PR 리뷰 절차) → **Graph Workflow**
- **문제가 애매하다** → **Agent Swarm**이 더 유연

## 7. 실전 예: PR 리뷰 자동화 그래프

PR 리뷰를 **이미 어떻게 하는지 알고 있기 때문에**, 그 절차를 워크플로로 고정한다.

전체는 세 구간으로 나뉜다.

```
[ Fan-out ] → [ Join ] → [ Router ]
```



### 7.1 Fan-out (분기·병렬)

- PR에서 정보를 모으기 위해 **여러 처리를 동시에** 돌린다.
- 영상 예: **5개의 병렬 처리**로 PR(pull request) 정보를 수집.
- 직렬로 하나씩 끝나는 것을 기다리는 것보다 **빠르다**.
- 소프트웨어의 “한 일을 쪼개서 동시에 돌린다”와 같은 발상이다.



### 7.2 Join (합류)

- 병렬이 끝난 뒤 **결과를 합치는(synthesize)** 노드.
- **가장 느린 처리가 끝날 때까지 기다린** 다음, 이후 단계에서 쓸 수 있게 결과를 모은다.
- 분산 시스템의 barrier / gather와 같은 역할로 이해하면 설명과 맞다.



### 7.3 Router (라우터)

- 웹의 **URL → 페이지** 라우터와 비슷하다고 설명한다.
- 여기서는 **입력/조건**에 따라 **다른 서브에이전트·전문가·하위 워크플로**로 보낸다.
- PR 예에서의 조건:
  - **호출/검사 실패** → specialized **fixer** 에이전트
  - **통과** → **human approval** 처리

영상 진행자 표현: **제어 흐름(control flow)의 기본 원리**를 AI 엔지니어링에 적용한 것이다.

## 8. Graph Engineering을 “팩트”로만 압축하면

명시적으로 말할 수 있는 사실만 모으면 다음과 같다.

1. Graph Engineering = **그래프 워크플로를 시스템에 만드는 것**.
2. 노드 예: **agent node**, **function node**(결정론적 로직), 그 이상도 가능.
3. 그래프 순회 시 **메모리/정보를 다음 노드로 전달**한다.
4. ADK 등에서는 **공유 상태**로 멀티에이전트·워크플로 노드가 연결된다.
5. **Harness** = 모델 주변(tools, memory, guardrails). **Loop** = harness 안 사이클. **Graph** = 조직도형 워크플로.
6. Knowledge Graph는 **데이터**, Graph Engineering은 **행동·순서**.
7. Loop Engineering은 **단일 루프**, Graph Engineering은 **노드·엣지 워크플로**.
8. Agent Swarm은 **느슨한 역할 부여 + 문제 투척**, Graph는 **단계·데이터 형태까지 엔지니어가 정의** → 예측·디버그·제어에 유리.
9. PR 리뷰 예는 **fan-out → join → router** 패턴으로 구체화된다.
10. 학습 다음 단계로 언급된 도구: **Google Agent Development Kit (ADK)** 튜토리얼.

- 특정 Graph DB, Cypher, Neo4j 구현
- LangGraph/LangChain API 세부
- 성능 벤치마크 수치
- Knowledge Graph 구축 방법론

---



## 9. 언제 Graph Engineering을 쓰는가 (영상 기준 의사결정)


| 상황                                  | 추천                              |
| ----------------------------------- | ------------------------------- |
| 절차를 **미리 알고** 있다 (PR 리뷰, 고정 승인 플로우) | **Graph Engineering**           |
| 목표가 단순하다 (짧은 요약)                    | **Loop Engineering**으로 충분할 수 있음 |
| 문제가 **모호**하고 탐색이 필요하다               | **Agent Swarm**                 |
| 예측·디버깅·통제가 중요하다                     | **Graph** (노드별 정의)              |


---



## 10. 맺음말

남기는 메시지는 단순하다.

> Graph Engineering은 에이전트 시대에 **자료구조·제어 흐름**을 다시 쓰는 일에 가깝다.  
> “그래프”는 지식 DB가 아니라, **누가(노드) 무엇을 어떤 순서로(엣지) 처리할지**를 엔지니어가 그리는 설계다.

실무적으로는 **fan-out / join / router** 같은 고전적 제어 흐름 패턴을, LLM·에이전트·결정론적 함수를 담은 노드에 올려 놓는 것이 Graph Engineering의 핵심이다.
