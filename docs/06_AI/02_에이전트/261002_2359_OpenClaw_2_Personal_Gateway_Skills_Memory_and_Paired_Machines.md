# OpenClaw 2: 자기 게이트웨이 위의 개인 에이전트

## 요약

OpenClaw는 채팅 앱과 모델, 자기 컴퓨터를 한 프로세스에 묶는 셀프 호스트 게이트웨이다. Discord, Telegram, Slack, Signal, WhatsApp, iMessage를 포함한 채널 플러그인이 바깥에서 말을 걸고, 게이트웨이가 세션과 자격 증명과 도구 정책을 소유한다. 모델은 Anthropic, OpenAI, Google, 로컬 엔드포인트 중 고른다. 중간에 호스티드 서비스는 없다.

2026년 8월 30일에 나온 `2026.8.1`이 OpenClaw 2.0이다. 패키지 이름에 2.0은 없다. `2026.7.1`까지가 이전 표면이고, `2026.8.1`부터가 2.0 라인이다. 릴리스 노트는 16,977개 풀 리퀘스트, 698개 직접 커밋, 987명 기여자를 적는다. 같은 날 블로그는 이 릴리스를 설치와 브라우저를 고치다 범위가 커진 결과라고 부른다. 제목의 Accidentally는 그 범위 확대를 가리킨다.

2.0에서 사람이 만나는 변화는 여섯 가지다. 대화가 중심인 Control UI, 반복 작업을 검토 가능한 스킬로 남기는 Skill Workshop, 세션을 넘어 기억하는 메모리와 Dreaming, 페어된 자기 컴퓨터와 클라우드 워커로의 실행 배치, 정확한 요청에 붙는 승인과 모델 밖에 두는 시크릿, 한 세션을 여러 사람이 역할로 나누어 보는 공유다.

저장소는 OpenClaw Foundation이 관리하는 MIT 오픈소스다. 창시자 Peter Steinberger는 2026년 2월 OpenAI에 합류해 개인 에이전트를 맡았고, 프로젝트는 재단으로 넘어갔다. OpenAI는 추론과 Claw Labs로 지원한다. 제품의 소유와 라이선스는 재단에 있다.

## 1. 게이트웨이가 소유하는 것

호스트당 게이트웨이는 하나다. 기본 바인드는 `127.0.0.1:18789`의 WebSocket이다. macOS 앱, CLI, 웹 Control UI, 자동화는 같은 소켓에 운영자로 붙고, iOS·Android·macOS·헤드리스 노드는 `role: node`로 붙는다. 첫 프레임은 `connect`여야 하고, 장치는 챌린지 논스에 서명한다. 새 장치 ID는 페어링 승인이 있어야 이후 접속에 쓰는 디바이스 토큰을 받는다. 루프백은 자동 승인될 수 있고, 테일넷과 LAN은 명시적 승인이 남는다.

```text
Telegram / Slack / Discord / 웹 / 네이티브 앱
        │  WebSocket
        ▼
   Gateway  ── 세션·트랜스크립트(SQLite) · 모델 자격 증명 · 도구 정책 · 승인 원장
        │
        ├── 이 호스트에서 실행
        ├── 페어된 자기 컴퓨터 (openclaw connect)
        └── 일회용 클라우드 워커 (Crabbox)
```

원격 배치에서도 모델 호출은 게이트웨이를 통한다. 프로바이더 자격 증명은 원격 기계에 내려가지 않는다. 완료된 작업은 게이트웨이 쪽 체크포인트나 관리되는 워크트리로 돌아온다. 게이트웨이가 죽어도 세션의 원본은 게이트웨이에 있고, 워커는 다음 메시지에서 재기동한다.

설치의 빠른 경로는 `npx openclaw@latest`다. 요구 런타임은 Node.js 24.16 이상 또는 26.1 이상이고, 26이 권장이다. 이미 Claude Code나 Codex CLI 로그인, 또는 API 키가 있으면 퀵 스타트는 그 자격으로 실제 완료 호출을 한 번 해보고 설정을 저장한 뒤 대시보드를 연다. 없는 값은 첫 대화 이후로 미룬다. 백그라운드는 `openclaw gateway install`이다. 업데이트 경로는 교체 전에 설치 상태를 검사한다.

2.0은 세션과 트랜스크립트를 파일에서 SQLite로 옮겼다. 상태가 버전 계약을 가진 데이터베이스에 있으면, 업그레이드와 롤백이 디렉터리에 흩어진 기록을 맞추는 일이 아니게 된다.

## 2. 대화가 중심인 Control UI

이전 웹은 게이트웨이, WebSocket, 스냅샷 같은 운영 용어로 열렸다. 2.0의 Control UI는 그 개요 화면을 치우고, 사이드바의 대화와 가운데의 현재 스레드로 연다. 설정과 받은편지는 필요할 때까지 밖에 둔다. 사이드바는 평평하게 두거나 프로젝트·사람·사용자 그룹으로 접고, 선택한 에이전트의 세션만 보여 준다.

한 게이트웨이 안에 에이전트를 여러 개 둔다. 일반 지시, 리뷰, 코딩, 마케팅처럼 역할을 나누면 세션과 스킬 허용 목록이 에이전트 경계 안에 남는다. 직접 대화는 기본적으로 `main`으로 모이고, 그룹은 격리된다.

대화 옆에는 파일이 붙는다. 관리자 연결에서는 워크스페이스의 텍스트와 Markdown을 채팅 안에서 고친다. 에이전트가 같은 파일을 먼저 바꾸면 편집기는 충돌로 멈추고 새 버전을 덮어쓰지 않는다. Changes는 브랜치 커밋과 워킹 트리 편집을 읽기 전용으로 보여주고, GitHub 체크아웃이면 풀 리퀘스트 상태와 CI 요약이 붙는다. Create PR은 GitHub로 넘긴다.

같은 사이드 레일에 터미널, 브라우저, 데스크톱, 대시보드가 탭으로 모인다. 본 작업이 도는 동안 옆에서 상태를 보고, 백그라운드 작업은 경과 시간과 최근 활동과 함께 남는다. 턴이 끝나면 중간 도구 호출은 "Worked for" 요약으로 접히고, 아직 끝나지 않은 활동·승인·오류는 접히지 않는다. 진행 카드는 새로고침 뒤에도 남는다.

대시보드는 채팅 출력 위에 얹는 작업면이다. 인터랙티브 위젯과 MCP 앱을 세션 대시보드에 고정하고, 액션과 네트워크 출처를 그 위젯에만 준다. 렌더 결과는 이미지로 보낼 수 있다. 홈에는 사용량, 세션, 활동 같은 카드가 있고, 채팅과 분할해서 둔다.

네이티브 앱은 iPhone, iPad, Android, macOS, Wear OS다. 음성, 첨부, 모델 선택, 대화 제어, 승인 알림이 게이트웨이의 같은 세션을 본다. Apple Watch에서도 실행 승인을 처리할 수 있다.

작곡기에서 고르는 축은 코딩 하네스와 같은 결이다. 어느 에이전트인지, 어느 기계에서 도는지, 어느 프로젝트인지, 권한 모드, 모델, 노력(effort)이다. 이 화면이 Codex와 닮은 것은 2.0 UI가 그 작업 선택을 대화 앞에 꺼냈기 때문이다.

## 3. 스킬: 반복을 절차로 남긴다

스킬은 모델이 다시 따라갈 절차다. 플러그인이 실행 코드를 더하는 자리라면, 스킬은 그 위에 올라가는 지시와 보조 파일이다. 둘은 Plugins 허브에서 같이 찾지만 수명 주기는 따로다. Discord, Telegram, Slack, Notion, 음성, 이미지 생성은 플러그인으로 붙이고, "글 제목을 이렇게 뽑는다" 같은 절차는 스킬로 남긴다.

만드는 길은 세 갈래다.

1. 자기 학습. 새 설치의 기본값은 `auto`다. 상당한 작업과 오래 가는 수정이 있으면 스킬 제안이 생긴다. `off`는 자동 수리를 끄고, `propose`는 검토 대기열만 만든다. `auto`는 Workshop이 소유한 스킬을 패치하거나 같은 턴에서 고칠 수 있다. 진행 중인 대화는 이미 읽은 버전을 턴이 끝날 때까지 유지한다.
2. 명시적 작성. 스킬 크리에이터로 호출 방법, 보조 파일, 검증까지 한 경로를 밟는다. 설명이 너무 길거나 메타데이터가 깨지면 그 스킬만 보고하고, 나머지 카탈로그는 그대로 로드한다.
3. 작업이 끝난 뒤의 학습 요청. `/learn`과 과거 세션 스캔은 라이브 스킬을 바로 고치지 않고 제안을 만든다.

제안은 처음에 제한된 상태다. Workshop에서 지시문, 스캐너, 벤치마크, 그레이더 결과를 보고 고친 다음 적용·거절·격리한다. 결정이 묶이는 대상은 그때 본 개정이다. 개정판이 바뀌면 다시 검토한다. 프롬프트 인젝션이 치명으로 나오면 적용이 막힌다. 적용이 중간에 끊겨도, 그 사이 다른 곳이 바꾼 대상을 덮어쓰지 않고 복구한다.

자기가 쓴 스킬과 다른 사람이 소유한 스킬은 자동 학습이 고치거나 지우지 못한다. 개선은 제안으로만 온다. 지원되는 런타임에서는 백그라운드 리뷰가 채팅에 끼어들지 않고 돈다. 학습 모드와 스케줄이 허용하면 주간 작업이 컬렉션을 돌아보고, 사용과 결과를 기록하고, 특화 스킬을 보존하고, 복구 가능한 백업을 만든다. 백업을 되돌리는 것은 명시적 선택이다.

쓸 때는 채팅에서 고르거나, 지원되는 진입점에서 `$skill-name`으로 최대 여덟 개까지 이름을 댄다. 이름을 안 대도, 활성 에이전트에 허용된 스킬이면 모델이 카탈로그에서 집어 쓴다. 모델에게 보이는 목록은 커질 때 압축되므로, 전체 재고는 `openclaw skills check`가 맞다.

반복을 줄이는 개인 비서는 이 루프에 기대 있다. 같은 종류의 요청이 쌓이면 제안이 생기고, 사람이 절차를 읽어 적용한 뒤부터는 짧은 말에도 그 절차가 붙는다. 적용 전의 제안은 실행되지 않는다.

## 4. 메모리: 검색, Dreaming, 위키

2.0의 기본 검색과 회상은 내장 메모리 엔진이다. 이전 QMD를 쓰던 설치는 `openclaw doctor --fix`로 넘긴다. 개인 설치에서는 같은 에이전트의 다른 비공개 대화를 기본으로 떠올린다. 리셋 직전에 중요했던 맥락이 여기 포함된다. 그룹, 채널, 다른 에이전트, 지운 기록, 정책이 막는 출처는 빠진다. 직접 메시지 격리를 켜면 그 설정이 이긴다.

세션은 리셋 정책이 없으면 날짜가 바뀌어도 열린 채다. 웹과 macOS, iOS, Android의 SQLite 대화는 사용자 메시지까지 되감고, 포크하고, 보존된 가지 사이를 옮긴다. 되감기는 트랜스크립트 가지를 바꾼다. 이미 쓴 파일, 이미 보낸 메시지, 도구의 부작용은 취소되지 않는다.

Dreaming은 `memory-core`의 백그라운드 통합이다. 기본으로 켜져 있고, 크론 한 줄이 스윕을 돌린다. 기본 시각은 `0 3 * * *`이다. 한 스윕은 light, REM, deep 순이다.

| 단계 | 하는 일 | `MEMORY.md` |
| --- | --- | --- |
| Light | 최근 단기 신호, 일일 노트, 세션 기록을 모아 중복을 걷고 후보를 올린다 | 쓰지 않음 |
| REM | 주제와 반복되는 생각을 요약한다 | 쓰지 않음 |
| Deep | 점수·재호출 횟수·서로 다른 질의 수가 모두 문턱을 넘은 후보만 승격한다 | 쓴다 |

Deep의 가중치는 관련성 0.30, 빈도 0.24, 질의 다양성 0.15, 최근성 0.15, 여러 날에 걸친 반복 0.10, 개념 밀도 0.06이다. 승격 전에는 출처가 `untrusted`이거나 `system`인 후보를 구조적으로 뺀다. 모델은 대체 산문을 쓰지 않고, 추가·병합·대체의 연산만 고른다. 쓰기 직전 이전 `MEMORY.md`는 SQLite에 남고, 사람이 읽는 일지는 `DREAMS.md`다. 일지는 승격의 입력이 아니다. 크론, 하트비트, 서브에이전트, 출처를 모르는 세션은 장기 후보로 들어가지 않는다.

메모리 위키는 그 옆의 컴파일된 지식 보관함이다. Dreams 화면의 하위 탭에서 합성 페이지, 개체, 개념, 출처, 주장, 열린 질문, 모순을 본다. 기억 그래프를 사람이 검토할 수 있는 위키로 굳힌 것이고, Dreaming이 매일 고르는 승격과는 역할이 다르다. 엔진은 설정에서 바꿀 수 있고, 위키 플러그인은 꺼 둘 수 있다.

한 가지 경계가 있다. Dreaming이 세션 기록을 삼킬 때 그 텍스트는 시크릿 마스킹을 거치지 않는다. 대화에 적힌 비밀은 기억 후보가 될 수 있다. 비밀은 대화 본문이 아니라 시크릿 저장소로 넣는다.

## 5. 실행은 세 곳에 둔다

세션은 하나이고, Place가 실행 위치만 고른다.

| 위치 | 기계 | 맞는 일 |
| --- | --- | --- |
| Gateway | `openclaw gateway`가 도는 호스트 | 평소의 대화와 가벼운 도구 |
| 페어된 기기 | `openclaw connect`로 한 번 붙인 자기 하드웨어 | GPU가 있는 데스크톱, 빌드 머신, 이미 가진 서버 |
| 클라우드 워커 | Crabbox가 빌렸다 버리는 기계 | 몰리는 작업, 긴 작업, 자기 기계와 격리 |

항상 켜 둔 작은 VPS에 게이트웨이를 두고, 집의 Windows에 GPU와 파일이 있으면 후자를 노드로 붙인다. 페어링은 조인 주소를 그 기계에 붙여 넣는 명령이다.

```bash
openclaw connect <join-url> --service --session-host
```

노드는 밖으로 연결을 유지하고, 기본으로 CPU 코어당 워커 슬롯을 알린다. 기기가 꺼지면 배치 기록은 남고 세션은 그 기기가 돌아오기를 기다린다. 파일 목록, 자막 추출, 로컬 GPU 작업은 게이트웨이가 아니라 그 노드의 도구로 나간다. 컨테이너 격리는 `nodeHost.workerRuns.isolation: "container"`로 켠다.

클라우드 워커는 AWS, Hetzner 등을 Crabbox 프로파일이 주문한다. 기계에는 상주 자격 증명이 없고, 세션이 멈추면 걷힌다. 게이트웨이 업데이트는 붙어 있는 클라우드 기계를 유지한 채 워커 런타임만 제자리에서 새로 고친다.

브라우저 패널은 브라우저를 광고하는 호스트와 관리자 연결이 있어야 한다. 헤드리스 VPS의 게이트웨이 프로세스만으로는 화면이 없다. Linux에서는 관리형 데스크톱을 켜야 하고, 그때의 컴퓨터 제어는 Control UI 데스크톱 패널과 같은 X11과 사설 D-Bus를 쓴다. 돌아가는 게이트웨이나 VNC 화면만으로 컴퓨터 제어가 된다고 보지 않는다. 집 컴퓨터에 게이트웨이 또는 노드를 두고 그 디스플레이의 권한을 줘야 브라우저와 데스크톱이 옆에 뜬다.

컴퓨터 사용은 내장 `computer` 도구다. 게이트웨이 데스크톱과 페어된 노드가 `computer.act`와 `screen.snapshot`을 같은 계약으로 수행한다. 좌표는 방금 받은 스크린샷의 `frameId`에 묶인다. 화면이 바뀌면 이전 좌표는 거부된다. macOS 기본 제공자는 Peekaboo이고, CUA는 앱이 접근성과 화면 기록을 물려 주는 드라이버다. Windows와 Linux는 실험적인 `cua-computer` 플러그인이다. 제공자 실패가 다른 제공자로 조용히 넘어가지 않는다. 비전 가능한 모델과 `computer`를 허용하는 도구 정책이 필요하다. 로컬 온보딩의 기본이 Full이면 이 도구가 열리지만, 명시한 `coding` 프로파일은 빼 두므로 `tools.alsoAllow`에 넣어야 한다.

클라우드 세션의 데스크톱은 그 세션에 고정된다. 사람이 데스크톱 패널에서 제어를 가져가면 에이전트 입력은 멈추고 관찰은 계속된다. 다시 맡기면 에이전트는 `take_control`로 신선한 스크린샷을 받고, 끊긴 입력은 재생되지 않는다.

채널은 이 게이트웨이를 주머니로 꺼내는 면이다. Telegram에 붙여 두면 밖에서도 같은 세션에 말하고, 집에 켜 둔 노드에 파일 작업을 시킨다. Slack, Discord, 그 밖의 채널 플러그인도 같은 게이트웨이의 다른 입구다.

## 6. 자동화

반복의 실행은 자동화다. 에이전트, Control UI, CLI, 문서, 네이티브 앱이 같은 이름을 쓴다. 스케줄은 크론 식이고, 깨우는 쪽은 게이트웨이의 `GatewayScheduler` 하나다. 잠에서 깨어난 뒤의 늦은 틱은 한 번만 돌고, 놓친 틱은 합쳐진다.

이메일은 두 경로다. IMAP 트리거는 인증된 메일을 고립된 리더 에이전트로 넣고, Gmail은 Pub/Sub로 깨운다. 리더 세션의 도구는 운영자가 제한한다. 격리만으로 도구가 줄어들지는 않는다. 받은편지함에서 필요한 항목을 찾아 표로 만들고, 택배 양식처럼 이미 있는 서식에 채우는 일은 이 트리거와 스킬과 파일 도구가 만나는 자리다.

크론이 브라우저나 컴퓨터 사용을 포함할 때는 절차가 본문이어야 한다. 모델이 한 번에 못 하겠다고 하면, 클릭과 입력과 확인의 순서를 스킬에 적고 그 스킬을 스케줄이 호출하게 둔다. 활성화, 일시 정지, 실행 기록은 Control UI에서 본다.

Dreaming 스윕과 스킬 컬렉션 리뷰도 이 스케줄러 위의 시스템 작업이다. 채팅을 닫아도 둘은 돈다.

## 7. 시크릿과 승인

권한 모드는 세션마다 읽기 전용, 가드, 워크스페이스, 전체 접근이다. 전체 접근은 관리자용이다. 한 턴의 실행 제한은 세션 정책을 더 조일 수만 있다. 느슨하게 풀지 못한다. 예전에 정책이 없던 세션은 그때의 전역 자세를 유지한다. MCP, 스킬, 웹 검색도 세션에서 덮어쓸 수 있다.

승인은 그 요청, 명령, 세션, 받은 사람에게 붙는 기록 하나다. 브라우저와 지원되는 모바일이 같은 기록을 보고, 첫 유효 응답이 확정이다. 재접속으로 끝난 요청이 살아나지 않고, 런을 중단하면 남은 승인은 취소된다. 대기열을 닫는 것은 승인이 아니다.

반복 작업은 정확한 연산에 대한 상주 허가를 한 번 줄 수 있다. 승인 화면과 CLI에 소유 자동화, 정확한 명령, 사용 횟수, 상태가 보인다. 허가를 거두면 다음 실행 경계에서 다시 묻는다. 작업이나 연산이 바뀌면 새 승인이 필요하다. 스크립트는 검토했던 바이트를 다시 확인한다. 인터프리터와 바뀌는 의존성, 다른 프로그램을 띄울 수 있는 래퍼는 다시 물을 수 있다.

시크릿은 대화에 타이핑하는 값이 아니다. 에이전트가 마스킹된 입력을 요청하면, 웹·iOS·Android에서 넣은 값은 그 런의 보호된 저장소로 들어가고 모델에게 보이는 텍스트와 채팅 기록에는 남지 않는다. 목적지 제한 치환은 게이트웨이가 호스트하는 HTTPS에만 적용되고, 기본은 꺼져 있다. 허용 목록을 켜야 그 프록시가 승인된 목적지에만 값을 넣는다. 원시 소켓, 컨테이너, 원격 노드, 일반 HTTP, WebSocket은 이 경로 밖이다.

저장소 자체는 디스크에서 암호화되지 않는다. 보호는 OpenClaw 상태 디렉터리의 파일 권한에 기대 있다. 에이전트가 읽을 수 있는 환경 값은 별도 허가이며, 그 값을 받은 명령은 출력하거나 전송할 수 있다. 1Password와 HashiCorp Vault 참조도 같은 SecretRef 계약 위에 있다.

샌드박스는 기본으로 꺼져 있다. 플러그인은 프로세스 안에서 돌고 샌드박스되지 않는다. 설치 때 퍼블리셔, 버전, 아티팩트를 다시 확인하고, 승인 기록이 요청과 어긋나면 재사용하지 않고 멈추거나 다시 묻는다. 장치를 빼거나 다시 페어링하면 이전 접근은 폐기된다.

## 8. 여러 사람이 한 세션을 볼 때

공유 세션은 만든 사람과 각 발화를 남긴다. 소유자나 관리자는 다른 사람에게 읽기, 수정 제안, 초안에서의 작업, 직접 참여 중 하나를 준다. 제안에는 작성자가 붙고, 초안은 경합 없이 만들고 게시한다. 온라인 카드는 누가 무엇을 하는지만 보여주고 IP와, 열 수 없는 대화는 보여 주지 않는다.

이 역할은 한 설치 안의 협력이다. 적대적인 테넌트를 가르는 경계가 아니다. 권한을 거둔 뒤 UI가 갱신되기 전에는 잠깐 열려 보일 수 있고, 게이트웨이가 그 행동을 거절한다.

Incognito는 기본 꺼짐이다. 대화는 프로세스 메모리에만 있고 보통의 트랜스크립트와 자동 메모리를 디스크에 쓰지 않으며, 게이트웨이가 재시작하면 사라진다. 모델 제공자에는 메시지가 가고, 도구는 파일과 외부 서비스에 여전히 손을 댄다. 내용 없는 감사 메타데이터는 남고, 게이트웨이 운영자는 라이브 작업을 볼 수 있다.

클라우드와 페어된 기기의 세션을 팀 안에서 넘기면, 이미 쌓인 트랜스크립트와 워크스페이스가 따라간다. 블로그가 말한 멀티플레이어는 이 공유다. 가족이나 팀이 같은 게이트웨이에 들어오되, 누가 읽고 누가 실행하는지는 세션 멤버십이 정한다.

## 9. 어떤 모델로 항상 켜 둘 것인가

카탈로그의 모델은 채팅에만 쓰이지 않는다. Dream Diary와 기억 통합은 에이전트 기본 모델을 쓰고, `dreaming.model`로만 바꿀 수 있다. 스킬 컬렉션 리뷰도 스케줄 위에서 같은 계열의 호출을 만든다. 기본 모델을 비싸게 두면, 사람이 말을 걸지 않는 밤에도 그 단가로 통합이 돈다.

`2026.9.2`는 카탈로그에 OpenAI GPT-6 Astra를 더했다. 2.0 자체보다 나중 릴리스다. Astra를 개인 비서의 기본값으로 두면 회상, 일지, 스킬 리뷰가 그 모델의 토큰을 쓴다. 평소의 절차 실행은 더 작은 기본 모델로 두고, 화면을 봐야 하는 컴퓨터 사용만 비전 가능한 모델로 나누는 편이 이 구조와 맞다.

코딩 세션은 OpenClaw 안에서도 돈다. Codex 런타임과 원격 실행, 워크트리, 풀 리퀘스트 패널이 그 자리다. 개인 비서의 본업은 그 옆이다. 이미 있는 받은편지함, 일정, 페어된 데스크톱에 대해 "해 줘"라고 말하고, 반복이면 스킬과 크론으로 남긴다. 프로그램을 새로 짜는 일과 생활을 대신 돌리는 일을 같은 기본 모델과 같은 전체 접근에 두면, 토큰과 권한이 둘 다 커진다.

## 10. 점검

- 패키지가 `2026.8.1` 이상인가. `2026.7.1`은 이전 표면이다.
- 게이트웨이는 루프백 또는 테일넷 뒤에 있고, 공개 인그레스에 `gateway.auth.mode: "none"`이 아닌가.
- 개인 에이전트의 교차 대화 회상이 그룹과 다른 에이전트로 새지 않는가.
- 비밀번호가 채팅이 아니라 마스킹된 시크릿 요청으로 들어가는가. 상태 디렉터리 권한이 그 저장소를 지키는가.
- 크론의 상주 허가가 명령과 작업이 바뀌면 무효가 되는가.
- 헤드리스 VPS에서 브라우저를 기대하지 않고, 화면이 필요한 일은 페어된 노드나 관리형 데스크톱으로 보냈는가.
- Dreaming이 삼키기 전에 대화 본문에 비밀을 적지 않았는가.
- 자기 학습이 `auto`라면, Workshop의 적용 전에 제안이 실행되지 않는가.
- 기본 모델이 밤의 일지와 스킬 리뷰까지 감당하는 단가인가.

## 결론

OpenClaw 2.0은 새 모델이 아니다. 한 게이트웨이가 채널, 세션, 자격 증명, 도구 정책을 소유한다는 구조를 유지한 채, 사람이 그 구조를 대화 화면에서 쓰게 만든 릴리스다. 반복은 스킬 제안으로 나오고, 기억은 점수 문턱을 넘을 때만 `MEMORY.md`가 되며, 실행은 게이트웨이·자기 컴퓨터·일회용 워커 중 세션이 고른 곳에서 돈다. 승인과 시크릿은 그 실행이 모델의 말 한마디에 기대지 않게 기록을 남긴다.

편해진 UI가 경계를 없애지는 않는다. 샌드박스는 기본으로 꺼져 있고, 플러그인은 프로세스 안이며, 시크릿 저장소는 파일 권한에 기대고, Dreaming은 대화에 적힌 비밀을 가리지 않은 채 읽는다. 2.0을 개인 비서로 켜 둔다는 것은 이 기본값을 알고 권한 모드, 시크릿 경로, 기본 모델을 먼저 고른다는 뜻이다.
