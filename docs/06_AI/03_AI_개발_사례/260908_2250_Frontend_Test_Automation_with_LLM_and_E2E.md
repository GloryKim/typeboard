# LLM 기반 프론트엔드 검증 자동화와 E2E 테스트 운영

출처 : https://www.youtube.com/watch?v=YCNcTpcDRf8&t

## 요약

생성형 AI가 코드 작성 속도를 높이면서 프론트엔드 개발의 병목은 구현에서 검증으로 이동하고 있다. 코드 생산량이 증가하면 사람이 수동으로 모든 화면과 디바이스를 확인하는 방식은 범위와 반복 비용을 감당하기 어렵다. 해결책은 단순히 E2E 테스트를 추가하는 것이 아니라, 테스트 가능한 제품 구조·실행 인프라·테스트 생성 자동화를 함께 구축하는 것이다.

이 보고서는 대규모 프론트엔드 조직에서 적용할 수 있는 검증 체계를 다음 네 요소로 정리한다.

1. 핵심 사용자 흐름을 정의하고 안정적인 E2E 테스트로 표현한다.
2. 테스트 전용 서버 API와 결정적인 테스트 데이터를 제공한다.
3. 실제 브라우저·모바일 기기를 디바이스 팜에서 병렬 실행한다.
4. LLM은 테스트 초안과 유지보수를 보조하되, 결과 판정과 품질 기준은 자동화된 검증 시스템이 담당한다.

## 1. AI 코딩 환경에서 검증이 어려워지는 이유

AI 도구는 컴포넌트, API 연동, 상태 관리 코드를 빠르게 생성하지만 다음 문제를 자동으로 해결하지는 않는다.

- 생성된 코드가 실제 브라우저·운영체제·화면 크기에서 동일하게 동작하는지 확인하기 어렵다.
- 네트워크 지연, 재시도, 권한 만료, 결제·인증 같은 상태 조합이 많다.
- 수동 검증은 담당자별 편차가 크고 회귀 테스트에 취약하다.
- 테스트가 불안정하면 실패 원인을 코드 결함과 테스트 환경 결함으로 구분하기 어렵다.

따라서 “AI가 코드를 작성했으니 테스트도 AI에게 맡긴다”는 접근만으로는 충분하지 않다. 테스트 대상의 관찰 가능성, 재현성, 실패 진단성을 먼저 확보해야 한다.

## 2. 테스트 피라미드와 E2E의 역할

단위 테스트는 함수·컴포넌트의 빠른 피드백에 적합하고, 통합 테스트는 모듈 간 계약을 검증한다. E2E 테스트는 브라우저에서 실제 사용자 흐름을 실행해 라우팅, 번들, API, 인증, 렌더링이 함께 작동하는지 확인한다.

E2E를 모든 경우에 사용하면 느리고 유지보수 비용이 커진다. 다음과 같이 계층을 나누는 것이 현실적이다.

| 계층 | 주요 목적 | 운영 원칙 |
| --- | --- | --- |
| 단위 테스트 | 순수 로직·컴포넌트 상태 | 빠르게 실행하고 사례를 넓게 구성 |
| 통합 테스트 | 모듈·API 계약 | 외부 의존성을 통제하고 경계 조건 검증 |
| E2E 테스트 | 핵심 사용자 여정 | 적은 수의 고가치 시나리오를 실제 환경에 가깝게 실행 |
| 수동 탐색 테스트 | 신규·비정형 동작 발견 | 자동화로 대체하기 어려운 영역에 집중 |

E2E 우선순위는 로그인, 핵심 조회·생성·결제 흐름, 권한별 접근, 장애·재시도 처리처럼 실패 시 사용자와 사업 영향이 큰 여정에 둔다.

## 3. 테스트 가능한 애플리케이션 설계

### 3.1 결정적인 데이터와 서버 API

테스트마다 동일한 계정과 상태를 재사용하면 실행 순서에 따라 결과가 달라진다. 테스트 시작 전에 데이터를 생성·초기화할 수 있는 전용 API를 제공하고, 테스트 종료 후 정리한다. 테스트 데이터에는 고유한 실행 ID를 붙여 병렬 실행 간 충돌을 방지한다.

```text
테스트 시작
  → 전용 API로 사용자·상품·권한 상태 생성
  → 브라우저에서 사용자 흐름 실행
  → UI·네트워크·서버 상태 검증
  → 실행 ID 기준으로 데이터 정리
```

테스트 API는 운영 환경에 노출하지 않고, 인증된 테스트 네트워크 또는 별도 환경에서만 활성화한다. 서버 시간을 고정하거나 외부 결제·문자·이메일 서비스를 가짜 구현으로 대체하면 재현성이 높아진다.

### 3.2 관찰 가능성과 실패 진단

실패 시 스크린샷 하나만으로는 원인을 찾기 어렵다. 각 테스트에 다음 산출물을 남긴다.

- 단계별 스크린샷과 동영상
- 브라우저 콘솔 및 네트워크 로그
- 서버 요청 ID와 분산 추적 ID
- 테스트 데이터 식별자와 실행 환경 정보
- 실패한 assertion, DOM 상태, 주요 API 응답

민감한 개인정보와 토큰은 로그에 기록하지 않으며, 산출물 보존 기간과 접근 권한을 별도로 관리한다.

## 4. 디바이스 팜과 병렬 실행

브라우저 자동화만으로는 모바일 키보드, 권한 팝업, 성능 차이, OS별 렌더링 문제를 충분히 검증할 수 없다. 실제 기기 또는 가상 디바이스를 제공하는 디바이스 팜에서 대표적인 OS·브라우저·화면 크기 조합을 병렬 실행한다.

디바이스 매트릭스는 모든 조합을 무작정 포함하기보다 사용자 비중과 장애 위험으로 축소한다. 예를 들어 데스크톱 주요 브라우저, iOS·Android 최신 및 최소 지원 버전, 저사양 기기 한 종류를 기본 세트로 두고, 변경된 기능에 필요한 조합만 확장한다.

병렬화할 때는 테스트 데이터, 계정, 포트, 파일 저장 경로를 실행별로 격리한다. 공유 상태가 남으면 테스트 수를 늘릴수록 간헐적 실패가 증가한다.

## 5. LLM을 활용한 테스트 생성과 유지보수

LLM은 요구사항·화면 명세·기존 컴포넌트에서 테스트 시나리오와 Playwright 같은 자동화 코드의 초안을 만들 수 있다. 그러나 생성 결과를 그대로 신뢰하지 말고 다음 검증 단계를 둔다.

1. 테스트 목적과 사전 조건을 사람이 승인한다.
2. 선택자에 안정적인 `data-testid` 또는 접근성 역할을 사용했는지 검사한다.
3. 네트워크 대기 대신 명시적인 상태·응답 대기를 사용하는지 확인한다.
4. 정상·실패·권한 경계 사례를 포함하는지 검토한다.
5. CI에서 반복 실행해 flaky 비율과 실행 시간을 측정한다.

테스트 생성용 프롬프트나 에이전트에는 저장소 구조, 실행 명령, 금지된 외부 호출, 개인정보 처리 규칙을 명시한다. 테스트가 실패하면 LLM이 무조건 재시도 코드를 추가하기보다, trace와 로그를 바탕으로 원인을 분류하도록 한다.

## 6. CI/CD 운영 모델

풀 리퀘스트에서는 빠른 단위·통합 테스트와 변경 영역 중심의 E2E를 실행하고, 병합 후에는 전체 핵심 여정과 디바이스 매트릭스를 병렬 실행한다. 야간 또는 주기적 작업에서는 장시간 시나리오와 호환성 조합을 추가한다.

품질 지표는 테스트 개수보다 다음 항목이 유용하다.

- 핵심 여정의 커버리지
- 테스트 성공률과 flaky 비율
- 코드 변경부터 결과 확인까지의 피드백 시간
- 실패 원인 분류까지 걸리는 시간
- 실제 결함을 발견한 비율과 결함 누출률

flaky 테스트를 반복 재실행해 숨기는 것은 품질을 높이지 않는다. 실패를 격리하고 소유자를 지정하며, 일정 기간 안에 수정하지 않으면 배포 신호에 반영한다.

## 7. 권장 도입 순서

### 1단계: 기반 정리

지원 브라우저와 핵심 사용자 여정을 정의하고, 테스트 전용 환경·계정·데이터 초기화 API를 마련한다.

### 2단계: 대표 시나리오 자동화

로그인과 핵심 업무 흐름부터 안정적인 E2E로 구현한다. 실패 산출물과 추적 ID를 표준화한다.

### 3단계: 디바이스·병렬 확장

사용자 비중이 높은 기기부터 디바이스 팜에 추가하고, 실행별 데이터 격리와 큐·재시도 정책을 적용한다.

### 4단계: LLM 보조 자동화

테스트 초안 생성, 선택자 보정, 실패 요약을 자동화하되, 병합 승인과 품질 기준은 코드 리뷰와 CI 정책으로 통제한다.

## 결론

AI 코딩의 효과를 지속하려면 구현 속도보다 검증 시스템의 처리량을 함께 높여야 한다. 핵심은 E2E 테스트의 숫자가 아니라 테스트 가능한 서버 인터페이스, 결정적인 데이터, 실제 디바이스 실행, 충분한 실패 증적, 그리고 측정 가능한 CI 운영이다. LLM은 이 체계를 빠르게 확장하는 도구로 활용할 수 있지만, 테스트의 신뢰성과 배포 판단을 대신하는 주체로 취급해서는 안 된다.
