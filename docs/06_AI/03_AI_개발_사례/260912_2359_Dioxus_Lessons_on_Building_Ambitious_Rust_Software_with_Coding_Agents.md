# Dioxus 사례로 본 코딩 에이전트 시대의 Rust 프레임워크 개발과 품질 관리

## 요약

Dioxus는 Rust 하나로 웹·iOS·Android·데스크톱 앱을 만드는 크로스 플랫폼 프레임워크다. 2021년 Jonathan Kelley가 대학 마지막 여름에 시작했으며, 5년 동안 핵심 엔지니어 3명이 30만 줄 이상의 코드를 손으로 작성했다. GitHub 스타 약 3만 7천 개, Rust 상위 50위권 프로젝트이며, Dioxus로 만든 앱의 최종 사용자는 약 2억 명으로 추정된다. 2026년 9월 Dioxus 팀은 Devin을 만든 Cognition에 합류했다.

Kelley는 2026년 7월 AI Engineer World's Fair 발표에서 지난 6개월간 코딩 에이전트를 도입한 경험을 정리했다. 팀은 처음에 에이전트로 수만 줄의 기능을 쏟아냈지만 대부분 머지 기준을 통과하지 못했다. 이후 에이전트에게 맡길 일과 사람이 지켜야 할 일을 구분하면서 성과가 나왔다. 지식 집약적인 플랫폼 통합과 반복적인 유지보수 작업은 에이전트가 잘했고, 의미 있는 테스트 설계는 여전히 약했다. 사람의 역할은 아키텍처 설계, 의도 전달, 줄 단위 리뷰로 옮겨갔다. 결론은 "코드는 싸졌지만 품질은 싸지지 않았다"는 것이다.

## 1. Dioxus 개요와 확인된 사실

Dioxus는 한 번 작성한 Rust 코드를 웹, iOS, Android, 데스크톱에서 실행하는 것을 목표로 한다. 출발점은 2021년 당시 React Native는 불안정하고 Flutter는 느리다는 판단이었고, Rust를 쓰면 가상 머신이나 JavaScript 없이 네이티브 앱을 직접 만들 수 있다는 구상이었다.

문제는 당시 Rust 생태계에 쓸 만한 부품이 거의 없었다는 점이다. 화면 갱신을 위한 반응성(reactivity), 폰트 렌더링, 핫 리로드, 앱 번들링까지 모두 직접 만들어야 했다. 그 결과물이 다음과 같은 하위 프로젝트다.

- **Blitz**: Firefox의 CSS 엔진을 가져와 만든 HTML/CSS 렌더링 엔진이다. 번들 크기 5MB 미만, 런타임 메모리 50MB 미만을 목표로 한다.
- **Subsecond**: 실행 중인 네이티브 앱의 코드를 100ms 이내에 교체하는 핫 리로드 엔진이다. Rust뿐 아니라 C, C++ 컴파일 코드도 대상으로 한다.
- **Taffy**: 레이아웃 라이브러리로, Zed의 GPUI, Bevy, Slint 등 다른 프로젝트에서도 사용된다.

Dioxus의 컴포넌트 작성 방식은 React와 비슷하다. 상태는 시그널로 관리하고, `rsx!` 매크로로 UI 트리를 선언한다.

```rust
use dioxus::prelude::*;

fn main() {
    dioxus::launch(App);
}

#[component]
fn App() -> Element {
    let mut count = use_signal(|| 0);

    rsx! {
        h1 { "Count: {count}" }
        button { onclick: move |_| count += 1, "+1" }
    }
}
```

2026년 9월 10일 Dioxus 팀은 Cognition 합류를 발표했다. Cognition은 이미 Devin CLI의 터미널 렌더러를 Dioxus로 만들어 쓰고 있었다. 팀은 Devin의 가상 머신, 컴퓨터 사용(computer use), 테스트 역량 개선을 맡고, Cognition은 Dioxus·Blitz·Taffy·Subsecond 지원을 이어가며 Dioxus-Native와 Blitz에 대한 투자를 늘리겠다고 밝혔다. 양측 모두 거래 조건은 공개하지 않았다.

> 출처: [Dioxus Labs 「Dioxus Labs is joining Cognition」](https://dioxuslabs.com/blog/joining-cognition/), [Cognition 「Welcoming Dioxus to Cognition」](https://cognition.com/blog/welcoming-dioxus)

## 2. 에이전트 도입 과정: 과대 기대에서 실제 엔지니어링으로

Dioxus 팀은 오랫동안 AI에 회의적이었다. 고품질 코드를 내보내는 일과 에이전트 코딩 도구를 쓰는 일은 양립할 수 없다고 봤고, 일상 업무에서도 AI를 쓰지 않았다. 생각이 바뀐 계기는 코딩 에이전트가 Rust를 갑자기 잘 다루기 시작한 것이다. 2025년 12월 Dioxus 공식 계정에는 "Claude Code가 Rust를 정복했다, 오늘 6시간 만에 VM 클론을 만들었다"는 글이 올라왔고, 한 달 뒤 OpenAI의 Greg Brockman은 "컴파일되면 거의 확실히 맞는 코드이므로 Rust는 에이전트에게 완벽한 언어"라고 썼다.

팀은 코딩 에이전트 구독 한도를 모두 쓰며 수만 줄의 Rust 코드를 만들었다. 수년간 원하던 기능, 버그 수정, 통합 작업이었다. 그러나 "이걸 머지해야 하는가"라는 품질 기준을 통과한 코드는 거의 없었고, 상당수는 지금도 드래프트 상태로 남아 있다. Kelley는 이를 기술 하이프 사이클의 세 지점으로 정리했다.

```text
① "뭐든 만들 수 있다"     : 에이전트로 대량의 기능 생성
  → ② "이건 그냥 슬롭이다" : 머지 기준 미달, 드래프트 누적
  → ③ "진짜 엔지니어링"    : 맡길 일과 사람이 할 일을 구분
```

### 2.1 Rust의 학습 곡선이 오히려 장점이 되다

Rust는 배우기 어려운 언어로 유명하다. 컴파일러가 메모리를 언제 빌리고 반납하는지 엄격하게 검사하는 빌림 검사기(borrow checker)는 초보자에게 빨간 펜을 계속 긋는 엄격한 선생님과 같다. Dioxus 팀은 5년 동안 친절한 오류 메시지와 쉬운 도구로 이 장벽을 낮추는 데 공을 들였다.

그런데 에이전트는 이런 사람 중심의 편의성에 크게 신경 쓰지 않았다. 에이전트가 엣지 케이스를 처리하고 빌림 검사기와 씨름하는 수고를 대신 떠안기 때문에, 사람은 Rust의 인지 부담에서 벗어난다. 반대로 엄격한 컴파일러는 에이전트가 만든 코드를 걸러내는 1차 검증 장치로 작동한다. 제거하려던 학습 곡선이 이제는 장점이 된 셈이다.

## 3. 품질의 정의

에이전트 활용의 성패를 판단하려면 먼저 품질 기준이 있어야 한다. Dioxus 팀이 제시한 기준은 다음과 같다.

- 더 빠른 배포
- 더 적은 버그
- 모든 플랫폼에서 고른 품질
- 유지보수하기 쉬운 코드

Kelley가 가장 강조한 것은 마지막 항목이다. 배포 속도는 그동안 쌓아 온 기반 위에서 나오므로 기반이 나쁘면 그 위에 쌓는 모든 것이 나빠진다. 수백만 명이 의존하는 API를 패치 버전에서 깨뜨리면 사용자는 즉시 알아챈다. 오픈소스 프레임워크에서는 코드 자체가 제품이며, 사용자는 그 코드 위에 자신의 사업을 올린다.

## 4. 에이전트가 잘한 일

### 4.1 지식 집약적인 플랫폼 통합

크로스 플랫폼 프레임워크를 만들려면 Android 빌드 시스템, iOS 런타임, Windows, WebAssembly의 세부 규칙과 예외를 모두 알아야 한다. 세 사람이 이를 전부 알 수는 없다. Kelley는 Dioxus의 문제 대부분이 지식 문제였다고 설명한다.

에이전트는 수천 쪽의 문서를 빠르게 훑고, 특수한 API를 읽고, 바이너리를 파고들어 API를 역공학한다. 개인 개발자보다 훨씬 끈기가 있다. 대표 사례가 Dioxus 빌드 시스템에 깊게 통합된 Kotlin·Swift 플러그인이다. React Native의 TurboModules처럼 사람이 수년에 걸쳐 다듬던 성격의 기능인데, 에이전트와 함께 약 2~3주 만에 출시했다. 구현 자체는 첫날 끝났고, 나머지 기간은 테스트 케이스 작성과 실기기 검증에 쓰였다.

Blitz에서도 비슷했다. CSS 레이아웃 버그를 고칠 때 Chrome과 Safari가 해당 케이스를 어떻게 처리하는지 에이전트가 바로 답해 주었기 때문에 WebKit 소스 코드를 직접 뒤질 필요가 없었다.

이 부분에서 가장 중요한 변화는 품질에 대한 태도다. 사람은 복잡한 작업 앞에서 빨리 배포하려고 지름길을 택하곤 했다. 에이전트가 들어오면서 팀은 "제대로 된 방식"을 선택할 여유를 갖게 됐다. 잘 쓰면 에이전트는 품질을 낮추는 것이 아니라 오히려 높인다.

### 4.2 지루하지만 중요한 유지보수 작업

3인 팀에게 배포 파일이 올바른 폴더에 풀리는지 확인하는 시간은 아키텍처를 고민할 시간을 빼앗는다. 한 릴리스에 에디터 확장 세 개를 추가했는데 패치마다 테스트하지 못하면 조용히 깨진다. 에이전트는 이런 일을 맡기 시작했다.

- 안정 버전에 대한 수정 반영(backport)
- 모든 API에 문서와 예제가 있는지, 문서가 실제 동작과 일치하는지 점검
- 코드는 고치고 주석은 그대로 두어 생기는 주석-코드 불일치 정리

그 결과 최근 Dioxus 버전은 역대 가장 많은 패치 릴리스를 냈다. 30만 줄 규모의 프로젝트를 3명이 주 1회 이상 릴리스하는 주기로 유지하고 있다.

## 5. 에이전트가 못한 일: 테스트

테스트는 원래부터 이 팀의 약점이었다. 프레임워크 같은 기반 소프트웨어는 엔드투엔드 테스트가 어렵다. 에디터 확장이 Zed에 제대로 설치되고 동작하는지는 실제로 Zed를 열어 써 보는 것 외에 확인할 방법이 마땅치 않다.

에이전트도 여기서 고전했다. 생성자를 주면 생성자가 객체를 반환하는지만 테스트하는 식의 엉성한 테스트를 쓰는 경향이 있다. 발표 슬라이드에는 "변경은 괜찮아 보이지만 테스트가 좀 쓸모없다. 목(mock) 구현을 테스트하고 있으니 그냥 지우면 안 될까?"라는 실제 리뷰 코멘트가 실렸다. 에이전트는 어떤 API든 테스트를 쉽게 작성하지만, 사람과 마찬가지로 올바른 테스트를 고르는 데 실패한다. 팀은 여전히 테스트 조건을 직접 나열하고, 테스트 API와 러너를 직접 다룬다. 다만 테스트 아이디어를 떠올리거나 경계 조건을 나열하는 상대로는 유용하다.

반대로 성공한 영역은 퍼징(fuzzing) 하네스 구축이다. 퍼징은 수백만 개의 이상한 입력, 특히 형식이 깨진 입력이나 사용자가 해서는 안 되지만 할 수는 있는 사용 방식을 프로그램에 넣어 깨지는지 확인하는 기법이다.

```text
에이전트가 잘하는 것 : 테스트 하네스·퍼징 프레임워크 구축, 테스트 아이디어 제안
사람이 해야 하는 것  : 어떤 테스트가 의미 있는지 선택, 사용자가 의존하는 동작 정의
```

## 6. 사람의 역할은 어디로 옮겨갔는가

### 6.1 아키텍처

사람 엔지니어와 달리 에이전트는 대규모 리팩터링을 두려워하지 않는다. 기능이 구조에 맞지 않으면 구조를 바꿔서라도 그냥 내보낸다. 따라서 기반이 나쁘면 그 위의 코드도 같은 속도로 망가진다. 사람이 스파게티 코드를 쓸 수 있듯 에이전트도 쓸 수 있고, 다만 더 빠를 뿐이다.

그래서 Dioxus 팀의 개발 시간 대부분은 이제 앞으로 어떤 기능이 필요할지, 시스템이 어떻게 진화할지를 고민하는 아키텍처 설계에 쓰인다. Kelley는 의도만 제대로 전달하면 최신 도구가 만드는 코드 품질 자체는 매우 높다고 평가하며, 앞으로는 코드 작성이 아니라 아키텍처가 대부분의 시간을 차지할 것으로 본다.

### 6.2 리뷰와 의도 전달

Dioxus 팀은 여전히 모든 PR을 줄 단위로 읽는다. AI 리뷰로 버그를 먼저 거르지만, 배포 전에는 사람이 직접 코드를 읽는다. 대형 오픈소스 프로젝트에는 낯선 기여자의 PR이 계속 들어오고, 이들은 자기 버그만 고치려 할 뿐 코드베이스가 어떻게 진화해야 하는지는 고려하지 않는 경우가 많다. 그래서 임시방편식 수정이 대량으로 제출된다.

에이전트는 아직 마음을 읽지 못하므로 지시는 텍스트로 전달해야 하고, 구현 품질은 프롬프트에 따라 크게 달라진다. Kelley의 표현대로 "프롬프트 엔지니어링은 실재한다". 그리고 이 점에서 본질은 변하지 않았다. 프로젝트가 성숙할수록 코드를 읽는 일은 코드를 쓰는 일보다 중요했고, 그 사실은 지금도 같다.

## 7. 에이전트 활용 점검표

| 영역 | 점검 항목 |
| --- | --- |
| 품질 기준 | 머지 여부를 판단하는 명시적 기준(호환성, 유지보수성, 플랫폼 커버리지)이 있는가? |
| 작업 분류 | 지식 집약·반복 작업과 설계 판단이 필요한 작업을 구분해 에이전트에 맡기는가? |
| 아키텍처 | 에이전트에 작업을 주기 전에 확장 방향과 경계가 설계되어 있는가? |
| 의도 전달 | 프롬프트에 목적, 제약, 코드베이스의 진화 방향을 함께 적는가? |
| 테스트 | 사람이 의미 있는 테스트 조건을 정의하고, 에이전트는 하네스와 퍼징을 맡는가? |
| 검증 | 실기기·실환경 검증 시간을 구현 시간과 별도로 확보하는가? |
| 리뷰 | AI 리뷰 후에도 배포 전 사람이 줄 단위로 읽는가? |

## 결론

Dioxus 사례는 코딩 에이전트가 소규모 팀의 생산성을 크게 끌어올릴 수 있지만, 그 효과가 자동으로 오지는 않는다는 점을 보여준다. 에이전트로 쏟아낸 수만 줄의 코드가 대부분 드래프트로 남은 반면, 지식 집약적인 플랫폼 통합과 지루한 유지보수 작업을 맡겼을 때는 수년 걸리던 기능을 몇 주 만에 출시하고 역대 가장 잦은 릴리스 주기를 유지할 수 있었다. 차이를 만든 것은 도구가 아니라 품질 기준, 아키텍처, 테스트 선택, 리뷰를 사람이 쥐고 있었는지 여부다. 에이전트 시대에 필요한 역량은 코드를 빨리 치는 능력이 아니라 무엇을 만들지 결정하고, 만들어진 것을 읽고, 의도를 정확히 전달하는 능력이다. 코드는 싸졌지만 품질의 기준은 오히려 높아졌다.
