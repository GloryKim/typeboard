# 9. 타입 검사 (bun check) — 1.4.3 신규

## 왜 따로 검사해야 하나요?

Bun은 TypeScript를 **빠르게 실행하기 위해 타입을 검사하지 않고** 타입 표기만 지운 뒤 실행합니다. 그래서 타입이 틀린 코드도 일단 실행됩니다.

```ts
const age: number = "스무 살"; // 숫자 자리에 문자열
console.log(age);
```

```bash
bun typo.ts
```

```text
스무 살
```

오류 없이 실행되었지만, 이런 실수는 나중에 버그가 됩니다. 실행 전에 타입을 확인하려면 **타입 검사**를 해야 합니다.

## bun check

1.4.3에서 새로 생긴 명령입니다. 1.4.2 이하에서 실행하면 `error: Script not found "check"`가 나옵니다. 이전 버전에서는 TypeScript 패키지의 `tsc --noEmit`을 따로 써야 했습니다.

```bash
bun check
```

타입 오류가 없으면:

```text
✓ No type errors in 1 file [19.37ms]
```

오류가 있으면 문제가 된 코드 줄과 위치를 함께 보여 줍니다.

```bash
bun check typo.ts
```

```text
1 | const age: number = "스무 살";
          ^
error: TS2322: Type 'string' is not assignable to type 'number'.
    at typo.ts:1:7

Found 1 error in 1 file, checked 1 file [20.60ms]
```

- `^`가 가리키는 곳이 문제 위치이고, `typo.ts:1:7`은 "1번째 줄 7번째 칸"이라는 뜻입니다.
- 메시지는 "문자열(string)은 숫자(number) 자리에 넣을 수 없다"는 뜻입니다. `TS2322`는 오류 번호라서 검색할 때 쓰면 좋습니다.
- 출력을 다른 명령으로 넘기거나(`|`) `--no-pretty`를 붙이면 `typo.ts(1,7): error TS2322: ...`처럼 **오류 하나당 한 줄**로 나옵니다. `tsc`와 같은 형식입니다.
- 오류가 있으면 종료 코드가 `1`이라서 `bun check && bun test`처럼 이어 쓰면 오류가 있을 때 뒤 명령이 실행되지 않습니다.

## 특징

- **설정을 그대로 씁니다.** 가장 가까운 `tsconfig.json`을 읽고, TypeScript(`tsc`)와 같은 오류를 보여 줍니다.
- **빠릅니다.** CPU 코어를 모두 사용합니다.
- **일부만 검사할 수 있습니다.** `bun check src/`처럼 파일이나 폴더를 지정하면 그것과 그것이 불러오는 파일만 검사합니다.

## 자주 쓰는 방법

| 명령 | 설명 |
|---|---|
| `bun check` | 프로젝트 전체 검사 |
| `bun check src/app.ts` | 특정 파일(과 그 파일이 불러오는 파일)만 검사 |
| `bun run typecheck` | `bun init`이 만들어 둔 스크립트로 검사 (내용은 `bun check`) |
| `bun --check index.ts` | 타입 검사를 먼저 하고, **오류가 없을 때만** 실행 |
| `bun check --all` | 같은 오류가 50개를 넘어도 묶지 않고 모두 표시 |
| `bun check --no-pretty` | 오류 하나당 한 줄로 표시 (`tsc`와 같은 형식) |

## 1.4.2 이하에서 타입 검사하기

`bun check`가 없는 버전에서는 TypeScript 패키지의 `tsc`를 씁니다. 결과로 나오는 오류 형식은 같습니다.

```bash
bun add -d typescript
bunx tsc --noEmit
```

- `--noEmit`은 "검사만 하고 JavaScript 파일은 만들지 말라"는 뜻입니다. Bun이 `.ts`를 바로 실행하므로 변환된 파일은 필요 없습니다.
- `package.json`의 스크립트를 `"typecheck": "tsc --noEmit"`으로 바꿔 두면 `bun run typecheck`로 똑같이 쓸 수 있습니다.

## 처음에 자주 만나는 타입 오류

`bun init`이 만든 `tsconfig.json`은 엄격한 설정이 켜져 있어서([3장](./03_%EC%B2%AB_%ED%94%84%EB%A1%9C%EC%A0%9D%ED%8A%B8_%EB%A7%8C%EB%93%A4%EA%B8%B0.md#tsconfigjson%EC%97%90%EC%84%9C-%EC%95%8C%EC%95%84-%EB%91%98-%EC%84%A4%EC%A0%95)), 실행은 잘 되는 코드도 다음 오류가 날 수 있습니다.

```ts
import { User } from "./types"; // types.ts: export interface User { name: string }

const names = ["철수", "영희"];
const first = names[0];
console.log(first.toUpperCase());
```

```text
pit.ts(1,10): error TS1484: 'User' is a type and must be imported using a type-only import when 'verbatimModuleSyntax' is enabled.
pit.ts(5,13): error TS18048: 'first' is possibly 'undefined'.
```

| 오류 | 뜻 | 고치는 법 |
|---|---|---|
| `TS1484` | 타입(`interface`, `type`)만 불러오면서 `type`을 안 붙임 | `import type { User } from "./types"` |
| `TS18048` `possibly 'undefined'` | 배열 칸이나 객체 값이 없을 수도 있음 | `if (first) { ... }`로 확인하거나 `names[0]?.length ?? 0`처럼 `?.`, `??` 사용 |
| `TS2322` `not assignable` | 정한 타입과 다른 값을 넣음 | 값이나 타입 표기를 맞추기 |
| `TS2339` `does not exist on type` | 없는 속성 이름을 씀 (오타 등) | 이름 확인 |

- `?.`는 "앞의 값이 없으면 더 들어가지 않고 `undefined`", `??`는 "앞의 값이 없으면 뒤의 값"이라는 뜻입니다.
- 이 오류들은 **실행에는 영향이 없어서** `bun pit.ts`는 그대로 돌아갑니다. 하지만 실제로 배열이 비어 있으면 `first.toUpperCase()`에서 실행 중 오류가 나므로, 미리 막아 두는 것이 좋습니다.

## 타입 검사와 실행은 따로입니다

| 하는 일 | 타입이 틀리면 |
|---|---|
| `bun index.ts` (실행) | 그대로 실행됨. 틀린 값 때문에 **실행 중에** 이상한 결과나 오류가 날 수 있음 |
| `bun check` / `tsc --noEmit` (검사) | 실행하지 않고 오류 목록만 보여 줌 |
| `bun --check index.ts` | 검사해서 오류가 없을 때만 실행 |

타입 표기는 실행할 때 지워지므로 **실행 중에는 아무 검사도 하지 않습니다.** 예를 들어 `const body: { name: string } = await req.json()`이라고 적어도, 실제로 들어온 값에 `name`이 없을 수 있습니다. 바깥에서 들어오는 값(요청 본문, 파일, 환경 변수)은 코드에서 직접 확인하거나 [5장](./05_%ED%8C%A8%ED%82%A4%EC%A7%80_%EA%B4%80%EB%A6%AC.md)의 `zod` 같은 검사 도구를 쓰세요.

## 언제 실행하면 좋나요?

- 코드를 Git에 올리기 전
- 다른 사람의 코드를 받은 직후
- 테스트와 함께: `bun check && bun test`

> 편집기(VS Code, Cursor 등)도 같은 오류에 빨간 밑줄을 그어 줍니다. `bun check`는 프로젝트 전체를 한 번에 확인할 때 유용합니다.
