# 4. 패키지 관리

1.4.4의 `bun install`은 새 명령보다, 1.4.3이 조용히 잘못하던 경우를 실패시키거나 다른 패키지 관리자와 같은 결과로 맞춘 변경이 많습니다. 잠금 파일에 이미 있는 버전은 대부분 그대로 두고, 다시 풀 때만 새 규칙이 적용됩니다.

패키지 관리 풀 리퀘스트 597개 중 464개가 전부, 40개가 일부 반영되었습니다. 각 풀 리퀘스트의 테스트는 이전 Bun에서 실패하고 1.4.4에서 통과합니다. 추가로 생성한 프로젝트 600개, 변형한 `bun.lockb` 90,000개, `npm-pick-manifest`와 비교한 경우 200,000개를 돌렸다고 합니다. 버전 선택이 npm과 다른 경우는 `latest`가 없는 버전을 가리킬 때와 `^1.0.0-a.0` 두 가지입니다.

## Yarn Berry 잠금 파일

1.4.3은 Yarn v1 `yarn.lock`만 `bun.lock`으로 옮겼습니다. Yarn 2 이상(Berry) 프로젝트에서 `bun install`을 하면 고정 버전을 버리고 `package.json`부터 다시 풀었습니다. 1.4.4는 Berry 잠금 파일의 고정 버전을 유지합니다.

```text
bun install v1.4.4
[59.59ms] migrated lockfile from yarn.lock
```

워크스페이스, `npm:` 별칭, `resolutions`, git·tarball·`file:` 의존성이 유지됩니다. `patch:`는 `package.json`의 `patchedDependencies`가 됩니다. `catalog:` 범위는 `.yarnrc.yml`에서 읽어 `package.json`으로 복사합니다.

한 항목이라도 보존하지 못하면 통째로 포기하고 이유를 찍은 뒤 `package.json`으로 풀립니다. `exec:` 의존성, `.yarnrc.yml`에만 있고 `bunfig.toml`이나 `.npmrc`에는 없는 레지스트리가 그 예입니다. Yarn v1 잠금 파일 20,000항목 이전도 24초에서 0.27초로 줄었습니다.

## 레지스트리 재시도

1.4.3은 실패하면 5ms 안에 다섯 번을 다시 시도해서, 레지스트리가 잠깐 죽으면 설치가 실패했습니다. 1.4.4는 50ms부터 두 배씩 쉽니다. 50, 100, 200, 400, 800ms이고 각 대기에는 ±20% 흔들림이 있습니다.

| 레지스트리 | 1.4.4 | 1.4.3 |
|---|---|---|
| 503 한 번 뒤 성공 | 성공, 78ms | 성공, 22ms |
| 100ms 동안 503 | 성공, 222ms | 실패, 8ms |
| 1초 동안 503 또는 429 | 성공, 1.6초 | 실패, 7ms |
| 3초 동안 503 | 실패, 1.5초 | 실패, 18ms |

1.5초보다 긴 장애를 견디려면 `BUN_CONFIG_HTTP_RETRY_BACKOFF=250`처럼 첫 대기를 늘립니다. 그러면 250ms, 500ms, 1초, 2초, 4초입니다. `=0`이면 1.4.3처럼 바로 다시 시도합니다. `Retry-After`는 최대 60초까지 따릅니다. 429와 408도 다시 시도합니다. `bun info`, `bun pm view`, `bun pm whoami`, `bun audit`도 503이나 연결 끊김 한 번에 포기하지 않습니다.

## 피어 의존성

프로젝트 안 누구도 피어 의존성을 제공하지 않으면, Bun은 그 범위를 만족하는 버전을 설치합니다. 1.4.3은 관계없는 패키지가 설치한 버전을 그대로 물려줬습니다.

`@modelcontextprotocol/sdk@1.20.0`은 `express@5`에 의존하고, `@remix-run/express@2.17.1`의 피어는 `express@^4.20.0`입니다.

| 버전 | `@remix-run/express`가 받는 express |
|---|---|
| 1.4.4 | 4 |
| 1.4.3 | 5. `incorrect peer dependency` 경고 |

`elysia`와 `@jest/schemas`를 같이 두면 `elysia`가 `@sinclair/typebox@0.27`을 받아 로드에 실패하던 것도 같은 종류입니다.

고르는 순서는 세 단계입니다.

1. 프로젝트, 워크스페이스, 그 패키지의 조상이 그 피어를 의존하면 그 버전을 씁니다. 범위를 벗어나도 그렇습니다. 앱이 `react@17`이면 라이브러리도 `react@17`을 봅니다.
2. 아니면 그 피어를 선언한 패키지들이 함께 만족하는 버전 하나를 공유합니다. 이미 설치된 버전을 우선하고, 없으면 레지스트리에서 가장 새 버전입니다.
3. 하나를 같이 만족할 수 없으면, `react`나 `graphql`처럼 복제본 두 개가 깨지는 패키지를 패키지마다 새로 깔지는 않습니다. 범위 안에 설치된 버전이 있으면 그것을 쓰고, 없으면 나머지가 쓰는 버전을 공유합니다.

의존성을 다시 푸는 설치에서는 `--verbose`가 범위를 벗어난 피어를 모두 찍습니다. `bun.lock`에 있는 버전은 바뀌지 않습니다. 1.4.3에서는 `bun update --latest`로 `react-dom` 17을 19로 올려도, 피어로만 깔린 `react`는 한 번 더 실행해야 17에서 벗어났습니다. 1.4.4는 한 번이면 됩니다.

## 리눅스 네이티브 패키지와 설치 속도

`sharp`, `@swc/core`, `lightningcss`, `rollup`은 플랫폼마다 optional 의존성을 내고, 리눅스 빌드에 `"libc": ["glibc"]` 또는 `"libc": ["musl"]`를 답니다. 1.4.3은 이 필드를 무시해서 리눅스 설치마다 두 빌드를 받았습니다. 1.4.4는 이 시스템에 맞는 것만 받습니다. `bun install --libc musl`은 glibc 머신에서 Alpine용을 받고, `--libc '*'`는 예전처럼 둘 다 받습니다. 필드는 `bun.lock`에 저장됩니다. 예전 잠금 파일에는 없어서, 그 패키지를 업데이트하거나 잠금 파일을 다시 만들 때 채워집니다.

hoisted 링커는 macOS와 리눅스에서 최대 8스레드로 링크합니다. 캐시가 따뜻하고 `node_modules`가 비어 있는 CI에서 효과가 큽니다. 리눅스에서 패키지 1,000개(각 파일 30개)를 캐시에서 설치하면, `node_modules`가 비고 코어가 8개일 때 381ms에서 120ms입니다. 워크스페이스 2,100개 모노레포의 최대 메모리는 91MB에서 35MB입니다.

## 새로 쓸 수 있는 명령

`bun pm fetch`는 의존성을 캐시에만 받고 `node_modules`를 만들지 않으며, 스크립트와 잠금 파일을 건드리지 않습니다. Docker에서 다운로드 레이어를 `package.json`·`bun.lock`에만 묶을 때 씁니다.

```dockerfile
COPY package.json bun.lock ./
RUN bun pm fetch
COPY . .
RUN bun install --offline --frozen-lockfile
```

`bun pm cache pack .ci/bun-cache.pack`은 잠금 파일이 필요로 하는 캐시를 파일 하나로 만들고, `unpack`은 다른 머신에 없는 항목만 채웁니다. 손상된 파일은 통째로 거절합니다. `bun pm cache prune`은 30일보다 오래된 캐시를 지우고, `--max-age 7`과 `--dry-run`이 있습니다.

`bun publish --recursive`는 모노레포 패키지를 의존 순서대로 배포합니다. private 패키지와 레지스트리에 이미 있는 버전은 건너뛰어서, 중간에 실패해도 다시 실행할 수 있습니다. 첫 배포 전에 모든 패키지를 먼저 묶습니다. `--filter "@acme/*"`로 워크스페이스를 고릅니다.

`package.json`의 `packageExtensions`는 의존성을 선언하지 않고 import하는 패키지에 항목을 더합니다. isolated 설치에서 깨지는 경우를 포크 없이 메웁니다. 형식은 pnpm·Yarn과 같고, 잠금 파일을 옮길 때 같이 복사됩니다.

```json
{
  "packageExtensions": {
    "legacy-plugin@2": { "dependencies": { "lodash": "^4.17.21" } },
    "react-redux@7": { "peerDependencies": { "react": "*" } }
  }
}
```

`link:./vendor/design-tokens`는 `bun link` 없이 그 디렉터리를 `node_modules`에 심볼릭 링크로 넣습니다. 경로는 그 의존성을 적은 `package.json` 기준입니다. 경로 없는 `link:shared`는 예전처럼 `bun link`로 등록한 패키지입니다.

지원이 끝난 패키지는 설치할 때 한 줄 경고가 납니다. `bun add rimraf@3`이면 `deprecated rimraf@3.0.2`가 보입니다. 직접 의존성만 찍고, `--verbose`면 간접 의존성도 나옵니다. 범위를 풀 때는 지원이 끝난 버전을 피하고, `bun add pkg`는 지원이 끝난 `latest`를 건너뜁니다. 잠금 파일에 있는 버전은 `bun update` 전까지 유지됩니다.

## 플래그와 설정

다른 도구의 플래그를 Bun에 해당하는 것으로 바꿉니다. 1.4.3은 `--save-dev`를 무시해서 `dependencies`에 넣었고, `--immutable`을 무시해서 잠금 파일을 갱신했습니다.

| 다른 도구의 플래그 | Bun |
|---|---|
| `--immutable` | `--frozen-lockfile` |
| `--package-lock-only` | `--lockfile-only` |
| `--save-dev`, `--save-exact`, `--save-optional`, `--save-peer` | `--dev`, `--exact`, `--peer` 등 |
| `--only=production` | `--omit=dev` |
| `--shamefully-hoist`, `--node-linker=hoisted` | `--linker=hoisted` |
| `--node-linker=isolated` | `--linker=isolated` |

대응 플래그가 없는 `--no-package-lock`, `--network-timeout 100000`은 플래그와 값을 함께 무시합니다. 1.4.3은 플래그만 버려서 `100000`이라는 패키지를 추가하려고 했습니다. npm·Yarn·pnpm 어디에도 없는 플래그는 오류입니다. `bun install --frozen-lockfil`은 `has no --frozen-lockfil flag`로 끝납니다. 1.4.3은 이런 오타를 무시하고 CI에서 일반 설치를 했습니다.

`bun add -d`, `--optional`, `--peer`는 다른 그룹에 이미 있는 패키지를 그 그룹으로 옮깁니다. 예전에는 원래 자리에 남겼습니다. `bun add --save-prod`로 되돌릴 수 있습니다.

`minimumReleaseAge`는 `"3d"`, `"90m"`, `"12 hours"`, `"2 weeks"` 같은 단위를 받습니다. 숫자만 쓰면 여전히 초입니다. `minimumReleaseAgeExcludes = ["typescript@5.9.3"]`은 그 버전만 대기에서 빼서, 오늘 받은 보안 패치는 바로 쓰고 같은 패키지의 다른 버전은 기다리게 합니다. 플래그는 `--minimum-release-age`와 `--minimum-release-age-excludes`입니다.

`bun install --env-file ci.env`는 1.4.3에서 `ci.env`라는 패키지를 설치하려고 했습니다. 이제 그 파일을 읽습니다. `bunx --env-file`, `bunx --cwd`, `bunx --minimum-release-age`, `bunx --trust`도 추가되었습니다. `--trust`는 그 패키지와 의존성의 라이프사이클 스크립트를 실행합니다.

`actions/setup-node`가 임시 `.npmrc`를 만들고 `NPM_CONFIG_USERCONFIG`로 가리키면 Bun이 그 변수를 읽습니다. GitHub Packages 토큰을 파일로 복사하지 않아도 됩니다.

## 잠금 파일과 배포에서 눈에 띄는 것

직접 의존성만 올리고, 지울 목록만 보고, 프리릴리스가 `latest`로 올라가는 것을 막는 명령입니다.

```bash
bun update --depth 0          # package.json에 적은 것만. 간접 의존성은 bun.lock 유지
bun prune --check             # 지울 패키지를 출력만. 있으면 종료 코드 1
bun publish --tag next        # 2.0.0-beta.1 은 --tag 또는 publishConfig.tag 없이 거절
```

- `publishConfig.registry`와 스코프별 레지스트리가 `bun publish`의 대상을 정합니다.
- `publishConfig.registry`와 스코프별 레지스트리가 `bun publish`의 대상을 정합니다.
- `2.0.0-beta.1` 같은 프리릴리스는 `--tag`나 `publishConfig.tag` 없이 배포할 수 없습니다. npm 11과 같이, `latest`로 올라가지 않게 막습니다.
- `workspace:*`가 루트 패키지를 가리킬 수 있습니다.
- `bun.lock`에 `"hasInstallScript": true`가 생겨, 커밋된 잠금 파일로 설치할 때 막힌 스크립트를 보고합니다. 예전 Bun은 이 키를 무시하고 다음에 잠금 파일을 저장할 때 지웁니다.
- `--frozen-lockfile`이 `package.json` 변경으로 실패하면 `is-odd was added`, `is-number changed from ^6.0.0 to ^7.0.0`처럼 어느 의존성인지 말합니다.
- `--dry-run`이 `bun link`, `bun pm version`, `bun pm cache rm`, `bun pm trust` 등에서 실제로 쓰지 않습니다. 1.4.3은 플래그를 받고도 파일을 썼습니다.
- `bun audit fix`는 취약한 버전에 고정한 `overrides`를 알려 주고 고칩니다.
- 패치 적용이 더 이상 변경 줄 수에 제곱으로 늘지 않습니다. 10만 줄 파일에서 4만 줄을 바꾼 `bun patch --commit`이 1.45초에서 0.09초입니다.
- `Cache-Control: no-cache`, `no-store`, `max-age` 5분 미만인 레지스트리 메타데이터를 따릅니다. 발행 직후 5분 동안 설치되지 않던 버전이 이 수정에 해당합니다.
- 피어가 `bun`이면 npm의 `bun` 패키지(80~170MB)를 받지 않습니다.
- `1.0.0 || ^2.0.0`이 `1.0.0`으로만 해석되던 범위 파서가 고쳐졌습니다.

hoisted와 isolated를 오가면 두 구조가 섞이고 `.old_modules-*`가 남던 것, 설치가 중간에 죽으면 깨진 패키지를 설치된 것으로 보던 것, 읽기 전용 `node_modules`에서 `EEXIST`로 실패하던 것도 설치가 실패하거나 더러워지던 경우에 해당합니다. `bun install --dry-run`은 1.4.3에서 라이프사이클 스크립트를 실행했고 `bunfig.toml`의 `dryRun = true`를 무시했습니다.
