# 6. 보안과 동작이 바뀌는 수정

1.4.4를 보안 패치로만 올리고 릴리스 노트의 앞부분을 건너뛰면, 커버리지 숫자와 WebSocket close, Glob, 설치 플래그에서 기존 동작이 바뀐 것을 나중에 만납니다. 이 글은 패치가 닿는 면과, 테스트·핫 리로드·빌드에서 결과가 달라지는 수정만 모았습니다. 앞 글의 내용과 겹치는 명령은 링크만 둡니다.

## 보안 수정이 닿는 곳

공식 노트는 CVE를 항목별로 풀어 쓰지 않고, 수정이 닿는 프로토콜과 API를 나열합니다.

TLS, HTTP/1.1, HTTP/2, HTTP/3, WebSocket, Brotli, `Bun.serve`, `Bun.listen`, `Bun.connect`, `Bun.SQL`, `Bun.RedisClient`, `Bun.password`, `Bun.Image`, `Bun.Archive`, `node:tls`, `node:https`, `node:http`, `node:http2`, `node:net`, `node:quic`, `node:crypto`, `node:vm`, `node:v8`, `ws`, `fetch`, `TextEncoder`, `bun install`, `bunx`, `bun patch`, `bun publish`, `bun pm pack`, `bun pm trust`, `bun audit`, `bun create`.

이 중에서 업그레이드 직전에 이슈로 확인된 것이 Brotli 디코더입니다. [oven-sh/bun#46352](https://github.com/oven-sh/bun/issues/46352)는 CVE-2026-111497, 즉 디코더의 범위 밖 쓰기가 1.4.3까지의 Bun에 있다고 보고했고, 1.4.4에서 닫혔습니다. Node.js는 2026년 10월 21일 보안 릴리스(22.23.4, 24.22.1, 26.12.1)에서 같은 결함을 고쳤고, 수정 원본은 `google/brotli`의 아직 릴리스에 없는 커밋입니다. 1.4.2 이하는 brotli 1.1.0, 1.4.3은 1.2.0을 쓰며 그 위에 패치가 없었습니다.

디코더에 닿는 기본 경로는 세 가지입니다.

- `fetch`가 `Content-Encoding: br` 응답을 풀 때. 호출하는 서버를 공격자가 바꾸거나 이미 들어간 서버라면 응답만으로 닿습니다.
- `node:zlib`의 Brotli 함수와 `DecompressionStream("brotli")`.
- 요청 본문을 Brotli로 푸는 프레임워크. 맨 `Bun.serve`가 들어온 본문을 알아서 Brotli로 풀지는 않습니다.

워크어라운드로 공식 노트가 제시하는 것은 없습니다. 막는 방법은 1.4.4 이상으로 올리는 것입니다. 루트 인증서 묶음은 NSS 3.131.1으로 바뀌어서, 그 묶음에서 빠진 인증서를 신뢰하던 TLS 연결은 실패할 수 있습니다.

이 문서 서버는 `Bun.serve`로 페이지를 주고, 브라우저가 같은 출처의 WebSocket으로 새로고침 신호를 받습니다. 서버가 방문자의 요청 본문을 Brotli로 풀지는 않습니다. 그래도 런타임이 `fetch`와 압축 해제를 포함하므로, 사이트를 이 버전으로 계속 돌리려면 1.4.4가 맞습니다.

## mTLS는 requestCert가 있어야 인증서를 요청한다

`Bun.serve`, `Bun.listen`, `node:tls` 서버는 `requestCert: true`일 때만 클라이언트 인증서를 요청합니다. 문서와 Node.js와 같고, 1.4.3은 `ca`만 있어도 요청했습니다. `ca`는 그 인증서를 신뢰하는 설정으로 남고, 요청과는 분리됩니다.

```ts
Bun.serve({
  tls: {
    cert: Bun.file("./server.crt"),
    key: Bun.file("./server.key"),
    ca: Bun.file("./client-ca.crt"),
    requestCert: true,
  },
  fetch(req) {
    return new Response("ok");
  },
});
```

Ed25519 인증서 서버로의 `fetch`와 `tls.connect()`도 연결됩니다. 1.4.3은 실패했습니다. `dotnet dev-certs`처럼 CA로 표시되지 않은 자체 서명 인증서도 `NODE_EXTRA_CA_CERTS`나 `ca`로 신뢰할 수 있습니다. 키·인증서 쌍을 여러 개 두면 마지막 쌍만 제공하던 것이, 클라이언트가 지원하는 쌍을 고릅니다.

## 테스트 커버리지 숫자가 내려갈 수 있다

`bun test --coverage`가 실행되지 않은 코드를 실행된 것으로 세던 경우를 뺐습니다. 임계값을 빡빡하게 걸어 두었다면 업그레이드 뒤에 같은 테스트가 실패할 수 있습니다. 테스트가 나빠진 것이 아니라 분모와 분자가 맞아진 것입니다.

실행된 줄에서 빠진 것:

- 한 줄에 혼자 있는 `||`, `&&`, `??`, `?:`의 오른쪽
- `?.`, `||=`, `&&=`, `??=`가 건너뛴 코드, 쓰이지 않은 기본값, 타지 않은 `break`
- 함수가 그 너머로 재개되지 않은 `await`·`yield` 뒤의 줄

반대로, 실행했는데 미실행으로 나오던 줄은 이제 실행으로 나옵니다. `while (true)` 블록 안의 `break`, `class Derived extends Base() {}` 위의 `import`, 실행된 함수 안에서 혼자 있는 `default:`와 다음 줄에 값이 있는 `case`가 그렇습니다. 실행되지 않은 함수의 미커버 줄 번호는 두 줄 앞에서 시작하고 마지막 줄을 빼먹던 범위가 고쳐졌습니다. `else`와 `{`가 다른 줄이면 `{` 대신 `else` 줄이 찍힙니다.

`% Funcs`는 암시적 생성자, 클래스 필드 초기화, `static` 블록, 제너레이터·async 함수 본문을 함수로 세서, 본문을 모두 검사한 클래스가 50%로 보이던 경우가 있습니다. `lcov.info`의 `DA:` 횟수는 줄이 실행된 횟수가 아니었습니다. 한 번 실행된 줄이 14로 찍힐 수 있었습니다.

`bun test --update-snapshots`는 `--bail`처럼 실행이 일찍 끝나면 스냅샷 파일을 비웠습니다. 새 내용을 다 쓰기 전에는 예전 내용을 유지합니다.

## 핫 리로드와 감시

macOS와 리눅스에서 `bun --hot` 도중 잡지 않은 예외가 나면, 그 뒤에 타이머가 멈추고 파일을 고쳐 저장해도 돌아오지 않았습니다. 이제 리로드가 타이머를 살리고 종료 코드도 0으로 되돌립니다. SQL 연결을 리로드마다 쌓던 문제는 [5장](./05_SQL%EA%B3%BC_WebSocket.md)에 있습니다.

## 셸, 빌드, 트랜스파일

Bun Shell에서 환경 변수 값에 NUL 바이트가 있으면 거기서 잘렸습니다. `.env()`와 `.cwd()`는 그런 문자열에 `ERR_INVALID_ARG_VALUE`를 던집니다. `mv -n`은 목적지가 있어도 덮어썼고, `cp -n`은 목적지가 있으면 종료 코드 1이었습니다. `cp -n`은 목적지가 있을 때 실패하지 않는 쪽이 일반적인 `-n`입니다.

`bun build --minify`는 `export default (function inc() {})`처럼 괄호로 감싼 이름 있는 함수·클래스 표현식이 기본보내기 두 개면 둘에 같은 이름을 줬습니다. 소스맵은 `export default function`, `export default class`, `export async function`, `abstract class`, `import()`, `require()`, `require.resolve()`의 열을 잘못 가리켰습니다. CSS에서는 같은 규칙에서 `transform`보다 앞에 있는 `translate`, `rotate`, `scale`을 버렸고, 뒤에 있는 것은 `transform`으로 합쳤습니다.

표준 데코레이터에서 클래스 데코레이터가 새 클래스를 돌려주면, 클래스 본문의 클래스 이름이 원래 클래스를 가리켰습니다. `@dec static {}`처럼 정적 블록에 데코레이터를 다는 것은 TypeScript·esbuild와 같이 문법 오류입니다. `0x` 리터럴이 2^53을 넘을 때의 반올림은 [3장](./03_%ED%83%80%EC%9E%85_%EA%B2%80%EC%82%AC%EC%99%80_%EB%9F%B0%ED%83%80%EC%9E%84.md)에 있습니다.

## 설치와 실행에서 자주 만나는 수정

[4장](./04_%ED%8C%A8%ED%82%A4%EC%A7%80_%EA%B4%80%EB%A6%AC.md)의 새 명령 외에, 업그레이드 직후 스크립트가 실패하거나 성공으로 바뀌는 경우가 있습니다.

- `bun install`, `bun link`, `bun update -i`가 `Failed to install N packages`를 찍고도 종료 코드 0이었습니다.
- 상대 `--cwd`를 `bun update`, `bun link`, `bun unlink`, `bun why`가 두 번 적용해서 `ENOENT`가 났습니다.
- `NODE_ENV=development` 또는 `test`인데 `bun install`이 `.env.production`을 읽었습니다. `bun run`이 읽는 파일과 달랐습니다.
- 심볼릭 링크를 지원하지 않는 파일 시스템에서 설치가 실패했습니다. 이제 한 번 경고하고 `.bin` 링크를 건너뜁니다.
- 바이너리 이름이 여러 패키지에 있으면 `.bin`에 들어가는 것이 임의였습니다. 직접 의존성이 우선합니다.
- `prepare`에서 바이너리를 만드는 워크스페이스 CLI는 다음 `bun install`까지 `.bin`에 연결되지 않았습니다.
- `bunx` 여러 개가 동시에 같은 설치를 건드리면 캐시가 깨졌습니다. 캐시가 하루보다 오래되고 레지스트리가 5xx·429·408이면 `bunx`가 실패했습니다.
- `bun patch`의 헝크가 줄 번호로만 적용되어, 파일이 바뀐 뒤 엉뚱한 자리에 들어갔습니다. 이제 `git apply`처럼 문맥으로 맞춥니다. 적용할 수 없는 부분이나 버전 없는 `patchedDependencies` 키는 조용히 건너뛰지 않고 경고합니다. 적용이 거절되면 `package.json`과 `bun.lock`을 바꾸지 않습니다.
- `bun publish --provenance`와 `NPM_CONFIG_PROVENANCE`는 무시되어 출처 없이 배포되었습니다. Bun이 출처를 만들지 못하므로 이제 오류입니다.
- Alpine(musl)에서 glibc와 musl 바이너리를 같이 가진 패키지가 glibc 바이너리에 명령을 연결할 수 있었습니다.
- 레지스트리 URL에 경로가 있고 끝에 `/`가 없으면 마지막 경로 조각이 빠져 모든 요청이 404였습니다.
- `~`로 시작하는 캐시·전역 경로가 이름 그대로 `~`인 디렉터리를 만들었습니다.

`bun add -E react@18`은 `18`이라고만 적었습니다. `--exact`는 적은 범위를 설치된 버전에 고정합니다. npm과 같습니다.

## node:http와 개발 서버가 매초 새로고침되던 경우

`node:http`에서 `'upgrade'`와 `'connect'` 소켓의 `socket.bytesWritten`가 0이었습니다. engine.io는 그런 소켓을 1초 뒤에 닫아서, socket.io를 붙인 Vite나 SvelteKit 개발 서버가 페이지를 매초 다시 불러왔습니다. Slack Bolt Socket Mode는 `undici`에 `ping()`과 웹소켓 ping·pong 진단 채널이 없어 재연결을 반복했습니다.

`res.end()`는 `res.statusCode`가 `"404"`나 `200.5`이면 `ERR_INVALID_ARG_TYPE`을 던졌습니다. 이제 `404`와 `200`을 보냅니다. `NaN`이나 `undefined`면 Node.js처럼 `ERR_HTTP_INVALID_STATUS_CODE`입니다. 잘못된 청크로 `res.end({})`가 던진 뒤에는 아무것도 보내지 않았는데 `headersSent`가 `true`여서 이후 `setHeader`가 실패했습니다.

## 이 사이트를 1.4.4로 돌릴 때

설명서 본문의 `bun check` 예시는 1.4.3에서 확인한 동작입니다. 1.4.4에서도 명령은 같고, 큰 프로젝트에서의 속도와 오탐이 이 범주의 [3장](./03_%ED%83%80%EC%9E%85_%EA%B2%80%EC%82%AC%EC%99%80_%EB%9F%B0%ED%83%80%EC%9E%84.md)처럼 달라집니다. 이 저장소의 `typecheck` 스크립트는 예전에 로컬 Bun이 1.4.1이라 `tsc`를 부르도록 되어 있습니다. 지금 런타임은 1.4.4이므로 `bun check`를 직접 써도 됩니다.

서버를 다시 띄운 뒤에는 `bun --version`이 `1.4.4`인지, 그리고 `http://localhost:3000`의 사이드바에 설명서와 `1.4.4` 범주가 같이 보이는지만 확인하면 됩니다.
