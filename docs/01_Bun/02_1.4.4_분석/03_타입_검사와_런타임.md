# 3. 타입 검사와 런타임

1.4.3에서 생긴 `bun check`가 1.4.4에서 큰 프로젝트 기준으로 빨라지고, 오탐과 누락이 `tsc`에 더 가까워졌습니다. 같은 릴리스에서 JavaScriptCore를 올리고, Glob 문법과 개발 서버 오류 화면도 바뀌었습니다.

## bun check가 빨라진 정도

콜드 런, 스레드 8개, Linux x64, 3회 중 가장 빠른 값입니다. 두 버전이 보고하는 오류 개수는 같습니다.

| 프로젝트 | 1.4.4 | 1.4.3 | 배율 |
|---|---:|---:|---:|
| MUI `docs` | 1.31초 | 10.28초 | 7.8배 |
| t3code `server` | 1.62초 | 4.59초 | 2.8배 |
| Supabase `studio` | 1.27초 | 2.84초 | 2.2배 |
| mikro-orm | 1.82초 | 3.30초 | 1.8배 |
| VS Code | 2.82초 | 4.09초 | 1.4배 |

MUI `docs`의 최대 메모리는 11.2GB에서 1.3GB로 줄었습니다. 나머지 네 프로젝트는 최대 0.3GB 더 씁니다. 다른 저장소 76곳 중 69곳은 10% 넘게 빨라졌고, Bun 자신의 `src/js`는 0.11초에서 0.20초로 느려졌습니다. 모든 저장소가 빨라진 것은 아닙니다.

케이스 수천 개인 `switch`나, 클로저에서 읽는 대입 수천 번이 더 이상 수 초를 잡지 않습니다. Windows에서 isolated install 프로젝트는 파일 로드가 31~45% 빨라져, opencode 패키지 기준으로 실행당 50~100ms가 줄어듭니다.

`tsconfig.json`의 `paths`처럼 키가 많은 객체를 다루는 시간이 키 수의 제곱이었습니다. 키 40,000개가 10.9초에서 0.1초로 줄었습니다. `paths`나 `files` 항목마다 오류가 있을 때도 마찬가지라, TS5090 4,000개가 35.5초에서 0.04초입니다. 프로젝트 폴더 옆에 파일이 수만 개 있으면(`$TMPDIR`, 큰 `~/code`) 검사도 느려졌는데 이 경우도 줄었습니다.

## bun check -b

프로젝트 참조(`-b`)가 선언 파일 파싱, 모듈 해석 캐시, 출력 파일 목록을 프로젝트끼리 공유합니다. 1.4.3은 프로젝트마다 복사본을 들고 있어서, 프로젝트 수가 늘면 시간이 그보다 가파르게 늘었습니다.

`skipLibCheck: true`인 생성 모노레포, M4 Max 16코어, 6회 중 가장 빠른 값입니다.

| 구성 | 1.4.4 | 1.4.3 |
|---|---:|---:|
| 독립 프로젝트 1,000개, 각 5파일 | 0.53초 | 2.07초 |
| 독립 프로젝트 4,000개, 각 5파일 | 0.87초 | 13.65초 |
| 참조가 최대 40개인 프로젝트 800개, 각 20파일 | 1.26초 | 7.36초 |

마지막 구성의 최대 메모리는 1,987MB에서 872MB입니다. 공통 `tsconfig.json`을 상속하는 프로젝트 1,000개에 `paths` 5,000개가 있으면 71초·3.08GB에서 1.6초·0.62GB입니다. 작은 프로젝트는 한 번에 4개 대신 최대 16개를 병렬로 검사해서, 큰 프로젝트가 많은 모노레포는 메모리를 더 씁니다.

`package.json`에 `check` 스크립트가 있어도 타입 검사를 돌리려면 `bun check --no-script`입니다. `-b` 같은 타입 검사 플래그를 뒤에 붙일 수 있습니다. `bun fmt`도 `--no-script`를 받습니다.

## tsc와 어긋나던 오류

속도보다 결과에 영향을 주는 수정입니다. 1.4.3에서 나오던 거짓 오류가 줄고, `tsc`가 잡는데 Bun이 놓치던 오류는 이제 나옵니다.

거짓으로 나오던 쪽:

- Slate의 `CustomTypes` 모듈 보강에서 TS2456·TS2502. `Editor`가 `any`가 되면서 진짜 오류가 숨었습니다.
- 스레드 수에 따라 달라지던 오류. `@sinclair/typebox`에서 스레드 2개 이상이면 TS2321이 거짓으로 나왔습니다.
- tRPC에서 `Promise | PromiseLike`의 `.then()` 결과를 `"catch" in result`로 좁힐 때의 TS18046·TS7006.
- TanStack Router의 `useLoaderData()`처럼, 빼먹은 선택 매개변수의 타입이 무한히 깊을 때의 TS2589.
- ts-pattern처럼 스프레드로 만든 객체가 제네릭 호출 사슬을 탈 때의 TS2589.
- immer의 `Draft`를 받는 메서드가 있는 클래스를 타입 가드가 좁힌 뒤의 TS2615.
- 서로 순환하며 `infer`를 쓰는 제네릭의 TS2344·TS2345·TS2339·TS7031.
- TypeScript 7.1과 같이, 중첩 비교 100번이 넘어가면 TS2321을 내지 않고 서로 관련된 타입으로 봅니다.

놓치던 쪽은 루프 안에서 변수를 다시 대입할 때의 TS2322·TS2367, `readonly`를 매핑 타입이 벗길 때의 TS2540·TS2704, `protected`/`private`를 교차 타입으로 읽을 때의 TS2445·TS2341입니다. `@ts-expect-error`가 사용되지 않았다고 나오던 자리도, 이제 그 아래에 있어야 할 TS2589가 나오면 사라집니다.

순환하는 `extends`를 가진 `tsconfig.json`의 TS18000은 파일 이름 자리에 `{0}`을 찍었습니다. 이제 파일 이름이 나옵니다.

## JavaScriptCore

WebKit 쪽 커밋 1,013개가 들어왔습니다. Apple Silicon에서 여러 번 돌려 가장 좋은 값을 고른 공식 수치입니다.

| 작업 | 1.4.4 | 1.4.3 |
|---|---:|---:|
| `n.toLocaleString("en-US")` 10만 번 | 25ms | 1,341ms |
| 정수 100만 개 배열 리터럴 로드 | 11ms | 45ms |
| 비라틴1이 섞인 문자열 `for...of` 100만 글자 | 1.2ms | 3.2ms |
| `new Array(n)`, n이 4 미만, 1,000만 번 | 31ms | 61ms |
| `throw "x"` 100만 번 | 37ms | 72ms |
| `throw new Error("x")` 100만 번 | 128ms | 174ms |

로케일만 주고 옵션 없이 부르는 `toLocaleString()`은 `Intl.NumberFormat`을 캐시해서, 포매터를 직접 만들어 `format()`을 부르는 것과 같은 속도가 됩니다. 숫자와 BigInt 모두 해당합니다.

```ts
1n + 2n; // 그대로 3n
+1n * 2n; // 1.4.4부터 TypeError. 1.4.3은 2n
```

문법과 평가 순서가 바뀐 곳이 있습니다.

- `switch`의 `case` 안에 중첩된 함수에서 `using`이 문법 오류였습니다. 이제 허용됩니다.
- `+1n * 2n`은 `2n`이 아니라 `TypeError`입니다.
- `+a * b()`는 `b()`보다 먼저 `a.valueOf()`를 부릅니다.
- `for...in`이 함수의 인덱스 프로퍼티(`fn[0]`)를 방문합니다.
- JIT에서 `(x + y + 0.5) | 0`이 32비트 오버플로 때 틀린 값을 내던 경우, `new Uint8Array(-1)`를 쓰지 않아도 `RangeError`가 나야 하는 경우가 고쳐졌습니다.
- 원소 16개 이하 정수를 `.sort()`할 때 `(a, b) => (a + 0.5) - (b + 0.5)` 같은 비교 함수가 틀린 순서를 내던 1.4.0 이후 회귀가 고쳐졌습니다.

오류를 가리키는 `^`는 그 줄 앞에 한글처럼 폭이 두 칸인 글자가 있으면 너무 왼쪽에 찍혔습니다. 열 번호도 0부터 세던 것이 1부터로 바뀌어, `source-map-support`가 1열 프레임에서 예외를 던지던 문제가 사라집니다. `error.stack`은 `file.js:3` 대신 `file.js:3:1`을 찍습니다.

## Glob의 extglob

`Bun.Glob`이 extglob과 중괄호 범위를 지원합니다. `bun install --filter`, `package.json`의 `workspaces`, `files`, `sideEffects`도 같은 문법을 씁니다.

```ts
new Bun.Glob("**/!(*.test).ts").match("src/cart.test.ts"); // false
new Bun.Glob("src/@(app|lib)/**/*.ts").match("src/app/a/b.ts"); // true
new Bun.Glob("shard-{1..3}.json").match("shard-2.json"); // true
```

| 패턴 | 뜻 |
|---|---|
| `?(a\|b)` | 패턴 중 하나, 또는 없음 |
| `*(a\|b)` | 패턴 중 하나 이상, 또는 없음 |
| `+(a\|b)` | 패턴 중 하나 이상 |
| `@(a\|b)` | 패턴 중 정확히 하나 |
| `!(a\|b)` | 그 경로 조각에서 패턴이 아닌 것 |
| `{1..3}`, `{01..10}`, `{a..e}`, `{1..9..2}` | 숫자·문자 범위. 세 번째 값은 간격 |

`?`, `*`, `+`, `@`, `!` 뒤에 오지 않은 `(`는 여전히 글자 그대로라, Next.js의 `app/(marketing)/**`는 그대로 매칭됩니다.

1.4.3에서 글자 그대로였던 패턴은 뜻이 바뀝니다. picomatch, minimatch, bash extglob과 맞추기 위한 변경입니다.

| 패턴 | 1.4.3 | 1.4.4 |
|---|---|---|
| `*(1).txt` | `copy(1).txt`와 매칭 | `1`이 0번 이상 나온 뒤 `.txt`. 예전 뜻은 `*[(]1).txt` |
| `!(g)/a.ts` | `(g)/a.ts`만 제외 | `g`가 아닌 폴더의 `a.ts` |
| `{1..3}` | 문자열 `1..3` | `1`, `2`, `3` |

패턴만 바뀝니다. 파일 이름에 이 문자가 있어도 `**/*.ts`는 그대로 매칭됩니다. Bun Shell의 따옴표와 `${}`는 여전히 글자 그대로입니다. `workspaces`에 `packages/!(internal)`을 쓰면 1.4.3은 `Workspace not found`로 실패했습니다.

`Bun.Glob.match()` 자체도 빨라져서, `**/*.{ts,tsx}`를 `src/components/button/index.tsx`에 대는 시간이 M4 Max에서 158ns에서 32ns입니다.

## 요청과 응답에서 자주 타는 경로

`Headers`의 `for...of`, `entries()`, `keys()`, `values()`, `forEach()`, `Object.fromEntries`가 1.7배에서 2.8배 빨라졌습니다. 헤더 3개를 `for...of`로 도는 시간이 M4 Max에서 277ns에서 98ns입니다. `@hono/node-server`처럼 응답 헤더를 `node:http`로 복사하는 어댑터가 매 요청마다 이 경로를 탑니다.

이미 메모리에 있는 본문(`new Response("...").body`, `request.body`, `blob.stream()`)을 읽는 속도는 1.5배에서 2.6배이고, 100바이트 본문의 할당은 270KB에서 7KB입니다. 같은 Hono 앱이 요청 24개를 처리하는 시간이 24.0ms에서 16.0ms로 줄었다는 측정이 있습니다.

`node:http`에서 `req.headers`와 `res.setHeader()`의 오버헤드도 줄었습니다. Express 5로 요청 256개가 Linux x64에서 9.91ms에서 9.45ms입니다. 큰 차이는 아니고, 헤더를 많이 복사하는 서버에서 쌓입니다.

## 문자열로 코드를 만드는 것 금지

`--disallow-code-generation-from-strings=strict`는 막힌 API 목록을 보던 방식에서, JavaScriptCore가 Bun 내장과 내 프로그램 파일이 아닌 코드는 실행하지 않는 방식으로 바뀌었습니다. 어느 API로 들어왔는지는 보지 않습니다.

`bun build --compile`로 만든 실행 파일에서는 실행 파일 안의 코드만 내 프로그램입니다. 디스크의 JavaScript·TypeScript, 방금 `Bun.write`로 만든 플러그인 파일, `contents`를 돌려주는 플러그인, 매크로, `BUN_OPTIONS`의 `--preload`, 디스크의 `.txt`·`.md` import는 막힙니다. `.json`, `.toml`, `.yaml`과 JSON `data:` URL import는 여전히 됩니다. `--compile`이 아니면 디스크의 파일이 내 프로그램으로 쳐서, 같은 `import()`는 실행됩니다.

## 개발 서버 오류 화면

HTML import를 쓰는 `Bun.serve`의 오류 오버레이가 다시 그려졌습니다. 같은 파일의 비슷한 오류는 카드 하나로 묶입니다. 글꼴 세 개가 없으면 블록 세 개가 아니라 한 카드에 `×3`으로 모입니다.

```text
BUILD FAILED
4 errors in 2 files

app.ts                                         1 ERROR
  ERROR  Could not resolve: "./render"

styles.css                                    3 ERRORS
  ERROR  Could not resolve                          ×3
```

오버레이가 스크롤되어 화면 아래 오류에 닿을 수 있습니다. 서버와 브라우저 양쪽으로 번들되는 스타일시트 오류는 한 번만 나옵니다. 밝은 테마는 시스템 설정을 따릅니다. 런타임 오류도 같은 모양이고, 제목은 오류 이름입니다.

`bun ./index.html --port 3000`처럼 띄어 쓴 `--port`와 `--host`가 무시되던 것, `--host=::1`의 `RangeError`, 시작 오류가 두 번 찍히던 것이 고쳐졌습니다.

## 그 밖의 런타임

- `Bun.JSON5.parse()`는 최대 1.6배. 126KB `bun.lock`이 M4 Max에서 0.67ms에서 0.42ms입니다.
- `Bun.markdown.html()`은 큰 비ASCII 입력에서 CPU 명령이 33% 줄었습니다. 이 사이트의 본문 변환이 이 함수입니다.
- 짧은 문자열 해시와 `new TextDecoder("utf-8", { fatal: true })`가 빨라졌습니다.
- `NODE_COMPILE_CACHE`나 `module.enableCompileCache()`로 컴파일 캐시를 쓰는 실행이 1.4.3에서 종료에 두 배(3.4MB 모듈 기준 300ms → 580ms) 걸리던 회귀가 되돌아갔습니다.
- 네이티브 애드온이 Linux·macOS에서 `uv_async_*`, `uv_timer_*`, `uv_queue_work` 등 libuv 함수 47개를 더 부를 수 있습니다. 전에는 `unsupported uv function`으로 프로세스가 끝났습니다.
- 루트 인증서 묶음은 NSS 3.131.1입니다. FreeBSD 바이너리의 기준 버전은 수명이 끝난 14.3 대신 14.4입니다.
- cgroup v1 계층만 있어도(`name=systemd` 포함) cgroup v2 제한을 무시하던 `navigator.hardwareConcurrency`, `os.availableParallelism()`, `process.constrainedMemory()`와 스레드 수·GC 힙 크기가 제한을 봅니다.
- 16진·8진·2진 리터럴이 2^53을 넘으면 잘못된 부동소수로 반올림되던 것이 Node.js와 같아졌습니다. `0xb3c8bf81fdf2247`이 그 예이고, `Bun.JSONC.parse()`도 같은 버그였습니다.
- 컨테이너에서 PID 1로 돌 때 Ctrl+C나 `docker stop`의 종료 코드는 128 + 시그널 번호입니다.

## 타입 정의

런타임은 원래 이렇게 동작했는데 `@types/bun`이 다르게 적혀 있던 것이 1.4.4에서 맞춰졌습니다.

```ts
Bun.hash("abc"); // bigint. 예전 타입은 number | bigint
expect(fn).toHaveBeenCalledOnce(); // bun test에는 원래 있음. 타입에 빠져 있었음
```

`Bun.mmap()`에 `Buffer`나 `URL`을 넘기는 타입은 빠졌습니다. 런타임은 둘 다 예외입니다. `Bun.MD5`, `Bun.SHA256` 같은 해시 인스턴스의 `byteLength`, 서브프로세스 `resourceUsage()`의 `cpuTime`(`bigint`), `FileSystemRouter`의 `origin`(`string | null`)도 런타임과 같아졌습니다.
