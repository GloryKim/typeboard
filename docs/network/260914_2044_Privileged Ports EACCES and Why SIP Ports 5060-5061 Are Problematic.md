# 특권 포트(Privileged Ports)와 EACCES, 그리고 SIP 포트 5060/5061

## 요약

유닉스·리눅스·macOS에서 TCP/UDP 포트 **0–1023**은 전통적으로 특권 포트(privileged / well-known ports)다. 일반 사용자 프로세스가 이 구간에 `bind()`하면 대개 `EACCES`(Permission denied)가 난다. 웹의 80/443, SSH의 22처럼 시스템·공용 서비스가 차지하는 대역을 임의 프로세스가 가로채지 못하게 하려는 역사적 보호 장치다.

**1042는 특권 포트가 아니다.** 1024 이상이므로 OS 특권 포트 규칙만 놓고 보면 일반 유저도 바인딩할 수 있다. 1042에서 실패한다면 원인은 `EACCES` 특권 제한이 아니라, 이미 사용 중(`EADDRINUSE`), 방화벽, 컨테이너/샌드박스 정책, 또는 배포 환경의 별도 포트 허용 목록일 가능성이 크다.

**5060·5061은 OS 특권 포트도 아니다**(둘 다 1024 초과). 그럼에도 일반 앱·홈 서버·게임·임의 API에 쓰지 말라고 하는 이유는 IANA상 SIP(Session Initiation Protocol) 표준 포트이고, ISP·공유기·보안 장비가 VoIP 사기·스캔·SIP ALG 때문에 이 포트를 차단·변조·감시하는 경우가 많기 때문이다. “root가 필요해서”가 아니라 “네트워크 경로와 정책이 적대적”이라서 피한다.

## 1. 포트 번호 체계와 특권 포트

IANA와 일반적인 운영 구분이다.

| 구간 | 이름 | 일반적 의미 |
| --- | --- | --- |
| 0–1023 | Well-known / privileged | 시스템·표준 서비스. 유닉스계열에서 bind에 높은 권한 요구 |
| 1024–49151 | Registered | 애플리케이션이 IANA에 등록해 쓰는 구간. OS 특권과 무관 |
| 49152–65535 | Dynamic / ephemeral | 클라이언트가 잠깐 쓰는 임시 출발지 포트 등에 활용 |

특권 포트 규칙의 핵심은 다음과 같다.

```text
포트 < 1024  →  일반 유저 bind 실패 (EACCES)가 기본
포트 ≥ 1024 →  일반 유저 bind 가능 (다른 제약만 없으면)
```

경계는 **미만(strictly less than 1024)** 이다. 즉 **1024는 특권 포트가 아니다.** 1023까지가 특권, 1024부터가 비상업적·비특권 바인딩의 시작이다.

이 숫자는 커널/OS 정책의 기본값이며, 리눅스에서는 `net.ipv4.ip_unprivileged_port_start`로 시작 포트를 바꿀 수 있다. 기본이 1024인 환경이 대부분이다. 컨테이너·루트리스 포드·일부 배포판은 이 sysctl이나 capability 설정 때문에 체감이 달라질 수 있다.

## 2. EACCES가 나는 이유

프로세스가 소켓을 만들고 특정 포트에 바인딩하는 흐름은 대략 다음과 같다.

```text
socket() → bind(IP, port) → listen()/또는 UDP 수신
```

`bind()` 시점에 커널이 “이 포트는 특권 포트인데, 호출자에게 권한이 있는가?”를 검사한다. 권한이 없으면:

```text
Error: listen EACCES: permission denied
Error: bind: Permission denied
```

같은 메시지가 Node, Bun, Python, Go, Rust 등 런타임에 그대로 전달된다. 애플리케이션 버그가 아니라 **OS가 거부한 결과**다.

권한이 있는 쪽의 대표 예:

- `root`로 실행
- Linux capabilities: `CAP_NET_BIND_SERVICE`를 바이너리에 부여 (`setcap`)
- systemd: `AmbientCapabilities=CAP_NET_BIND_SERVICE`
- authbind, 또는 앞단 리버스 프록시가 80/443을 받고 백엔드는 8080 등으로 받기
- macOS에서도 전통적으로 1024 미만은 elevated 권한이 필요. 개발 중에는 `sudo` 또는 비특권 포트 사용이 흔하다

실무에서는 **앱을 root로 돌리기보다**, 공개 포트는 Caddy/Nginx/클라우드 LB가 받고 앱은 `3000`·`8080` 같은 높은 포트를 쓰는 구성이 일반적이다.

## 3. 1042 포트도 안 되는가?

**OS 특권 포트 기준으로는 된다.** 1042 ≥ 1024 이므로 일반 유저 `bind()`의 대상이다.

```text
22    → 특권 (SSH)     → 일반 유저 EACCES 가능
80    → 특권 (HTTP)    → 일반 유저 EACCES 가능
443   → 특권 (HTTPS)   → 일반 유저 EACCES 가능
1023  → 특권 (마지막)  → 일반 유저 EACCES 가능
1024  → 비특권         → 일반 유저 OK
1042  → 비특권         → 일반 유저 OK
5060  → 비특권 (SIP)   → OS상 OK, 네트워크 정책상 비권장
8080  → 비특권         → 일반 유저 OK
```

1042에서 “안 된다”면 특권 포트와 원인을 분리해서 본다.

| 증상/에러 | 해석 |
| --- | --- |
| `EACCES` / Permission denied | 특권 포트(<1024)이거나, 샌드박스·seccomp·MAC 정책이 bind를 막음. 1042면 후자 쪽을 의심 |
| `EADDRINUSE` / address already in use | 다른 프로세스가 이미 1042를 사용 중 |
| 타임아웃·외부만 실패 | 로컬 bind는 됐지만 방화벽·공유기 포트포워딩·ISP 필터 문제 |
| 컨테이너 안에서만 실패 | 네트워크 네임스페이스, 포트 publish, rootless 제한 |

빠른 확인 예:

```bash
# 일반 유저로 1042 바인딩이 되는지
python3 -c "import socket; s=socket.socket(); s.bind(('0.0.0.0', 1042)); print('ok', s.getsockname()); s.close()"

# 누가 쓰는지
# macOS
lsof -nP -iTCP:1042 -sTCP:LISTEN
# Linux
ss -lptn 'sport = :1042'
```

정리하면, **“1024 미만 → 일반 유저 불가” 규칙의 연장선으로 1042를 금지하지 않는다.** 1042는 그 규칙의 바깥이다.

## 4. 특권 포트를 써야 할 때와 피해야 할 때

### 4.1 써야 하는 경우

- 브라우저 기본 HTTPS(443)·HTTP(80)처럼 **포트를 URL에 안 쓰고** 표준 관례를 따라야 할 때
- 조직 표준이 특정 well-known 포트를 요구할 때

이 경우에도 앱 프로세스 자체에 root를 주지 말고, 프록시·로드밸런서·`CAP_NET_BIND_SERVICE`로 권한을 최소화하는 편이 안전하다.

### 4.2 개발·홈랩에서 흔한 선택

- 앱: `3000`, `5173`, `8000`, `8080`, `8443`
- DB·캐시: 각 제품 기본 포트(내부 전용) + 외부 노출 금지
- 외부 공개가 필요하면 443 → 내부 높은 포트로 리버스 프록시

특권 포트를 직접 bind하지 않으면 `EACCES` 클래스의 문제를 설계 단계에서 제거할 수 있다.

## 5. 5060·5061을 쓰면 안 되는 이유

### 5.1 무엇이 할당되어 있는가

IANA 등록상:

| 포트 | 프로토콜 | 용도 |
| --- | --- | --- |
| 5060 | TCP/UDP | SIP (평문·일반 시그널링) |
| 5061 | TCP/UDP | SIP over TLS (SIPS) |

SIP는 전화·화상·PBX·소프트폰의 세션을 열고 닫는 시그널링 프로토콜이다. 즉 5060/5061은 “아무 서비스나 올려도 되는 빈 포트”가 아니라, **전 세계 스캐너·교환기·ALG·통신사 장비가 VoIP로 가정하는 번호**다.

참고로 둘 다 1024보다 크므로 **root 없이 bind는 된다.** “특권 포트라서 안 된다”와 “쓰면 안 된다”는 다른 층위다.

```text
특권 포트 문제:   80, 443, 22 …   → OS 권한 (EACCES)
정책·관례 문제:  5060, 5061 …   → ISP/공유기/보안/오인 탐지
```

### 5.2 ISP·주거용 회선에서의 차단과 제한

많은 ISP는 주거용 회선에서 다음을 한다.

- 5060/5061 인바운드 또는 아웃바운드 차단·제한
- 비인가 VoIP·국제전화 사기(toll fraud) 방지 목적의 필터
- CGNAT·방화벽 정책에 SIP를 민감 포트로 분류

그래서 집 서버에 “그냥 API를 5060에 올렸는데 밖에서 안 된다”는 증상이, 포트포워딩과 무관하게 **회선 사업자 정책**으로 재현될 수 있다. 80/443/SSH는 열고 SIP만 막는 식의 비대칭 정책도 흔하다.

### 5.3 공유기의 SIP ALG

가정용 공유기에는 **SIP ALG**(Application Layer Gateway)가 기본 켜져 있는 경우가 많다. ALG는 SIP 메시지 안의 주소·포트를 고쳐 NAT를 통과시키려 한다. 의도는 VoIP 지원이지만, 실제로는 다음을 자주 만든다.

- SIP 헤더·SDP 변조로 등록·통화 실패
- 비SIP 트래픽이 5060을 쓰면 페이로드를 “SIP처럼” 만지려다 파괴
- “포트는 열렸는데 프로토콜만 깨짐” 형태의 난해한 장애

임의 프로토콜(HTTP, gRPC, 게임, 커스텀 TCP)을 5060에 올리면, OS는 정상인데 중간 상자가 패킷을 망가뜨리는 그림을 만들기 쉽다.

### 5.4 인터넷 전역의 스캔과 공격면

5060/5061은 봇넷·스캐너가 상시 훑는 포트다. 노출 즉시 다음이 들어온다.

- 기본 암호·취약 PBX를 노린 REGISTER 폭주
- 국제 통화 도용 시도
- SIP 취약점·증폭·자원 고갈 시도

서비스를 SIP가 아닌데도 이 포트에 열어 두면, **실제 취약점이 없어도 노이즈·로그 폭주·자동 차단(fail2ban 등)에 휘말린다.** 운영 비용만 늘고 이득이 없다.

### 5.5 프로토콜 오인과 보안 장비

기업 방화벽·IDS/IPS·클라우드 WAF·보안 그룹은 포트 번호로 애플리케이션을 추정하는 규칙이 많다.

```text
5060/5061 → “이건 VoIP/SIP”
```

그 결과:

- SIP 전용 검사·차단 규칙이 적용된다
- 허용 목록에 HTTP만 열어 둔 환경에서 침묵 드롭된다
- 감사·규정 문서에 “비인가 VoIP”로 찍힐 수 있다

앱이 HTTP여도 포트가 SIP면 **운영·보안 관점의 라벨이 SIP**가 된다.

### 5.6 언제 5060/5061을 쓰는가

쓰는 것이 맞는 경우:

- 실제 SIP/SIPS 서버(Asterisk, FreeSWITCH, Kamailio 등)
- 표준 소프트폰·트렁크가 기본 포트를 기대하고, 방화벽/ISP를 VoIP용으로 열어 둔 환경

그 외의 웹 API, 게임 서버, 홈랩 대시보드, DB, 개발용 mock 서버에는 **등록되지 않은 높은 포트**나 조직이 정한 포트를 쓴다. SIP가 필요하면 그때 5060/5061과 ALG·ISP·인증·TLS(5061)를 함께 설계한다.

## 6. “안 된다”를 층위로 나누는 진단

포트 문제를 한 바구니로 뭉개면 원인을 놓친다.

```text
1) OS bind 권한     → <1024 특권, EACCES
2) 로컬 점유         → EADDRINUSE
3) 호스트 방화벽     → pf, iptables, nftables, Windows Firewall
4) 공유기/NAT        → 포트포워딩, Hairpin, ALG
5) ISP/CGNAT 정책    → 5060/5061 등 민감 포트 차단
6) 앱/인증서/DNS     → 포트는 열렸는데 상위 계층 실패
```

체크리스트:

1. 포트 번호가 1024 미만인가? → 특권/`EACCES`부터 볼 것
2. 1024 이상인데 `EACCES`인가? → capability·컨테이너·샌드박스
3. `EADDRINUSE`인가? → `lsof`/`ss`로 점유 프로세스 확인
4. 로컬은 되고 외부만 안 되나? → 포워딩·방화벽·ISP
5. 포트가 5060/5061인가? → SIP ALG·ISP VoIP 정책을 의심하고, SIP가 아니면 **포트 자체를 변경**하는 것이 우선

## 7. 실무 권장

- 개발·자체 서비스 리슨 포트는 **1024 초과**로 둔다. 특권 `EACCES`를 설계로 제거한다.
- 공개 HTTPS가 필요하면 **443은 프록시/LB**가 받고, 앱은 높은 포트로 둔다.
- **1042는 특권 제한 대상이 아니다.** 실패 시 점유·방화벽·환경 정책을 본다.
- **5060/5061은 SIP 전용으로만** 쓴다. 일반 앱에 쓰면 ISP 차단·ALG 변조·스캔 노이즈를 산다.
- “되면 되는 포트”보다 **충돌·차단·오인 탐지 확률이 낮은 포트**를 고른다. 팀 내 포트 표를 문서화하면 중복을 줄일 수 있다.

## 결론

특권 포트는 **1024 미만**이며, 일반 유저의 `bind()`는 `EACCES`로 거절되는 것이 기본이다. **1042는 이 규칙 밖**이므로 특권 포트 때문에 막히지 않는다. 1042 실패는 다른 원인을 찾아야 한다.

**5060·5061은 특권 포트가 아니지만**, SIP 표준 포트로서 ISP 차단, 공유기 SIP ALG, 전역 스캔, 보안 장비의 프로토콜 오인 때문에 일반 서비스용으로 부적절하다. OS 권한 문제와 네트워크·관례 문제를 나누어 진단하고, 웹·API·홈랩 서비스는 높은 비SIP 포트를 쓰는 것이 안전하다.
